# skill-creator、prompt-design、agent-workflow-designの役割と使い分け

> **Notice：** 本文書では、2026年8月時点で筆者がCodex環境で利用しているスキルの役割を整理しています。`skill-creator`は同環境に含まれるシステムスキル、`prompt-design`と`agent-workflow-design`は独自に作成したスキルです。後者の2つはいずれもOpenAIの公式ドキュメントを参考にしており、`prompt-design`はGoogle、`agent-workflow-design`はAnthropicの公式資料も参照しています。ただし、OpenAIが提供する公式スキルではなく、ここで示す分類や使い分けもOpenAI公式の標準構成ではありません。
>
> `agent-workflow-design`を実運用へ適用する場合は、影響に応じて、代表的なタスクで停止条件、回復、権限、承認境界などを確認してください。

`skill-creator`、`prompt-design`、`agent-workflow-design`は、いずれもエージェント向けの仕組みを設計するときに使えますが、主に扱うレイヤーが異なります。3つを毎回すべて使うのではなく、成果物がCodexスキルかどうか、モデル向けの指示文を含むか、作業が反復・長期実行を伴うかを見て選びます。

端的には、`skill-creator`は**Codexスキルの構造・作成・検証**、`prompt-design`は**モデルに渡す指示**、`agent-workflow-design`は**処理を実行・反復・停止・回復する仕組み**を扱います。1つのCodexスキルに3つの観点が必要になることもありますが、それぞれの責務を混ぜないことが重要です。

## skill-creator：Codexスキルの構造を作る

`skill-creator`は、Codexスキルを新規作成したり、既存スキルの構造を変更したりするときに主に使います。スキル名、ディレクトリ構成、`SKILL.md`先頭のYAML frontmatter、発火条件となる`description`、`agents/openai.yaml`、`scripts/`、`references/`、`assets/`の使い分け、初期化、検証、実利用後の改善までを扱います。

Agent Skills仕様では、スキルディレクトリに必須の`SKILL.md`に加え、任意のファイルやディレクトリを置けることが明記されています。`scripts/`、`references/`、`assets/`は許可リストではなく、一般的な内容を整理するための推奨例です。そのため、評価ケースを置く`evals/`や、用途固有の補助ファイルもスキルへ同梱できます。実際、Agent Skillsの評価ガイドは、`evals/evals.json`をスキル配下へ置く構成を示しています。ただし、任意のディレクトリを置けることは、ChatGPTやCodexなどのホストがそれを自動検出・読み込み・実行し、ライフサイクルを管理することまでは意味しません。利用方法と管理責任は、スキルの指示、評価ハーネス、ホスト側の実装などで別途定めます。

中心となる考え方は、Codexがすでに持つ一般能力を前提に、繰り返し必要になる専門知識、手順、ツール連携、再利用資源だけをスキルへ持たせることです。詳細を参照ファイルへ分けて必要なときだけ読む段階的開示や、作業の壊れやすさに応じて、文章による指示、疑似コード、実行手順を固定したスクリプトを使い分ける設計も、このスキルで扱います。

一方、`skill-creator`だけで、モデル向け指示文の明確さや、長期実行ワークフローの状態遷移まで十分に設計できるとは限りません。`SKILL.md`や`description`の内容を調整する場合は`prompt-design`を、スキルで定義する作業が反復処理や中断・再開を伴う場合は`agent-workflow-design`を組み合わせます。

## prompt-design：モデル向けの指示を設計する

`prompt-design`は、プロンプト、`system`／`developer`／`agent`／`tool`向けの指示、プロンプトテンプレート、評価用プロンプト、`AGENTS.md`、Codexスキルの`description`や本文など、**モデルが読み、判断や出力に使う指示文**を設計・レビュー・修正するときに使います。Geminiの通常プロンプト、Gemの指示、画像・動画生成プロンプトも対象に含みます。OpenAIやCodex向けの成果物では、別の対象が指定されない限り、現在のGPT-5.6向けガイダンスを既定として扱います。

このスキルでは、期待する結果、必要な文脈、制約、根拠、出力形式、承認境界、停止・確認条件を整理します。重複や矛盾、曖昧な指示、過剰な手順指定を減らし、モデルに任せる判断と、ランタイムやスキーマ、権限設定などで強制する内容を分けます。既存の意図や必要な手順を保ちながら、挙動を変える情報だけを残すことを重視します。

ただし、`prompt-design`はCodexスキルのディレクトリ構成や検証手順を決める主スキルではなく、スケジュール、永続状態、再試行カウンター、排他制御などをプロンプトだけで実現するためのスキルでもありません。Codexスキルとして実装するなら`skill-creator`を、実行制御を設計するなら`agent-workflow-design`を使います。

## agent-workflow-design：反復・長期実行の制御を設計する

`agent-workflow-design`は、処理を繰り返す、長時間実行する、スケジュールやイベントに反応する、複数のツールやサブエージェントを調整する、中断から再開する、実行結果をもとに改善するといったワークフローを設計・レビュー・修正するときに使います。

対象は、トリガー、状態、処理、観察、根拠、評価、未解決差分、再試行・再計画、停止条件、回復、監査、権限、人間の承認境界です。すべてをプロンプトへ書くのではなく、意味判断はモデル向け指示、状態遷移や再試行はランタイム、中断や反復を越えて必要な進捗だけを永続状態、機械的に判定できる検証は評価器に分けます。公開、デプロイ、購入、削除などの操作は、人間の確認または保護された承認手順に委ねます。

### 実行証拠から改善する

実行証拠から再利用可能な仕組みを改善する場合は、現在またはユーザーが指定した保存済みセッション、成果物、差分、検証結果を使い、問題がプロンプト、スキル構造、参照導線、ツール、状態遷移、ランタイム、評価器、ドメイン固有ルールのどこにあるかを先に診断します。単発の成果物修正、複数タスクで再利用するハーネス改善、AIの研究・開発能力や改善機構自体を対象にする自己改善／再帰的自己改善（RSI）を分け、必要な層だけを`prompt-design`、`skill-creator`、ドメイン保守スキルなどへ渡します。利用可能なセッションと成果物で足りる場合、新しいログ収集基盤は前提にしません。

改善候補は、問題が再発したことを示す証拠そのものではなく、まだ確定していない判断を保持する記録です。別のケースで同じ問題や判断パターンが独立して確認され、その事実が正式化、適用範囲、例外、再確認条件を変え得る場合だけ、元セッションや成果物へ戻れる最小限の証拠参照を追加します。回数が必要なら独立した証拠参照から導き、発生件数だけで正式化、一般性、強制力を決めたり、判断を変えない重複観測を履歴として蓄積したりしません。

候補が解決したら、採用した挙動はスキル、コード、設定、ポリシー、評価定義などの正本へ反映し、候補記録は削除します。ただし、正本だけでは分からない理由、退けたが再提案されやすい代替案、重要なトレードオフ、判断を見直す条件が将来の保守に影響する場合だけ、別のdecision recordとして残せます。decision recordは判断を説明する記録であり、それ自体が有効なルールや証拠になるわけではありません。

### 改善記録とruntime stateを必要な場合だけ持つ

多段階または改善を含むことだけでは、永続記録やruntime stateを作りません。現在または保存済みセッションと既存の正本で足りる場合はそれらを使い、再開、複数ケース照合、設定済みの監査要件による価値が保存・保守コストを上回る場合だけ、所有者、読む条件、再確認条件、競合処理、整理・削除の条件を定めて必要な情報だけを保存します。

保存先は、対象ワークフロー、プロジェクト、外部システムがすでに持つ正本を優先します。このCodex環境で、複数のプロジェクトやセッションをまたぐ、人が読み返す未解決候補や設計判断に新しい保存先が必要な場合だけ、`~/.agents/notes/<owner-id>/candidates/<candidate-set-id>/`または`~/.agents/notes/<owner-id>/decisions/`を提案し、絶対パスを示してから書き込みます。これはAgent Skills仕様ではなく、この環境のローカル規約です。`owner-id`には、schema、書き込み、競合、整理・削除を管理するスキル、プラグイン、ランタイムなどの識別子を使い、単にワークフローを呼び出しただけのスキルを所有者にはしません。

スキル配下には、配布・バージョン管理する指示、参照、スクリプト、資材、メタデータなどを置き、レビュー済みの再利用知識は明示的なスキル保守として取り込みます。利用者、プロジェクト、セッションごとに変化する未解決候補、チェックポイント、履歴、ログ、キャッシュは、スキル配下へ置きません。`~/.agents/notes/`には人が再検討する候補と必要なdecision recordだけを置き、生ログ、評価結果、チェックポイント、ロック、再試行回数などのruntime stateは混ぜません。

runtime stateは常に永続化するものではありません。中断やrun境界を越えた再開、重複実行防止、監査、並行制御などに必要な場合だけ、ランタイム、コントローラー、プラグイン、外部システム、またはプロジェクトが、schema、更新規則、所有者、回復、cleanupとともに保存先を定めます。保存先が未定ならstate contractは未完成であり、便宜的な退避先を作りません。`~/.codex/state/`も、Codex、プラグイン、ランタイムが明示的に割り当てた場合だけ使います。

### 評価定義と評価結果を分ける

レビュー済みのテストケース、検査条件（assertion）、固定入力・期待値（fixture）は、実行時の状態ではなく、評価ハーネスの定義です。複数のバージョンで使う場合はレビュー・バージョン管理し、Agent Skillでは`evals/`などの追加ディレクトリへ同梱できます。ただし、ホストによる自動検出、実行、配布、ライフサイクル管理まで標準化されるわけではありません。

評価実行によって生成されたoutput、score、timing、traceは、実行ごとに変化する根拠または履歴であり、一時利用を既定にします。継続保存が必要な場合は、既存のプロジェクト、ランタイム、プラグインが所有する場所を優先し、共通の評価用workspaceを暗黙に新設しません。生成結果をレビューして安定したfixtureとして正式採用する場合は、明示的なハーネス保守として取り込みます。採用後は、保持された実行履歴ではなく、バージョン管理する評価定義として扱います。

### 複数成果物、フィードバック、評価の実行基盤を分ける

一つのワークフローが複数の永続成果物やシステムを使う場合も、すべての情報へ一律に正本マップを要求しません。同じ情報の不一致が、次の判断、外部作用、回復、監査、引き渡しを変え得る場合に、その情報の所有者を定めます。必要に応じて、意図・計画、観測済みの状態と根拠、レビュー所見、承認・有効化状態を分け、同じ本文を同期するより正本を参照します。単一の正本で足りる作業や、重複しても判断へ影響しない情報には追加の管理を設けません。

検証は、信頼でき費用に見合う範囲で、現在の処理へ結果を返せる位置に置きます。作業中の自己検証は修正を速めますが、独立した最終判定が必要かは別に判断します。既存の決定的検査で十分なら検証担当を追加せず、影響や評価器の弱さに応じて、別コンテキスト、決定的検査、人、保護された外部システムを使います。

評価ケースを残すか、いつどこで実行するか、結果を警告または強制ゲートとして使うかも別の判断です。一回の診断には一時的または手動のケースを使えます。将来の退行検出価値が作成・実行・保守コストを上回る場合だけ、レビュー済みの回帰ケースとして残します。実行契機は手動、変更時、定期、リリース時、障害後などから選び、CIは実行・強制の場所の一つとして扱い、既定にはしません。

高速化や並列化が後続工程の負荷を変える場合は、処理量だけでなく、待ち、検証・レビュー負担、手戻り、承認待ち、全体の完了時間も考慮します。後続工程が制約になるなら、並列度の調整、バックプレッシャー、優先順位付け、バッチ化、対象範囲の縮小を候補にします。小規模で後続負荷が無視できる作業に、この分析を一律には要求しません。

このスキルは、複雑であっても1回の処理と1回の検証で終わる作業には原則として使いません。各反復で新しい根拠、変更された成果物、外部状態の変化を観察できる場合だけループを設け、必要を満たす最小の制御構造を選びます。通常のプログラム内ループと、指示文の言い換えだけを行う作業も対象外です。

## 3つの関係

| 判断したいこと | 主に使うスキル | 補助的に組み合わせるスキル |
| --- | --- | --- |
| Codexスキルをどのような構造で作り、検証するか | `skill-creator` | 指示文には`prompt-design`、反復実行には`agent-workflow-design` |
| モデルに何をどの強さ・順序・形式で指示するか | `prompt-design` | Codexスキル化するなら`skill-creator` |
| 作業をいつ開始し、何を保持し、何を見て続行・停止・回復するか | `agent-workflow-design` | モデル向け判断には`prompt-design`、スキル化するなら`skill-creator` |
| 実行証拠から、再利用するプロンプト、スキル、ツール、状態、評価器のどこを改善するか | `agent-workflow-design` | 指示変更には`prompt-design`、Codexスキルの構造変更には`skill-creator` |

3つの関係は、上位・下位の序列ではなく責務の分担として捉えます。`skill-creator`がスキルの入れ物と再利用資源を整え、`prompt-design`がその中のモデル向け指示を整え、`agent-workflow-design`が必要に応じてプロンプトの外側を含む実行制御を整えます。

## 選び方

依頼を受けたら、次の順で判断すると使い分けやすくなります。

1. **成果物はCodexスキルか。** 新しいスキルの作成や、既存スキルの構造変更なら、`skill-creator`を主に使います。
2. **モデル向けの指示文を作成・評価・修正するか。** 該当するなら、`prompt-design`を使います。Codexスキルの新規作成や構造変更を伴う場合は、`skill-creator`と併用します。
3. **処理が反復・長期実行・イベント駆動・中断再開・実行結果による改善を含むか。** 該当する場合だけ、`agent-workflow-design`を加えます。

たとえば、単発の専門作業を支援するCodexスキルを作る場合は、`skill-creator`を主に使い、`prompt-design`で`description`と`SKILL.md`を確認します。永続状態や再試行を追加する必要がなければ、`agent-workflow-design`は使いません。

一方、定期実行する調査エージェントを設計し、Codexスキルとして配布しない場合は、`agent-workflow-design`でトリガー、状態、評価、停止、回復を設計し、`prompt-design`でモデル向け指示を整えます。`skill-creator`は使いません。

## 3つを併用する場合の進め方

反復・長期実行する作業を定義するCodexスキルを作る場合は、次の順を基本にします。

1. `skill-creator`で利用例、発火条件、スキルの境界、必要な再利用資源を整理します。
2. `agent-workflow-design`で、ループの必要性、トリガー、状態、観察・評価、未解決差分、停止・回復・承認境界を設計します。
3. `prompt-design`で、モデルが担う判断、必要な根拠、ツール利用、出力、引き渡し条件を明確な指示文へ落とします。
4. `skill-creator`に戻り、`SKILL.md`、参照、スクリプト、メタデータの整合を確認し、スキルを検証します。
5. 代表的な依頼で実際の挙動を確認し、問題が見つかったレイヤーだけを修正します。

この順序を毎回固定する必要はありません。既存スキルの一文を直すだけなら`prompt-design`だけで足り、既存エージェントの停止条件だけを見直すなら`agent-workflow-design`が中心になります。必要なスキルだけを選び、構造、指示、実行制御のどこに問題があるかを分けて修正します。
