# `~/.agents/config/`による利用者固有指示の試行方針

> **状態：** 2026年8月31日時点の設計ノートです。`~/.agents/config/`は、少なくとも確認したAgent Skills仕様、Agent Plugins v1仕様、OpenAI公式のCodex関連資料では定義されていません。一般規約や自動読み込み場所としては採用せず、対応を明示した所有者がローカル契約として試行する場合だけ使います。

このノートは、インストール済みのスキルやプラグインを直接編集せず、利用者固有の指示を外部から適用する場合の設計境界をまとめたものです。ここに書かれたパスやファイルは、対応する所有者が明示的に読み込む場合だけ意味を持ちます。ファイルの存在だけでCodex、他のクライアント、スキル、プラグインが自動的に読むことは想定しません。

## 現時点の結論

- 利用者固有の指示を外部へ置く場合は、`~/.agents/config/<owner-id>/instructions.md`を候補にする。
- `<owner-id>`は、設定の読み込み、解釈、優先関係、更新、検証を管理する単位とする。
- 読み込み時点、適用範囲、競合、失敗時の扱いは、設定を使う所有者が明示する。
- `~/.agents/config/`をクライアント共通の自動読み込み場所、スキルのオーバーレイ仕様、同名スキルのマージ機構として説明しない。
- `config.yaml`、共通schema、仕様バージョン、ルートの`README.md`は、互換性や検証上の必要性が生じるまで追加しない。
- 利用者が採用を決め、具体的な指示と書き込みを求めるまでは、設定ファイルや親ディレクトリを自動作成しない。

想定する最小構成は次のとおりです。

```text
~/.agents/config/
└── <owner-id>/
    └── instructions.md
```

`instructions.md`は、複数の利用者指示を人とモデルの双方が確認できる形でまとめる仮のデフォルト名です。`AGENTS.md`や`SKILL.md`と同じ意味は持たせません。

## 外部の設定場所を検討する理由

利用者が正本を所有し、更新で置き換えられないスキルであれば、正本を直接編集する方法が単純です。一方、配布元やインストーラーが管理する内容は、更新や再インストールで置き換えられることがあります。インストール先にあることだけでは、利用者が正本を所有しているとは判断できません。

そのため、次を分けます。

- **利用者が所有する正本：** 直接編集できる。別の上書き層を必須にしない。
- **配布元やインストーラーが管理するコピー：** 直接編集せず、利用者固有の指示は所有境界の外へ置く。
- **クライアントが管理するインストール先やキャッシュ：** 正本やカスタマイズ先として扱わない。

外部の指示ファイルは、配布元の既定を保ったまま、利用者の安定した好みやデフォルトを更新後も維持するための選択肢です。すべてのスキルやプラグインへ必要な仕組みではありません。

## `notes`、`config`、正本、runtime stateを分ける

| 場所 | 役割 | 動作への反映 |
| --- | --- | --- |
| `~/.agents/notes/<owner-id>/candidates/` | 後で再検討する未解決候補 | 反映しない |
| `~/.agents/notes/<owner-id>/decisions/` | 将来の保守に必要な判断理由や再検討条件 | 反映しない |
| `~/.agents/config/<owner-id>/instructions.md` | 所有者が対応を明示した、採用済みの利用者固有指示 | 所有者の読み込み規則に従って反映する |
| スキルやプラグインの正本 | 配布する既定の指示、参照、評価定義 | 通常動作として反映する |
| プロジェクトの`AGENTS.md`やスタイルガイド | そのプロジェクトや媒体に固有の指示 | 適用範囲内で反映する |
| ランタイムが所有する状態保存先 | チェックポイント、ロック、再試行回数など | ランタイムのstate contractに従う |

`notes`の候補や判断記録は、存在するだけで有効な指示にはなりません。逆に、`config`へ置く内容は、利用者が採用済みの既定に限定します。未解決の改善案、生ログ、評価結果、実行途中の状態を混ぜません。

## 所有者が読み込み契約を定める

`~/.agents/config/`はクライアントが自動発見する場所ではありません。設定を使う所有者は、少なくとも次を自身の契約で定めます。

- どの`owner-id`配下の、どのファイルを読むか。
- どの入口、成果物、処理へ設定を適用するか。
- いつ読み、どの実行単位で値を固定するか。
- 同じタスク内で再読する条件と、新しいタスクでの扱い。
- 現在の依頼、プロジェクトの正本、既存成果物、同梱された既定との優先関係。
- 設定で変更できる範囲と、変更できない保護範囲。
- ファイルが存在しない、読めない、解釈できない場合の扱い。

複数の入口が一つの設定を共有する場合も、設定を一度書けばすべてへ自動適用されるとはみなしません。各入口の参加条件と対象範囲を契約で示し、対応しない入口や成果物へ漏れないようにします。

読み込み結果をタスク内で固定するか、変更を即時反映するか、読み込み失敗時に既定へ戻るか停止するかは、対象と影響によって異なります。ここでは一つの動作を共通仕様として固定せず、所有者が再読境界、報告条件、停止条件を選べるようにします。

## 指示の優先関係

最初に、クライアントがsystem、developer、user、tool contractなどへ割り当てた指示階層と、sandbox、権限、承認境界を適用します。`AGENTS.md`はファイル名だけで順位を決めず、クライアントが供給した位置付けと対象ファイルへの適用範囲に従います。

Codexは、グローバルな`AGENTS.override.md`または`AGENTS.md`を確認した後、プロジェクトルートから現在の作業ディレクトリへ向かって、各階層の`AGENTS.override.md`、`AGENTS.md`、設定されたfallback名のうち一つを結合します。同じ`AGENTS.md`チェーンでは、作業ディレクトリに近い指示ほど後に置かれ、先の指示を上書きできます。これはCodex内の`AGENTS.md`同士の探索・結合順であり、`~/.agents/config/`との一般的な順位ではありません。

その範囲で、同じ種類の好みやデフォルトが競合する場合は、次の順で判断する方式が候補になります。

1. 適用される指示階層が許す範囲で、現在の依頼や今回の正本として明示された資料
2. プロジェクト、媒体、組織などが管理する適用範囲内の正本
3. `~/.agents/config/<owner-id>/instructions.md`のうち、現在の対象に適用できる利用者既定
4. 上位の方針が当該項目を定めていない場合に、対象成果物の比較可能な用例から確認できる暫定基準
5. スキルやワークフローに同梱されたデフォルト

`AGENTS.md`自体の指示は前段の指示階層で扱います。`AGENTS.md`がスタイルガイド、用語集、仕様書などを指定している場合は、その資料をプロジェクトが管理する正本として扱います。

既存成果物は明示的な指示ではありません。上位の方針がない項目について、同じ適用範囲の比較可能な用例に一貫した傾向がある場合だけ、現在の成果物に限る暫定基準として利用できます。一つの出現、混在、旧版や引用などから方針を確定せず、判断結果が大きく変わる場合は確認事項にします。

この順序は、すべてのクライアントや所有者へ適用できる標準ではありません。所有者は、扱う設定の種類と対象に応じて優先関係を定義し、競合を自動解決できない場合の扱いも示します。

## 利用者設定で変更させない範囲

`instructions.md`は、好みやデフォルトを調整するためのモデル向け入力であり、権限や安全境界を広げる手段ではありません。少なくとも次を弱めたり、回避したりする指示は適用しません。

- system、developer、tool contract、sandbox、権限、承認境界
- 明示された作業範囲と、ファイルの作成・更新・削除に関する権限
- 外部調査、外部送信、公開、配布、第三者への連絡に関する範囲と承認
- ソース整合性、事実主張の強さ、正式名称、引用の正確さ
- 認証情報、課金、削除、本番環境などに関する安全確認
- 適用されるスキルやワークフローが必須とする検証、監査、完了確認
- 結果を判断するために必要な重要情報や未確認事項の報告

たとえば、設定に「検証を省略する」「確認なしで公開する」「未確認事項を報告しない」と書かれていても、保護された契約を変更する指示としては使いません。技術的な強制が必要な境界は、ツール、サンドボックス、権限、承認手順などでも維持します。

## 形式とバージョンは必要になってから導入する

読み手と設定形式が限定され、短いMarkdownとして成立する間は、schema、frontmatter、専用形式、仕様バージョンを先に増やす必要はありません。次のような互換性問題が現れた時点で、構造化とバージョン管理を検討します。

- 複数の読み手が同じ形式を機械的に解釈する。
- 新旧の形式を区別しないと誤って適用される。
- validation、migration、互換性判定を自動化する必要がある。
- 複数のクライアントや所有者が契約を共有する。

識別子だけを先に追加せず、導入するときは、解決する互換性問題と古い設定の扱いもあわせて定めます。

## 試行時に確認すること

この方法を試す場合は、少なくとも次を確認します。

- 設定がない場合に従来の結果と動作を保てるか。
- 設定がある場合に、意図した入口と対象だけへ反映されるか。
- 対象を限定した指示が、別の成果物や処理へ漏れないか。
- 現在の明示依頼とプロジェクトの正本を、利用者既定より優先できるか。
- 既存成果物を暫定基準にする条件と、推定しない条件を区別できるか。
- 設定が権限、ソース確認、安全性、必須の検証や報告を弱めないか。
- 不在、読み込み失敗、解釈失敗、競合時に、定めたフォールバックまたは停止条件へ進めるか。
- 読み込み、固定、再読の境界が、所有者の契約どおりに機能するか。
- インストールや更新によって、利用者が所有する設定を置き換えないか。

設定機能を追加したこと自体を改善の証拠にはしません。評価では、設定の有無、適用範囲、競合、失敗、保護範囲、従来動作への影響を確認します。

## 今は一般化しないこと

現時点では、次を一般規約として扱いません。

- `~/.agents/config/`をAgent SkillsやAgent Plugins v1のポータブルな構成要素として説明する。
- すべてのスキルやプラグインへ共通の要件として追加する。
- 同名スキルの優先解決や自動マージを前提にする。
- 未対応の所有者も従う共通ローダーや共通schemaを先に設ける。
- 一つの試行で選んだ適用範囲、読み込み時点、フォールバックを、別の所有者へそのまま広げる。

参照したAgent Skills仕様はスキルディレクトリと`SKILL.md`の形式を、Agent Plugins v1仕様はプラグイン内のコンポーネント発見を定めています。少なくともこれらの公開仕様には、`~/.agents/config/`による外部オーバーレイや、同名スキルの自動マージは定義されていません。この配置は、対応する所有者が明示的に採用するローカル契約として扱います。

## 一般化を再検討する条件

複数の独立した試行から、利用価値、適用漏れ、競合、更新時の安定性、保守コストに関する証拠が得られた場合にだけ、共通化を検討します。その時点で、次を判断します。

- 所有者、読み込み条件、優先関係、失敗時の扱いを共通文書へ切り出す価値があるか。
- スキルやプラグインの作成・保守ガイドへ選択肢として含めるだけの再利用性があるか。
- schema、contract version、validation、migrationが必要な互換性問題を実際に観測したか。
- クライアント固有の機能と、複数クライアントで共有できる契約を分離できるか。

実証前に共通規約を増やさず、個別所有者の試行から再利用可能な部分だけを一般化します。
