# Workspace review after upgrading from 0.3 to 0.4

Use when the user reports updating the installed plugin to 0.4, an explicit check observes that transition, or the user requests workspace review or organization. Follow [dot-guidelines](../../SKILL.md#cloud-workspace) for placement, preservation, and authority.

This is optional workspace organization, not a required data conversion. Users may request it at any time to bring folders created under 0.3 or earlier into a more consistent layout, including folders that still work. INDEX, provenance schemas, and adopted skill/plugin layouts are unchanged. Leave private instructions, adopted packages, INDEX, and manifests outside this operation. Actual 0.1 common files or legacy inventory use the separate [0.1 migration](0.1-to-0.2.md).

## Offer once after an update

On an update report or observed transition, briefly offer to review and organize existing work folders under the new conventions. A report is not verified installation evidence: check installed resources only when the requested work needs it. Source edits, ZIP generation, or static 0.4 text do not establish an update. Do not assume an internal update notification, poll versions, or scan workspace contents merely to make this offer.

Keep one small private entry in a known migration/resumption record; if none is established, use `/workspace/.codex/dot-toolkit-migrations.md`. Record only the update basis, whether the offer was made, the reply (`pending`, `deferred`, `declined`, or `requested`), and completed scope or unresolved work. Do not duplicate the record, search the whole workspace for it, or publish it. Read or update it only for an update report/check, a reply, or requested resumption, not ordinary tasks.

Use the available conversation and known record to avoid repeating an offer already made, answered, requested, or completed. Declined or deferred answers cause no automatic reminders. If history is missing, inaccessible, or inconclusive, briefly offer conditionally at this update event, for example, "If still useful, I can review the work folders created under the previous layout." Do not claim this is the first offer, search broadly, ask solely to reconstruct history, or delay independent work. Preserve unreadable or conflicting records rather than replacing them; an unavailable record does not block the offer. An explicit current request takes precedence over past handling. A record is not permission and cannot guarantee continuity if lost.

## Inspect the relevant work

Confirm the environment, assigned locations, accessible scope, and requested outcome. Start with the relevant project/task and known retained files; expand only to resolve its originals or references. Do not read unrelated projects or private settings simply because the request mentions `/workspace`. Report access gaps without bypassing denials or claiming complete coverage.

Follow existing project storage/privacy rules. Check current editable originals, needed assets, ownership or unexplained edits, references, active work, and destination conflicts. Dates, filenames, formats, and completion state alone do not determine placement. Useful candidates include continuing work left in scratch, a standalone outputs document now used for reading/revision, and old scratch copies superseded by retained originals. Leave usable existing homes in place where appropriate.

For Git-managed work, distinguish the candidate's root from enclosing or nested repositories and check uncommitted changes, worktree/submodule relationships, and affected references. A `.git` file alone does not identify the relationship. Git presence or uncommitted work does not prohibit renaming an independent repository's containing directory; preserve those changes and use the method appropriate to linked worktrees, submodules, or enclosing tracked paths. Do not bulk-move repositories as ordinary folders.

For active task directories, aim for consistent task-based names without dates, respecting existing project naming rules and environment-assigned roots. Keep meaningful run/snapshot dates beneath the task; consider a project destination when work becomes ongoing. If removing dates causes a name collision, keep needed records of the same task under that task by date/version, or use meaningful target/purpose names for different tasks. Safe separation may proceed within delegated scope while preserving references and distinct Git roots. Do not mechanically rename all dated directories, merge or overwrite same-named targets, duplicate files just for classification, precreate every category, or add an inventory/retention system.

## Explain, apply, and verify

Before changes, recommend a coherent scope and explain the relevant effects: old/new locations, retained or deferred items, references and active work, Git relationships and uncommitted changes, conflicts, and verified recovery options or limits. Do not promise unverified rollback or ask the user to design every minor choice.

Determine decision and execution authority from the request and context, not a particular phrase. Clear permission to organize, including acceptance of the offer, allows scoped inspection followed by this explanation and ordinary renames, moves, and reference updates without repeated plan/execution approvals. A review-only request ends with findings; an update alone authorizes no organization. If execution is not authorized, wait for acceptance or adjustment of the proposed scope; silence is not approval. Consolidate questions about unclear authority and honor later scope changes.

Preserve user-provided originals and unexplained edits. Pause only targets whose current originals, conflict resolution, active use, or Git relationships remain unresolved, explain what is needed, and continue independent safe work. Before authorized writes, recheck affected files and coordinate concurrent work. Retain needed originals/assets, update references, and continue from the verified new location rather than competing copies. Deleting leftover or obsolete files needs separate authorization; a checked move or copy does not authorize cleanup.

Read back retained files and verify affected references. Briefly report main old-to-new changes, checks, and concrete reasons for anything retained or deferred. File organization does not establish restart persistence or unprompted main-dot behavior.
