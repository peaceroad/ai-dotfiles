# Migration routing

Read this only for an update report, a relevant legacy state, a requested migration or workspace review, or resuming an incomplete transition. Choose by the actual state and requested outcome, not a mandatory sequence of version numbers. Keep useful existing work in place when no migration is needed.

- **0.1 common files or schema-4 aggregate skill inventory:** [0.1 to 0.2](0.1-to-0.2.md) preserves edited common guidance and converts established selection/provenance. Its historical paths describe that conversion, not the normal 0.5 root. If adopting 0.5 directly, establish the 0.5 destination and permission gate first, then apply the conversion there without an unnecessary intermediate live installation. Preserve the old path resolution bases and source bytes.
- **Work folders created under earlier conventions:** [0.3 to 0.4](0.3-to-0.4.md) is optional organization, not a prerequisite for 0.5 and not a migration of private guidance, packages, INDEX, or manifests. When an update to 0.4 is reported or explicitly observed, make its brief offer only if not already addressed; a 0.5 update alone does not trigger this offer; no version polling or automatic organization.
- **An explicit choice of 0.5 for a 0.4 installation/update limitation, including direct adoption from an older layout using the same destination and permission gate:** [0.4 to 0.5](0.4-to-0.5.md). Users with a working 0.4 setup may stay there. Future consolidation has no promised version or date.

The plugin bundles this router and its procedures; reading migration guidance does not depend on the destination private guide already existing. A plugin update alone neither authorizes migration nor proves it completed. If the transition from old guidance or selection remains unresolved and the new root is absent, partial, or inaccessible, retain that known state as migration pending, pause only dependent work, and do not fall back silently or initialize replacement guidance. Do not scan unrelated directories to guess the active version.

If the user installs 0.5 but declines migration, do not reinterpret that choice as permission to use old paths under 0.5. Explain that remaining on the old layout requires an explicit, supported reinstatement of the prior plugin/entry and verification that it is available and coherent. Do not promise that reinstatement is possible, perform it without applicable authorization, or silently fall back. Continue independent work while the choice or route is unresolved.
