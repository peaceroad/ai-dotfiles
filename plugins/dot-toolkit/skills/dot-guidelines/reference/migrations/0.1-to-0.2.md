# Migrate 0.1 to 0.2

Use only for an authorized migration in dot's own cloud. A newer plugin or detected old file does not authorize migrating or deleting anything. Read [computer checks](../computer-checks.md) and [skills maintenance](../skills-maintenance.md) for the affected contracts. Keep plugin replacement, common-guidance retirement, inventory conversion, and upstream skill updates separate; migration preserves currently adopted skill bytes and intentional selection.

## Inspect before switching

Identify the installed plugin entry and version, the adopted old common source if known, `/workspace/AGENTS.md`, `/workspace/.codex/dot-setup.md`, private instructions and pending inputs, legacy `/workspace/.agents/skills/INDEX.md` and `skills-manifest.json`, and complete skill folders. Read needed existing files and compare them against their old records before generating new expectations. Preserve unexplained differences and unknown ownership.

Pin the procedure and helper content/identity used for this operation. Separate resource reads are not known to pin an entire installed package. If the plugin changes mid-operation, verify identity and reconcile before continuing; stop the affected step if a coherent version cannot be established. An identified repository snapshot can support source work, but is not proof of identical installed resources.

Where possible, prepare and check the new records before changing the active client route. If the new plugin must be installed first, explicitly mark the old state as migration pending. Do not treat the installation alone as completed setup or route around unresolved migration automatically.

## Preserve the old common document

Compare the whole old `/workspace/AGENTS.md` with the **known adopted public source revision**, not the latest branch HEAD. A version label without source/content identity is insufficient.

- If its bytes match that known source, it may be retired after the new route and preservation checks below succeed.
- If it differs, or its adopted comparison source is unknown, preserve the whole old file at `/workspace/.codex/AGENTS-migrate-0.1.md` before retiring it. Create without overwrite, then compare saved bytes with the original. If the destination exists, leave both intact; verify whether it already contains this exact original or resolve a different preservation destination with the user. Never overwrite a collision.
- If the old file cannot be read, do not claim preservation or retire it.

Tell the user what was preserved and why, without exposing private contents. The archive is evidence, not active guidance: do not automatically load it in normal work, link it as required private instructions, or extract rules into `AGENTS-private.md`. The user chooses which additions should continue. Do not silently lose edits in the old setup procedure or unresolved private inputs either; preserve content whose retirement has not been agreed.

## Convert legacy inventory deliberately

The supported starting point is the old `schema_version: 4` inventory. Other versions require an explicit verified conversion; never renumber them to make them fit. Read the complete legacy contract and record when needed. Its historical public definition is available at [the pinned 0.1 source](https://github.com/peaceroad/ai-dotfiles/blob/cb7d3ea6632ae5ab54d19619f6061cac9f21284e/dot/dot-setup.md#5-manifest-format-and-verification); the actual adopted revision governs if different.

For each verified legacy skill:

1. Match `skills[].source_id` to one `sources[].id`. Map `name` unchanged, `repository_url` to `source.repository`, `source_path` to `source.path`, `requested_branch` to `source.ref`, and `resolved_commit` to `source.commit`.
2. Require `managed_path` to identify that skill's directory. Select only its `files[].relative_path` entries and remove that directory prefix for new `files[].path`; preserve each adopted `sha256`. Verify all missing/extra/modified files against the old record. Do not hash unknown current content into an accepted replacement.
3. Review `upstream_relationship` and `intentional_changes`. Preserve the description and meaning of verified intended edits in `localChanges`; keep existing restoration files and necessary acquisition evidence privately available. An unresolved relationship or missing evidence needed to explain current bytes remains unresolved. The new record does not promise the old restoration capability.
4. Write the independent schema-1 manifest only for established identity and adopted content. Verify it against actual files. Do not copy obsolete aggregate hashes/counts, environment paths, common-guide pointers, timestamps, or source-acquisition machinery into the minimal new schema. Retain old records until their useful information is preserved and retirement is authorized.

Build `/workspace/.agents/skills-state/INDEX.md` from the **established previous selection**, using `../skills/<name>/SKILL.md` links and each selected skill's full description. Do not assume that every old manifest member was selected. If membership cannot be established from the old INDEX and known intent, preserve the ambiguity and resolve it rather than selecting all or clearing the list. Preserve a genuinely empty selection as empty. Do not upgrade any skill during this conversion.

## Verify, then retire

With the requested 0.2 package available, verify actual installed access to the entry, needed references, and complete helper code, and execute the relevant helpers through the supported route. If the reader supplies text only, follow the verified-copy procedure in [computer checks](../computer-checks.md). Source tests do not substitute for this installed-resource check.

Before retirement, confirm new INDEX/manifests/files agree, private instructions and unresolved inputs remain available, and any required old AGENTS archive is verified. Retire only files positively identified as old dot-toolkit-managed material, using an authorized method: the old common AGENTS, setup copy, INDEX, and aggregate manifest where their contents are safely accounted for. Leave unrelated project AGENTS files, shared settings, unknown owners, and unresolved local edits alone. Permanent deletion still follows the applicable approval boundary.

After the old common files are no longer referenced, test normal requests, relevant private instructions, and skill selection in an actually observed fresh main-dot context. Removing a file does not remove instructions already loaded into a conversation. Report file conversion, installed-resource access/script execution, and fresh-context behavior separately. If the latter cannot be observed, it remains unverified even when the files are migrated.

On interruption, inspect current state before resuming; do not restart the whole migration or fetch newer commits. If a return to the old route is needed, verify retained old bytes and old-entry availability first. Do not promise rollback, recreate lost edits from hashes, or overwrite later changes.
