# Opt in to the 0.5 layout

Use for an explicitly authorized adoption of 0.5 in dot's own cloud when 0.4 skill or plugin installation/update is blocked, or to inspect/resume that migration. This changes the toolkit's placement convention, not Codex's sandbox, protected-path policy, native discovery, or client installation mechanism. Source tests alone do not establish an executable adoption route.

## Scope and prerequisites

Map only the agreed dot-managed files, preserving their internal layout:

- `/workspace/.codex/` → `/workspace/shared/ai-dotfiles/codex/`
- `/workspace/.agents/` → `/workspace/shared/ai-dotfiles/agents/`

These are migration source and destination, not two normal runtime roots. Do not treat all contents of a similarly named directory as toolkit-owned. Exclude credentials, unrelated settings, unknown-owned files, and other projects unless separately scoped. Review private inputs and pending decisions without publishing their contents or actual inventory. Do not conflate a layout move with upstream package updates, selection changes, or converting standalone skills into plugins.

Before any live copy or switch, establish both the user's intended scope and a supported, permitted route for adopting instruction-bearing files at the destination. A writable ordinary folder, an existing file edit, or a successful isolated test does not establish this permission. A source path change or installing a plugin cannot grant it. If the runtime denies the operation or the route is not established, stop that dependent stage and report the exact prerequisite. Do not use UI/file-manager operations, symlinks, alternate loaders, or renamed paths to circumvent restrictions.

Identify the actual installed plugin/resources and selected source version. Installing 0.5 and migrating its cloud files are separate actions: installation alone leaves a known old environment migration pending. Retain access to the previous plugin/entry and any required source before promising rollback. No built-in migration engine, atomic transaction, or automatic recovery is supplied.

## Inspect and prepare

1. Inspect only the agreed old files, private references, selected INDEX, standalone/plugin manifests, complete packages, and needed retention records. For presence-only legacy inspection use the explicitly scoped migration-source mode in [computer checks](../computer-checks.md); it does not validate old content. Reuse verified matching-version 0.4 read-only helpers or a scoped manual comparison for old integrity. Do not point 0.5 normal helpers at a fabricated layout and call that legacy verification.
2. Establish source ownership, fixed upstream identities, intentional local changes, required resources, permissions, and location-bound references. Resolve absolute paths and relative references from their original bases; a relative link outside the moved tree can change its target after relocation. Preserve actual bytes needed for recovery; hashes do not restore private instructions or local edits. Unknown differences, unreadable sources, links, and unsupported file types remain unresolved, not omissions from a successful inventory.
3. Record the intended mapping, current selected keys and full descriptions, source identities, unresolved conflicts, and the last verified stage privately in the existing task record when needed for resumption. Do not introduce an always-read locator, a second catalog, or a version-state framework. INDEX grammar and manifest schema 1 stay unchanged; package-relative links and hashes do not change merely because the root moves.
4. Inspect destination conflicts without overwriting. An existing identical copy can be reused only after comparison; a differing or partial copy needs reconciliation. Preserve newer edits at either side. Serialize affected maintenance during the transfer and switch.

## Copy, verify, then switch

Only after the prerequisites above are satisfied:

1. Copy the agreed files to the destination without deleting the old source. Retain complete package boundaries, raw bytes, provenance, selection, and private reference-loading conditions. Do not normalize line endings or regenerate manifests to conceal discrepancies. A transfer is not a source upgrade.
2. Verify destination files against the preserved inventory and trusted manifests, including missing/extra/modified files, package-internal references, and unchanged intentional selection. Run 0.5 normal INDEX and package checks for the copied layout. A destination directory or successful copy command alone is not verification.
3. Update only the approved location-bound references after comparing their full content, then verify that affected absolute and relative references resolve to the intended resources from the destination. Keep private guidance edits separate from unchanged upstream packages. An upstream package that requires location changes is a conflict to resolve, not permission to rewrite it silently or manufacture matching hashes.
4. Verify access to the actual installed 0.5 entry and required references/scripts, then establish use of the destination through its supported route. The normal root is now only `shared/ai-dotfiles/{codex,agents}`. Do not maintain parallel active copies or fall back to the old root when a new file is missing or invalid.
5. Report file preservation, source/manifest/INDEX checks, installed-resource access, and actually observed main-dot use separately. Fresh-context behavior and persistence remain unverified until actually observed. Do not claim an unobservable boundary passed.

Keep old files as retained recovery material until their retirement is explicitly authorized and safe. Inability to delete old files does not invalidate a verified destination switch, but unresolved old automatic loading or references do prevent claiming a single active route. Old deletion is neither a prerequisite for copying nor an implicit consequence of this procedure.

## Interruption and rollback

After interruption, inspect actual source, destination, records, installed entry, and the last established route before continuing. Do not infer completion from the plugin version or directory existence; do not restart by overwriting a partial destination. Reuse the original pinned source and resume only unfinished authorized work. A missing/corrupt destination INDEX or manifest pauses its dependent use; it never activates the old layout automatically.

A rollback is an explicit switch, not a fallback: verify the old plugin/entry is available and permitted, its needed files and references remain coherent, and newer destination edits are retained or deliberately reconciled before changing routes. Merely retaining the old directory does not establish rollback readiness. If old content or its entry cannot be recovered, report that limit and preserve both sides; never reconstruct lost edits from hashes. Cleanup remains a separate scoped decision.
