# 評価・改善スキルを作る理由と使う場面

`agent-eval-tools` は、繰り返し使うスキルを実験で改善し、その改善方法も次の改善対象にできるようにするためのプラグインです。公開スキルは `agent-improve` の一つです。このノートでは、作る価値があると判断した理由と、想定する利用場面を整理します。実装の順序と完了条件は[計画](../plans/agent-eval-tools.md)、研究から得た設計上の判断と限界は[研究ノート](agent-rsi-research.md)で扱います。

以下は目指す利用方法の説明であり、各機能の実装完了や性能向上を示す評価結果ではありません。

改善対象は、専門分野を問わずエージェントスキルとエージェントプラグインです。その対象が何を扱っていても、目的と専門的な判断基準に合う証拠を選びます。以下の用途は例であり、対応領域の一覧ではありません。付属のテキストランナーと既存ハーネスの使い分け、比較採点と費用の扱いは、[評価方法の見直し](../agent-eval-tools/measurement-review.md)に整理しました。

比較基盤を試用できること、計画で定めた初版（段階 0〜2）が完了すること、改善能力の向上を実証することは別々に判断します。初版には既存スキルとの併用と自己適用の確認も含み、通常の比較が動くことだけで完了とはしません。実装済みの範囲と残作業は、[計画の完了状況](../plans/agent-eval-tools.md#完了状況と初版の残作業)を参照してください。方式や費用の最適性も、別途結果から判断します。

## 構造と読む場所

一つのプラグインに、一つの入口 `agent-improve` があり、その下に必要時に読む参照と実行スクリプトがあります。`agent-eval.mjs` は実行スクリプトの名前であり、二つ目のスキルではありません。対象を実行する担当、改善案を作る担当、採点する担当も、その都度使う役割であり、別々にインストールするスキルではありません。

通常の改善では、固定した `agent-improve` を使って対象スキルを改善します。自身の改善では、改善方法のコピーを対象にし、現行版と候補版へ同じ課題と同じ開始状態の対象スキルを渡して、それぞれが生む改善を比較します。自己改善専用の入口を増やす構成にはしていません。

読む文書は目的で選べます。

- **現在のファイル構成と使い方**は[プラグインの README](../../plugins/agent-eval-tools/README.md#package-structure)。実行時の指示と設定の詳細は、そこから `SKILL.md` と各参照へ進みます。
- **何のために作り、どう使うか**はこのノート。ファイル一覧や設定仕様を複製しません。
- **これから何を作り、何を確かめるか**は[計画](../plans/agent-eval-tools.md)。RSI に向けて次に用意する課題も、計画の[課題整備](../plans/agent-eval-tools.md#直近の課題整備と比較の進め方)にまとめます。
- **研究をどう解釈して設計したか**は[研究ノート](agent-rsi-research.md)。現行の操作手順としては読みません。

## 作る価値があると判断した理由

既存の `prompt-design` と `agent-workflow-design` は、指示の設計と原因診断に使えます。新しいスキルは、その設計能力を、変更案の実行、結果の比較、次の実験の選択、採用した方法の再利用につなぎます。変更が実際の依頼に役立つかを、成果物と比較結果から判断するための仕組みです。

このリポジトリには、改善対象にできる既存のスキルと評価ケースがあります。改善した設計方法を次の改善にも使えるため、対象の品質を高めることと、改善を生む能力を高めることを接続して調べる意義があります。ただし、評価にかかる費用まで含めて役立つかは、実装後の比較で確かめる必要があります。

新プラグインは比較実行と実験記録を所有し、既存の設計スキルは単独でも使える状態を保ちます。一般的な設計知識をすべて新プラグインへ移すことや、通常の修正すべてを実験にすることは想定していません。

## 利用場面

### 実務で繰り返す問題を改善する

「必要以上に確認して止まることがある。このセッションを手掛かりに、必要な確認は残しつつ改善して」と依頼します。問題が起きるケースと、確認が必要なケースで変更前後を比べ、その場の修正がほかの依頼を悪化させないかを調べます。

### 完成度の高いスキルを調整する

「手順や参照を減らしたい。現行版と比較して、品質が落ちない変更だけ採用して」と依頼します。簡略化した版や一部を残した版を比較し、成果物の品質と、測定できる範囲の実行費用を比較します。短くすること自体を成功条件にせず、現行版を維持する結論も認めます。

### 問題が起きる前に能力を伸ばす

「途中変更の多い長時間作業を、もっと適切に設計できるようにして」と依頼します。目標から課題を用意し、現在の限界を調べ、予算内で改善案を探索します。実務の失敗ログが届くことを開始条件にはしません。

### モデルの更新後に指示を見直す

「新しいモデルでも、このスキルの細かい手順が役に立つか比較して」と依頼します。同じモデル上で現行版と変更案を比べ、指示の追加と削除の両方を検討します。モデルの変更とスキルの変更による効果を混同しないようにします。

### 評価・改善の方法自体を改善する

「これまでの改善記録から、`agent-improve` 自身の改善案を作り、現在版より有効か確かめて」と依頼します。原因診断の外れ、採点器の誤判定、実験の選択などを対象に、記録から仮説を立てます。

候補と現在版に同じ開始状態の改善課題を渡し、それぞれが対象スキルにもたらした成果と費用を比較します。文章の見栄えや自分への高評価では採用を決めません。有効な版を次の改善へ使い、その版がさらに有効な後継を生めるかを調べます。このノートでは、モデルの周囲にある指示や実行の仕組みをハーネスと呼び、その改善が次の改善を生む能力へ戻ることを、ハーネスの RSI（再帰的な自己改善）として目指します。

### 実行中のループを評価する

途中指示、不要な再試行、中断と再開なども対象になります。ただし、こうした場面では実行中にイベントを届け、応答と外部状態を観測する仕組みが必要です。初版の単発比較で代用せず、計画の後続段階で対応します。

## 日常の運用との関係

利用者は対象と望む結果を自然な言葉で伝え、スキルが必要なケース、実行方法、採点方法を組み立てます。既存の評価がある場合は再利用します。評価だけの依頼では対象を書き換えず、改善まで依頼された場合は、許可された対象と予算の中で反復します。

会話内では、親エージェントが既存のサブエージェント機能で試行を進めます。スクリプトは条件の固定や採点、記録を担当し、モデル実行のために別の CLI へログインすることは必須にしません。手元のターミナルでまとめて実行したい場合は、CLI を使う経路も選べます。実行方法に応じて、観測できる使用量や停止の保証は区別します。

サブエージェント数は固定せず、判断したい変更、ケース数、比較する版、採点方法から決めます。一つの課題への一回の応答と、複数の課題を使う評価実験全体も区別します。たとえば、機械的に採点できる合成の2ケースで、用意済みの現行版と候補を一回ずつ比べるなら、対象を実行する試行は計4回です。採点と採点器の正例・誤例の確認はスクリプトで行えるため、それだけのためにモデルを呼び出しません。意味に基づくモデル採点が必要なら、その判定と校正が加わり、改善の依頼では現行版の測定、候補生成や最終確認も予算に含めます。

ホスト経由では、各モデル試行に新しいサブエージェントを使います。別の版の回答や過去の採点を引き継いで比較をゆがめないためです。これは多数の担当を同時に常駐させる設計ではなく、親が試行を一件ずつ進められます。親が直接進行する通常運用では、進行役のサブエージェントを追加する必要もありません。別の進行役は、新しい文脈で手順を使えるかを検証するなど、その分離に目的がある場合に使います。

負担を抑えるには、判断に必要なケースを選び、機械的に確認できる条件にはスクリプトを使い、目的のないレビュー担当や反復を増やさないことを優先します。独立した試行を同じ会話へまとめて見かけの人数だけを減らしても、比較の信頼性を損なう場合があります。同じ実験の再開では完了済みの試行や校正結果を再利用できます。採点は既定では個別で、`judgeBatchSize` を明示したときに校正と実際の採点を小さくまとめられます。別の実験からの校正結果の再利用は未対応です。一括化には、採点器・基準・実行条件や、同じ入力内の別回答からの影響の確認が必要です。初期検証で使った実験規模を、日常運用の固定費にはしません。

通常の実行では、評価スキル自身の版を固定して対象を改善します。後の診断に必要な証拠と、意味のある気付きだけを残し、自身の変更と比較を毎回の必須工程にはしません。既存のセッションログで証拠を追えるなら、その URL と該当箇所、実験記録への参照を使います。未検証のメモを通常実行の指示へ自動的に追加しません。

保存先は、そのプロジェクトやワークフローが管理する場所から選びます。後から使う実行記録、再検討する判断と参照、消してよい作業用ファイルは役割を分けますが、すべてのスキルへ共通のディレクトリ構成を要求しません。配置の選び方は[~/.agents/とプロジェクト内の保存先](../agents-directory.md)を参照してください。保持する証拠を一時領域へのリンクだけで済ませず、別の場所へ保管する場合は内容を照合してから参照を更新します。現在のランナーが使える保存先と具体的な手順は[実行契約](../../plugins/agent-eval-tools/skills/agent-improve/references/runtime.md#retained-evidence-and-temporary-work)で管理します。

自身の改善は、目的、範囲、予算を定めた別の実行として始めます。処理の仕組みは共通ですが、通常の対象を改善する費用と、自身を育てる費用は区別して測ります。

返す結果は、採用できる変更と根拠、棄却して維持する現行版、判断に足りない証拠、または評価方法の問題です。変更案が採用されなかった場合も、その判断を支える証拠が残れば、次の検討に使えます。

## 負担を抑えるワークフロー

親が実験を進行し、対象スキルの試行は新しい文脈に分け、必要に応じて採点だけを小さくまとめます。ランナーには、通常のケースを対象とする `validate` の呼び出し数見積もりと、明示的に選ぶ一括採点を実装しています。個別採点を既定とし、目的と入力に合う単位を確認して選びます。経路の実装は、あらゆる課題で同品質や費用削減を保証する意味ではありません。

1. **求められた判断と予算を定める。** 親が、現行版の評価、用意済み候補との比較、候補生成を含む改善のどこまで必要かを依頼から判断します。ケース、維持条件、採点方法を選び、校正から最終判断までに必要な呼び出し数と、候補を試す場合の追加分を実行前に見積もります。固定人数の評価チームは作りません。
2. **採点器を、実際に使う形式で確認する。** 機械的に確認できる要件にはスクリプトを使います。モデル採点では、既知の正例・正当な別解・重要な誤例を、選択した個別または一括の形式で判定させます。期待ラベルは判定側に渡さず、返された判定をスクリプトが照合します。一括採点を選んだ場合だけ、この校正も適切な大きさの集合で行います。
3. **対象スキルはケース・版ごとに新しい文脈で動かす。** 対象の試行には、ほかの試行の回答や採点結果を渡しません。採点をまとめる都合で、複数の対象試行まで一つの会話へ統合しません。用意済み候補との比較では、同じケース同士を対応させ、現行版と候補の実行順を入れ替えます。
4. **モデル採点は、対象の実行とは別の文脈で行う。** 判定側には必要な課題、基準、成果物だけを渡し、現行版・候補の名前や変更理由を伏せます。選択した形式で判定と根拠を返させ、一括の場合は各成果物の識別子も使って、スクリプトが欠落・重複・対応違いを検査します。校正用の応答と実際の採点は別の文脈にし、校正の期待ラベルは引き継ぎません。決定的な検査だけで判定できる課題には、このモデル採点を追加しません。
5. **評価は評価で完了し、改善だけ候補生成へ進む。** 評価だけの依頼に、候補生成や停止判断のためのモデル呼び出しを追加しません。改善まで依頼された場合は、固定した改善方法を使う担当が、証拠と目標から候補または停止理由を返し、候補があれば同条件で比較します。自己改善の比較でも、この担当を新しい文脈で実行し、どの方法の版が候補を生んだか追えるようにします。
6. **必要な判断ができたところで終了する。** 親が結果と限界を説明し、後で役立つ気付きだけを証拠へ結び付けます。追加試行は未解決の判断を変えうるものに絞ります。高得点でも能力目標を測れない課題なら、現行版を万能とせず課題の感度を見直します。固定したケースや採否条件を変える場合は別の実験とし、都合のよい結果が出るまで測り直しません。

仮に、意味に基づいて採点する2ケースについて、校正集合と実行結果がそれぞれ一回の一括採点に収まるなら、現行版の評価は「校正1回、対象実行2回、採点1回」の計4回です。改善を依頼し、候補生成の担当が現行維持を判断する経路なら、さらに1回を加えた計5回になります。候補を実際に比較する場合や、集合を分割する場合、追加確認が必要な場合は増えます。ホスト経由で数えているのはワーカーへの依頼であり、その内部と親のモデル呼び出し全体ではありません。これは構成上の試算であり、実測、固定の人数制限、実行時間やトークン費用の削減保証ではありません。

親が進行することと、親がすべての判定を兼ねることは区別します。親の文脈で作った候補や、変更理由を知る親の評価は実務上の判断に使えますが、固定した改善方法の能力や独立した採点を測った証拠にはしません。改善能力を比較する経路では、候補生成に使う方法・材料・予算を固定した担当と、成果物を評価する担当の分離を維持します。

### 採用前に確かめること

一括採点は、同じモデルが複数の成果物を見るため、判定同士が影響し合う可能性があります。個別採点を基準の一つとしつつ、その結果を正解とは決めつけず、独立に確認した要件やラベルに照らして誤合格と誤不合格を比べます。順序の変更、長い回答、正当な別解、ほかの回答と混同しやすい例、採点への誘導を含む例も必要な範囲で確認します。一括化で判定が崩れる条件は個別採点を使います。

まとめる単位、上限、順序、結果の対応方法、失敗時の扱いは比較前に固定します。応答の一部が欠けたり期限を超えたりした場合に、比較全体を合格扱いにしないことを確認します。一回の呼び出しで複数の判定を得ても、それらを独立した複数回の測定とは数えません。呼び出し単位と判定対象の単位を両方記録します。個別採点へ切り替えるための追加実行にも理由と予算が必要で、元の試行は残します。

別の実験から校正結果を再利用する仕組みは、最初の変更には含めません。採点基準、校正例、判定の入力形式、モデルや実行条件の一致を確かめる必要があり、実モデルの版が分からない場合は同一条件を保証できません。まずは同じ実験内で校正を重複させず、一括化でどこまで負担を下げられるかを確かめます。モデルを安価なものへ替える変更や、複数試行を並列に進める変更も、この効果の確認へ同時に混ぜません。

校正だけを一括化して実際の採点を個別のままにすると、確認した形式と使う形式にずれができます。そのため、選択式の一括経路では、校正と成果物の採点に共通の入力形式、指示、応答形式、検証処理を使います。基準となる正解はスクリプトだけが保持し、判定側へは渡しません。各集合の大きさや組み合わせが違えば影響も変わりうるため、形式をそろえるだけで同品質とは判断しません。上の4回・5回という試算は、校正と成果物の両方がそれぞれ一括に収まる場合です。

実装では、識別子による固定順序で上限件数ごとに分け、呼び出し一件とその中の判定対象を別々に記録します。欠落、重複、未知の識別子、型の不正があれば、その集合全体を未採点とします。失敗した集合を黙って個別にやり直さず、判断不能として記録します。合成テストは、この対応付け、再開、予算共有、回帰による採用拒否を確認するものであり、実モデルの判定品質の証明にはしません。

現行ランナーの自動採用は品質の上昇を条件としているため、同じ品質での費用削減を採用するには、その基準を別途実装・検証する必要があります。比較前に、維持すべき品質、許容できない誤判定、改善を求める費用とその測定範囲を定めます。現在の `retain` を費用だけで `accept` と読み替えません。

費用には、取得できるモデル使用量に加え、親の進行、入力の受け渡し、待機、採否の説明まで含めます。取得できない費用は不明とし、サブエージェント数だけで効率向上を断定しません。少ない費用で有効な改善を選べることも、将来の自己改善で測る能力の一つです。ただし、このワークフローを実装したことだけでは、その能力が高まった証拠にはなりません。

採点対象に応じてコードとモデルを使い分ける考え方は [Anthropic の評価解説](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)、モデル採点の順序・長さによる偏りや、費用を最適化する前に正解との一致を確かめる考え方は [OpenAI の評価指針](https://developers.openai.com/api/docs/guides/evaluation-best-practices)を参考にしています。このプラグインの一括採点と上記の呼び出し数は、これらの資料が有効性を実証したものではなく、適用範囲を確かめながら使う独自の設計です。
