# skill-creator、prompt-design、agent-workflow-designの役割と使い分け

このCodex環境にある3スキルを整理した文書です。`skill-creator`は組み込みのシステムスキル、`prompt-design`と`agent-workflow-design`はこのリポジトリで管理する独自スキルです。後者は公式資料を参考にしていますが、この組み合わせや役割分担がOpenAI公式の標準構成という意味ではありません。

3スキルは、スキルの構造、モデル向け指示、実行の仕組みという観点を主に担当します。依頼に必要な観点を組み合わせ、共通の成果物を確認します。毎回3スキルを読み込み、それぞれの作業手順や検証を繰り返す構成ではありません。

## 主に担当すること

| スキル | 主な責任 | 組み合わせる場面 |
| --- | --- | --- |
| `skill-creator` | Codexスキルの境界、構造、資源の配置、メタデータ、構造検証 | 指示の意味やモデル別調整には`prompt-design`、実行制御の設計には`agent-workflow-design` |
| `prompt-design` | モデルに渡す指示の意味、強さ、適用条件、根拠、出力、対象モデルに応じた調整 | Codexスキルの新設・構造変更には`skill-creator`、待機や回復などの仕組みを設計する場合には`agent-workflow-design` |
| `agent-workflow-design` | 作業の開始、進行、待機、方向修正、完了、再開、権限、評価と、その担当層 | モデル向けの指示文には`prompt-design`、Codexスキルとしての構造には`skill-creator` |

この表は指示の優先順位を定めるものではありません。`skill-creator`を先に使うのは、Codexスキルの新設や構造変更で入れ物と境界を決めるためです。実際の権限と指示の優先関係は、利用先のランタイムと有効な指示に従います。

### skill-creator：再利用できるスキルにまとめる

スキル名、`SKILL.md`のYAML frontmatter、`description`、`agents/openai.yaml`、`scripts/`、`references/`、`assets/`の使い分け、初期化、検証を扱います。Codexの一般能力を前提に、判断や作業を改善する情報だけを持たせ、用途限定の詳細は必要なときに読める参照へ分けます。

`skill-creator`自身も、指示を簡潔にすること、意図を保つこと、影響に応じて検証することを扱います。`prompt-design`は、そこへ指示の意味・条件・対象モデルに応じた詳しい観点を加えます。`skill-creator`を単なる空のディレクトリ作成器として扱う必要はありません。

`scripts/`、`references/`、`assets/`は一般的な整理方法であり、追加ディレクトリを禁じる許可リストではありません。[Agent Skills仕様](https://agentskills.io/specification)は、必須の`SKILL.md`に加えて任意のファイルやディレクトリを認めています。ただし、ファイルを置けることだけでは、ホストによる自動読み込みや実行、保存期間の管理までは決まりません。

### prompt-design：モデルが何を判断し、どう出力するかを整える

プロンプト、system／developer／agent／tool向け指示、評価用プロンプト、`AGENTS.md`、Codexスキルの本文や`description`など、モデルが読む指示文を設計・レビュー・改訂します。共通の設計方針は他モデルにも使い、モデル固有の判断は公式資料や適切な補助スキルで補います。

期待する結果、必要な文脈と根拠、制約、出力契約を保ち、重複、矛盾、曖昧さ、過剰な手順指定を減らします。必須条件、好み、目安を区別し、短くする場合も必要な意味や説明を残します。通常の記事の執筆、資料の要約、事実確認、画像生成そのものは、このスキルの成果物ではありません。

ツールの選択条件や戻り値を説明するだけなら、このスキルとツール契約の確認で足りる場合があります。ジョブの寿命、並行実行、再試行、永続化、外部操作の回復まで設計するなら、`agent-workflow-design`を組み合わせます。

Gemini固有の補足は、同じプラグイン内の[`prompt-gemini-reference`](../../plugins/agent-design-tools/skills/prompt-gemini-reference/SKILL.md)へ分離しています。Geminiのテキスト向け指示、Gems、画像・動画向けプロンプトを設計する場合に、まず`prompt-design`の共通方針を使い、必要な専用参照だけを読みます。依存は補助側から共通側への一方向であり、別のGemini向けスキルを選んでも`prompt-design`は利用できます。画像生成ツールの提供や、GPT-6向け参照の一律読み込みは行いません。個別導入では両スキルが必要です。

### agent-workflow-design：許可された仕事が進む仕組みを整える

反復・長期実行、スケジュールやイベント、ツールやエージェントの調整、中断と再開、実行証拠に基づくハーネス改善を扱います。ここでいうハーネスは、複数の仕事で再利用する指示、ツール、参照導線、状態管理、評価、実行制御などです。

モデルには意図や根拠の解釈、ツール・引数の選択、意味の評価、再計画を任せます。ツールの実装には引数の受入条件と許される効果を、ランタイムにはジョブ、排他制御、再試行の計数などを担当させます。どの保証を実装が強制し、どこをモデルが判断し、何を後から検出するのかを分けます。

使える部分結果があれば依存しない仕事を進め、意味のある変化がなければ待機します。途中の質問で元の目的を失わず、依頼変更、開始済みの処理、遅れて到着する結果、外部操作の完了を区別します。現行版では、これらを固定した手順ではなく、設計時に決めるべき状態変化として扱っています。

通常の単発業務を実行するために毎回使うスキルではありません。設計した結果、1回の処理と検証で足りるなら直線的な流れにします。通常のプログラム内ループや、指示文の言い換えだけを行う作業も対象外です。

## skill-creatorの更新とAstraとの関係

Codexリポジトリの[更新履歴](https://github.com/openai/codex/commits/main/codex-rs/skills/src/assets/samples/skill-creator/SKILL.md)では、2026年8月13日に[Refine skill creation guidance and validation（#38384、`5e32f72`）](https://github.com/openai/codex/commit/5e32f728f1f86a967c6be057351f12505778df8f)が記録されています。`description`を短くし、必要な参照だけを読む構成を明確にし、順番どおりの作成手順を依頼に応じて調整する指針へ改めた更新です。独立した実行検証も、複雑さやリスクに見合う場合に使う位置付けになりました。初期化テンプレートの簡素化と、未完成のTODOプレースホルダーを検出する検証処理の変更も含みます。

この文書の使い分けは、更新後の組み込み版を前提にしています。利用環境への反映時期はコミットの日付だけでは判断できないため、適用時にはその環境の`skill-creator/SKILL.md`を確認します。

コミット説明と更新後の本文にはAstraの名前がなく、Astra専用のスキルとは位置付けていません。関連する背景として、[OpenAIのCodex DX担当者によるX投稿](https://x.com/pvncher/status/2095991462416490862)では、Astraに向けて既存の指示を見直す文脈の中で、skill-creatorの最近の更新が紹介されています。この発言は更新の背景を理解する補助資料とし、個別コミットの変更内容はGitHubの記録で確認します。

[Astraの公式モデルガイド](https://developers.openai.com/api/docs/guides/latest-model#instruction-following)も、スキル内の曖昧・矛盾した指示が早期停止につながり得ることを説明し、変更に見合った検証を勧めています。この更新はAstra向けの指針と方向が一致すると捉えられますが、モデル固有の調整は引き続き対象モデルを確認して行います。このリポジトリの独自2スキルも、既存の対象モデルを保持し、用途別の参照と影響に応じた検証を使う構成です。

## 具体的な依頼での選び方

以下は適用判断の例です。新しいエージェントへ実行させた試験結果ではありません。

| 依頼 | 主に使うスキルと理由 |
| --- | --- |
| 既存プロンプトの一文を直す | `prompt-design`。ファイル構造や実行制御を変えなければ、残りの2つを追加する理由はない |
| スキルの`description`だけを明確にする | 文言・発火条件は`prompt-design`。名前、配置、UIメタデータなどの整合も変わるなら`skill-creator`を加える |
| 単発の専門作業を支援するCodexスキルを新設する | `skill-creator`で構造を決め、`prompt-design`で指示を整える。反復や再開は必要な場合だけ設計する |
| 既存の定期調査の待機・再開を見直す | `agent-workflow-design`。指示文も変える場合は`prompt-design`を使い、Codexスキルの構造を変えなければ`skill-creator`は不要 |
| 長期調査のワークフローをCodexスキルとして新設する | 3つの観点を使う。構造、実行制御、モデル向け判断を分担し、共通の成果物で確認する |
| 実行履歴から不要な承認要求の原因を直す | 原因が未確定なら`agent-workflow-design`で実効版・参照導線・実行契約を診断する。修正対象が指示だけと分かれば`prompt-design`で直す |
| 既存ワークフローをレビューだけする | 該当する設計スキルで調べて報告する。例として書かれた公開や送信を実行せず、修正も依頼されている場合はその範囲を直す |
| 普通の資料作成、要約、コード修正を実行する | その仕事に合うスキルを選ぶ。ツールや複数ステップを使うというだけでは、この3つの設計スキルを追加しない |

## 対象モデルと参照の分担

`prompt-design`と`agent-workflow-design`は、依頼、会話で確定した前提、成果物の導入先から設計対象を判断します。OpenAI／Codex向けで対象が決まっていなければ、どちらも**GPT-6 Astra向け**を既定とします。既存の対象がGPT-5.6やGeminiと分かっていればそれを保持し、明示的な移行依頼があれば移行先を優先します。

これはスキルを実行しているモデルへの自動追従ではありません。GPT-5.6でスキルを使っても、設計対象が未確定なら既定はAstraです。参照を選ぶこと自体は、実行中のモデルや導入先の設定を変更しません。`skill-creator`は、このモデル選択とは別にスキルの構造を担当します。

| 必要な情報 | 主な参照先 |
| --- | --- |
| Astra・GPT-5.6向けの指示調整とモデル設定 | `prompt-design`のモデル別参照。具体的な読み分けは[プラグインのREADME](../../plugins/agent-design-tools/README.md#reference-selection) |
| OpenAI APIのツール経路、状態、機能の組み合わせ | `prompt-design`の[tools and runtime boundaries](../../plugins/agent-design-tools/skills/prompt-design/references/openai-tools-and-runtime.md)と公式資料。Codexなどの管理された製品では、公開されているツール契約を使う |
| 進行・待機・再開・評価・権限の設計 | `agent-workflow-design`の[共通参照への入口](../../plugins/agent-design-tools/skills/agent-workflow-design/SKILL.md#reference-routing) |
| GPT-5.6を維持・適用・比較する際の補足 | `agent-workflow-design`の[GPT-5.6用参照](../../plugins/agent-design-tools/skills/agent-workflow-design/references/openai-gpt-5.6-workflow-design.md)。モデルやランタイムの差が関係するときだけ読み、Astraだけを対象にする仕事には読み込まない |
| Gemini、Gem、画像・動画生成向けの指示 | `prompt-design`の共通方針と`prompt-gemini-reference`の専用参照。別モデルの事例を対象モデルの挙動の証拠や必須構成にはしない |

GPT-5.6用のワークフロー参照は、Gitの旧設定を参考にした補足です。旧版の完了証拠、未解決事項、制御の担当などは現行の共通参照に引き継がれているため、旧版一式を別の必須手順として保持していません。追加の判断と検証範囲は[ワークフロー側の記録](../agent-workflow-design/README.md#モデル別参照の追記)にあります。

### 実行用の参照と保守用の出典

プラグインやスキルの資料は、実行時の判断、配布物に添える説明、保守時の振り返りという用途と、分量・配布範囲に応じて配置を決めます。この方針は[ルートのAGENTS.md](../../AGENTS.md#skill-and-plugin-reference-placement)に定めています。URLの本数やファイルの短さだけで配置の良し悪しを判断しません。

APIの制約、ツールの契約、検証に使う根拠資料など、正しい実行に必要な情報とリンクは、担当するスキル本文や参照に残します。必要な場面で辿れるよう、何を判断するときに読み、どの仕様を確認するのかを明確にします。出典を照合すること自体が仕事の一部なら、その参照も実行に必要な情報です。

短い出典一覧やプラグインと一緒に持たせたい背景説明は、プラグインのREADMEに置くことを優先します。各出典を何の参考にしたかを短く添え、プラグイン側から直接辿れるようにします。プラグインを持たない単独スキルでは、まず`docs/`の既存の公開ノートを候補にし、保守に役立つ出典や背景説明を残します。

詳しい採用理由、代案との比較、評価結果や検証の限界は、将来の保守に役立つものを`docs/`のノートへ残します。適切な既存文書を使い、必要に応じてREADMEや関連文書から辿れるようにします。通常のスキル実行で、背景資料まで毎回読むことは求めません。

移動や削除の前には、資料の内容と現在の参照経路を確認します。必要な条件や出典の明示が失われないか、配布先でも実行に必要な資料へアクセスできるかを見て判断します。たとえば、agent-workflow-designの[改善用参照](../../plugins/agent-design-tools/skills/agent-workflow-design/references/agent-improvement-and-rsi.md)には判断規則を置き、背景となる出典と短い用途説明は[プラグインのREADME](../../plugins/agent-design-tools/README.md#sources-for-agent-and-harness-improvement)で案内しています。

## 重なる観点をどう扱うか

### 構造と指示の境界

`description`は、スキルを発見するためのメタデータであると同時に、モデルが読む指示です。形式や配置は`skill-creator`、どの依頼に反応するかという意味は`prompt-design`が扱います。同じファイルを見ても、確認する責任が異なります。

### 指示と実行制御の境界

待機、再試行、承認、引き渡しは、指示とワークフローの両方に現れます。`prompt-design`は「モデルへどう伝えるか」を、`agent-workflow-design`は「何を根拠に状態を変え、誰が保証するか」を担当します。短い基本原則の重なりは、各スキルを単独で使うために残せます。APIの細かな互換性や状態管理の手順を各所へ複製する必要はありません。

### 裁量、承認、検証の境界

3スキルとも、成果と必要な制約を保ちながら手段を選べる設計です。レビュー・計画に限定した依頼と、作成・修正を許可した依頼を区別します。既存の許可は範囲内で引き継ぎ、質問に依存しない仕事を進めます。公開・デプロイ・保存などの操作名だけで、承認済みの行為を再確認する設計にはしません。

追加の権限やランタイム所定の承認が必要なら、許可済みの作業で具体的なレビュー対象を用意してから、その残る境界を解決します。無回答や経過時間は許可を与えず、実際の拒否を指示で回避することもできません。

数値制限、状態ファイル、別の評価担当、追加の承認を、モデル名やスキル併用だけを理由に増やしません。利用者がタイムアウトや再試行数の設計を求めた場合は、その設定に限って理由付きの変更可能な提案を示せます。既存の目安や必須条件の強さは保ちます。

## 実行証拠と保守記録

単発の成果物修正、再利用するハーネスの改善、AI研究・開発の支援、再帰的自己改善（RSI）を区別します。RSIを扱う場合は、改善が次の改善能力にどう戻るか、能力向上のどこまでが観測済みかを確認します。研究支援や通常の指示修正を繰り返しただけでは、再帰的な能力向上が実証されたことにはなりません。

原因の診断には、使えるセッション、成果物、差分、検証結果、実効版を使います。似たルールがあるだけで単発の実行漏れと決めず、発火条件、読み込み経路、適用できる具体性を確認します。一方、原因が不明というだけで規則やログ基盤を増やしません。改善対象を決めた後は、その層を担当するスキルで直します。

作業の加速を評価するときは、コード量や実験数などの活動量と、受け入れ可能な成果までの時間を区別します。ある工程が速くなっても、レビューや統合、計算資源の確保へボトルネックが移れば、全体の加速につながらないことがあります。中間工程の測定だけで全体の加速を断定しません。

### 改善記録とruntime stateを必要な場合だけ持つ

保存する情報の役割に応じて、担当と保存先を分けます。

| 情報 | 扱い |
| --- | --- |
| 採用済みの動作・規則 | スキル、コード、設定、ポリシー、評価定義などの正本へ反映する |
| 未解決候補・将来必要な判断理由 | 再検討する価値があり、保存が許可されたときだけ、担当者の記録方針に従って残す |
| 進捗、チェックポイント、ロック、再試行回数 | 再開や並行制御に必要な場合だけ、ランタイムやプロジェクトの状態契約で管理する |
| 評価の入力・判定条件と生成結果 | 再利用する定義と実行ごとの証拠を区別し、下記の評価方針に従う |
| 公開用の解説 | この文書のように、所有するプロジェクトのドキュメントとして管理する |

既存の正本や保存先を優先し、許可済みの目的・範囲に含まれるディレクトリ作成を再承認の理由にはしません。保存目的や利用者スコープへの拡張に権限が足りなければ、記録と保存先を具体化してから確認します。スキルの配布ディレクトリへ、実行ごとに変わる候補、履歴、ログ、キャッシュを置くことはしません。

複数プロジェクトやセッションをまたぐ判断で適切な既存保存先がない場合、任意のローカル規約として`~/.agents/notes/<owner-id>/candidates/<candidate-set-id>/`と`decisions/`を選べます。所有者は記録の形式、書き込み、再読、競合、整理を管理する主体であり、設計を手伝ったというだけでこのスキルを所有者にはしません。

具体的な保存・重複統合・候補整理は[Maintenance records](../../plugins/agent-design-tools/skills/agent-workflow-design/references/maintenance-records.md)、ローカル規約は[`~/.agents/notes/`の説明](agents-notes-local-convention.md)に集約します。同梱の[READMEテンプレート](../../plugins/agent-design-tools/skills/agent-workflow-design/assets/maintenance-notes/README.md)は、規約の採用と設置が許可された場合だけ使い、採用済みの規約と対象範囲を保ちます。候補の整理と、別の監査要件で必要な証拠の保存は分けます。

採用済みの利用者設定も別の情報です。[`~/.agents/config/`の設計案](agents-config-local-convention.md)は、外部設定が必要なスキルやプラグインが個別に採用する任意の規約です。読み込み先、適用範囲、優先関係は、採用した側が実行用の指示として定めます。この3スキルや`plugin-creator-agent-plugins`が共通の読み込み機構を提供するものではありません。

### 評価定義と評価結果を分ける

レビュー済みのケース、判定条件、固定入力・期待値は、再利用する評価定義としてバージョン管理できます。[Agent Skillsの評価ガイド](https://agentskills.io/skill-creation/evaluating-skills)は、スキル内の`evals/evals.json`にケースを、隣接する作業ディレクトリに実行結果を置く例を示しています。この配置例を、すべてのスキルに必要な保存場所や実行基盤とは扱いません。

生成された出力、スコア、所要時間、トレースは実行時の証拠です。一時利用で足りるか、比較・回復・監査のために許可された場所へ残すかを判断します。生成結果を固定入力として採用する場合は、元の実行履歴とは分けて評価定義に取り込みます。

このリポジトリでは、評価定義と証拠を[`evals/`](../../evals/README.md)、説明と採否判断を`docs/`に置きます。過去のmanifestと保存版は評価時点の記録であり、後の本文へ合わせて対象ハッシュを書き換えません。ケースの保存、手動・変更時・定期などの実行契機、警告や強制ゲートへの利用は、それぞれ必要性に応じて決めます。

## 併用時の検証

3スキルが同じ成果物を扱う場合も、同じ確認を3回行う必要はありません。確認結果を共有し、何を確かめたのかを分けて報告します。

| 確認する層 | 確かめること | それだけでは分からないこと |
| --- | --- | --- |
| スキルの構造 | frontmatter、名前、参照、配置、必要なメタデータやスクリプト | 指示の意味や、実行時の判断の正しさ |
| 生成した指示・設計 | 要件、適用条件、役割分担、参照経路、進行・停止の判断根拠 | ツールや外部システムを含む実際の成功 |
| 下流の実行 | 実成果物、待機・再開、外部操作、回帰、必要な介入 | 未試験の用途での信頼性や、モデル固有の改善幅 |

必須チェックを保ち、変更と影響に応じて正常系、具体的な失敗、既存の良い動作、新規入力を選びます。意味のある検証が済んだ後は、新しい変更・失敗・重要な未解決事項があるときに範囲を広げます。`skill-creator`の独立したサブエージェントによる確認も、複雑さや影響、利用可能な機能と委任の許可に応じて使うもので、小さな編集の必須工程ではありません。

改善候補が、自分の評価条件、保護された証拠、権限、承認境界を弱めて成功扱いすることはできません。主観的な品質の評価に人や別の担当が必要かは、判断の質と影響で選びます。構造検証、机上確認、実行試験をまとめて「動作確認済み」と報告しないことも、3スキルに共通する考え方です。

過去の設計生成や下流試行、その検証範囲と限界は、[prompt-designの評価記録](../prompt-design/README.md)、[agent-workflow-designの初回改訂](../agent-workflow-design/README.md)、[再監査](../agent-workflow-design/second-review.md)にまとめています。この文書の役割分担や使い分けの説明は、自動選択の精度や併用時の性能を測った結果ではありません。
