# Codexの保存済みセッションを期間指定で整理する

`agent codex session`は、ローカルに保存されたCodexのセッションを一覧表示し、対象を確認してからアーカイブ・削除・エクスポートするための補助コマンドです。日付や「4週間前」のような条件でまとめて選べます。

本ノートでは、一括処理の範囲をどう決めるか、何を保護するか、エクスポートで何を残せるかを説明します。導入と各オプションの使い方は[利用ガイド](../agent-codex.md#manage-codex-sessionsmjs)、実装は[セッション管理スクリプト](../../tools/agent/codex/manage-codex-sessions.mjs)を参照してください。`agent`はこのリポジトリのコマンドであり、公式の`codex`コマンドとは別です。

**実験的な機能です。** 2026年9月10日時点では、試験用データと代替コマンドを使って検証しています。実際の利用者の履歴に対するアーカイブ・削除・エクスポートは未検証です。エクスポートからの復元機能もありません。

## 整理・削除・保存を分ける

セッションを整理するときは、まず目的を分けます。

- **一覧を整理する**：`archive`を使います。履歴ファイルは同じCodexホーム内に残るので、そのファイル分の容量は減りません。
- **不要な履歴を消す**：`delete`を使います。永久削除であり、この補助コマンドに取り消し機能はありません。表示するファイルサイズは、削除後に空く容量の保証ではありません。
- **履歴を手元に残す**：`export`を使います。元のセッションは変更せず、別の保存先へ履歴を書き出します。後から読むための保存であり、元のセッションを再開できるバックアップではありません。

エクスポート後に自動で削除する機能は設けていません。「書き出せた」と「不要なので消してよい」は別の判断だからです。

## 期間は更新日時で指定する

Node.js 24以降と、対応する`state_5.sqlite`の保存形式が必要です。対象のCodexホームは、`CODEX_HOME`の指定先、未指定なら`~/.codex`です。SQLiteの保存先を個別に変更した構成には対応しません。

`agent`をインストール済みなら、任意のディレクトリから次のように対象を確認できます。これらは読み取り専用で、セッションを変更しません。

```powershell
agent codex session list --before 4w --limit 0
agent codex session plan archive --before 4w
agent codex session plan delete --before 2026-07-01
```

`--before 4w`は、コマンドの起動時刻から28日前よりも前に更新されたセッションを選びます。`--before 4weeks`や`--before 4 weeks`も同じ意味です。日付指定は、その日のUTC午前0時より前を対象にします。どちらも境界時刻ちょうどのセッションは含めません。

基準は最終閲覧日時ではなく、索引に記録された更新日時です。週数指定の基準時刻は処理中に動かさず、確認待ちの間に対象期間が広がらないようにしています。誤字や単位のない数字は推測で補わず、エラーにします。

`list`にはUUID・更新日・履歴ファイルのサイズ・タイトル・保護理由を表示します。`plan`では、指定した操作の対象と除外理由を確認できます。タイトルにも機微情報が含まれ得るため、出力を他人に渡す前に確認してください。

## 一括処理では子セッションも確認する

セッションには、サブエージェントの実行などで生まれた子セッションが関連付いていることがあります。公式の削除処理は、指定したセッションだけでなく、その子孫も対象にします。アーカイブも、未アーカイブの子孫への処理を試みます。[公式のセッション操作仕様](https://learn.chatgpt.com/docs/app-server#archive-a-thread)

そのため、この補助コマンドでは親と子孫を一つのグループとして検査します。期間指定の場合は、次のルールを適用します。

- 同じ子セッションを重ねて処理しないよう、グループの起点だけを操作します。
- 古い親の下に基準日時以降に更新された子がある場合は、親を含むグループ全体を除外します。
- アーカイブ・削除では、保護対象を含むグループも除外します。

除外したグループには`Skipped family`と理由を表示します。したがって、日付だけで抽出した一覧と、実際に操作できる件数は一致しない場合があります。UUIDを個別指定した場合も子孫を含めて確認しますが、期間による絞り込みは行いません。

## 公式コマンドへ渡す前後に検査する

アーカイブ・削除には、Windows、PowerShell 7、確認対象のCodex CLI 0.153.4が必要です。別のCLIバージョンでは処理を止めます。Codex・ChatGPTのアプリ、CLI、IDE連携などを終了し、完了まで再起動しないでください。プロセス情報を取得できない場合も停止し、終了できないプロセスを強制的に止めることはしません。

ピン留め、サイドバーのセクション所属、未完了の目標、自動実行・受信箱・実行待ち情報との関連を保護理由として確認します。保護情報を読み取れない場合は、一括アーカイブ・削除全体を止めます。既知の保護情報を確認する仕組みであり、利用者にとって重要なセッションを自動判定するものではありません。

期間指定の一括操作では、対象を表示した後、操作名・件数・計画の短い識別子を入力して確認します。確認後に計画を作り直し、各グループも操作直前に再検査してから、公式の`codex archive`または`codex delete`へUUIDを渡します。補助スクリプト自身は、元の履歴ファイルの削除やDBの直接編集を行いません。

終了コードだけで成功とは判断せず、対象の子孫も含めて結果を確認します。公式のアーカイブ処理には、子孫の一部をアーカイブできなくてもリクエスト自体は成功する場合があるためです。途中失敗や結果の不一致があれば後続グループを止め、確認済みの起点UUIDを報告します。一括処理全体を巻き戻すことはできず、自動再試行もしません。[公式のアーカイブ仕様](https://learn.chatgpt.com/docs/app-server#archive-a-thread)

また、アプリ側には、関連するチャットのアーカイブに伴って管理対象worktreeを自動整理する仕組みがあります。必要な作業内容は先に保全してください。この補助コマンドはworktreeの削除や復元を代行しません。[公式のworktree整理仕様](https://learn.chatgpt.com/docs/environments/git-worktrees#worktree-cleanup)

## エクスポートは検証付きの履歴保存

エクスポートでは、既存の保存先フォルダーの下に毎回新しい出力フォルダーを作ります。そこへ元のJSONLログと、対応する履歴DBがある場合は選択したセッションのDB行を書き出します。タイトル・UUID・親子関係・保存ファイル名・SHA-256は`manifest.json`にまとめます。無関係なセッションを含むDB全体のコピーは行いません。

生ログとDB行は逐次出力し、書き出したファイルを読み直してハッシュを照合します。最後に元セッションの情報も再検査し、履歴DBだけが処理中に更新された場合も検知します。すべての検査が通った場合だけ、`complete: true`のmanifestを書きます。失敗時は途中ファイルを残し、不完全な出力フォルダーの場所を報告します。

ただし、ハッシュの一致で確認できるのは、読み取ったデータと保存したデータの一致です。添付ファイル、作業ディレクトリ、セッションの全登録情報は収集せず、Codexへ再取り込みする手順も実装していません。**エクスポートを、削除したセッションを復元するための唯一の備えとして扱わないでください。**

元データを変更しないため、エクスポートにはピン留めなどの保護対象も含められます。ただし、読み取れないファイルや対象期間外の子孫があるグループは除外します。必要な履歴DBがない場合や、未対応の保存形式を検出した場合は停止します。

出力には会話やツールの実行結果が含まれ、個人情報や認証情報などが混ざる可能性があります。公開用の匿名化は行いません。Codexホーム内とGitリポジトリ内への出力は拒否しますが、それ以外の保存先が非公開であることまでは確認できないため、保存先の共有設定も確認してください。

エクスポートも、Codexなどの書き込み元を終了してから実行することを推奨します。複数のDBとログファイルを同じ瞬間の状態に固定する仕組みではなく、並行更新下での完全な整合性は保証しません。

## 検証範囲と今後の保守

[自動テスト](../../tools/agent/codex/manage-codex-sessions.test.mjs)では、試験用のSQLite DBとログファイルを作成し、期間境界、親子の重複、保護対象、確認後の変更、部分成功、エクスポート内容とハッシュを検査しています。大きなUTF-8ログ、多数のDB行、空の履歴ファイル、ログのサイズ変化、履歴DBだけの並行更新も対象です。公式コマンドを呼ぶ部分は代替処理で検証し、Windowsの引数引き渡しも偽の実行コマンドで確認しています。

テストはリポジトリのルートで実行できます。通常の`npm run check`にも組み込んであります。

```powershell
node --test tools/agent/codex/manage-codex-sessions.test.mjs tools/agent/codex/codex.test.mjs
```

一覧・計画・エクスポートはmacOS／Linuxでも実行可能な構成ですが、実機未検証です。アーカイブ・削除のWindows限定を、OS名の判定だけ外して解除しない方針にしています。

読み取り側はCodexの内部保存形式に依存します。対象は現在の`CODEX_HOME`の索引に登録されたローカルセッションであり、アカウント全体や別端末の履歴、索引にないログを網羅するものではありません。将来の保存形式に対応する際は、CLIのバージョン条件だけでなく、読み取る項目・保護情報・子孫の処理範囲・書き出す履歴の内容を再確認する必要があります。

`state_5.sqlite`は、確認対象のCodex CLI 0.153.4で固定されているファイル名であり、利用者ごとに増える連番ではありません。同じファイル内でもマイグレーションによってDB構造が更新されるため、ファイル名の一致だけでは互換性を保証できません。この補助コマンドでは任意のDB名への切り替えを提供せず、確認対象の保存形式に限定しています。[0.153.4のDB名と初期化処理](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/state/src/sqlite.rs)、[マイグレーションの定義](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/state/src/migrations.rs)

今回の整理では、対象グループごとの全親子関係の走査をなくし、作成済みの索引と集計値を再利用しました。生ログとDB行の書き出し・検証も共通化しています。実行前後の再検査は残しており、実データでの速度改善率を測定したものではありません。
