# Codexアプリで承認設定が反映されないときの確認と対処

`config.toml`に`approval_policy = "never"`を設定していても、Codexアプリのタスクが`on-request / auto_review`で動く場合があります。設定ファイル、アプリの保存状態、タスクの実行記録を分けて確認し、必要ならタスクの権限メニューから設定を選び直します。

## 再発時の簡単な手順

`config.toml`で`never`と`workspace-with-agents`を設定済みなら、まず入力欄の権限メニューで選び直します。

1. タスクの実行が終わってから、**入力欄の権限メニュー → カスタム（config.toml）**を選ぶ。
2. 同じメニューで**workspace-with-agents**を選び直す。ここまでメッセージは送らない。
3. **「このターンの実効値がneverか、アクセス範囲が元のままか、読み取り専用で確認して」**と送る。

画面の表示が変わらなくても、内部の設定は変わっている場合があります。次のターンの確認結果で`never`と元のアクセス範囲が確認できれば完了です。設定ファイルや保存JSONを直接編集する必要はありません。

選び直しても直らない場合や、詳しく確認したい場合は、後述の[設定と実行記録の確認](#設定と実行記録の確認)へ進みます。

## 権限が決まるまでの関係

設定ファイル同士の読み込み順は、[ユーザー設定とプロジェクト設定のノート](codex-config-toml.md#設定ファイルの役割)で扱っています。ただし、その順序だけでは、アプリから開始・再開したタスクの実効値を説明し切れません。確認したアプリには、次の段階があります。

1. **設定の読み込み**：ユーザー設定、信頼されたプロジェクト設定、選択した設定プロファイル、起動時の指定などから設定を解決する。
2. **アプリからの指定**：権限メニューや保存された選択状態に応じて、承認方法や権限プロファイルをタスクの開始・更新リクエストに指定する。既定値に任せる経路もある。
3. **タスク設定の保持・更新**：動作中のアプリ／サーバーがタスク設定を保持する。既存タスクへの追加入力では、設定ファイルだけから毎回作り直すとは限らない。
4. **実行と記録**：適用された権限が、そのターンの`turn_context`に記録され、モデルにも権限の指示が渡される。

管理設定やモデルに対する必須条件は、選べるモードや承認方法を制限しうる要素です。この調査では、その実行時の全容を取得していません。上記は処理の関係であり、「アプリの保存JSONは常にすべての設定より優先する」という優先順位ではありません。

設定項目をまとめる設定プロファイル（`profile`）と、アクセス範囲を定義する権限プロファイル（`permissions`）は別物です。また、`AGENTS.md`などの作業指示を書いても、実行環境のアクセス権が追加されるわけではありません。実効設定が正しくてもWindowsのACLなどで操作が拒否される場合は、[Git書き込みと拒否ACLのノート](codex-windows-git-write-acl-recovery.md)のように、OS側の条件を別に調べます。

### アクセス範囲と承認方法

`default_permissions`と名前付きプロファイルは、ファイル・ネットワークなどのアクセス範囲を選ぶための設定です。`approval_policy`は追加権限が必要な場面の承認方針、`approvals_reviewer`は承認要求を誰が審査するかを表します。プロファイル名が一致しても、承認方法まで一致するとは限りません。

確認したアプリには、名前付きプロファイルの選択時にプロファイルIDだけを送る経路と、カスタム選択時に設定ファイルの承認方法を含めて送る経路があります。タスク設定の更新処理も、指定された項目を既存の設定へ反映します。この違いが、カスタムを選んだ後でアクセス範囲のプロファイルを選び直す対処の根拠です。確認した経路のすべてが常に有効になるわけではなく、最終判定には新しいターンの記録を使います。

既存タスクの不一致事例では、アプリログに、初回送信時の`on-request / auto_review`の明示指定がありました。以後の送信では、アプリ／サーバー側のタスク設定を使って同じ値が継続していました。最初の指定を生んだ条件が保存モードだけだったかは未確定です。

## アプリの画面を読み違えない

- **設定 → 構成**：選択した設定レイヤーの値を表示する画面です。今回、承認ポリシーは「承認を求めない」と表示されていましたが、実行記録は`on-request`でした。サンドボックス欄には、`sandbox_mode`が未設定なら「読み取り専用」を表示する処理もあります。名前付きプロファイルの実効範囲とは分けて読みます。
- **設定 → 一般 → 権限**：「フルアクセス」のスイッチは、入力欄の権限メニューにその選択肢を表示する設定です。オンだけでタスクがフルアクセスになるわけではありません。「デフォルト権限」は常に表示するため、スイッチが固定されています。
- **会話の入力欄 → 権限メニュー**：タスクの設定を選択・更新する入口です。名前付きプロファイルを表示すると、承認モードの表示よりその名前が優先される場合があります。名前やチェックだけで`never`を判定しません。
- **設定 → ブラウザ → エージェントの権限**：閲覧・ダウンロード・アップロードなどの許可です。コマンド実行の承認設定とは別に扱います。詳細は[Browserの設定と安全性](codex-browser-config-and-security.md)を参照してください。

## アプリに保存される権限設定

アプリの選択状態は`~/.codex/.codex-global-state.json`に保存されます。`electron-persisted-atom-state`にある主な権限関連の項目は次のとおりです。内部形式なので、アプリ更新で変わる可能性があります。

- `agent-mode-by-host-id`の`local`：ホスト単位のモード保存値。今回の不一致時は`guardian-approvals`、対処後は`custom`。
- `preferred-non-full-access-agent-mode-by-host-id`の`local`：非フルアクセス時の優先モード。今回の対処後は`null`。
- `permission-selection-by-host-id:local`：選択の保存値。対処後は`kind = "profile"`と`profileId = "workspace-with-agents"`。
- `heartbeat-thread-permissions-by-id`の対象タスク：`approvalPolicy`、`approvalsReviewer`、`activePermissionProfile`、`sandboxPolicy`などの保存値。

タスクごとの権限保存値には、動作中のタスクから結果を記録する処理と、再開時に参照する処理があります。保存値が実効値と一致することだけで、それが設定決定の原因だったとは判断できません。

権限メニューは、選択状態の保存と動作中のタスク設定の更新を行います。通常の対処にはこのメニューを使います。JSONの直接編集で同じ効果が得られるか、起動中のアプリに上書きされないかは未確認です。今回の不一致だけで、保存ファイルが壊れているとは判断できません。

## 設定と実行記録の確認

対処前に原因を調べたい場合や、メニューで選び直しても直らない場合は、次を確認します。

- **実行記録**：対象タスクの`approval_policy`がすでに`never`なら、承認設定を選び直す必要はありません。別の権限制約による拒否かを調べます。
- **設定ファイル**：`approval_policy = "never"`と`default_permissions = "workspace-with-agents"`があり、対応する`[permissions.workspace-with-agents]`が定義されているかを確認します。プロジェクト設定などに異なる承認方針があれば、その意図も確認します。

`workspace-with-agents`は利用者が定義した権限プロファイル名です。`never`は、許可範囲外の操作で承認を求めず失敗させる方針であり、フルアクセスを与える設定ではありません。

カスタム選択時には、`sandbox_mode`が未設定だと読み取り専用を組み立てる経路があります。このため、簡単な手順では元のプロファイルを選び直してからメッセージを送ります。操作はホスト単位の選択保存にも関わり、対象タスクだけに影響が限定されるとは扱いません。

クリックが無効、エラーが出る、または操作後も`on-request`のままなら、その結果を残して調査します。設定の削除やフルアクセスへの切り替えで代用しません。表示が変わらないことだけでは失敗と判断できないため、[診断スクリプト](#診断スクリプトで確認する)か[確認用プロンプト](#スクリプトを使わず対象タスクへ確認を依頼する)を使って実行記録を確認します。

### 操作後の実効値

操作後の`turn_context`で、次を確認します。

- `approval_policy`が`never`である。
- 今回の構成では`approvals_reviewer`が`user`である。設定ファイルで別の審査役を明示した環境へ、この期待値を一律に適用しません。
- `active_permission_profile.id`が`workspace-with-agents`である。記録にこのフィールドがない場合、アプリ保存値で確認した名前と、実行記録の権限内容を区別します。
- `sandbox_policy`と`permission_profile`のアクセス範囲が、操作前と一致する。

今回の事例では、既存タスクで承認設定だけが変わり、両ポリシーの内容は完全一致しました。同じプロジェクトの新規タスクにも`never / user`と同じ名前付きプロファイルが適用され、その新規タスクはアプリ再起動後も承認設定を維持しました。

再起動後には追加ワークスペース1件の書き込み許可が外れました。それ以外の権限は一致し、環境に渡されたワークスペース一覧にも同じ差がありました。承認設定の再発と、ワークスペース変更による権限範囲の差は別々に判定します。許可が外れた原因までは確定しておらず、自動で追加し直す根拠にはしません。

## 診断スクリプトで確認する

このリポジトリの`permission`コマンドは、再発の判定と操作後の確認に使う読み取り専用ツールとして残します。修復機能はありません。メニュー操作だけで解決しても、表示に出ない承認設定を比較する用途があります。

Node.js 24以降と、PATHから実行できるPython 3.11以降が必要です。未導入でも、ai-dotfilesのリポジトリルートで次を実行できます。

```powershell
node tools/agent/agent.mjs codex permission status
```

対応するCLIを[インストール済み](../agent-development.md#配置とインストール)なら、短いコマンドで実行できます。リポジトリ内の更新がインストール済みコピーへ自動反映されるわけではありません。

```powershell
agent codex permission status
```

対話端末でオプションなしなら、最近のタスクを最大12件、プロジェクト名・タイトル・記録更新時刻付きで表示します。番号で選択し、一覧になければ`m`でタスクIDとプロジェクトを入力します。Enterまたは`q`で取り消します。並び順はセッション記録のファイル更新時刻であり、最後に画面を開いた時刻ではありません。

詳細な記録を読む場合は、対象を明示してJSONで出力できます。`<タスクID>`はタスクのUUID、`<プロジェクトパス>`はそのタスクの作業ディレクトリに置き換えてください。未導入なら、先頭の`agent`を`node tools/agent/agent.mjs`に置き換えます。

```powershell
agent codex permission status --thread <タスクID> --project "<プロジェクトパス>" --json
```

`--turn <ターンID>`を加えると、そのターンを指定できます。省略時は対象タスクの最新の記録です。オプションを指定した場合や入出力をリダイレクトした場合は、対話選択を開きません。`permissions`も互換エイリアスとして使えます。

### 出力の見方と限界

- `executionRecord`のタスクID、ターンID、時刻、行番号を確認してから、承認ポリシーと権限内容を見る。別タスクや操作前の記録を操作後の実効値として扱わない。
- `appSaved`は現在の保存値であり、過去ターンの実行時点の保存値ではない。`--turn`で過去を選んだ場合、この時点の違いだけでも差が出る。
- `permission_profile`の全内容はJSON出力に含まれる。現実装は`active_permission_profile`を実行記録から出力しないため、名前は`appSaved`由来である。名前を実行記録から確認したい場合は、対象JSONLの同じ`turn_context`を追加で読む。
- 設定レイヤーを個別に報告するが、Codexの設定解決処理そのものは再実装していない。管理設定の探索先も候補に限られ、アプリの機能フラグ、モデルの必須条件、起動時指定、モデルへの権限指示などは未取得として残る。
- 診断レポートの終了コードは現実装では`3`。未取得項目が残るためであり、設定破損や`never`への変更失敗を意味しない。`1`は検査・実行環境の失敗、`2`は引数の誤り。原因の判定にはレポート本文を使う。
- 会話本文や他タスクの保存値は出力しない。ホームパスは`~`へ短縮するが、プロジェクト名・タスク名・IDは残るため、共有前に出力を確認する。

診断は追加権限を要求せず、アプリ／サーバーを起動せず、SQLiteを開かずに行います。読み取り不能や保存形式の不一致は未取得として報告します。取得不能を回避するために権限設定を変えることはしません。

## スクリプトを使わず、対象タスクへ確認を依頼する

メニュー操作後は、対象タスクに次を送れます。

```text
このターンの承認・権限設定を読み取り専用で確認してください。
現在のタスクIDに一致するセッションJSONLの、今回の turn_context で、
approval_policy = "never"、approvals_reviewer = "user"、
active_permission_profile.id = "workspace-with-agents" になっているか確認してください。
sandbox_policy と permission_profile を操作前のターンと比較し、
ファイル・ネットワークのアクセス範囲の差を報告してください。
比較したタスクID・ターンID・時刻・記録位置を示してください。
設定ファイル、アプリ保存値、実行記録、モデルへの指示を区別し、
取得できない値は「未取得」としてください。
設定・ファイル・Git状態・権限モードは変更しないでください。
追加権限の要求、Web検索、WSL、承認画面を出す実験は行わないでください。
読み取りが拒否されたら再試行せず、対象と制約を報告してください。
認証情報や無関係なタスク内容は出力しないでください。
```

既存タスクで直ったら、同じプロジェクトの新規タスクでも、メニューを操作せず初回ターンの値を確認します。続いて、実行中のタスクが終わってからアプリを通常終了・再起動し、その新規タスクを開いて再起動前後を比較します。新規作成時と既存タスクの復元時は、別の確認として扱います。

## 確認済みの根拠と未確認事項

このノートは、Windows版Codexアプリで確認した事例をもとにした再発時の手引きです。確認対象はDesktopパッケージ`26.908.4834.0`、ランタイム`0.154.0-alpha.6.2`です。Web検索や承認画面を出す実験は行わず、ローカル実装、設定画面、実行記録を照合しました。別バージョンや管理設定がある環境で、同じ操作が使えるとは限りません。

根拠は、上記バージョンのアプリに同梱された次の処理と、タスクIDが一致するセッションJSONLの`turn_context`です。内部ファイル名・関数名は保守時の照合用であり、利用者が実行するコマンドではありません。

- `general-settings-3a1ea42609bb.js`：フルアクセス選択肢の表示設定。
- `agent-settings-6cf296a71a10.js`：`sandbox_mode`未設定時の画面表示。
- `permissions-mode-dropdown-8266f079a0d0.js`：プロファイル名の表示とメニュー操作。
- `src-996ff3571e1f.js`：プロファイル選択・カスタム選択からの送信値生成。
- `app-initial-d9bed9d614d8.js`：タスク設定の更新・保持と、権限保存値の参照。

当初の承認モードを決めた条件の全容、別バージョンでの再現性、再起動後に追加ワークスペースが外れた原因は未確定です。また、ネットワークの`enabled`は記録で確認しましたが、設定の限定モードやドメイン一覧が通信時に強制されるかは検証していません。ネットワーク有効化の一致を、ドメイン制限の有効性の証拠にはしません。
