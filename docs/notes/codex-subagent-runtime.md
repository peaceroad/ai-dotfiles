# Codexのサブエージェント：利用条件と起動・待機の設定

サブエージェントは、利用者と対話する主担当のエージェントから仕事の一部を受け取り、その結果を返す別のエージェントです。たとえば、主担当が実装を調べる間に、別のエージェントへ関連テストの調査を任せる使い方があります。

このノートでは、Codexが役割分担を実行する仕組みと、委任を始める条件、結果を確認するタイミングを説明します。2026年9月13日に公開実装と、このプロジェクトのCodexセッションに提示された指示・ツール定義を確認しました。実際の起動テストはしていません。

## V2とは何か

ここでいうV2は、Codexのサブエージェント連携機能の実装方式を区別する名前です。Astraなどのモデル名や、サブエージェントの人数を指すものではありません。公開リポジトリには従来方式のV1とV2があり、エージェントを起動・管理するツールや設定の扱いが異なります。

V2では、主担当が起動ツールで仕事を渡し、必要に応じてメッセージや追加依頼を送り、返ってきた結果を使って作業を進めます。主担当も別の作業を進められるため、すべてを順番に処理する必要はありません。ただし、独立して進められる仕事があることと、その場で委任が認められていることは別です。

確認したセッションには、`collaboration`の`spawn_agent`、`followup_task`、`send_message`、`interrupt_agent`、`list_agents`、`wait_agent`が公開されていました。これらを公開実装の[V2のツール定義](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/core/src/tools/handlers/multi_agents_spec.rs)と照合し、V2に対応する構成と判断しています。ツール一覧自体にV2という版の表示があるわけではありません。新規セッションの回答も、提示された定義だけではV1・V2を判別できないとしています。

## 誰の判断で委任を始めるか

委任を始める方針は、実装方式とは別の「委任モード」で決まります。公開実装では`MultiAgentMode`という名前で、次の3種類が定義されています。各モードの内容は、[モードごとの指示の実装](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/core/src/context/multi_agent_mode_instructions.rs)で確認できます。

- `ExplicitRequestOnly`：ユーザー、適用されるAGENTS.md、またはスキルからの明示的な委任指示を必要とする。
- `Proactive`：時間短縮や品質向上につながる場合に自発的に委任する。
- `Custom`：独自の指示文を使う。

公開実装の[モードの定義](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/protocol/src/config_types.rs#L339)で既定に選ばれる値は`ExplicitRequestOnly`です。既存セッションと、利用者が共有した新規セッションの確認回答も、このモードに対応する条件でした。ただし、V2を使うこと自体が、明示的な委任だけに制限する理由ではありません。

このノートで「実行時の指示」と呼ぶのは、その会話を進める際にCodexからエージェントへ与えられる指示です。利用者が書くAGENTS.mdや、ローカルに保存された指示キャッシュとは区別します。

確認したローカルキャッシュには主担当とサブエージェントの役割説明がありましたが、明示的な委任を求める制限文は見当たりませんでした。キャッシュに保存された説明だけでは、そのセッションで自発的に委任できるかを判断できません。この制限が利用環境へ導入された時期や、他のプロジェクト・環境への適用範囲は未確認です。

## 起動するときに引き継ぐものと上限

ここで「親」は、そのサブエージェントを起動したエージェントを指します。既存セッションの指示・ツール定義と、新規セッションの確認回答では、次の条件が一致していました。

- **並列数**：セッションに提示された条件は、主担当を含めて同時にアクティブにできる4枠です。主担当がアクティブなら、追加で最大3エージェントが同時に動けます。累計の作成数や、アイドル・中断後の枠の扱いまでは、この記述だけでは分かりません。
- **会話履歴**：`fork_turns`の既定は`all`です。履歴なしの`none`や、直近のターン数も指定できます。
- **モデルと推論設定**：親からの継承が既定で、全履歴を引き継ぐ場合は上書きが認められていません。履歴なし、または直近のターン数を指定する場合は上書きできますが、確認した運用指示では、ユーザー・AGENTS.md・スキルが明示的に求めた場合に限られます。
- **ファイル**：このセッションではファイルシステムを共有します。サブエージェントの起動だけで、編集対象が別の作業コピーへ隔離されるわけではありません。

公開V2実装にも、主担当を含む並列数の既定値として4が定義されています。公開実装の対応箇所は、[V2の並列数と上限計算](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/core/src/config/mod.rs)、[起動時の履歴指定](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/core/src/tools/handlers/multi_agents_v2/spawn.rs)、[モデル・推論設定の継承と上書き](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/core/src/tools/handlers/multi_agents_common.rs)です。公開実装にはサブエージェント用の既定モデル・推論設定を指定する項目もありますが、確認したローカル設定には専用の指定はありませんでした。公開実装に上書きの仕組みがあることは、このセッションのツールで同じ指定が許されることを意味しません。

従来方式のV1とV2では、設定の意味も異なります。たとえば、確認した[設定スキーマ](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/core/config.schema.json)では、`agents.max_depth`はV1向けで、V2では無視すると明記されています。設定を変更するときは、古い設定例だけで判断せず、使用中の方式と、その版の設定項目を確認します。

## 主担当はいつ結果を受け取るか

V2には、メッセージや完了通知を受け取る仕組みがあります。更新を待つための`wait_agent`は、[待機ツールの定義](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/core/src/tools/handlers/multi_agents_spec.rs#L280)に記載されています。主担当に独立して進められる仕事があれば、その間に進められます。結果待ちになったら待機機能を使います。[通知待ちの実装](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/core/src/tools/handlers/multi_agents_v2/wait.rs)では、メッセージ・完了通知・新しいユーザー入力を受けて、期限前でも待機が終了する構成を確認できます。

公開V2実装の[待機時間の既定値](https://github.com/openai/codex/blob/a592c38c16cdd7623dacc9168926ebccedfb67d3/codex-rs/core/src/config/mod.rs#L242)と、このセッションのツール定義では、待機の既定の上限は30秒、指定範囲は10秒から1時間でした。これは、更新が届かない場合に1回の待機をどこまで続けるかという値です。主担当が30秒ごとに状況を確認する義務でも、通知が届いてから30秒待つ指定でもありません。

`wait_agent`の戻り値は、更新やタイムアウトなどの概要であり、メッセージ本文そのものではありません。本文や完了結果の通知とは区別します。また、ツールが受け付ける待機時間と、実際に選ぶべき待機時間も別です。確認した運用指示には、短い反復ポーリングを避ける方針と、長時間のブロッキング待機を避ける方針がありました。最大1時間という指定範囲が、その長さの待機を常に推奨するわけではありません。

## 主担当による内容の確認とAGENTS.md

結果を受け取ることと、その内容を検証することは別です。待機ツールは、返ってきた調査や編集が正しいことを保証しません。

運用上は、主担当がその結果に依存する編集や結論へ進む前に、根拠、対象の版、他の結果との整合性を確認するのが適切です。部分結果を使える仕事と、比較・統合のために全結果が必要な仕事も分けます。共有ファイルを編集する場合は、担当範囲の重複や、確認後に対象が変わっていないかが判断に関わります。これらは、このノートでの運用判断であり、固定間隔で自動的に検証されるという実装上の保証ではありません。

[共通AGENTS.mdの指示と設計理由](codex-agents-md-instruction-rationale.md#waiting)で説明している`Waiting`は、独立した作業、部分結果の利用、必要な場合の全結果待ち、待機機能の使用を定めています。この仕組みに合っているため、固定の確認間隔は追加しません。一方、`Waiting`はサブエージェントへの明示的な委任指示ではありません。

自発的な委任を望む場合は、実行時の使用条件に沿って別途その方針を指定する意味があります。その際は、委任する条件と主担当による結果の統合・確認を扱い、小さな仕事まで一律に委任させる規則にはしない方針です。今回の整理では、共通AGENTS.mdに委任指示を追加していません。

## 確認した資料と範囲

公開実装は、[openai/codexの確認時点のコミット](https://github.com/openai/codex/tree/a592c38c16cdd7623dacc9168926ebccedfb67d3)を参照しました。本文の実装リンクもこの版へ固定しています。公開リポジトリの最新版と、デスクトップ版で動いている実装が完全に同一とは限りません。

ローカルでは、`~/.codex/config.toml`、Astraの指示キャッシュ（`~/.codex/models_cache.json`）、既存セッションに提示された実行時の指示とツール定義を確認しました。同じプロジェクトの新規セッションでは、既存ノートや指示キャッシュを参照せず、その場に提示された指示とツール定義だけを確認するよう利用者が依頼しました。その確認回答を、このノートの編集時にもタスク閲覧機能で読みました。ただし、新規セッションに渡された指示一式を直接取得・監査したわけではありません。キャッシュの取得日は9月13日、`client_version`は`0.154.0`でした。この値はキャッシュに記録されたクライアント版であり、デスクトップアプリ全体の版を保証するものではありません。

サブエージェントの起動、上限到達、通知の遅延、AGENTS.md変更前後の動作比較は試していません。文面・実装の確認は、動作や性能を実測した結果とは区別します。
