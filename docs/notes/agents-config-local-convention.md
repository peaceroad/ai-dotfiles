# `~/.agents/config/`を利用者所有の設定面として使う考え方

> **位置付け：** これはローカルな設計案です。`~/.agents/config/`をAgent Skills、Agent Plugins、Codexなどの標準的な設定場所や自動読み込み場所として定めるものではありません。対応を明示したスキルやワークフローだけが、自身の契約に従って利用します。

スキルの配布元が定めたデフォルトを保ちながら、利用者が継続して使いたい好みだけを外部へ置きたいことがあります。そのような場合に、`~/.agents/config/<owner-id>/instructions.md`を利用者の設定場所として選び、対応するスキルやワークフローが明示的に読む方法を説明します。

ここで調整するのは、読み手が設定可能と定めた項目の既定値です。配布されたスキルのファイルを書き換えたり、同名スキルを自動的にマージしたりする仕組みではありません。このノートは採用を判断するための資料であり、具体的な読み方や適用範囲は採用先のスキルが定めます。

## この方法が候補になる場面

外部の利用者設定は、次の条件が重なるときに候補になります。

- 配布パッケージやインストーラーが管理する内容を、更新のたびに利用者が編集したくない。
- 複数のプロジェクトで使う、利用者個人の安定した好みがある。
- 現在の依頼やプロジェクト固有の指示とは別に、再利用できるデフォルトを持たせたい。
- 設定の適用範囲、優先関係、読み込み時点、失敗時の扱いを、読み手側で明示できる。

既存の設定機構で目的を満たせる場合は、それを使います。利用者自身が正本を所有し、更新で置き換えられないスキルなら、正本を直接編集するほうが単純なこともあります。インストール先にあることだけでは、利用者が正本を所有しているとは判断できません。すべてのスキルへ外部設定を追加する必要はありません。

Codexには、`~/.codex/AGENTS.md`または`~/.codex/AGENTS.override.md`と、プロジェクト内の`AGENTS.md`または`AGENTS.override.md`を読む公式の仕組みがあります。広く適用する作業方針やプロジェクト固有の指示には、この仕組みを使えます。`~/.agents/config/<owner-id>/instructions.md`はそれらを置き換えるものではなく、特定のスキルやワークフローだけが読む利用者設定を分離したい場合の案です。

## 最小の配置案

設定ファイルとその内容は利用者が所有します。ディレクトリ名には、どの設定をいつ読み、どう適用するかという読み込み契約を管理する単位を置きます。

```text
~/.agents/config/
└── <owner-id>/
    └── instructions.md
```

`<owner-id>`は、読み込み契約の所有者を表す識別子です。単独のスキルが契約を管理するならスキル名、複数の関連スキルで共有するならプラグインIDなどが候補になります。他の所有者と衝突しにくく、更新後も変わらない名前を選びます。設計を手伝ったという理由だけで、作成用・設計用のスキルを所有者にはしません。

`instructions.md`は、人とモデルの双方が確認しやすく、複数の指示をまとめるファイルだとわかる仮のデフォルト名です。`AGENTS.md`や`SKILL.md`の役割を置き換えるものではありません。機械的な解析や移行が必要になるまでは、通常のMarkdownだけでも運用できます。

この配置案を説明するだけでは、設定ファイルや親ディレクトリを作りません。具体的な内容と書き込み範囲について利用者の許可がある場合に作成し、すでに許可された作業を重ねて確認する必要はありません。インストールや更新によって、利用者の設定を配布元の内容で置き換えないようにします。

## 対応するスキルやワークフローが明示的に読む

`~/.agents/config/`を共通の自動ローダーとして想定せず、設定を使うスキルやワークフローが、次の内容を自身の契約で定めます。

- どの`owner-id`配下の、どのファイルを読むか。
- どの入口や処理で設定を適用するか。
- いつ読み、どの実行単位で値を固定するか。
- 同じタスク内で再読する条件と、新しいタスクでの扱い。
- 現在の依頼、プロジェクトの指示、同梱されたデフォルトとの優先関係。
- 設定で変更できる範囲と、変更できない保護範囲。
- ファイルが存在しない、読めない、解釈できない場合の扱い。

複数の入口で設定を共有する場合は、参加する入口と対象を示します。設定を新たに読むことと、同じ成果物の作業で採用済みの方針を後続工程へ引き継ぐことも区別します。入口の切り替えだけで設定全体を別の処理へ広げたり、採用済みの方針を捨てたりしないよう、必要な引き継ぎ範囲を決めます。

たとえば、好みを扱う設定なら、対応する入口が最初に使われたときに一度読み、同じタスク内では有効な値を固定する方式が考えられます。利用者が更新を明示した場合だけ読み直し、新しいタスクでは改めて読むようにすると、処理の途中で結果が不意に変わりにくくなります。

ただし、これは一つの運用例です。設定の変更を即時に反映する必要がある処理や、設定を読めなければ安全に続行できない処理では、別の再読境界や停止条件が必要です。欠落時に黙ってデフォルトへ戻るか、警告するか、停止するかも、情報の重要性に応じて所有者が決めます。

## 置く情報と置かない情報

`config`には、複数のプロジェクトで継続して使う、採用済みの利用者既定を置きます。配布する既定はスキルやプラグインの正本、プロジェクト固有の指示はそのプロジェクトの`AGENTS.md`やスタイルガイド、一度きりの指定は現在の依頼で管理します。

未解決の改善候補や判断理由は、必要に応じて[保守記録](agents-notes-local-convention.md)へ残します。生のログ、評価結果、チェックポイント、ロック、進捗は、それぞれの実行・保存の規則に従います。これらを設定として自動適用したり、利用者設定の内容を改善の証拠として扱ったりしません。

## 優先関係は所有者が定義する

利用者設定は、現在の依頼やプロジェクトの正本を置き換えるためのものではなく、それらに指定がない場合のデフォルトとして扱うのがわかりやすい設計です。

まず、クライアントが定める指示階層と、サンドボックス、権限、承認境界に従います。`AGENTS.md`にファイル名だけで固定順位を与えず、クライアントが供給する位置付けと適用範囲に従います。

`AGENTS.md`がスタイルガイドや用語集を正本として指定している場合は、その資料を指定された範囲で使います。Codexでの`AGENTS.md`の探索・結合順は[公式資料](https://learn.chatgpt.com/docs/agent-configuration/agents-md)で確認でき、ここでは外部設定との共通順位を定めません。

同じ種類の好みを選ぶ際は、現在の明示依頼や適用されるプロジェクトの正本を先に使い、指定のない項目を利用者設定、同梱の既定で補う方式が候補になります。ただし、既存成果物の形式を保つことと利用者の好みを反映することのどちらを優先するかは、作業の目的によって異なります。所有者は、この違いも含めて優先関係を定めます。

既存成果物から方針を推定する場合は、明示的な指示と区別します。同じ対象範囲の比較可能な用例に一貫した傾向がある場合だけ暫定基準にし、一つの出現や混在する表記から確定しません。競合を解決できず、結果に大きく影響する場合の確認方法も、読み込み契約で明らかにします。

## プロジェクト固有の資料はプロジェクト側から案内する

特定プロジェクトのスタイルガイド、用語集、仕様書などを常に参照させたい場合は、通常、そのプロジェクトの`AGENTS.md`やプロジェクト所有の文書から案内するほうが自然です。これにより、プロジェクトとともに更新すべき指示を、利用者共通の設定から分離できます。

初期段階では、`instructions.md`を自己完結させ、そこから別ファイル、URL、コマンド、スキル、ツールを連鎖的にたどらない設計が扱いやすいでしょう。外部参照を許可する場合は、少なくとも次を所有者の契約へ追加する必要があります。

- 読み取りを許可するルートとパスの解決方法
- 相対パスの基準
- 参照の深さ、循環参照、重複読み込みの扱い
- URL、コマンド、ツール呼び出しを許可するか
- 参照先がない、読めない、信頼できない場合の扱い

`instructions.md`にファイル名が書かれているだけでは、任意の場所を探索したり、指示を無制限に連鎖させたりしません。参照先を読む必要があるなら、対象、解決方法、許可範囲を読み手の契約で明示します。

## 設定の適用範囲と権限を分ける

読み手は、文体や出力の好みなど設定から変更できる項目と、事実の正確さ、対応形式、依頼された検証など守るべき条件を区別します。利用者設定を読むこと自体を、ファイル変更、外部送信、公開、課金、削除などの新たな許可として扱いません。必要な権限や承認は、現在の依頼と適用される指示、実行環境に従って判断します。

設定で扱う項目を限定する読み込み契約と、ランタイムが強制する権限・安全境界は別です。スキルが「必須」と書いたという理由だけで、その指示を現在の利用者の明示指示より上位には置きません。指示自体の変更が許可されている場合は、その正本を保守対象として扱います。サンドボックスやツールの実際の制限は、設定や指示文で解除できません。

設定によって、未確認の内容を確認済みと報告したり、結果の判断に必要な情報を隠したりする設計にはしません。技術的な強制が必要な境界は、ツール、権限、承認手順などで維持します。

## 形式とバージョンは必要になってから導入する

読み手と適用範囲が明確で、設定が短いMarkdownとして成立する間は、スキーマ、フロントマター、仕様バージョンを先に増やす必要はありません。次のような互換性の問題が現れた時点で、構造化とバージョン管理を検討できます。

- 複数の読み手が同じ形式を機械的に解釈する。
- 新旧の形式を区別しないと誤って適用される。
- 検証、移行、互換性判定を自動化する必要がある。
- 複数のクライアントや所有者が契約を共有する。

識別子だけを先に追加せず、導入するときは、解決する互換性問題と古い設定の扱いもあわせて定めます。

## 読み込み契約と利用案内を置く

採用先では、実行するエージェントと設定する利用者の両方が、必要な情報へ辿れるようにします。

- **スキル内の指示と参照**：読み込み条件、適用範囲、優先関係、失敗時の動作を定めます。公開ノートを読まなければ動作を判断できない構成にはしません。
- **採用先のREADMEや利用ガイド**：設定場所、設定可能な項目、適用の確認方法を説明します。プラグインではREADMEを案内の入口にします。
- **公開ノート**：外部設定を選ぶ理由や、他の保存先との違いなど、設計時に必要な背景を残します。

設定を使うときは、採用先が配布する版の利用案内と読み込み契約を確認します。一つの採用例の対象や優先順位を、別のスキルへそのまま適用するものではありません。この配置案を知っていることと、個々のスキルが対応していることも区別します。

## 採用時の確認と共通化の判断

この方法を採用する所有者は、少なくとも次を文書化し、代表的なケースで確認します。

- 読み込み契約の所有者と`owner-id`
- 対応する入口と、対応しない入口
- ファイル名、読み込み時点、固定範囲、再読境界
- 適用できる設定項目と対象範囲
- 現在の依頼、プロジェクトの正本、同梱されたデフォルトとの優先関係
- 保護される権限、安全性、根拠確認、検証、報告の境界
- 不在、読み込み失敗、解釈失敗、競合時の動作
- インストールや更新時に、設定ファイルを置き換えないための所有境界
- 設定がない場合に従来の動作を保つか
- 設定がある場合に意図した対象だけへ反映されるか
- タスク内の固定と、定めた境界での再読が機能するか

導入したこと自体を改善の証拠にはせず、設定の有無、競合、失敗、非対応入口、適用範囲を含む評価で挙動を確認します。

複数の採用例で同じ判断の欠落や保守負担が繰り返され、共通化によって改善できると分かった場合は、作成用スキルの指針へ含めることを検討できます。個別の読み込み契約、作成時の共通指針、共通ローダーやスキーマは、それぞれ必要性を判断します。個別スキルで使えたことだけを理由に、全スキルの要件へ広げません。

## 公式仕様との境界

Agent Skillsの公開仕様は、スキルディレクトリ、`SKILL.md`、`references/`などの構成を定めています。Agent Plugins v1の公開仕様は、配布パッケージとそのコンポーネントの発見方法を定めています。このノートの外部設定案は、それらのパッケージ形式とは別の、所有者が明示的に採用するローカル契約として扱います。
