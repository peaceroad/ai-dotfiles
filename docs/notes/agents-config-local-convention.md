# `~/.agents/config/`を利用者所有の設定面として使う考え方

> **位置付け：** これはローカルな設計案です。`~/.agents/config/`をAgent Skills、Agent Plugins、Codexなどの標準的な設定場所や自動読み込み場所として定めるものではありません。対応を明示したスキルやワークフローだけが、自身の契約に従って利用します。

スキルの配布元が定めたデフォルトを保ちながら、利用者が継続して使いたい好みやデフォルト値だけを外部へ置きたいことがあります。そのような場合は、`~/.agents/config/`を利用者所有の設定面として設け、対応するスキルやワークフローが必要なときに明示的に読む方法を検討できます。

この方法は、インストール済みスキルの内容を上書きしたり、同名スキルを自動的にマージしたりする仕組みではありません。設定ファイルの存在だけでは動作せず、読み手となるスキルやワークフローの対応が必要です。

## この方法が候補になる場面

外部の利用者設定は、次の条件が重なるときに候補になります。

- 配布パッケージやインストーラーが管理する内容を、更新のたびに利用者が編集したくない。
- 複数のプロジェクトで使う、利用者個人の安定した好みがある。
- 現在の依頼やプロジェクト固有の指示とは別に、再利用できるデフォルトを持たせたい。
- 設定の適用範囲、優先関係、読み込み時点、失敗時の扱いを、読み手側で明示できる。

一方、利用者自身が正本を所有し、更新で置き換えられないスキルなら、正本を直接編集するほうが単純なことがあります。すべてのスキルへ外部設定を追加する必要はありません。

Codexには、`~/.codex/AGENTS.md`または`~/.codex/AGENTS.override.md`と、プロジェクト内の`AGENTS.md`または`AGENTS.override.md`を読む公式の仕組みがあります。広く適用する作業方針やプロジェクト固有の指示には、この仕組みを使えます。`~/.agents/config/<owner-id>/instructions.md`はそれらを置き換えるものではなく、特定のスキルやワークフローだけが読む利用者設定を分離したい場合の案です。

## 最小の配置案

設定ファイルとその内容は利用者が所有します。ディレクトリ名には、その設定の読み込み契約を管理する単位を置きます。

```text
~/.agents/config/
└── <owner-id>/
    └── instructions.md
```

`<owner-id>`は、設定の読み込み、解釈、優先関係、更新、検証を定める契約の所有者を表す識別子です。単独のスキルが契約を管理するならスキル名、複数の関連スキルを一つの配布単位が管理するならその配布単位の安定した識別子などが候補になります。他の所有者と衝突しにくく、更新後も変わらない名前を選びます。

`instructions.md`は、人とモデルの双方が確認しやすく、複数の指示をまとめるファイルだとわかる仮のデフォルト名です。`AGENTS.md`や`SKILL.md`の役割を置き換えるものではありません。機械的な解析や移行が必要になるまでは、通常のMarkdownだけでも運用できます。

この配置案を説明するだけでは、`~/.agents/config/`や`instructions.md`を自動作成しません。実際に設定を作るのは、利用者が採用を決め、対応する所有者の読み込み契約を確認した後です。

## 対応するスキルやワークフローが明示的に読む

`~/.agents/config/`を共通の自動ローダーとして想定せず、設定を使うスキルやワークフローが、次の内容を自身の契約で定めます。

- どの`owner-id`配下の、どのファイルを読むか。
- どの入口や処理で設定を適用するか。
- いつ読み、どの実行単位で値を固定するか。
- 同じタスク内で再読する条件と、新しいタスクでの扱い。
- 現在の依頼、プロジェクトの指示、同梱されたデフォルトとの優先関係。
- 設定で変更できる範囲と、変更できない保護範囲。
- ファイルが存在しない、読めない、解釈できない場合の扱い。

たとえば、好みを扱う設定なら、対応する入口が最初に使われたときに一度読み、同じタスク内では有効な値を固定する方式が考えられます。利用者が更新を明示した場合だけ読み直し、新しいタスクでは改めて読むようにすると、処理の途中で結果が不意に変わりにくくなります。

ただし、これは一つの運用例です。設定の変更を即時に反映する必要がある処理や、設定を読めなければ安全に続行できない処理では、別の再読境界や停止条件が必要です。欠落時に黙ってデフォルトへ戻るか、警告するか、停止するかも、情報の重要性に応じて所有者が決めます。

## 置く情報と置かない情報

`config`には、利用者が採用済みの永続的なデフォルトだけを置きます。情報の役割を分けると、設定ファイルが履歴や作業メモへ膨らむのを防げます。

| 情報 | 主な置き場所 | 役割 |
| --- | --- | --- |
| 配布されるデフォルト | スキルや配布パッケージの正本 | 全利用者へ提供する通常動作 |
| 利用者共通のデフォルト | `~/.agents/config/<owner-id>/instructions.md` | 対応するスキルやワークフローが読む、採用済みの個人設定 |
| プロジェクト固有の指示 | 適用範囲内の`AGENTS.md`、スタイルガイド、用語集など | そのプロジェクトの正本 |
| 今回だけの指定 | 現在の依頼 | 1回のタスクに固有の要求 |
| 未解決候補や判断記録 | 所有者が定めた保守ノート、未解決候補、判断記録の保存先 | 将来の保守や再検討の材料。存在だけでは動作へ反映しない |
| 実行中の状態 | ランタイムやコントローラーが定めた状態保存先 | チェックポイント、ロック、再試行回数、進捗 |
| 履歴や証拠 | 所有者が定めた履歴・評価結果・証拠の保存先 | 何が起きたか、何が判断を支えるかを記録する |

設定をランタイム状態、履歴、評価結果、未解決の改善候補、判断記録の保存先として使いません。逆に、保守ノートへ書いた候補や判断理由を、有効な利用者設定として自動的に扱いません。`~/.agents/notes/`を使う場合の考え方は、[`~/.agents/notes/`を保守記録の入口として使う考え方](agents-notes-local-convention.md)で説明しています。

## 優先関係は所有者が定義する

利用者設定は、現在の依頼やプロジェクトの正本を置き換えるためのものではなく、それらに指定がない場合のデフォルトとして扱うのがわかりやすい設計です。

まず、クライアントが定める指示階層と、サンドボックス、権限、承認境界に従います。`AGENTS.md`にファイル名だけで固定順位を与えず、クライアントが供給する位置付けと適用範囲に従います。

Codexでは、グローバルな`AGENTS.override.md`または`AGENTS.md`を確認した後、プロジェクトルートから現在の作業ディレクトリへ向かって、各階層の`AGENTS.override.md`、`AGENTS.md`、設定されたfallback名のうち一つを結合します。同じ`AGENTS.md`チェーンでは、作業ディレクトリに近い指示ほど後に置かれ、先の指示を上書きできます。これはCodexが`AGENTS.md`を探索・結合する規則であり、現在の依頼、`~/.agents/config/`、スキル既定との一般的な順位を定めるものではありません。

`AGENTS.md`自体の指示はクライアントの指示階層で扱います。そこからプロジェクトのスタイルガイドや用語集が正本として指定されている場合は、その資料をプロジェクトが管理する正本として扱います。

そのうえで、同じ種類の好みやデフォルトが競合する場合は、次の順に扱う方式が候補になります。

1. 適用される指示階層が許す範囲で、現在の依頼や今回の正本として明示された資料
2. プロジェクト、媒体、組織などが管理する適用範囲内の正本
3. 利用者共通の設定
4. スキルやワークフローに同梱されたデフォルト

これは、すべてのクライアントやワークフローへ適用できる標準順序ではありません。設定の所有者は、対象ごとの優先関係に加え、競合を自動的に解決できない場合の扱いと、利用者への確認が必要な条件を定めます。

## プロジェクト固有の資料はプロジェクト側から案内する

特定プロジェクトのスタイルガイド、用語集、仕様書などを常に参照させたい場合は、通常、そのプロジェクトの`AGENTS.md`やプロジェクト所有の文書から案内するほうが自然です。これにより、プロジェクトとともに更新すべき指示を、利用者共通の設定から分離できます。

初期段階では、`instructions.md`を自己完結させ、そこから別ファイル、URL、コマンド、スキル、ツールを連鎖的にたどらない設計が扱いやすいでしょう。外部参照を許可する場合は、少なくとも次を所有者の契約へ追加する必要があります。

- 読み取りを許可するルートとパスの解決方法
- 相対パスの基準
- 参照の深さ、循環参照、重複読み込みの扱い
- URL、コマンド、ツール呼び出しを許可するか
- 参照先がない、読めない、信頼できない場合の扱い

`instructions.md`にファイル名が書かれているだけでは、任意の場所を探索したり、指示を無制限に連鎖させたりしません。参照先を読む必要があるなら、対象、解決方法、許可範囲を読み手の契約で明示します。

## 利用者設定で変更させない範囲

利用者設定は、好みやデフォルトを調整するための入力であり、権限や安全境界を広げる手段ではありません。所有者は、少なくとも次のような保護範囲を明示します。

- システム指示、開発者指示、ツール契約、サンドボックス、承認などの上位制約
- 依頼範囲、ファイル変更、外部送信、公開、配布などの権限
- 認証情報、課金、削除、本番環境などに関する安全確認
- 事実確認、ソース整合性、必須の検証、監査に必要な記録
- 結果を判断するために必要な重要情報や未確認事項の報告

たとえば、設定に「検証を省略する」「確認なしで公開する」「未確認事項を報告しない」と書かれていても、保護された契約を弱める指示としては適用しません。Markdownに保護範囲を書くだけでは、技術的な強制力はありません。権限や安全性の強制が必要な場合は、ツール、サンドボックス、承認手順などでも境界を維持します。

## 形式とバージョンは必要になってから導入する

読み手となるスキルやワークフローが1つに限られ、設定が短いMarkdownとして成立する間は、スキーマ、フロントマター、専用の設定ファイル、仕様バージョンを先に増やす必要はありません。次のような互換性の問題が現れた時点で、構造化とバージョン管理を検討できます。

- 複数の読み手が同じ形式を機械的に解釈する。
- 新旧の形式を区別しないと誤って適用される。
- 検証、移行、互換性判定を自動化する必要がある。
- 複数のクライアントや所有者が契約を共有する。

識別子だけを先に追加せず、導入するときは、解決する互換性問題と古い設定の扱いもあわせて定めます。

## 対応するスキルやワークフローの確認項目

この方法を採用する所有者は、少なくとも次を文書化し、代表的なケースで確認します。

- 読み込み契約の所有者と`owner-id`
- 対応する入口と、対応しない入口
- ファイル名、読み込み時点、固定範囲、再読境界
- 適用できる設定項目と対象範囲
- 現在の依頼、プロジェクトの正本、同梱されたデフォルトとの優先関係
- 保護される権限、安全性、根拠確認、検証、報告の境界
- 不在、読み込み失敗、解釈失敗、競合時の動作
- インストールや更新時に、設定ファイルを置き換えないための所有境界
- 設定がない場合に従来の動作を保つか
- 設定がある場合に意図した対象だけへ反映されるか
- タスク内の固定と、定めた境界での再読が機能するか

導入したこと自体を改善の証拠にはせず、設定の有無、競合、失敗、非対応入口、保護範囲を含む評価で挙動を確認します。

## 公式仕様との境界

Agent Skillsの公開仕様は、スキルディレクトリ、`SKILL.md`、`references/`などの構成を定めています。Agent Plugins v1の公開仕様は、配布パッケージとそのコンポーネントの発見方法を定めています。このノートの外部設定案は、それらのパッケージ形式とは別の、所有者が明示的に採用するローカル契約として扱います。
