# ~/.agents/とプロジェクト内の保存先

スキルやCLIを使うとき、導入するファイル、利用者設定、保守メモ、評価記録、一時ファイルは、用途と管理する主体に応じて保存先を選びます。このガイドは、このリポジトリのツールとローカルな運用規約で使う場所を案内します。`~`は利用者のホームディレクトリを表します。

まず、対象のプロジェクトやワークフローに既存の保存先があれば、その規約を確認します。以下のディレクトリを一括で作る必要はありません。設定や保守メモを読み込む条件は、それぞれを使うスキルやツールの指示に従います。

## スキルとCLIの配置

- **`~/.agents/skills/`**：個別に導入したスキルや、開発元へのリンクを置きます。開発中のソースを直接使う手順は[スキルリンクのガイド](skill-links.md)を参照してください。
- **`~/.agents/ai-dotfiles/`**：このリポジトリが提供する`agent` CLIの設定、管理状態、インストール済みランタイムを置きます。直下の設定、`state/`、`runtime/`の役割と変更方法は[CLIの開発・利用ガイド](agent-development.md)で管理します。

`ai-dotfiles/`はCLIが管理する領域です。各スキルの保守メモや評価結果を、この名前の下へすべて集める運用にはしていません。プラグインのソースは各開発リポジトリで保守します。

## 利用者設定と保守メモ

次の二つは、対応するスキルや運用で採用する任意のローカル規約です。`<owner-id>`には、その設定や記録を継続して管理するスキル・プラグイン・ワークフローの識別子を使います。一時的に設計や評価を手伝ったスキルの名前にそろえる必要はありません。

- **`~/.agents/config/<owner-id>/`**：配布されたスキル本体を編集せず、対応する項目の既定の振る舞いを利用者指定で上書きするための設定を置きます。スキルの更新とは別に、利用者側で指定を保てます。読み込みに対応するスキルが、定められた範囲で同梱の既定より優先して使います。形式・読込条件・現在の依頼やプロジェクト指示との優先関係は、対応するスキルの指示を確認してください。[設定を外部に置く考え方](notes/agents-config-local-convention.md)に設計理由があります。
- **`~/.agents/notes/<owner-id>/`**：後で再検討する改善候補や、残す価値のある判断理由と証拠への参照を置きます。すべての作業を記録する必要はありません。会話全文、評価の生記録、実行中の状態、採用済みの設定は別の保存先で管理します。[保守記録の規約](notes/agents-notes-local-convention.md)で、残す情報と整理の考え方を説明しています。

`agent-workflow-design`で設計を見直す場合も、`agent-improve`で評価する場合も、後の保守に必要な情報だけを、採用済みの保存先へ残します。既存のセッションログを根拠にできるなら、URLや識別子、該当箇所と短い判断で足ります。ただし、参照先を後から確認できることが条件です。参照できない場合は、その不足を明示します。

## 評価記録

再利用する評価定義、合成の検証用データ、公開可能と確認した課題・応答・判定は、保守対象のプロジェクトで管理できます。このリポジトリでは評価記録を[`evals/`](../evals/README.md)、説明や採用判断を`docs/`へ置きます。他のリポジトリのスキルを評価した場合は、そちらの規約に従って選びます。

公開可否は内容から判断します。公開されたスキルの評価でも、実行記録に利用者の環境や入力が含まれることがあります。このリポジトリへ残す情報は、[プライバシーの規約](../AGENTS.md#privacy-of-repository-content)に従い、再利用できる知見や合成例を中心に選びます。

`agent-eval-tools`の付属ランナーは、加工前の実行記録を保存する`--out`に、**Git作業ツリー外のディレクトリ**を指定する必要があります。Gitの追跡対象から除外した場所でも、作業ツリー内には出力できません。公開する抜粋を後でプロジェクトへ残すことは、これとは別の判断です。保存と再開の条件は[ランナーの実行契約](../plugins/agent-eval-tools/skills/agent-improve/references/runtime.md#retained-evidence-and-temporary-work)を参照してください。

ホーム配下で評価記録を保持する場合には、`~/.agents/evals/<project-id>/<run-id>/`を保存先として選び、必要に応じて作成できます。既存の保存先がある場合は、その規約との整合を確認します。付属ランナーも、`--out`に指定された保存先が存在しなければ、必要な親ディレクトリとともに作成します。この配置がランナーの既定値という意味ではありません。付属ランナーで使う場合は、この場所もGit作業ツリー外という条件を満たす必要があります。

`<project-id>`は保守対象を識別できる名前、`<run-id>`は実験ごとに重ならない名前にします。同じ実験の再開では元の保存先を使い、対象の版や評価条件を変えて試す場合は、別の実験として新しい保存先を使います。

### ~/.agents/evals/を選ぶ場面

次のように、評価の入力・応答・判定を後からたどる必要があり、ホーム配下で管理したいときに使えます。

- **スキルの変更前後を比較する**：同じ課題を現行版と候補版で試し、採用・現行維持の判断に使った条件と結果を残す。付属ランナーの生の記録を、開発リポジトリの外で保持する場所になります。
- **途中で止めた評価を再開する**：完了済みの試行と未完了の処理を識別できる記録を残す。再開は、ランナーが定める条件を満たす同じ実験に限ります。
- **後日、評価や改善の方法を見直す**：採点の食い違い、候補が改善につながらなかった理由などを、元の応答や条件に戻って調べる。短い保守メモだけでは判断できない場合の証拠になります。

通常の作業でスキルを使っただけなら、毎回ここへ記録を作る必要はありません。会話中の気付きを保守メモと既存ログへの参照で残せるなら、それで足ります。記録が蓄積しても、評価スキル自身の改善が自動的に始まるわけではありません。

### スキルを一つ改善するときの配置例

架空の`example-plugin`に含まれるスキルについて、指示を変えると制約の見落としが減るかを比較する例です。

1. 繰り返し使う合成の課題と判定条件は、対象リポジトリの`evals/`で管理します。
2. 付属ランナーの保存先に`~/.agents/evals/example-plugin/constraint-check-01/`を指定し、対象の版・入力・応答・判定を保持します。途中で止めた場合も、この実行記録を使って再開条件を確認します。
3. 後日検討する気付きがあれば、短い判断と該当記録への参照を保守メモに残します。`notes/`の規約を採用している場合は`~/.agents/notes/example-plugin/`を使い、別の保守先がある場合はそちらを使います。応答全文をメモへ複製する必要はありません。
4. 共有や将来の回帰確認に使う課題・応答・判定は、保存・公開の規約に沿って内容を確認し、対象リポジトリの`evals/`へ選んで残します。説明や採用判断は`docs/`にまとめます。この工程は必要な場合だけ行い、非公開のプロジェクト内で保守する場合にも選べます。

この例の`~/.agents/evals/`は保持する証拠の置き場です。応答の受け渡しなどに使う一時ファイルを`temp/`へ置く場合は、次の条件に従います。

## 一時ファイル

既存の作業用領域がなければ、`~/.agents/temp/<owner-id>/<run-id>/`のように、用途と実行を識別できる配置を選べます。これも任意の例です。CLI自身が管理する一時処理なら、そのCLIの保存先の規約に従います。

一時領域に置くのは、消えても必要な成果物や証拠を失わない作業用ファイルです。後で比較・再開・保守に使う評価記録は、最初から保持する場所へ保存します。自動生成されたファイルでも、結果の唯一のコピーや、処理中に必要なファイルは削除できません。

付属ランナーへ応答を渡すファイルは、対応するリクエストと実行ID、応答本文が実行記録に正しく保存されたことを確認してから、一時ファイルとして扱います。判断の根拠になる追加の成果物も保持します。`temp/`という名前だけで削除対象を決めず、実行の終了と必要な記録の保管を確認してください。

## このリポジトリの公開用コピーとの違い

リポジトリ内の`home/.agents/`は、ホーム側から選んで書き出した公開用ファイルの配置先です。利用中の`~/.agents/`そのものではなく、上記のディレクトリをすべて公開する場所でもありません。コピーの方向と対象の選び方は[エクスポートガイド](export.md)を参照してください。
