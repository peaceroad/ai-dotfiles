# クラウドのファイル管理

dotにファイルの作成や編集を頼むときの、作業場所と保存・整理のガイドです。継続する仕事の資料や成果物は、既存のプロジェクト内にまとめます。

ターミナルと画面操作の違い、アクセス範囲の確認は[クラウドコンピュータを使う](cloud-computer.md)、初回の導入は[インストールと初期設定](setup.md)を参照してください。

## ファイルを扱う前に確認すること

メインのdotは、初期設定や保守に限らず、通常のファイル作成・ダウンロード・編集・整理でも、保存先を決める前に共通指示を使います。その仕事へ割り当てられた作業ディレクトリ、既存のプロジェクト構成、読み書きできる範囲を確認し、明示された保存先がその範囲内なら指定に従います。指定がない場合は、`/workspace/shared/`直下へその場限りのタスク用ディレクトリを作らず、以下の規約を使います。

以下の`/workspace/`配下の配置は、[共通指示](../../plugins/dot-toolkit/skills/dot-guidelines/SKILL.md#cloud-workspace)に基づくdot-toolkitの運用規約です。保存期間、バックアップ、共有範囲は、作業環境で確認します。

## 用途ごとの保存場所

保存先は、どの仕事に属するかと、保持するファイルの役割で選びます。必要な場所だけを作り、最初からすべてのディレクトリを用意することはしません。

```text
/workspace/shared/
├── projects/<project>/     継続する仕事の資料・コード・文書・テスト・成果物
├── docs/                   プロジェクト外で読み返し・更新に使う文書
├── outputs/<topic>/        プロジェクト外の利用・受け渡し用成果物
├── downloads/              保持する取得資料・固定版のスナップショット
└── tools/                  利用者管理のツール・ランタイム
```

### 既存プロジェクトの仕事は、その場所で続ける

既存プロジェクトに属する仕事は、短いテストでもそのプロジェクトの場所と保存・プライバシー規約に従って進めます。下書き、参照資料、文書、テスト・評価の定義、公開可能な評価の証拠、成果物は、その規約に合う既存の構成で扱います。たとえば、保守に役立つ評価の証拠と非公開の実行ログは、同じ評価で生じたものでも保存先が異なることがあります。

新しく継続管理する仕事は、小さなものでも`projects/<project>/`で始められます。継続するか未定の独立した試行は、一時作業用のscratch領域から始められます。後から継続管理すると決めた場合は、必要な資料・編集元・成果物をプロジェクト内へまとめ、以後はその場所で続けます。

プロジェクト内の計画も、既存の規約に従います。`docs/plans/`などの置き場所や、Issue・PR・特定ツールで管理する計画があれば、それを使います。分類をそろえるためだけに新しい階層や管理用のコピーを増やしません。別の作業コピーは、固定版との比較や隔離した試験など、具体的な目的がある場合に使います。

### 独立した文書と、利用・受け渡し用の成果物を残す

プロジェクトに属さない計画、調査メモ、ガイドなど、読み返したり更新したりする文書には`shared/docs/`を使えます。文書が増えて分類が役立つ場合は、計画を`docs/plans/`、調査・検討の記録を`docs/notes/`へまとめられます。独立したガイドはdocs直下でも構いません。書きかけか完成済みかだけを理由に、保存先を変える必要はありません。

`outputs/<topic>/`は、利用や受け渡しのために用意した成果物を保持する場所です。たとえば配布用PDF、画像、ZIPなどを置けます。ただし、形式だけで振り分けるのではなく、そのファイルの役割で判断します。docsの文書やプロジェクト内の成果物をそのまま渡せるなら、outputsへ複製しません。

後で修正するために必要な編集原本や素材も残します。たとえばプロジェクトに属さない画像制作なら、確認済み画像とともに、レイヤーを保った編集ファイルなどを同じ`outputs/<topic>/`で保持できます。既存のdocsやプロジェクトに編集元がある場合は、その場所で管理を続けます。

独立した試行のためだけの仮の計画は、タスク用のscratchに置けます。短ければ会話内だけで十分です。後から読み返す計画やメモとして残すならdocsを使い、同じ計画を複数の場所で重複管理しません。

### 一時作業は、同じ仕事・対象の場所を再利用する

scratchでは、環境から割り当てられた作業ディレクトリを確認し、その配下に仕事別のタスク用ディレクトリを置きます。アクセスできる適切な場所がすでにあれば再利用し、同じ名前でも別の仕事・対象の場所は使いません。継続プロジェクトの外で新しく必要な場合は、日付を付けず、作業内容を表す短い名前で作ります。日時に意味がある検証結果やスナップショットは、仕事の配下で区別します。既存プロジェクトの命名規約と、環境が割り当てたディレクトリ名は優先します。毎回のディレクトリ新設や作業全体の複製を、既定の進め方にはしません。

再開時は、現在編集すべき原本を確認します。docsやoutputs、プロジェクトへ保持した原本が更新されていれば、古いscratch内のコピーではなく、その原本から続けます。ユーザーが提供した原本や、由来が分からない編集は勝手に移動・上書きしません。

プロジェクトのテスト・評価、一時・ビルド用ファイルは既存の規約に従います。比較に必要な結果は関係する作業場所の配下で、条件や版を区別して保持します。並行作業では、原本・中間ファイル・出力の競合や、必要な結果の上書きを防ぐため、書き込みを分担するか順番に行い、必要なら作業領域を分けます。

割り当てられたディレクトリ自体は改名せず、scratch領域内で割当先の外へ共通の分類用ディレクトリを増やしません。`/tmp`は破棄できるものに限り、重要な作業の唯一のコピーは置きません。作業後に残す成果物と編集原本は、上で説明した役割に合う場所へ保持します。

### 取得物とツールを区別する

`downloads/`は、保持する取得資料や固定版のスナップショットに使います。プロジェクトに関係する資料は、そのプロジェクト内に保存できます。スキルの取得元スナップショットも、[保守手順](../../plugins/dot-toolkit/skills/dot-guidelines/reference/skills-maintenance.md#pin-source-identity)では`projects/`または`downloads/`へ置けます。

`tools/`は、利用者が管理するツールやランタイムの置き場所です。場所を用意することと、ソフトウェアのインストールや実行を承認することは別です。必要なランタイムがなければ、前提条件として報告し、無断で導入しません。環境固有の補助文書には、具体的な必要がある場合だけ`/workspace/.codex/docs/`を使えます。

## 容量を確認するときの読み方

容量の値には、何を測ったかと確認時点を添えます。次の3つは別の指標です。

- **ファイルシステムの容量と空き**：保存先が属するファイルシステム全体の値です。同じファイルシステム上の複数ディレクトリで同じ空き容量が表示されても、それぞれに独立した容量があるという意味ではありません。
- **ディレクトリの使用量**：その場所にあるファイルなどが占める量です。ディレクトリ自体に割り当てられた上限や、今後書き込める量を示すものではありません。
- **メモリーの容量と利用可能量**：処理中に使うRAMの状態です。ファイルを保存する領域の空きとは分けて確認します。メモリーを使う一時ファイルシステムがある場合も、表示された容量を通常の保存領域へ足し合わせません。

観測時の空き容量は、将来の確保量、仕事ごとの割り当て上限、保存期間の保証にはなりません。大きな生成・変換処理では、対象の保存先と必要な作業領域を実行時に確認します。実環境の数値は非公開の記録に残し、公開文書には一般化した確認方法を載せます。

## 保存したファイルを確認して、必要なものを残す

ファイル作成や編集では、保存先の既存内容と変更の許可を確認し、保存後に読み戻して、依頼した内容が反映されたかを確かめます。文書や画像などは、内容の検査だけでなく、成果物に必要な形式・表示の確認も行います。確認方法は、担当するタスクのスキルや利用できるツールに従います。

保存したこと、内容を確認したこと、利用者が開ける方法で渡したことは別の状態です。必要な成果物は、利用者が利用できる受け渡し方法とアクセス範囲を確かめて渡します。クラウド内のパスを伝えただけで、利用者が開けると判断しません。

整理や削除は、承認された範囲で行います。価値のある下書き、資料、成果物は先に保持し、由来や所有者が分からないファイルは残します。`scratch`という名前や時間の経過だけを理由に、定期的な一括削除はしません。

## 指示・スキルの管理ファイルと分ける

仕事のファイルとは別に、任意の個別指示は`/workspace/.codex/AGENTS-private.md`、採用したスキルやプラグインは`/workspace/.agents/`配下で管理します。個別指示は実際の内容があるときだけ作り、読む条件と参照先を保ちます。

共通指示と設定手順はプラグインに同梱されています。0.2以降は、共通の`/workspace/AGENTS.md`と`/workspace/.codex/dot-setup.md`を常設しません。旧ファイルがある場合は自動で消さず、[移行手順](setup.md#01から02へ移行する)に従います。`.codex/`には、実際に提供された個別文書、必要な非公開の再開記録、具体的な必要がある環境固有の補助文書などを置けます。

INDEX、採用記録、開発ソース、クラウドの採用コピーの役割は、[スキルとプラグインの管理](skills-management.md#管理するファイルと役割)で説明します。

## アクセス範囲と非公開情報

共通指示・個別指示・スキルは、現在の依頼、サービスの制約、アプリの承認手順の下で使います。プラグインのソースを修正する依頼だけで、実環境のインストールや移行を始めることはありません。

個別文書、実際のスキル在庫、取得・復元・移行の記録、実環境での観測内容は非公開として扱います。公開リポジトリ、PR、配布ZIP、公開用の検査ログへ持ち込まず、説明や試験には一般化した内容と合成例を使います。生成ZIPもリポジトリへコミットしません。
