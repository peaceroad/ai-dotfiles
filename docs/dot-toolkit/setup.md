# dot-toolkitのインストールと初期設定

まずChatGPT Webでプラグインをインストールし、メインのdotから共通スキルを読めることを確認します。個別指示や自作スキルをファイルで管理したい場合だけ、続けてdotのクラウドを設定します。

0.5は、0.4の配置でスキルやプラグインの追加・更新に支障がある環境向けの任意の選択です。問題がなければ、0.4のプラグインと配置を維持できます。0.5を採用する場合は、プラグイン更新と、既存の個別指示・スキルの配置移行を分けます。

既存構成がある場合は、同梱の[移行案内](../../plugins/dot-toolkit/skills/dot-guidelines/reference/migrations/README.md)から必要な手順だけを選びます。既存ファイルを新規設定として置き換えません。

## 1. ChatGPT Webでプラグインをインストールする

### パッケージを用意する

配布者からdot-toolkitのZIPまたは共有プラグインを受け取ります。共有プラグインを使う場合、ZIPの作成は不要です。

ソースからZIPを作る場合は、配布者が指定したタグまたはコミットを使います。指定がなければ、この手順書を含むコミットを選びます。`plugin.json`の`version`が`0.5.0`であることを確かめ、[plugins/dot-toolkit/](../../plugins/dot-toolkit/)の`plugin.json`、`README.md`、`skills/`をZIPの直下へ入れます。リポジトリ全体や、外側の`dot-toolkit/`フォルダーは含めません。

Gitのチェックアウトから作る場合は、選んだコミットへ切り替え、リポジトリのルートで次を実行できます。

```sh
git rev-parse HEAD
git show HEAD:plugins/dot-toolkit/plugin.json
git archive --format=zip --output=../dot-toolkit-0.5.0.zip HEAD:plugins/dot-toolkit
```

最初の2コマンドで対象コミットと版を確認し、最後のコマンドで親ディレクトリへZIPを作成します。同名ZIPがあれば、実行前に出力名を変えてください。含まれるのはコミット済みの内容で、未コミットの編集は入りません。生成ZIPはコミットせず、個別指示や実際の管理記録を混ぜないでください。同じ版番号の候補パッケージでも内容が異なる場合があるため、取得元コミットとZIPのSHA-256で区別し、検証結果を実際に確認した候補へ結び付けます。

### Webで追加・インストールする

ChatGPT Webを開き、dotを使うアカウントとワークスペースを選びます。

- **ZIPを使う場合**：利用できるプラグインアップロード機能から追加します。アップロード権限のあるワークスペース管理者向けの経路は、管理コンソールのPlugins → Add → Upload pluginです。
- **共有プラグインを使う場合**：ChatGPTのPluginsから、共有された`dot-toolkit`を開きます。

プラグインの詳細を開き、Install pluginが表示される場合は選択します。アップロードできたことに加えて、対象アカウントでインストール済み・利用可能になったことを確認してください。機能や必要な権限はアカウント・ワークスペースによって異なります。項目が見つからない場合は、[公式のプラグイン案内](https://help.openai.com/en/articles/20001256-plugins-in-chatgpt)で提供条件を確認します。

チャットへのZIP添付、ライブラリへの保存、クラウドへの展開だけでは、プラグイン導入は完了しません。

### メインのdotから確認する

インストール後、メインのdotへ次のように依頼します。

> インストールしたdot-toolkitのdot-guidelinesを読めるか確認して。

実際の導入済み共通スキルと、今回の作業に必要な同梱資料を確認します。版の情報が得られる場合は、意図した`0.5.0`かも確かめます。リポジトリのソースや、ローカルCodexにある同名プラグインの確認では代用しません。

読めない場合は、アカウント・ワークスペース、プラグインの状態、確認できた版を調べます。原因が分からないまま再インストールを繰り返したり、端末間の同期を前提にしたりしません。一度確認できたら、版や利用環境の変更、読取失敗などがない限り、同じ導入確認を依頼のたびに繰り返す必要はありません。

## 2. 必要なクラウド設定を依頼する

個別指示やタスク用スキルをファイルで管理したい場合は、「dot-toolkitで初期設定して」と依頼します。dotは[同梱の手順](../../plugins/dot-toolkit/skills/dot-guidelines/reference/setup.md)で既存ファイルを確認し、必要な設定だけを進めます。別の`dot-setup.md`を添付する必要はありません。共通指示だけを使う場合は、この設定を省けます。

初めて設定する場合も、指示・スキルをその場所へ配置することが現在の環境で許可され、導入済みプラグインから対応する方法で読めることを先に確かめます。通常のフォルダーへ書けることだけでは、この条件を満たしません。未確認なら配置に依存する部分を保留します。

### 個別入力を選ぶ

まだ判断が決まっていない場合は、次の2つについて、それぞれ今渡す・後で渡す・今回は不要を選びます。

- **個別指示**：利用者固有の作業条件や、特定の仕事で参照する文書。
- **追加スキル候補**：次の共通候補以外に検討したいスキル。

後回しや提供待ちの内容は、再開に必要な判断だけを非公開で残します。状態だけを書く空の指示ファイルは作りません。入力が保留でも、それに依存しない作業は進められます。

### 使うスキルを選ぶ

初期設定では、次の4スキルを共通候補として案内します。すべてを採用する必要はありません。

- `agent-workflow-design`：継続・反復する仕事の役割分担、待機、再開、終了を設計する。
- `prompt-design`：モデルへ渡す指示を設計・レビュー・改訂する。
- `agent-improve`：スキルやプラグインを比較評価し、改善実験を行う。
- `plugin-creator-agent-plugins`：プラグインを作成・検証・移行・パッケージ化する。

dotが用途、取得元、提案する版、必要な環境、現在の配置と変更内容を示してから、配置するものを選びます。共通候補と個別の追加候補は、別々に追加・更新の範囲を承認します。すでにその範囲を承認していれば、確認をやり直しません。どちらも見送れます。「追加なし」は既存スキルの更新・削除を意味しません。

取得元がプラグインなら、承認したプラグインのパッケージ一式をdotのクラウドへコピーします。manifest、各スキルの参照・スクリプト・素材、MCPや拡張用のファイルも、取得元の構成のまま保ちます。そのうち、普段の選択対象にするスキルを一つずつ選びます。単体スキルは、これまでどおりフォルダー一式で配置できます。

このファイル配置は、最初のdot-toolkitのインストールや、ChatGPTへのスキル登録とは別の作業で、アプリ側の既存スキルを自動でコピー・更新しません。未選択の依存スキルやランタイムが必要なら、その扱いを別途確認します。保存場所は[クラウドのファイル管理](cloud-workspace.md#用途ごとの保存場所)と[スキルの管理配置](skills-management.md#管理するファイルと役割)にあります。

### MCPや拡張機能を含む場合

ファイルを配置しただけでは、MCPサーバーの登録・起動・認証や、拡張機能の有効化は行いません。利用したい機能を指定し、対象環境で対応している接続方法と必要な承認を確認してから進めます。

たとえばローカルのMCP通信試験でツールの一覧と応答を確認できても、dotの会話でそのツールを呼べる証拠にはなりません。完了報告では、ファイル配置、Webでの導入、MCP通信、会話での利用のうち、どこまで確認できたかを分けます。

構成例を試したい場合は、別パッケージの[スキル差分比較サンプル](../../examples/skill-diff-plugin/README.md)を参照してください。初期設定で自動導入するものではありません。

## 3. 普段の仕事を依頼する

共通スキルを読めることと、依頼に必要な設定を確認できたら、普段の仕事を頼めます。たとえば`prompt-design`を普段の選択対象にした場合は、「この依頼文の曖昧なところを減らして」と伝えます。スキル名や場所を毎回指定する必要はありません。

初期設定を依頼した場合は、dotの完了報告で、次を確認します。

- **プラグイン**：メインのdotから共通スキルと必要な同梱資料を読めたか。
- **個別入力**：何を適用し、何を提供待ち・後回し・不要としたか。
- **スキル配置**：配置した内容が採用記録に一致し、選択一覧が承認した範囲を保っているか。

保留や未確認の項目があれば、それに依存する作業だけを待ちます。

## 0.1から0.2へ移行する

0.1から0.2への手順は、外部の共通指示と旧形式の管理記録を整理するための歴史的な手順です。[同梱の移行案内](../../plugins/dot-toolkit/skills/dot-guidelines/reference/migrations/README.md)から該当する場合だけ読みます。0.5の新配置を採用するだけで、この手順を必ず先に実行するわけではありません。0.1から0.5へ直接移る場合は、先に0.5の保存先と採用条件を確立し、その場所で必要な形式変換を行います。途中の版を実環境へ導入する必要はありません。旧共通指示の編集、保留入力、既存の選択と採用内容を保全し、旧相対パスの解決基準と生のバイト列を保ちます。

## 後から変更するとき

### Webにインストールしたdot-toolkitを更新する

手動アップロードしたプラグインは、必要な権限があり、詳細画面にUpload new versionが表示される場合に新しいZIPをアップロードできます。取得元から管理されるプラグインは、その更新方法に従います。[公式の更新案内](https://help.openai.com/en/articles/20001256-plugins-in-chatgpt)を確認し、更新後にメインのdotで利用できる版を確かめます。

この更新で、個別指示やクラウドのタスク用スキルを一括更新することはありません。

### 0.4から0.5を選ぶ場合

0.5.0の通常の管理先は`/workspace/shared/ai-dotfiles/codex/`と`/workspace/shared/ai-dotfiles/agents/`です。旧`/workspace/.codex/`と`/workspace/.agents/`は移行元・復帰用に限り、通常の読込み先を自動で切り替えたり、旧配置へフォールバックしたりしません。INDEXの形式、manifestのschema 1、パッケージ内部の相対配置は維持します。

1. **採用条件を確認する。** 対象環境で新配置へ置くことと、指示・スキルの読込み先を切り替えることの両方について、許可された対応方法を確認します。新しいソースやZIPがあるだけでは、その方法が使える証拠になりません。方法が未確立なら、ソース検証までに留め、実移行を保留します。
2. **プラグインと実データを分ける。** 0.5をインストールして必要な同梱資料を読めるか確認します。この更新は、旧データのコピー、保護された指示の移設、削除を許可するものではありません。
3. **必要な移行だけを依頼する。** [0.4から0.5への手順](../../plugins/dot-toolkit/skills/dot-guidelines/reference/migrations/0.4-to-0.5.md)に沿って、現在の内容・採用版・選択範囲を保全し、許可範囲でコピー、照合、参照の更新、切替を行います。移す範囲の外を指す相対参照も、移動前の基準で対象を特定し、新配置から意図した資料を参照できるか確かめます。最新版への更新は混ぜません。
4. **動作を確認してから整理する。** 読取り・内容一致・実際の選択と読み込みを分けて確認します。旧配置の削除は移行成功の必須条件ではありません。ただし旧入口からの自動読み込みや参照が未解決なら、単一の有効な経路への切替完了とは報告しません。復帰には旧ファイルだけでなく旧プラグイン／入口の利用可能性も必要で、切替後の編集を失わない方法を先に確認します。

新配置がない場合も、旧設定を使っていたと分かる環境は「空の新規環境」ではなく移行未完了です。部分コピー、不正な記録、読取失敗があれば依存する作業だけを保留し、旧配置への暗黙の代用や記録からの選択一覧の再生成はしません。将来0.4と統合するか、その版と時期は未定です。

すでに0.5を導入した後で移行を見送る場合、旧配置の利用を続けるには、以前のプラグインと読込み方法へ戻す必要があります。対応する方法で復帰でき、必要なファイルや参照が整っていることを確認し、許可された範囲で進めます。旧ファイルが残っているだけでは復帰できると約束しません。

### 以前の版での変更

以下は各版の変更の説明です。0.5へ進むために順番に適用する手順ではありません。旧パスは当時の配置を表し、0.5の新規保存先ではありません。

#### 0.4.1から0.4.2へ更新する場合

0.4.2は、クラウドへ採用したスキル・プラグインの更新前に、何を保護するかを明確にします。固定済み上流コミットとの一致と再取得可能性を確認できれば、通常は全体バックアップを省きます。以前の採用記録と必要な選択情報、上流から復元できない編集・設定・追加ファイルは保護し、既存バックアップは削除しません。詳しくは[スキルとプラグインの変更手順](skills-management.md#追加更新選択変更を依頼する)を参照してください。保存形式は変わらず、データ移行は不要です。

#### 0.4.0から0.4.1へ更新する場合

0.4.1は、[PR #33](https://github.com/peaceroad/ai-dotfiles/pull/33)で追加した編集方針を補い、dot自身のクラウドで許可されたテキストファイルの変更に、利用できて変更に適した専用の`apply_patch`ツールを優先します。ツールの利用可否、起動やファイルシステムのエラー、承認手順を区別し、明示的なアクセス拒否・ポリシー上の拒否は回避しません。この方針を、それ以前の0.4.0と版番号で区別できます。権限や保存データの形式は変わらず、データ移行は不要です。

#### 0.3から0.4へ更新する場合

0.4ではファイルの探索・配置・引継ぎを補っていますが、INDEX、採用記録のschema、スキルやプラグインの配置は変わりません。データ移行は不要です。更新後は、導入済みの入口と今回必要な参照が利用できることを確認します。

利用者が更新を伝えたとき、または明示的な確認作業で導入版の切替を観測したときに、以前の案内・対応を確認できる範囲で確かめ、未対応なら作業フォルダーの見直しを短く案内します。履歴が分からなければ、「まだ必要なら、以前の作業フォルダーの見直しもできます」と条件付きで案内し、過去の対応を思い出してもらうためだけの質問はしません。更新報告と実確認は区別し、通常作業で版を繰り返し調べません。内部通知は前提にせず、ソース編集、ZIP生成、静的な0.4本文だけで更新を判断しません。

案内・回答・完了範囲は既知の非公開の移行記録へまとめ、未確立なら0.4では`/workspace/.codex/dot-toolkit-migrations.md`、0.5への配置移行後は`/workspace/shared/ai-dotfiles/codex/dot-toolkit-migrations.md`を使います。この記録のためだけに新配置を作りません。通常は読み込まず、案内済みと分かる提案や、辞退・延期後の催促は繰り返しません。記録が読めない場合は、上書きや広い探索をせずに残します。記録を確認できなくても、案内や独立した仕事は続けます。ただし、初回とも、整理を許可済みとも決めつけません。

0.3までの配置を揃えたい場合は、後から「これまでの作業フォルダーを0.4の方針で整理して」と依頼できます。今も使えるフォルダーも対象にでき、更新時に辞退・延期した場合でも、現在の依頼を優先します。整理は[作業領域の見直し手順](../../plugins/dot-toolkit/skills/dot-guidelines/reference/migrations/0.3-to-0.4.md)に沿って進めます。

1. **関係する場所から調べる。** 現在の原本、参照、稼働状況、Gitの関係、移動先の衝突を確認し、移すもの・残すものを選びます。現役フォルダーは日付なしの作業名を基本とし、日時に意味がある検証記録は仕事の配下で区別します。既存プロジェクトの規約と環境の割当先を優先し、日付だけで一括改名したり、同名の別資料やGitリポジトリを結合・上書きしたりしません。
2. **変更前に具体的に説明する。** 推奨する移動元・移動先、保持・保留するもの、影響、戻す方法と未確認点を示します。整理実行まで委ねられた範囲は、その説明後に続けます。調査だけなら結果報告で止め、許可が曖昧なら一度にまとめて確認します。沈黙を承認とせず、後からの範囲変更も反映します。
3. **許可範囲で整理・確認する。** 安全に解決できる改名・移動・参照更新は重ねて承認を求めず進め、未解決の対象だけ保留します。別のファイルシステムへコピーして移す場合は、内容と参照を検証してから、許可範囲内で移動元を削除します。削除が許可に含まれていなければ移動元を残し、その許可だけを確認します。移動の許可を他の不要ファイルの削除へ広げず、サービスの規則で必要な承認にも従います。整理後の内容と参照を確認し、主な変更と保留理由を報告します。

プラグイン更新だけで既存ファイルを動かすことはありません。個別指示や採用済み資産を保ち、scratchに残る継続資料のproject化などを、[ファイル管理の方針](cloud-workspace.md)に沿って必要な範囲で検討します。

### 個別指示やスキルを変える

変えたい対象と内容を伝えます。個別指示だけを保存・変更する場合は、初めてでも、その指示と参照先だけを比較・適用し、読み戻して確認します。初期設定全体やスキル候補の選択を行う必要はありません。

クラウドに配置したプラグイン・単体スキルの追加、更新、選択変更は、[スキルとプラグインの管理](skills-management.md#追加更新選択変更を依頼する)を参照してください。Webにインストールしたdot-toolkitの更新とは別に扱います。中断した保守の再開や同じ版の再現も、[同ページの手順](skills-management.md#中断した作業を再開する同じ版を再現する)にまとめています。

## 困った場合

- **ZIPはあるがdotで使えない**：保存・アップロード・インストールのどこまで済んだか、対象アカウントで利用可能か確認します。
- **個別ファイルが初めからない**：追加指示に依存しない仕事は続けられます。空ファイルや代替設定は不要です。
- **読めない、使っていたファイルが消えた**：未作成とは区別し、その資料に依存する部分を止めます。無断で再構築したり、別経路でアクセス拒否を回避したりしません。
- **更新が反映されたか分からない**：プラグイン、開発ソース、クラウドのスキルコピー、採用記録のうち、どれを変更したか確かめます。
- **検査で不一致が出た**：編集を保ち、差分の由来を調べます。検査ツールはファイルを書き換えません。[検査結果の意味](skills-management.md#読み取り専用の検査)も参照してください。

## 読み込みと自動選択の受け入れ確認

ここは、開発・検証担当者が「動作を検証済み」と報告するための確認です。通常利用の前に、利用者全員が新しい会話や環境を用意して試験する必要はありません。

実際のメインdotでの同梱資料の取得・スクリプト実行、スキル名を指定しない依頼での選択、会話や環境をまたぐ継続性は、それぞれ別に観測します。0.5の新配置では受け入れ確認が未完了で、ソース検査や合成テストの成功では補えません。移行に必要な導入済みリソースの確認は、[0.5への移行](#04から05を選ぶ場合)の条件を満たす必要があります。

試験の前提と証拠の条件は[受け入れ確認](../../evals/dot-toolkit/README.md)にあります。確認のためだけにdotをリセットしたり、個別設定を変更したり、定期テストを始めたりはしません。
