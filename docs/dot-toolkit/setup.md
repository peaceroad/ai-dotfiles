# dotの構築と更新手順の解説

[dot/dot-setup.md](../../dot/dot-setup.md)は、dot自身のクラウドを初期設定し、後から変更し、採用した版を再現するための手順です。この文書では、利用者が何を用意・選択し、どの結果を確認するかを説明します。実行時の細かな条件と管理記録の形式は、採用する手順本文を参照してください。

全体の入口は[dot-toolkitの使い方](README.md)、共通指示の内容と配置は[共通指示の解説](instructions.md)にあります。日本語の説明ページが更新されても、初期設定に添付した手順や中断中の採用版が自動で切り替わることはありません。

## 依頼する作業を分ける

- **初期設定**：既存の状態を調べ、共通指示と手順を置き、個別入力とスキル候補を扱う。
- **更新**：指定した対象について、既存の内容と新しい版・編集を比較して反映する。
- **再開**：中断時の版と承認範囲を保ち、実際の結果を確認して未完了の作業を続ける。
- **固定版の再現**：採用した版と意図した変更を、記録と復元資料から揃えて照合する。

構築の依頼は、候補スキルすべての採用や、付属コードの実行、外部ランタイムの導入、接続設定の変更まで一括で承認するものではありません。内容と対象を確認し、各操作に必要な範囲で進めます。アクセスの考え方は[権限の説明](instructions.md#アクセス範囲と権限)を参照してください。

## 初期設定の進め方

### 用意するもの

1. 利用するクライアントの方法で`dot-toolkit`を導入する。
2. このリポジトリの[dot-setup.md](../../dot/dot-setup.md)を用意し、メインのdot会話へ添付する。
3. 「この手順で初期設定して」と明示的に依頼する。

`dot-setup.md`は、3ファイル構成のプラグインとは別に用意します。開発用PCで管理しているファイルを添付してもかまいません。この手順は、プラグインZIPを特定のWebサイトからダウンロードする運用を要求しません。

初回は添付した手順を先に読みます。まだ作られていないクラウドの設定ファイルを、開始条件として要求しません。一方、添付だけ、内容の確認だけという依頼では、構築を実行しません。会話は利用者が使っている言語で進められます。

### 共通指示と既存状態の確認

dotは、添付手順にあるリポジトリ・パス・固定コミットから共通指示を検証して取得します。利用者が別の取得元を指定した場合も、採用する内容を特定して扱います。共通指示の固定版と、後で選ぶスキルの版は別です。

保存や変更の提案の前に、既存ファイル、採用済みスキル、管理記録、同名のコピー、途中の作業を確認します。読めないファイルを未作成とみなして上書きせず、既存の編集を保ちながら差分を扱います。

### 個別指示と追加候補を選ぶ

未提供で状態が分からない場合は、次の二つについて、それぞれ「今渡す」「後で渡す」「今回は不要」を選びます。

- 個別指示：利用者固有の指示や、条件付きで読む文書
- 追加スキル候補：共通候補とは別に検討したいスキル

「追加スキルは不要」と「個別指示は不要」は別の判断です。後回しや未回答は保留として扱い、不要とは記録しません。不要と決めた場合はdotがその状態を記録するので、利用者が空のファイルを用意する必要はありません。既存の個別文書は、簡略な状態記録で置き換えません。

個別入力が保留でも、それに依存しない共通部分は進められます。共通設定、個別指示、スキル選択それぞれの完了・保留を分けて確認します。

## スキルの選択と導入

構築手順の共通候補は次の4スキルです。用途の概略をここに示し、取得元パスや利用要件の詳細は[手順の候補一覧](../../dot/dot-setup.md#skill-candidates-and-selection)で確認します。

| スキル | 主な用途 |
| --- | --- |
| `agent-workflow-design` | 継続・反復する仕事の役割分担、待機、再開、終了の設計 |
| `prompt-design` | モデルへ渡す指示の設計・レビュー・改訂 |
| `agent-improve` | スキルやプラグインの比較評価と、証拠に基づく改善実験 |
| `plugin-creator-agent-plugins` | Agent Plugins形式の作成・検証・移行・パッケージ化 |

共通候補と個別の追加候補は、別のグループとして選びます。この区分は候補をどこで指定したかを表し、取得元リポジトリの公開・非公開の区分ではありません。追加候補にも公開スキルを指定できます。

配置の前に、用途、取得元、提案する版、利用要件、導入済みの状態、追加・更新・変更なし・競合・見送りを確認します。共通グループを承認しても、追加グループを承認したことにはなりません。有効な既存承認はその対象と範囲で引き継ぎ、実行時に必要な確認も守ります。

どちらのグループも見送れます。「追加なし」だけで既存スキルを更新・削除することはありません。同じ候補を二重に配置せず、同名で取得元や版が異なる場合は、影響する対象の競合を先に解決します。依存スキルや外部ランタイムが必要な場合も、選択していないものを自動で追加しません。

採用後の`INDEX.md`は、用途と読込先を示します。`skills-manifest.json`は、採用した版と内容の照合に使います。候補一覧や承認待ちの履歴を、そのまま採用済みの在庫として記録しないための分担です。

## 後から変更するとき

### 個別設定を後から渡す

個別ファイルを添付し、適用したいことを明示します。対象の個別設定を既存の内容と比較し、共通設定や採用済みスキル、関係のない編集は保ちます。共通設定を初めからやり直す必要はありません。追加候補が含まれていても、スキルの追加・更新は選択と承認を経て進めます。

### 新しい版へ更新する

変更したい対象と、取得元や版の希望を伝えます。新規取得や上流更新では、指定コミット、または取得時に確定したブランチのHEADを使います。同じ取得元の選択スキルは、その確定した版をそろえて扱います。ローカルで編集したソースを採用する依頼では、その指定内容と差分を確認します。

手順の説明や候補一覧だけを編集しても、管理スキルの版や内容が変わったことにはなりません。ソース、管理コピー、INDEX、manifestのうち何が変わったかを確認して反映します。

### 中断した作業を再開する

使っていた手順と、採用・変更途中の版が分かる記録を残しておきます。再開時は実際の配置状態を確認し、記録した版で未完了の作業を続けます。途中で上流が更新されていても、再試行を理由に最新版へ切り替えません。前の操作が成功したか不明なときも、その結果を調べてから進めます。

### 同じ版を再現する

採用済みmanifestと、固定コミットの取得元が必要です。意図して変更したスキルには、その変更を再適用できる差分やスキル一式の保存物も必要になります。ハッシュだけでは失われたファイルを復元できません。

再現では、記録した版から揃えた内容をファイルごとに照合します。最新の上流を取得するだけでは同じ版の再現になりません。必要な資料が欠ける場合は、未確認の状態を完了とせず、不足を確認します。詳細は[管理記録と再現の定義](../../dot/dot-setup.md#5-manifest-format-and-verification)を参照してください。

### バージョン表示の読み分け

| 表示 | 何を特定するか |
| --- | --- |
| plugin.jsonの`version` | プラグインの版。初期版は`0.1.0` |
| リポジトリのコミット | READMEや手順を含むソースの改訂。試行中は同じplugin版でも内容が変わり得る |
| 手順に記載した共通指示の固定コミット | 初期設定で採用する共通指示の取得元の版 |
| スキルmanifestの`resolved_commit` | 各取得元から採用したスキルの版 |
| スキルmanifestの`schema_version` | 管理記録の形式。現在の手順は形式4であり、スキルやプラグインの版ではない |

プラグインのmanifestと、クラウドのスキルmanifestは別のファイルです。ZIP名の`0.1.0`だけで細かな改訂を区別せず、配布時に対応するコミットやハッシュを確認します。

## 配置と管理記録で確かめること

採用するスキルは、`SKILL.md`だけでなく、必要な参照、スクリプト、素材を含むディレクトリ単位で扱います。取得範囲を確認し、利用条件、依存物、同名スキルとの競合を調べます。配置で足りない外部依存物が分かった場合は、その対応を確認してから依存する作業を進めます。

コピー後は、採用するソースの内容と管理コピーを比較します。ファイル数だけが同じでも、内容が揃ったとは限りません。更新途中の内容と古い記録を混在させたまま、通常利用を再開しないための確認です。

### 一覧と採用記録の違い

- `INDEX.md`は、採用スキルの名前、用途、`SKILL.md`の読込先、管理記録への参照を持ちます。共通指示と構築手順も明示します。
- `skills-manifest.json`は、取得元と固定コミット、採用したスキル、各ファイルのサイズ・ハッシュ、照合結果を記録します。
- 未決定の候補、グループごとの選択・承認、途中の作業は、現在の採用在庫と混ぜずに扱います。

初期状態でスキルがなく、配置するものも選んでいない場合は、確認した空の採用在庫を記録できます。これは候補をすべて却下したという意味ではありません。既存スキルがある環境で「追加なし」を選んだ場合は、その在庫を消しません。

### 比較の記録が証明する範囲

ファイルのハッシュは、信頼できる基準との内容差を調べるためのものです。公開者の真正性やコードの安全性、自動読み込み、実行の成功、永続性まで証明するものではありません。意図した変更がある場合は、上流との差分と、その変更を再適用する資料を組にします。

管理記録の形式4は、この構築手順の配置と照合方法のための定義です。Agent SkillsやAgent Pluginsの標準仕様ではありません。以前の形式から移る場合も、番号だけを書き換えず、既存の内容と参照先を確認します。未対応の形式や、固定コミットを検証できない取得物を、推測で同じ形式へ当てはめません。

全フィールド、パスの解決、ハッシュの計算、意図した変更の保存方法は、[手順の定義](../../dot/dot-setup.md#5-manifest-format-and-verification)を参照してください。この解説へ同じスキーマを複製せず、詳細を確認する場所を一つに保ちます。

## 完了を確認する観点

構築結果では、保存先だけでなく、次の状態を分けて確認します。

- 共通指示と添付手順を、確認した内容で保存し、読み直せたか
- 個別指示と追加候補が、提供済み・保留・不要のどの状態か
- 各グループのスキルについて、承認した追加・更新が反映され、変更しないものが保たれているか
- スキル一式の内容・参照と、INDEX・manifestが一致しているか
- プラグインの有効化、実際の読み込み、スクリプトの動作、保存内容の保持について、何を確認できたか

必要な入力や承認が残っていれば、完了した部分と再開に必要なものを示します。見送りや明示的に不要と決めたものを、未完了の作業として残す必要はありません。

構造検証やファイル照合の成功は、クライアントでの導入・自動選択・実行やクラウドの永続性の証拠にはなりません。dot-toolkitの読み込みを試すときは、対象となるメインのdot会話で確認し、通常のCodexタスクでのパッケージ検査と区別します。自動読み込みを確認できない場合は、共通指示を明示して読む方法と、その未確認点を報告します。

### 困った場合

- **必要なファイルがない、または読めない**：初期設定中の未作成と、既存ファイルの読取失敗を区別します。通常時の欠落から勝手に再構築せず、必要な入力やアクセスを確認します。
- **版や同名スキルが競合する**：ソース、管理コピー、有効な導入元を比較して、採用対象を決めます。どれかを黙って優先しません。
- **更新が反映されたか分からない**：変更したソース、管理コピー、記録、クライアントで利用される版を分けて確認します。pluginのversion表示だけで一致としません。
- **同じ状態を再現できない**：固定コミットや意図した変更の復元資料が揃っているかを確認します。資料がないまま期待ハッシュを現在の内容へ書き換えません。

このガイドの配置や判断方法は公開テンプレートの契約です。利用中の環境で何が検証済みかは、その構築・変更時の結果で確認してください。
