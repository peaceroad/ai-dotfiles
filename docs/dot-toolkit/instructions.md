# dotの共通指示と読み込みの解説

[dot/AGENTS.md](../../dot/AGENTS.md)は、メインのdot会話で継続して使う共通指示の公開テンプレートです。採用後は、dot自身のクラウドにある`/workspace/AGENTS.md`を正本として読みます。この文書では、その各部分が何を受け持ち、個別の使い方にどうつなげるかを説明します。

初期設定と更新の進め方は[構築・更新手順の解説](setup.md)、全体の入口は[dot-toolkitの使い方](README.md)を参照してください。この解説は共通指示の内容を理解するためのもので、別の実行用コピーを作るものではありません。

## 共通指示と個別指示の分担

共通指示には、資料の読み込み、応答の方針、クラウドの配置、既存の内容を保つ扱いなど、利用者に依存しないルールを置きます。個別指示には、利用者固有の条件や、特定の仕事で参照する基準を置きます。

この分担なら、公開する共通指示へ個別の事情を混ぜずに、同じローダーを使えます。タスク用スキルも別に管理するため、共通指示を変更するたびにすべてのスキルを作り直す必要はありません。

`dot-guidelines`は共通指示の全文を複製せず、正本の場所と初回の入口を示します。通常時の詳しい読み込み方は共通指示へ集約し、片方だけの修正で二つの指示が食い違う状態を避ける構成です。共通指示自体が読めない場合の扱いは、入口にも残しています。

## 通常の依頼で読むもの

[共通指示の読み込み部分](../../dot/AGENTS.md#load-relevant-guidance)は、次の流れを定めています。

1. ローダーから`/workspace/AGENTS.md`を全文読む。
2. `/workspace/.codex/AGENTS-private.md`を読み、今回に関係する個別指示と、条件に合う参照先を確認する。
3. `/workspace/.agents/skills/INDEX.md`の用途説明や、利用可能なdescriptionから、必要なタスク用スキルを選ぶ。
4. 選んだ`SKILL.md`と、その作業に必要な参照資料を全文読んでから、それに依存する仕事を進める。

この順序は、利用者の条件を踏まえて作業方法を選ぶためのものです。スキル一覧の要約は選択に使い、実行時の制約や手順まで要約だけで済ませません。一方、一覧にあるスキルの本文を、関係のない依頼で全部読む必要もありません。

### 個別指示は直接書ける

`AGENTS-private.md`には個別指示を直接書けます。別文書へ分けるなら、読む条件と参照先を示します。一つの文書に直接記載した指示と、条件付き参照を併用してもかまいません。

たとえば、「文章を校正するときに用語表を参照する」という条件なら、校正の依頼で必要な用語表を読みます。別の仕事でも毎回その資料を読み込む指定にはしません。これは条件の書き方の例であり、特定の個別文書を追加する依頼ではありません。

個別入力がまだ提供されていない場合は、適用不要と決めた場合と区別します。その指示に依存しない作業を続け、必要な依存関係が生じたときに不足を伝えます。無関係な依頼のたびに、回答済み・保留中の初期設定の質問を繰り返さないための扱いでもあります。

### 構築手順を読む条件

構築・更新・固定版の再現を依頼した場合は、採用した`dot-setup.md`と必要な個別入力を読みます。通常の仕事では、これらを一律に読むことはありません。

明示された初期設定だけは、クラウド内の共通指示を開始条件にせず、添付した手順から始めます。初回に作成するファイルを先に要求すると、設定を始められなくなるためです。初期設定後の通常会話でファイルが見つからない場合まで、この例外を広げません。

## 必要な指示を全文読む理由

[完全読み込みの指示](../../dot/AGENTS.md#complete-reading)は、資料の選択と、選んだ資料の内容取得を分けています。条件や例外が本文の後半にある場合、先頭の要約だけでは判断に必要な内容が揃いません。

長い文書は、出力の上限で途中までしか返らないことがあります。ファイルの大きさと返された範囲を確認し、必要なら区切って末尾まで読みます。複数の長い指示を一度に出して、結果全体の上限で後半が欠ける状態も避けます。

必要なのは、依存する判断の前に必要な全文を揃えることです。未取得の部分を推測で補ったり、検索結果の抜粋を全文として扱ったりしません。参照リンクは、その作業に必要な範囲でたどります。

読めない必須資料がある場合は、その資料に依存する部分を止めます。初期設定や修復の依頼がないのに、別の場所を探して代用品を採用したり、設定ファイルを新しく作ったりすることはありません。

## 応答の方針

[応答品質の指示](../../dot/AGENTS.md#response-quality)は、次を重視します。

- 最初に、答え、結果、または必要な次の行動を示す。
- 理解に必要な背景、根拠、注意点を含める。
- 明らかな内容を、末尾のまとめとして機械的に繰り返さない。
- 結論に影響する場合は、確認できた事実、推測、未確認点を分ける。
- 単純な説明は文章や箇条書きを使い、比較が読みやすくなる場合や利用者の指定がある場合に表を使う。

短い返答だけを求める指示ではありません。複雑な依頼や成果物では、必要な説明や整理を残します。推測と根拠が食い違う場合も、単に利用者へ同意せず、判断に影響する点を明らかにする方針です。こうした文面だけで、モデルの性能改善を測定したことにはなりません。

## クラウドの基本配置

次は、公開テンプレートが定めるdot自身のクラウド内の配置です。利用者のPCへ同じ絶対パスを作る指示ではありません。配置前に、その実行環境がこの構成を使えることと、必要な読み書きが認められていることを確認します。

```text
/workspace/
├── AGENTS.md                       共通指示の正本
├── .codex/
│   ├── AGENTS-private.md            個別指示・条件付き参照、または入力の状態
│   ├── dot-setup.md                 採用した構築・更新手順
│   └── dot-setup-private.md         追加スキル候補、または候補の状態
├── .agents/
│   └── skills/
│       ├── INDEX.md                 採用スキルの用途と読込先
│       ├── skills-manifest.json     採用した版・内容・照合結果
│       └── <skill-name>/            採用スキル一式
└── shared/
    ├── projects/<project-name>/    継続する作業とそのソース・成果物
    ├── downloads/                  取得資料と固定版のスナップショット
    ├── tools/                      利用者管理のツール・ランタイム
    └── outputs/<project-name>/     一時作業から残す確認済み成果物
```

`.codex/`には、個別指示から条件付きで参照する文書も、必要に応じて置きます。上のファイル名は公開手順の共通の入口であり、実際の個別文書名や内容を公開する例ではありません。

### ソースと日常利用するコピーを分ける

継続する仕事は`shared/projects/<project-name>/`へまとめ、リポジトリもその直下に置きます。取得して比較や再現に使う固定版は、用途に応じて`shared/downloads/`へ保持します。

日常利用するスキルは`.agents/skills/`の管理コピーです。承認した版のスキルディレクトリを、参照・スクリプト・素材ごと配置します。ソースを編集しても、管理コピーを自動で書き換えません。反映したい変更を比較し、採用する範囲を決めて更新します。

このリポジトリの`dot/`は公開テンプレートの編集・配布場所です。クラウドで採用したファイルとは役割が異なります。また、`home/`は利用者のホームから書き出した公開用コピーなので、dotの構築でそこへ設定を保存することもありません。

### 作業中のファイルと残す成果物

継続プロジェクトの下書き、素材、完成物は、そのプロジェクト内で管理できます。一時的な作業だけなら、その時点で割り当てられた作業ディレクトリ内に必要な作業フォルダを作り、後で使う成果物を確認してから適切な保持先へ移します。常に`outputs/`へ複製する必要はありません。

図のディレクトリを最初からすべて作る必要はありません。`shared`という名前だけで公開範囲や永続性が決まるわけでもありません。保存場所のアクセス範囲と保持条件は、実際の環境で確認します。不要になった作業の整理でも、必要な成果物の保持を確認し、一時領域全体を一括で削除する運用にはしません。

## 指示を調整するとき

共通指示を変更する場合は、クラウドで採用している正本と、変更したい内容を比較します。特定の作業だけの条件を、継続的な共通ルールに広げないことが重要です。利用者・プロジェクト固有の条件は、個別指示やその参照先で扱います。

公開テンプレートを直すこと、クラウドの正本へ反映すること、プラグインを更新することは、対象が異なります。どれを変更する依頼かを確認し、関係のない内容や既存の編集を保ちます。別環境向けのコピーが必要な場合も、正本から派生したことと内容の一致を確認し、複数の正本として独立に編集しません。

指示の読み込み方を変更するなら、通常の依頼、条件付き参照が不要な依頼、資料が不足する場合、初期設定の場合を分けて確認します。説明が短くなったことやファイルが揃ったことだけで、意図どおりに選択・実行されると判断しないためです。

## アクセス範囲と権限

このプラグインは、指示の読み込み方と利用者が管理する配置を定めます。ファイルへ操作方法を書いたり、プラグインを有効にしたりしても、使えるツールやアクセス権が増えるわけではありません。

- **dot自身のクラウド**：その作業に提供されたツールと、実際に認められたファイル・ネットワークの範囲で作業します。上の配置を利用できるかも、構築前に確認します。
- **利用者のPC**：クラウドとは別の作業先です。会話に使っている端末というだけで操作できるとは限りません。必要な接続・許可と利用可能な方法を確認します。
- **外部サービス**：接続しているアカウントと、そのサービスで認められた操作範囲を確認します。読み取れること、変更できること、第三者へ共有できることは、それぞれ確認します。

共通指示・個別指示・スキルは、その時点の依頼、指示の優先関係、サービスの制約、承認手順の範囲で使います。ファイルへの記載を、外部への送信、プログラムの実行、インストール、自動化の開始、権限設定の変更の一括承認にはしません。

必要な操作が認められない場合は、影響する作業と必要な対応を説明します。拒否された操作を、別の保存場所、リンク、権限変更などで回避しません。原因を確認できない失敗を、恒久的な機能制限と断定することも避けます。

個別文書、採用したスキルの在庫、取得・復元の記録には非公開情報が含まれ得ます。公開リポジトリやPRへ持ち込まず、共有が必要なときは対象と相手を確認します。公開用の説明には、一般化した配置と手順を使います。

## 共通指示の確認と限界

確認では、どの正本を読み、どの個別条件とスキルを選び、その判断に必要な内容を取得できたかを見ます。要約にスキル名が載ること、ファイルが存在すること、実際の依頼でその指示が使われることを区別します。

共通指示は、現在の依頼、適用される指示の優先関係、安全上の制約、アプリの承認手順の下で使います。同じ優先度・範囲なら利用者の後の明示的な指示に従いますが、ファイル内の記述でアクセス権や上位の制約を変更することはできません。アプリ側の権限や接続設定を、過去の文書から復元する扱いにもしません。

動作を確認する場所は、この指示が対象とするメインのdot会話です。通常のCodexタスクでのソース確認やパッケージ検査は、別の検証として扱います。初期設定や変更後に確認する項目は、[構築結果の確認](setup.md#完了を確認する観点)を参照してください。
