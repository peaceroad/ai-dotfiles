# agent-plugin-toolsのAstra向け改訂と再監査

レビュー日：2026年9月6日。改訂前の基準はコミット`a00affea7efec3902e4d78dd79d20b7ce07a9d29`です。改訂版はプラグイン`0.4.0`、含まれる`plugin-creator-agent-plugins`スキルは`0.6.0`です。使い方とセットアップは[プラグインのREADME](../../plugins/agent-plugin-tools/README.md)を参照してください。

## 設計の根拠と変更

このリポジトリの`prompt-design`と`agent-workflow-design`、組み込みの`skill-creator`を使い、依頼された成果まで進めること、必要な参照と検証を選べること、失敗後に状態を照合して再開できることを見直しました。

[Astra公式ガイド](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra)は、確認質問による停止、指示ファイルへの感度、必要以上の検証などの傾向を挙げています。これらは指示を点検する観点であり、このプラグインに実運用上の不具合があったことを証明するものではありません。

パッケージの契約は[Agent Plugins 1.0.0仕様](https://agent-plugins.org/specification)と[Agent Skills仕様](https://agentskills.io/specification)に従います。Astraへの対応でpackage形式やクライアント設定は変更していません。[Codexのプラグイン資料](https://learn.chatgpt.com/docs/build-plugins)とローカルの`codex-cli 0.153.4`のヘルプも確認しました。

| 対象 | 採用した変更 |
| --- | --- |
| 入口と権限 | 依頼された成果を決めてから参照を選ぶ。既存の許可を引き継ぎ、CLIが選択を要求するだけで利用者へ聞き直さない |
| 検証 | 変更箇所と確認したい性質で検査を選ぶ。必要なリポジトリ検査は維持し、文章の変更に無関係なクライアント検査を追加しない |
| Codex導入 | ソースへの直接リンク、開発元からの導入、組み立て済みMarketplaceからの導入を区別する。version方針がなく変更も求められていなければ`--keep-version`を使う |
| 復旧 | 導入や組み立ての失敗後に、一部の変更が残る可能性を説明する。書き込みの直列化は呼び出し側や管理層が担う |
| portable形式への移行 | 必要なクライアント固有機能を対応表で確認し、必要なら別の派生パッケージで維持する。ソースだけの変換に実導入を必須としない |
| Marketplace | 非公開の設定や複数担当者の調整を、必要時だけ読む専用参照へ分離する |
| 内包する指示の設計 | OpenAI／Codex向けで対象が決まっていなければAstraを既定とする。モデルに依存しないパッケージ作業にはモデル資料の読み込みを要求しない |

スクリプト、生成テンプレート、設定schemaの動作は変更していません。managerは有効状態やコンポーネントの実行を検査せず、名前とversionの一致だけではファイル全体の同一性を証明できないという制限も残しています。

## 初回改訂の検証

リポジトリ内の両プラグインの構造検証、対象スキルの`quick_validate.py`、ローカルのMarkdownリンクと参照先の見出し、`git diff --check`を確認しました。

既存ヘルパーのテストは計57件です。初回の一括実行では、到達した53件中50件が成功し、3件の子プロセスが失敗しました。1件には`VirtualAlloc failed`が含まれ、残る2件はWindowsの終了状態`3221226505`でした。失敗した3件だけを並列数1で再実行すると、すべて成功しました。一括実行の停止で未到達だった組み込み指示チェッカーの4件も、別途成功しました。したがって、57件を確認できていますが、最初の`npm run check:plugin-tools`自体は終了コード1であり、一度の実行ですべて成功した結果ではありません。

基準版と初回改訂版には、それぞれ独立したCodexサブエージェントを割り当て、同じ7件の依頼と前提を渡しました。対象はソース修正、指摘のみのレビュー、versionを維持する導入、中断した導入、利用者側の導入、範囲を限定した共有、最小ソースの新規作成です。各担当には他方の版や提案した修正内容を渡していません。モデル設定は親から継承し、実効モデル・reasoning effortの独立した計測はしていません。

両版とも7件すべてで判断基準を満たし、質問はしませんでした。初回改訂版は、導入が全体として取り消せる処理ではないこと、managerが検査しない項目、指示の設計対象と実行互換性の違いを明示しましたが、基準版も必要な判断に到達しています。

これは各ケースの操作を実行せず、行う操作・質問・完了条件を回答する机上試行です。各版1回答ずつであり、成功率・効率・信頼性の改善は立証していません。基準版の曖昧さを、Codex側の共通指示やモデルの知識が補った可能性もあります。

## 使いやすさと冗長さの再監査

利用者からの追加依頼を受け、独立した担当が入口と7参照を通読し、managerとscaffoldの前提条件を実装で照合しました。先の評価結果は渡していません。

具体的な欠落は、新しい開発元を導入する際のMarketplace項目です。managerとscaffoldは既存の項目を必要とする一方、その項目を作る説明がありませんでした。共有用のassemblerは派生コピーを生成するため、この前提を満たす経路とは異なります。初回の7ケースには「新規ソース作成から導入まで」を組み合わせた依頼がなく、そこでの成功はこの経路の完全性を示していませんでした。

integration参照に、カタログの場所、最小のlocal entry、相対パスの基準、既存項目の保持を追加し、scaffoldからも案内しました。例は[Codexのカタログ資料](https://learn.chatgpt.com/docs/enterprise/plugin-management)と付属managerの照合条件に基づきます。ワークスペースの管理・公開手順をローカル開発の必須工程にはしていません。

重複する完了報告と検証結果の説明を、入口、validation、integration、migrationの役割に合わせて整理しました。設計スキルが担当する一般的な助言は減らし、Astraの設計既定値は残しました。生成ファイルの更新条件はテンプレート変更の取り込み時とし、保留中のチェック定義の追加と`import`時の実行も区別しました。書き込みできない場合の復旧説明は、通常の設定・実行手順の後へ移しました。

ソースだけで完了できる条件、snapshotの識別情報とファイルの同一性の違い、新しいタスクでの発見、必要なクライアント固有機能の保持、一部だけ反映された状態からの復旧は残しています。リポジトリ、クライアント、共有Marketplaceは異なる書き込み先なので、直列化の説明も対象ごとに維持しました。

初回固定版と比べ、入口は5,942 bytesから5,192 bytesへ12.6%、入口と7参照の合計は60,558 bytesから58,253 bytesへ3.8%減りました。integration参照は欠落した前提を補うために増えています。これはUTF-8の文章量であり、トークン数・時間・品質の改善率ではありません。

隔離した一時リポジトリで、次の5件を実際のヘルパーで確認しました。

1. カタログがない場合は、scaffoldを作る前に拒否する。
2. 文書の最小JSONを置くと、新規scaffoldを作成できる。
3. `prepare`は保留中の設定だけを作成する。
4. チェック定義を追加した設定の`import`は、生成したランナーでそのチェックを実行する。
5. `refresh --check`はテンプレートを比較し、リポジトリのチェックは再実行しない。

ソースのversionとカタログは保持され、Codex固有manifestも生成されませんでした。プラグイン・スキルの構造検証と、8指示ファイル内のローカルリンク・見出し30件も成功しました。修正後の独立レビューでは、この範囲で追加修正を要する具体的な問題は見つかっていません。

[再監査の記録](../../evals/agent-plugin-tools/plugin-creator-agent-plugins/usability-review.json)には対象指示のハッシュと確認範囲を、[ヘルパーの実行記録](../../evals/agent-plugin-tools/plugin-creator-agent-plugins/evidence/usability-smoke-results.json)には5件の結果を保存しています。初回の比較記録は変更しておらず、そこにある評価は初回固定版だけに適用されます。

## 公開前の情報確認と文書整備

今回追加・変更したプラグイン、評価記録、関連文書を対象に、認証情報、個人用パス、端末名、連絡先、非公開の接続先を確認しました。JSONに保存した指示本文や実行ログも、文字列として復元して検査しています。`export.js`の既存の認証情報検出パターンを読み取り専用で再利用し、検査の除外や無効化はしていません。

ヘルパー出力に残っていたホーム相対の一時ディレクトリ2か所を`<fixture-root>`へ統一しました。コマンド、終了状態、検証結果、パッケージ内の相対パスは保持し、実行記録のハッシュも更新しました。認証情報や実際のユーザープロファイルの絶対パスは見つかっていません。

プラグインmanifestと、その初回スナップショットには既存の作者名と公開GitHub URLが含まれます。これは改訂前からある作者情報と一致しており、公開用メタデータとして維持しています。例示のパスや共有名、評価用の仮名、コミットID、SHA-256も残しています。

文書は現在の配置・言語規約に合わせました。利用手順はプラグイン直下の英語READMEにまとめ、この評価記録と既存ノートは日本語で説明します。関連ノートでは、古いスキル版、参照の分担、導入ヘルパーの照合範囲、再試行前の状態確認を更新しました。

最後に、据え置きだった`plugin.json`の概要と`agents/openai.yaml`の表示名・短い説明・起動時プロンプトを更新しました。portable pluginの開発・移行・ローカル導入と、プラグインや単体SkillのMarketplace組み立てを区別し、起動時も依頼された成果に合う手順と検証を選ぶ説明にしています。これは先の評価後に行ったメタデータの調整です。過去のスナップショットと評価結果は維持し、今回の改訂版`0.4.0`／スキル`0.6.0`へ含めています。
