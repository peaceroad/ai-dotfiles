## 数値設定を提案する範囲の調整

9月6日、`agent-workflow-design`からの引き継ぎを受け、数値制約の適用条件を確認しました。従来の「数値を作らない」という共通ルールと、数値の出所を利用者・ツール契約・ランタイムに限るチェック項目は、初期設定の選択を依頼された場合の提案まで抑える読み方ができました。これは指示の適用範囲に関する静的な指摘であり、実際に提案を拒否した動作が観測されたという意味ではありません。

共通ルールは、既存の制約と目安の強さを保ち、設定値の選択が依頼に含まれる場合は、適用される制約の範囲で、理由付きの変更可能な提案として示す形にしました。チェックリストも同じ条件にそろえています。Astraの並列処理とOpenAIのツール経路に関する参照では、数値を一律に禁じる表現を、実際のランタイム・ツールの上限を守る条件へ変更しました。

変更後の指示と参照を、次の境界に照らして読み直しました。

| 依頼や前提 | 指示が保つ判断 |
| --- | --- |
| 既存の指示の文言修正だけを依頼する | 再試行回数や予算を新しい要件として追加しない |
| 初期設定の選択も依頼する | 理由を添えて変更可能な値を提案し、既存の要件・実測値と区別する |
| 長さなどが目安として与えられる | 厳密な上限や独自の許容幅へ変えない |
| ランタイムに上限がある | 設定の提案でも上限を越えず、提案を設定変更の実施や許可と混同しない |

この確認は静的な条件照合です。新しい指示生成・下流実行・性能比較は行っていません。今回の10ファイルの版と4ファイルの復元用差分は[数値設定の調整manifest](../../evals/agent-design-tools/prompt-design/numeric-settings-review-manifest.json)に記録し、過去の評価対象のハッシュと応答は維持しています。

## 評価方法

公式資料との照合、静的レビュー、指示生成・レビュー、生成指示を使う下流試行、機械的な整合性確認を分けました。入力と判定条件を先に保存し、試行担当には依頼と必要な入力を渡しました。期待解と判定条件は渡さず、他担当の結果も参照しないよう求めています。

実行には、このGPT-6 AstraのCodexセッションから親の設定を継承した既存サブエージェントを使いました。担当の履歴を再利用し、1担当へ複数の依頼を渡しているため、会話履歴のない独立試行ではありません。Responses APIで設定を固定した反復、実効reasoning effort・トークン数の計測、人間による独立採点は行っていません。「条件を満たす」は、保存した入力と出力を主担当が照合した判断です。

R01・R04では指示を設計する担当が例題も処理し、D01・D02では生成指示を別の担当へ渡しました。R07では互換性の判断に必要な公式資料を取得しましたが、API接続、Gem設定、実際の長期調査やメール送信は実施していません。

結果は少数ケースの回帰確認として扱い、成功率、モデル間の順位、旧スキルに対する統計的な優位性へ換算しません。評価対象に合う入力と判定条件を設ける方針は、[OpenAIのEvaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)も参考にしています。

## GPT-6 Astraの公式指針との対応

[Astraのモデルガイド](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra#prompting-best-practices)が挙げる傾向は、用途ごとに調整の必要性を確かめるために使います。公式の例文をすべての指示へ追加する設計にはしていません。

| 公式が挙げる調整観点 | このスキルで採った設計 | 確認の範囲 |
| --- | --- | --- |
| 質問で期待した進行が止まる | 既存の許可を確認し、欠けた情報に依存しない作業を進める | R03は修正版まで返した。実際の承認フローは未試験 |
| skillsやAGENTS.mdの指示に敏感 | 実際に作用する指示と読み込み条件を追い、矛盾を定義元で解消する | 静的確認とR02の引用指示の扱い |
| 詳細な書式や定型表現に寄る | 必要な内容と表示形式を分け、求められた長さ・形式を保つ | R05・R06・R09は短い完成形。下流D02には反復が残った |
| 必要な委任が少ない | 委任の許可、独立して進められる仕事、調整コストを条件にする | R08で対象ランタイムの委任条件を保持 |
| 小さな変更でも検証が広がる | 影響範囲と完了条件に検証を対応させる | 静的確認。実プロジェクトのテスト選択は未試験 |

積極的な委任の例を、委任を制限するランタイムへそのまま持ち込むことはできません。利用者がスキルのガイドラインを上書きできる環境でも、system/developer指示を含む実際の優先関係を保つ必要があります。この境界を、スキル本文と[Astra向け参照](../../plugins/agent-design-tools/skills/prompt-design/references/openai-gpt-6-astra-prompt-design.md)で確認しました。

## OpenAI APIの互換性確認

APIの境界は、指示だけで解決できない実装条件を見分けるために参照します。2026年9月5日時点で、次を公式資料と照合しました。

| 項目 | 確認した条件と指示設計への影響 |
| --- | --- |
| 非同期ツールとPTC | `async: true`のfunction/customツールは直接呼び出し、PTCからは呼ばない。ジョブの実行と管理はアプリが担当する。[Async tool calling](https://developers.openai.com/api/docs/guides/async-tool-calling#compatibility) |
| API Multi-agentと非同期ツール | 非同期ツールとparallel tool callsを併用しない。他のランタイムの協調ツール全体へ一般化しない。[Async tool calling](https://developers.openai.com/api/docs/guides/async-tool-calling#compatibility) |
| 推論量の途中変更 | `configuration_update`はAstraのstandard・single-agent向け。自動compaction、自動truncation、単独の`/responses/compact`とは併用できない。明示的な`compaction_trigger`の後には新しい更新が必要。[Reasoning](https://developers.openai.com/api/docs/guides/reasoning#change-reasoning-mid-conversation) |
| API Multi-agentの状態管理 | 自動compactionは暗黙に有効。単独の`/responses/compact`は非対応。R07の代替案は主担当がこの条件も照合した。[Multi-agent](https://developers.openai.com/api/docs/guides/responses-multi-agent) |
| 実行中の追加指示 | steeringの受付と適用を分け、開始済みツールの取消や完了済み操作の巻き戻しとは扱わない。[Mid-turn steering](https://developers.openai.com/api/docs/guides/steering) |
| ランタイムによる停止 | `misalignment_policy_violation`で停止された処理を自動再試行しない。先行する操作は巻き戻らない。[Misalignment monitoring](https://developers.openai.com/api/docs/guides/safety-checks/misalignment-monitoring) |

移行条件は[モデルガイド](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra#update-api-and-model-parameters)と[モデルページ](https://developers.openai.com/api/docs/models/gpt-6-astra)も照合しました。APIと製品側のreasoning設定を分け、対応する実効設定は保持し、`none`や`minimal`からは`low`を比較の起点とします。GPT-5.5以前からの移行に関するキャッシュ変更を、GPT-5.6からAstraへの新しい必須変更とは説明していません。

## 冗長さと保守性のレビュー

冗長さと進行への影響は、スキル本体、Astra参照、[APIランタイム参照](../../plugins/agent-design-tools/skills/prompt-design/references/openai-tools-and-runtime.md)、[詳細チェックリスト](../../plugins/agent-design-tools/skills/prompt-design/references/prompt-review-checklist.md)を静的に確認しました。新しい動作試行は行っていません。

| 似た記述がある箇所 | 役割の違いと判断 |
| --- | --- |
| 作業手順と設計原則 | 手順は判断する順番、原則は各判断で守る条件を示す。修正の要否と要件保持を省かず残す |
| 共通本文とAstra参照 | 本文は対象・範囲・指示の配置、参照は観測した行動の調整を扱う。公式例を常時適用しない条件を残す |
| 行動の助言とAPI参照 | 待機・許可・継続の考え方と、API固有の互換性・状態管理を区別する。単なる文言修正ではAPI参照を読まない |
| 原則と詳細チェックリスト | チェックリストは広い診断で使う問いであり、全項目の実施を求めない。読み込みの効率は別途確認が必要 |
| 指示の完成形と編集結果の報告 | チャットで返す指示とファイル編集の報告を分ける。例示書式は任意で、生成先の成果物には強制しない |

この範囲では、意味を保ったまま削るべき重複や、義務・例外の強さを変えるべき具体的な欠陥は見つかりませんでした。最小の分量であることまでは立証していません。評価ノートでは、同じ結果や留保の反復を整理し、設計能力の評価を本書、要約試験の詳細を別紙へ分けました。
