# エージェントの評価と改善を支援するプラグインの計画

この計画は、評価実験を使ってスキルやエージェントの反復処理を改善し、さらに改善を生む能力そのものを高めるハーネスを目指すものです。`agent-eval-tools` を、このリポジトリの要求から独自に設計・実装する新しいプラグインとして作ります。中心となるのは、評価から仮説を立て、変更案を実行・比較し、その結果で次の実験を選ぶ反復です。まず一つのスキルを比較できる基盤を作り、予算内での改善探索、改善用スキル自身の比較と次世代への反映へ進みます。実務の証拠は、目標や評価課題を現実の用途に結び付けるために使います。

改善対象は、扱う専門分野を問わないエージェントスキルとエージェントプラグインです。対象側の目的、知識、要件、ツールに応じて評価方法を選び、複数の構成要素を持つ場合は連携も含めて確認します。文中の分野や課題の例は適用範囲を限定しません。共通化する改善手順と、対象固有の正しさを確かめる方法、実行環境が観測できる範囲を区別します。

本書は、2026年10月3日までに確認した公開研究と既存の構成を踏まえて、責務、検証順序、採用条件を定めた計画です。10月5日の研究および OpenAI、Google、Anthropic の公式資料との追加照合は、[評価方法の見直し](../agent-eval-tools/measurement-review.md)に記録しました。実装を開始し、プラグインとテキスト応答を比較する実行部分を追加しました。ホストのサブエージェントによる小さな実モデル比較を通しましたが、段階 0 の実行条件の確認全体は完了していません。性能上の最適性や RSI の成立を認定するものではなく、実行能力と結果に応じて計画を更新します。

研究の要点、判断理由、まだ実験で確かめる必要がある問いは、[ハーネスの RSI に関する研究ノート](../notes/agent-rsi-research.md)に残します。[作る理由と使う場面](../notes/agent-eval-tools-use-cases.md)は、利用者から見た価値と運用のノートです。この計画は、採用した設計、実装順序、完了条件を扱います。各節には未実装の設計要件も含みます。現行の対応範囲と確認状況は、次の二節にまとめます。

## 現在の実装範囲

[agent-eval-tools](../../plugins/agent-eval-tools/README.md) に、`agent-improve`、参照文書、Node.js 標準モジュールによる実行部分を追加しました。現在の範囲は、明示的に渡したテキスト束の比較、採点器の校正、予算内の候補生成、改善方法の比較、記録の再利用、競合を検査したソースへの反映と復旧です。通常実行では改善方法を固定し、意味のある観察を記録しても自身の更新は始めません。

会話内では、既存のサブエージェント機能を使う経路を優先します。親エージェントが新しい文脈の試行を担当させ、スクリプトが条件の固定、呼び出しの予約、応答と実行 ID の対応、採点と記録を担当します。利用者が手元の認証済みターミナルから進めるために、`codex exec` を使う経路も残します。どちらも同じ比較・改善処理を使い、CLI の認証をホスト経由の評価の前提にはしません。

長い試行入力は、親が転記せず、固定した入力ファイルとハッシュを子へ渡します。子は必要に応じて分割して全文を確認し、実行用の指示と出力形式だけを受け取ります。呼び出し ID、採点基準、ほかの試行結果は入力から分けます。これは内容を変えずに届けるための仕組みであり、ファイルへのアクセスを保護する隔離ではありません。ホスト側の受け渡しと待機も所要時間に含め、モデル処理だけの費用と取り違えないようにします。

候補生成の担当へ渡す参照は、役割に必要な範囲を実験設定で選べます。実行管理を含む方法全体は固定したまま、実際に渡したファイルと内容のハッシュも残します。候補自身に参照の除外を決めさせず、親が読む実行手順を省いたことで実験条件が不明にならないようにします。応答の受領と同じ実験の再開を一つのコマンドで進められ、結果の受信が不確かな場合も既存の記録を確認して重複を避けます。

[合成ケース](../../evals/agent-eval-tools/agent-improve/README.md)と自動テストでは、失敗や未完了を成功として扱わないこと、共有予算を使うこと、自己適用した候補を比較して次の実行へ渡すことを検査します。合成応答で経路が通ることと、実モデルで改善能力が高まることは区別します。

個々の比較経路を動かせることと、段階ごとの完了条件を満たすことは区別します。初版の残作業は次節で管理し、実装された機能だけを根拠に全計画を完了扱いにしません。付属ランナーは、自然なスキル選択、ツールを伴う実行、途中イベント、保護された評価集合、生成した補助コードの実行には未対応です。これらの観測が必要なら、対象プロジェクトの検証済みハーネスを使います。自動採用は品質の改善に限定し、同等品質での費用削減は追加の検証対象です。比較採点には、任意の両順序採点、同一成果物の再採点、グループ単位の限定した統計判定を追加しました。その仮定と限界は[実行部分の参照文書](../../plugins/agent-eval-tools/skills/agent-improve/references/runtime.md)、変更理由は[評価方法の見直し](../agent-eval-tools/measurement-review.md)に記載します。

## 完了状況と初版の残作業

計画全体は未完了です。最初の到達点は段階 0〜2 であり、限定した比較基盤を試用できることを、その到達点の完了とは扱いません。ここでは実装範囲と未完了条件を管理し、私的な実行記録、環境情報、測定値は掲載しません。

- **比較・記録の基盤は実装済み。** テキスト束の固定、校正、候補生成、比較、採否、予算、再開、系譜、ソース反映・復旧、ホストと任意の CLI 経路を持ちます。自動テスト、公開可能な合成課題、既存の回帰課題もあります。配布物の検査や合成応答による成功を、実際の利用・自己改善の証明とはしません。
- **段階 0 は実行能力ごとの確認を区別する。** 明示したテキストを渡す経路を基準とし、実行 ID、対象の版、終了と未完了、親による停止と受領、費用の観測範囲を確認します。一方のアダプターの確認を他方へ流用せず、保護された評価や生成コードなど未対応の能力は有効にしません。
- **段階 1 は、併用を確かめる範囲を分けて進める。** カタログを明示した通常修正・改善設計の比較と、複数条件の移行課題を[検証用素材](../../evals/agent-eval-tools/agent-improve/README.md)に追加しました。追加確認では、設計支援を明示した候補作成から比較・採否へ引き継ぎました。自然な発見と読み取りイベントの独立した確認は未完了です。明示した引き継ぎの成功で、導入先での選択も確認したことにはしません。
- **段階 2 は、限定した自己候補比較と後続実行を確認済み。** [公開前確認](../agent-eval-tools/prepublication-review.md#自身の候補を比較した追加確認)では、H0 が自身の参照への追加候補 H1 を作り、同じ開始状態と予算の改善課題で比較しました。追加の効果は示されず H0 を維持し、同じ版を別の改善課題へ渡して下流の結果まで確認しました。親が能力目標、変更範囲、課題を指定しており、保存した観察から自律的に課題を選ぶ条件は未確認です。既知の合成課題による経路確認を、改善能力の向上や段階 0〜2 全体の完了には置き換えません。候補生成・比較を毎回強制する条件も加えません。
- **段階 3・4 は後続段階。** 固定した改善方法との対照、世代をまたぐ効果、イベントやツールを伴う実行の評価は、初版の基盤だけで完了したことにしません。

初版の完了へ向けて、次の順に進めます。

各段階では、要求、実装または外部ハーネスによる実行経路、対応する試験、そこから主張できる範囲を照合します。合成応答による制御の検査で、採点器の妥当性や対象品質の改善を代用しません。プログラミング、ルール適用、設計、文章では必要な成果物と観測が異なるため、編集用途や二値のテキスト採点を共通の前提にしません。

1. **既存スキルとの統合条件を確認する。** 第1節と第10節の条件を、既存スキルだけの構成と新スキルを加えた構成で比べます。明示した対象の評価、カタログからの選択、設計支援、比較の実行への引き継ぎを区別します。公開した併用課題は凍結したカタログと参照を使う補助試験です。現行ランナーだけでは自然な発見を測れないため、導入先で選択と読み込みを観測できる方法を確保してから、その確認へ進みます。
2. **課題の感度を確かめ、自己適用を通す。** 段階 0 の[課題整備](#直近の課題整備と比較の進め方)に従って用途上必要な課題を選び、段階 1・2 の残りを進めます。複数条件の移行課題では、新能力と既存動作の保持を別ケースで採点し、入口と参照の整合も扱います。一課題の成功を方法の上限全体とはみなさず、同時に、すでに解ける課題だけで方法の品質向上を測りません。既存の設計方法を支援として使う場合は、その指示と参照の版、実際に渡した範囲も固定します。未実装の候補操作を、方法の文章だけで実行できたことにしません。
3. **後から検証できる証拠と運用境界を整える。** 有効な版を次の実行で識別できること、根拠を再参照できること、失敗や未完了を追えることを確認します。長期に利用する証拠には、許可された保存場所と保持範囲を定めます。要点メモや一時領域へのリンクだけで、生記録を永続保存したとは扱いません。インストール・有効化・公開は別の操作として扱います。

費用だけの改善の採用、採点器や課題生成・試行配分を候補側から変えて実行する経路、保護された最終評価、モデル更新後の再比較には、それぞれ追加の実装や検証が必要です。すべてを初版の必須機能へ追加することはしませんが、課題を増やすだけで解消したことにもせず、必要な能力と未確認の保証を残します。既存用途での回帰を確認する前に、共有スキルの規則を RSI のために緩めません。

## 目指す RSI と設計上の結論

目指すのは、改善機構が自分の実行結果を使って自身を更新し、その更新が、次の未知の改善課題で有効な変更を生む能力へ戻る状態です。各比較では基盤モデルの重みを固定し、スキル、参照、診断・実験選択の方針、補助コード、再利用する知見を変更対象にします。本計画でいう RSI は、このハーネスの範囲での再帰的な自己改善です。

実行する改善機構は一つにします。通常の対象スキルと改善機構自身を、同じ「目標を定める、仮説を作る、変更案を実行・比較する、採用する、次の実験を選ぶ」という処理で扱います。自己改善のたびに上位の改善エージェントを追加しません。比較対象が改善機構なら、その版を使って別のスキルを改善させ、得られた成果を測ります。対象が何かによって評価課題が変わり、改善処理自体は共通です。

一つの改善機構であることは、一つのファイルや会話で全処理を行う意味ではありません。候補の生成、対象の実行、採点は、版と情報の流れを追跡できる形で分割します。また、実務へ採用する版と、次の候補を探すために使う実験上の版を区別します。採用しなかった候補からも、理由と予算を定めて別案を試せる構成にします。

たとえば、現在版で複数のスキルを改善してみると、失敗原因の見誤りが反復の費用を増やしていると分かったとします。現在版は、その証拠から自身の診断方法の変更案を作ります。その変更案と現在版に、同じ開始状態の未使用の改善課題を渡して比較します。変更案が有効なら、それを次の改善実行の現在版にします。次の実行では対象スキルも自身の方法も再び変更候補にし、その更新が次の有効な変更を生む能力に寄与するかを調べます。

分離するのは、変更を提案する権限と、その変更の成否を決める根拠です。各比較では、実行する改善機構の版、対象の開始状態、評価条件、予算を固定します。固定した外側の評価で確認してから、採用した版を新しい実行へ渡します。この評価上の分離は、別の改善システムを作ることを意味しません。

最初の到達点は、汎用評価基盤だけの完成ではなく、「現在版が自身の候補を作る → 同条件で比較する → 選ばれた版が次の改善を実行する」という経路を通すことです。その後、初期版の改善方法を固定した場合との比較で、自己更新が実際に役立つかを調べます。到達点と検証の順序は第9節に定めます。

## 1. 新しいプラグインにする理由

既存の `agent-design-tools` は、指示やワークフローの設計を支援しています。ここに評価の反復実行、結果保存、予算管理、採点器の保守を加えると、設計だけを使う利用者にも実行基盤の保守が及びます。そのため配布単位を分け、判断手順をスキルに、比較の再現に必要な処理を小さなスクリプトに置きます。

外部スキルのフォーク、文章の翻訳移植、ランナー雛形の取り込みは行いません。スキル本文、実験の記録形式、スクリプトは、この計画の要件と確認できた実行能力から作ります。独自実装であることを品質の根拠にはせず、実際の比較と利用試験で判断します。

対象が既に持つ採点器や実行コマンドには接続できるようにします。独立した実装にすることと、利用者の評価基盤を重複して作ることは別です。初版は一つの実行方法と必要最小限の採点に絞り、汎用評価フレームワーク、外部サービスへの依存、広範な互換性は先に持ち込みません。

### 参考資料と、この計画での位置付け

着想の出発点は、Anthropic の [Automating eval design and hillclimbing](https://claude.dev/blog/automating-eval-design-and-hillclimbing/) です。動く評価を作り、実行結果の診断から変更案を比較する方法を参考にします。具体的な比較材料は [build-eval](https://github.com/anthropics/skills/blob/main/skills/claude-api/shared/evals/build-eval.md)、[評価監査](https://github.com/anthropics/skills/blob/main/skills/claude-api/shared/evals/eval-audit.md)、[hillclimb](https://github.com/anthropics/skills/blob/main/skills/claude-api/shared/evals/eval-hillclimb.md) です。これらは設計の参考資料であり、配布物のソースや実行時の依存にはしません。

OpenAI の [Iterating development workflows with Codex](https://developers.openai.com/cookbook/examples/codex/iterating-development-workflows-with-codex) は、実際の作業を振り返り、知見の反映先を選び、新しい文脈で確かめる循環の参考です。本計画では、実務の証拠から改善対象を選ぶ入口と、比較後の知見を適切な所有者へ戻す出口を設けます。記事のファイル構成や工程ごとの承認は例示として扱い、このリポジトリの必須工程にはしません。

OpenAI の [Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra) は、モデルの能力に応じてスキルの入口、読み込み量、細かすぎる手順を見直す参考です。本計画では、不要な指示の削除も比較候補にし、新プラグイン自身の過剰な参照読み込みや途中停止も評価します。特定モデル向けの助言だけで全モデルへの有効性を決めず、対象モデルで確かめます。

これらを組み合わせた構成は本計画の設計判断であり、資料がこのプラグインや RSI の効果を実証しているわけではありません。参考資料と採用理由はこの文書に残し、配布時にはプラグインの README に短く案内します。通常の実行で参考記事の通読は要求しません。特定の公開ソースの挙動を比較根拠に使う際は、その版も特定します。

本計画では、Anthropic の評価に基づく反復探索を中核の方法として重視します。OpenAI の振り返りは改善課題と反映先の選択に、Astra 向けの助言は探索する変更案とスキルの使いやすさに活用します。実務の失敗報告を待つことや、手順を減らすことだけを目的にはしません。独自実装であることは、参考にした方法を弱める理由にはしません。

自己適用と検証の設計では、[STOP（COLM 2024）](https://arxiv.org/abs/2310.02304v3)と [Hyperagents](https://arxiv.org/abs/2603.19461v1) も参考にします。研究の要点と限界は[研究ノートの第2節](../notes/agent-rsi-research.md#2-自己改善の研究から押さえる点)にまとめます。本計画では、改善方法自体を変更対象にし、対象を改善する能力と、有効な後継を生む能力を確かめる構成を採ります。過去の候補を探索に使う余地も設けますが、論文の実装や探索方式全体は導入せず、結果が本プラグインへそのまま移るとも仮定しません。

同ノートでは、AIDE²、Meta-Agent Challenge、GEPA、ACE、および評価・課題生成を学習する研究も確認しています。そこから本計画へ反映するのは、強い初期版との比較、評価器自身を判定する外側の根拠、知見の再利用、モデル更新後の再検証です。個別方式の報告を RSI 全体の実証とは扱いません。新しい手法を増やすこと自体を目的にせず、第6節、第9節、第10節の比較で採否を決めます。

### 既存プラグインとの責任分担

このリポジトリには、既に評価と改善の判断方針があります。[agent-design-tools の README](../../plugins/agent-design-tools/README.md)、[改善と RSI の参照](../../plugins/agent-design-tools/skills/agent-workflow-design/references/agent-improvement-and-rsi.md)、[評価と状態管理の参照](../../plugins/agent-design-tools/skills/agent-workflow-design/references/state-evidence-and-recovery.md)を、原因診断、修正、証拠の扱いに活用します。新プラグインは、比較実行と改善の進行に、これらの設計能力を接続します。

- **`prompt-design`**：指示を変更する候補について、意味、適用条件、強さ、重複、対象モデルとの関係を整えます。不具合の修正と、能力目標に基づく再設計の両方で使えます。
- **`agent-workflow-design`**：原因を指示、参照導線、ツール契約、状態管理、評価などに切り分け、制御と改善の設計を担当します。
- **`agent-eval-tools`**：評価条件を具体化して実行し、変更案を比較できる証拠を返します。`agent-improve` は診断、変更、比較、採否の進行をまとめ、必要な設計能力を使います。
- **`agent-plugin-tools`**：配布物の構造検証、パッケージ作成、導入を担当します。これらの検証とスキルの行動評価は分けます。[既存の検証境界](../../plugins/agent-plugin-tools/skills/plugin-creator-agent-plugins/references/validation.md)
- **`ai-dotfiles-cli`**：既存の管理対象や導入経路を操作する場合に使います。評価の実行エンジンや必須依存にはしません。

既存の設計スキルを利用できる場合は、必要な変更箇所について使い、汎用的な設計手順一式を新プラグインへ複製しません。一方、単独配布でも評価を完了できるよう、結果の解釈、変更範囲、採用条件に関する最小限の契約は同梱します。判断方針の重複を避けることと、実行に必要な条件を外部プラグインに依存させないことを両立させます。

既存の [evals/README.md](../../evals/README.md)は、保存された評価入力・証拠と、自動実行できる基盤を区別しています。既存ケースと記録は再利用し、過去の manifest を新ランナーの結果に見せかけて更新しません。新ランナーで再実行した結果には、新しい実行記録を作ります。

### 既存の指示が探索を狭めないための統合条件

責任分担を文書に書くだけでは、併用時の振る舞いは保証できません。既存のスキルと参照には、実行証拠に基づく保守、局所的な修正、必要な確認を終えた後の停止を扱う記述があります。これらは通常の保守に有用ですが、適用範囲を広げすぎると、能力を伸ばす探索を不具合修正だけに限定したり、候補一件の確認で実験全体を終えたりするおそれがあります。現時点でその誤動作を実測したわけではなく、以下を設計上の統合条件として検証します。

既存スキルをそのまま使う構成を基準とし、まず新プラグイン側で実験の進行と記録の適用範囲を整えます。既存側の変更は導入の前提ではありません。具体的な指示の矛盾や併用時の問題を確認し、原因が既存側にある場合に限り、隔離した候補版で必要な適用条件を修正します。RSI を目指すこと自体を、通常の設計・修正を支える規則を緩める理由にはしません。

1. **実験の進行を引き継ぐ。** 評価の構築、比較、予算内の改善探索は `agent-improve` がまとめます。`prompt-design` は指示の変更、`agent-workflow-design` は制御や診断の設計に使い、実験の目的、残予算、採否を一から決め直しません。既存側から評価実行へ案内する場合も、進行中の実験があればそこへ結果を返し、相互呼び出しで新しい改善ループを増やしません。単発の修正や設計レビューは、既存スキルだけで完了できます。
2. **候補を試す条件と、採用する条件を分ける。** 不具合の修正では証拠から原因を診断します。能力目標に基づく探索では、未検証の仮説や複数箇所にまたがる再設計も、許可された範囲で候補にできます。[prompt-design](../../plugins/agent-design-tools/skills/prompt-design/SKILL.md) の条件付き修正に関する規則を、探索一般への禁止に広げません。[改善用参照](../../plugins/agent-design-tools/skills/agent-workflow-design/references/agent-improvement-and-rsi.md)の原因診断や変更範囲の助言も、用途に応じて適用します。採用には、どちらの場合も比較の証拠を求めます。
3. **保守メモと探索の記録を混同しない。** [Maintenance records](../../plugins/agent-design-tools/skills/agent-workflow-design/references/maintenance-records.md) は、未解決の保守判断や選択的な判断理由を扱います。実験の候補、系譜、失敗、比較結果は、新プラグインが所有する実験記録として保持し、保守メモの解決・棄却時の整理規則で削除しません。再検討する価値と保存範囲は実験の契約で定めます。実行中に変わる記録と、採用してスキル・参照へ反映する安定した知見も区別します。
4. **既存の方法も、必要なら改善対象にする。** 診断順序、参照の選択、候補生成、試行配分などは、既存の Reference に書かれているというだけで不変にしません。変更範囲に含めた正本を版管理し、変更案を比較できます。別プラグインを暗黙に編集せず、対象外なら依存先の制約として報告します。利用者の目的、実行権限、保護された評価、予算の強制は維持します。組み込みスキルやホスト側の指示など変更できない層も明示し、完全に自律した自己改変を実現したとは主張しません。
5. **読み込みと検証を用途にあわせる。** 必要な設計スキルと参照は、それぞれの適用条件に従って使います。既に読んだ内容や同じ版に対する検査結果を再利用し、各候補で作成手順や配布検査をすべて最初から行いません。候補を作るモデル、対象スキルを動かすモデル、採点に使うモデルを区別し、既存スキルの設計用の既定値で実験条件を変更しません。一件の確認が終わったことと、依頼された探索の終了を区別し、継続には第7節の仮説と予算を使います。

統合時に確認する箇所は、`agent-workflow-design/SKILL.md` と改善用参照の入口、`maintenance-records.md` の記録対象、両設計スキルと新スキルの呼び出し条件です。これは一括した書き換え対象ではなく、問題が見つかったときに原因を特定する範囲です。既存の独立した利用を保ち、公開スキルから新プラグインへの必須依存を作りません。導線を変更した場合は、`agent-design-tools/README.md` と[役割分担のノート](../notes/skill-creator-prompt-design-agent-workflow-design.md)にも実装した境界を反映します。パッケージ側は、[既存の検証方針](../../plugins/agent-plugin-tools/skills/plugin-creator-agent-plugins/references/validation.md)が既に作成・配布・導入の確認を区別しているため、その境界を利用します。

矛盾が見つかったときは、実際の指示の優先関係に従い、権限のある正本に対する修正候補を比較し、有効なものを反映します。新プラグインへ強い指示を追加するだけで、既存側の規則を打ち消す構成にはしません。既存の一般用途の品質を維持することを採用条件とし、確認できなければ既存版を保ち、接続方法を見直します。この統合確認と必要になった修正を初版の実装範囲に含め、併用時の確認は第10節で行います。

## 2. 利用者ができるようになること

初版の公開スキルは **`agent-improve`** 一つにします。利用者は「このスキルを評価して」「この変更を比較して」「このスキルを予算内で改善して」「改善方法自体を良くして」と依頼できます。入口は、対象と、設計・評価・比較・改善のどこまで求められたかを判断し、必要な参照と処理だけを使います。評価が未整備なら同じ依頼の中で整えます。

入口を一つにする理由は、評価設計、診断、変更、再評価が一つの実験の中で行き来し、その状態を引き継ぐためです。自己改善も対象の指定として扱えます。処理と参照は分割できますが、利用者やエージェントに評価用・改善用・自己改善用の入口を選び直させません。

評価の依頼だけで対象スキルを書き換えません。一方、改善まで依頼されている場合は、ケース作成や各反復のたびに同じ承認を取り直さず、許可された範囲で進めます。実行費用や変更対象に必要な条件が未確定なら、その点だけ確認します。変更権限の違いは、別スキルへの分割ではなく、その実験の依頼内容と設定で扱います。

通常のバグ修正や文章の修正すべてに、このプラグインを起動させることは避けます。反復利用する指示の品質、変更前後の比較、複数ケースでの振る舞いが問題になったときに使います。利用者が実行形式、評価器、保存ファイルを一から指定しなくても、既存資産と依頼から最小の実験を組めるようにします。

実行まで依頼された評価は、ケース、実行方法、採点方法をつなぎ、実測と結果の検査まで進めます。実行できない場合は理由と未検証の範囲を示します。設計だけを依頼された場合はその範囲で終えます。比較・改善の依頼では、次のいずれかを返します。

- 変更案を採用できる根拠と、変更内容。
- 変更案を棄却する根拠と、維持する現行版。
- 差を判断するには証拠が不足している理由と、判断を変えうる追加検証。
- 評価そのものに問題があり、比較を始める前に直すべき箇所。

改善が見つからないことを失敗扱いにしません。スコアが上がるまで変更を続けることも、スキルを書き換えたこと自体を成果とすることも避けます。

### 通常運用と自己改善のタイミング

通常の評価・改善では、使う `agent-improve` とその支援用スキル・知見の版を固定し、依頼された対象を扱います。その結果から後の自己改善に必要な証拠と気付きを残しますが、評価スキル自身の変更や比較は毎回の必須工程にしません。記録のためだけの追加モデル呼び出しや、全履歴を読む振り返りも既定にしません。

評価スキル自身の改善は、その目的、変更範囲、予算を定めた実行として行います。利用者が依頼したとき、または別途許可した開始条件を満たしたときに、蓄積した記録から関係する材料を選び、候補を作って比較します。一度許可された範囲内では各反復の承認を取り直しません。改善の仕組みは一つのまま、通常の対象を改善する実行と、自身を改善する実行のタイミング・予算を分けます。

## 3. 何を評価したのかを区別する

評価対象は、次の四つに分けます。同じスキルに対して複数の評価を持てますが、異なる対象の点数を一つの「スキル品質」にまとめません。

1. **呼び出しの適切さ**：必要な依頼でスキルが選ばれるか、不要な依頼で選ばれないかを調べます。スキルを強制指定した実行では、この能力を評価できません。
2. **スキルを使った作業の結果**：スキルを読み込ませ、実際の成果物、変更差分、検査結果を評価します。文章がもっともらしいかだけでなく、依頼が達成されたかを見ます。
3. **生成した指示の下流での効果**：プロンプト設計スキルなどが生成した指示を別の実行で使い、その結果を評価します。生成された指示のレビューと、その指示で動くエージェントの評価を区別します。
4. **実行中のワークフロー**：待機、途中指示、部分完了、中断、復旧、外部操作の結果不明などの状況で、必要な処理が続き、不要な処理が止まるかを評価します。

たとえば「中断できるワークフローを設計できた」と「実行中の中断を正しく処理できた」は別の証拠です。さらに、エージェントのターンを中断できても、既に送った外部操作まで取り消せるとは限りません。評価報告には、設計のレビュー、模擬環境での実行、実サービスでの確認のどれを行ったかを明記します。

既存の [agent-workflow-design のケース](../../evals/agent-design-tools/agent-workflow-design/cases.json)や[評価記録](../agent-workflow-design/README.md)は、期待する振る舞いを定める出発点として使います。既に改善に利用した公開ケースは回帰確認に使い、未見の最終評価用ケースとは扱いません。

## 4. プラグインと実行部分の構成

配置先は `plugins/agent-eval-tools/` とします。プラグインの README には、対象、利用例、実行環境の要件、参考資料をまとめます。`SKILL.md` は依頼の判別と手順の入口に絞り、採点、比較、改善、実行環境ごとの詳細は必要なときだけ読む参照ファイルへ分けます。

スクリプトと参照契約は `skills/agent-improve/` が所有します。評価作成、比較、原因診断、改善探索、世代の切り替えは必要時に読む参照へ分け、同じ実験設定と結果を使います。プラグインの配布物だけで参照とスクリプトが動くことを検査します。

責任の分担は次のとおりです。

- **スキル**：成功条件を定める、ケースの妥当性を判断する、失敗を診断する、変更案を考える、証拠から採否を判断する。
- **共通ランナー**：実験の設定を検証する、ケースごとの作業領域を準備する、実行を開始・停止する、結果と試行履歴を記録する、再開可能な単位を管理する。
- **実行アダプター**：対象の起動方法、利用できるイベント、使用量、終了状態を共通形式へ変換する。
- **採点器**：成果物や実行後の状態を検査する。意味や読みやすさなど、コードだけでは扱えない観点には、具体的な基準を持つモデル判定を追加する。

ランナーは Node.js の標準モジュールで独自に実装します。初版で必要なケース実行、結果取得、採点、比較を一つずつ通し、その実行から記録契約を固めます。初めから外部ランナーの形式を再現したり、将来の全アダプターを想定した抽象化を作ったりしません。

比較条件の版、変更範囲、試行の識別、予算による停止など、機械的に検査できる契約はコードで支えます。調査する順序、読む参照、仮説や変更案の選択はモデルの判断に残します。設計文書の各節を毎回実行するチェックリストに変換せず、比較の成立に必要な条件と、状況に応じた調査方法を区別します。

改善方法をすべて固定ランナーへ埋め込むことは避けます。診断、候補の選択、試行配分、継続・停止の判断を支える指示や補助コードは、自己改善の許可範囲に含められる構成にします。実行環境が強制する権限、予算上限、その候補を判定する評価契約は、候補の編集範囲から外します。補助コードを変える場合も、現在版の実行途中で差し替えず、新しい版として比較します。

このため、共通ランナーのうち実験を管理する部分は、候補の作業領域の外から、固定した設定で起動します。候補が提案する試行配分や採点処理と、それを実行してよいかを検査する処理を区別します。候補のコードが、実行中の管理処理、保護した評価、総予算の記録を書き換えられる状態では、補助コードの自律的な実行を有効にしません。パスの指定だけで保証せず、実行環境のアクセス制御と子プロセスを含む停止を段階 0 で確認します。

CLI ランタイムの `tools/agent/`、インストール済みキャッシュ、別プラグインの発見結果には依存させません。既存の `agent-design-tools` は必要に応じて設計に使えますが、通常実行の必須依存にはしません。

初版では、専用の MCP サーバー、常駐プロセス、スケジューラー、ダッシュボードを作りません。ケース単位の構造化結果と、根拠へたどれる簡潔な比較レポートを先に作ります。

### 実行環境の能力を先に確認する

最初に使うのは、依頼を受けたホストが既に提供するサブエージェント機能です。会話履歴を引き継がない文脈へ、固定した対象と課題だけを渡し、親が結果を共通ランナーへ戻します。試行の文脈を分けることと、ファイルアクセスや最終評価を保護することは区別します。ホストが使用量や実モデルの版を返さない場合は不明と記録し、サブエージェントの費用だけで親の調整を含む総費用を測れたとは扱いません。スクリプトは次の呼び出しを制限できますが、ホストの実行に対する中断と終了確認は親が行います。

手動または単独で実行する選択肢として、`codex exec --json` も使えます。公式資料では、非対話実行とイベントの JSONL 出力が説明されています。ただし、取得できるイベントだけで、すべてのスキル読み込みやツール操作を観測できるとは仮定しません。アプリの認証と、別プロセスから起動した CLI が利用できる認証も同一とは仮定せず、その実行経路で確認します。認証を必要とする経路が使えないことを、評価全体ができない理由にしません。[Codex の非対話実行](https://developers.openai.com/codex/noninteractive)

実行中の追加指示と中断には、別段階で Codex App Server を検討します。公式プロトコルには `turn/steer` と `turn/interrupt` があります。これらを使った試験を、単発の非対話実行だけで代用したことにはしません。[Codex App Server](https://developers.openai.com/codex/app-server)

アダプターは、スキル指定、自然な発見、途中指示、ターン中断、状態の再開、ツール履歴、使用量などについて、対応の有無を宣言します。必要な能力がないケースは実行前に未対応と判定します。観測できなかった動作を合格にせず、実行した CLI と普段のアプリが同等であるとも断定しません。

## 5. 比較を成立させる最小の記録

最初に、実験の目的、変更対象、採否を比べるケース集合と採点方法、採否条件、総予算を固定します。探索用のケース追加・選択や予算配分は、事前に定めた許容範囲内で変更でき、版と利用時点を記録します。探索用の採点器を更新した場合は、その評価で比べる現行版と候補を測り直します。採否の尺度や変更範囲、総予算など、固定した条件を変える場合は別の実験として扱います。初版の記録契約には、少なくとも次を含めます。

- **対象の版**：対象スキルと同梱参照のスナップショット、変更可能なパス、現行版と変更案のハッシュ。
- **改善機構の版**：変更案を作ったスキル・参照・補助コード・引き継いだ知見の版、親となる版、採用した版と次の実行で実際に有効だった版。対象の版とは別に識別する。探索用に残した候補には、再検討する仮説、利用範囲、追加予算を結び付ける。
- **評価の版**：ケースと採点器の版、ケース群の分割方法、環境の準備方法。
- **実行条件**：アダプターと実行環境の版、指定したモデルと取得できた実モデル情報、有効な指示や設定について確認できた範囲。候補生成、対象の実行、採点の役割ごとに、使ったスキル・参照の版と読み込みを確認できた範囲、変更可能な層と固定された依存先を記録する。
- **試行**：ケース ID、変更案 ID、反復 ID、実行 ID、再試行の理由、開始・終了状態、成果物への参照。
- **判定と使用量**：観点ごとの判定と根拠、取得できたトークン使用量、実行時間、採点側の使用量。

分からない設定や使用量は不明のまま記録します。モデル名を指定しただけで実際に使われた版を確認済みとせず、取得できない金額を API 価格から推定してサブスクリプションの費用として表示しません。

同じケースの各試行は、新しい会話で始めます。ファイルを使って課題を実行する経路では、作業領域も初期状態をそろえて用意します。テキストだけを渡すホスト経路は、共有ファイルシステム上で入力を受け渡す構成であり、試行ごとのファイル隔離を保証しません。現行版と変更案の順序は偏りを避けるよう入れ替え、差分比較では同じケース同士を対応させます。作業ディレクトリを分ける場合も、それだけではホームディレクトリ、上位の指示、ネットワーク、他の作業領域からの情報流入を防げません。何を分離できたかを実行条件として残します。

実行結果は、課題の成功・失敗、基盤のエラー、採点不能、未対応を区別します。たとえば、課題で定めた時間制約に違反した場合と、サービス障害で実行できなかった場合を同じ失敗点にしません。未完了やエラーを集計から黙って消さず、予定件数、実行件数、採点できた件数と理由を示します。成功するまで再実行した最後の結果だけを採用することも避けます。

再開は実験設定と対象のハッシュが一致する場合だけ許可します。各試行を一意に識別し、完了済み試行の二重実行や、設定変更後の結果混在を防ぎます。採点だけを再実行した場合は、実行結果の版と採点器の版を別々に残します。

### 保存先と公開可能な内容

保存先は、証拠が何の保守に使われるかで決めます。このリポジトリのスキル・指示・ワークフローに関する、公開可能で保守に役立つ評価定義と行動評価の証拠は `evals/`、設計理由と評価の説明は `docs/` で管理します。他プロジェクトの評価は、その管理元の方針に従います。`agent-eval-tools` を使ったことだけを理由に、すべての記録をこのリポジトリへ集めません。公開範囲の規約は [AGENTS.md](../../AGENTS.md#privacy-of-repository-content)、評価ごとの配置は [evals の案内](../../evals/README.md)を正本とします。

公開・合成の課題に対する入力、応答、判定基準、ケース別の判定、対象の版は、個人情報、秘密情報、非公開の案件資料、実環境の情報を含まないことを確認して選びます。ローカルで実行したことだけを理由に、応答まで一律に非公開とは扱いません。

生の実行記録は原則としてリポジトリ外に保持し、公開用の抜粋と区別します。実環境の構成、診断ログ、環境の計測などは、記録を明示的に依頼されない限り公開物へ含めません。公開用に選んだ証拠は、抜粋・加工と出典の対応、解釈上の限界を明示し、観測した応答を架空の出力へ置き換えません。現行維持や棄却の結果も、比較の基準や判断理由として必要なら残します。公開できることと、保守のために残す価値があることは別に判断します。無視設定だけで保存や公開の許可を得たとはみなしません。

診断に必要な入出力とツール結果を対象とし、認証情報や非公開の内部推論の取得は求めません。既存の承認済み保存先を使える場合は、反復ごとに保存の確認を取り直さない設計にします。

ランナーの `note` は、その実験記録への注記であり、永続的な保守メモの作成ではありません。保守メモの保存先に実験結果や実行状態を置けない場合は、再検討する価値のある判断と参照だけを残します。実験記録を別の場所へ黙って複製せず、一時保存しかできない場合はその制約を示します。保守メモの整理と元の証拠の整理は別々に判断します。

全スキル共通の保存ディレクトリを先に規定せず、プロジェクトやワークフローの所有する保存先と保持条件を優先します。保持する証拠、選択的な保守判断、一時ファイルの区別と、応答の保存確認・検証した保管コピーの扱いは[実行契約](../../plugins/agent-eval-tools/skills/agent-improve/references/runtime.md#retained-evidence-and-temporary-work)を正本とします。保存先を変えただけで再開可能とは扱わず、実験 ID、契約、証拠への参照を保ったまま再読できることを確かめます。

### 後の自己改善に残す証拠

保存の目的は、後から判断を確かめ、次の比較を作れることです。上記の版、試行、判定、使用量の記録を共通ランナーで残し、成功・失敗・棄却・未完了を選別せずに追跡します。会話全文や全ツール出力の恒久保存を既定にはせず、比較、再開、採否の説明、具体的な再検討に必要な成果物と入出力を保持します。既存の保存先で証拠を追える場合は、その参照を使います。

評価方法に関係する気付きが得られた場合だけ、実験記録に短い注記を結び付けます。含めるのは、観測した食い違い、該当する結果と版への参照、原因仮説と未確定点、判断に必要な次の比較です。既に結果に含まれる情報を転記せず、原因が不明なら不明のまま残します。毎回すべてを埋める反省文にはしません。たとえば、要件を落とした回答の誤合格、正当な別解の誤不合格、診断の繰り返し、不要な質問や評価費用を手掛かりにできます。維持したい成功例も含め、失敗だけから方法を変更しないようにします。

情報の粒度を示す架空の例は、次のとおりです。項目名と書式は説明用であり、固定の出力形式や別ファイルの作成を要求するものではありません。

- **metadata（対象と根拠）**：採点基準を点検した実行。対象の版・実行条件は実験記録を参照し、証拠となるセッションログの URL と該当箇所を結び付ける。
- **overall（結論）**：今回の採点結果だけでは、変更案を採用できない。
- **findings（分かったこと）**：要件を満たす別解が、特定の書式に従っていないという理由で不合格になった。該当する回答と判定を根拠として参照する。
- **unresolved（残る問い）**：個別の採点基準だけの問題か、評価スキルが基準を作る方法に共通する問題かは未確認。異なる課題でも比較する必要がある。

結論は短くし、該当する気付きや未確定点がなければ無理に作りません。判定の対象と範囲を残し、たとえば構成レビューの「指摘なし」を、性能も検証できたという意味には広げません。自己改善時は気付きと残る問いから必要な証拠を読み、要約の結論だけで変更を決めないようにします。

保存した要点には、必要な証拠へたどれる参照を持たせます。既存のセッションログを後から読める場合は、その URL と該当ターン・メッセージ、対応する実行 ID を使い、全文を複製しません。使用した版や実行条件は、対応する実験記録から追えるようにします。変化・消失する元データに依存する場合や、再実行に必要な素材がログにない場合は、許可された保存範囲で必要部分を補います。証拠を確認できなくなった記録は、その制約を付け、確かな原因や再実行可能なケースとして扱いません。後から結果を調べられることと、同条件で再実行できることを区別します。参照を残しても、保護された最終評価へのアクセスを改善側へ広げません。

再利用時は、指定された記録が読めることに加え、実行 ID、実験契約のハッシュ、参照した試行や判定が一致するか確認します。欠落や不一致を、メモの要約で補って確認済みとはしません。通常実行で全履歴を走査する仕組みは追加せず、必要になった参照だけを確かめます。

実験記録の形式と保存・再読の手順は `agent-eval-tools` が管理し、保存先と公開・保持の条件は対象を保守するプロジェクトやワークフローに従います。初版では実験記録とその注記を使い、横断的な記憶サービスは作りません。保存範囲と整理条件は実験の開始時に定め、同じ手掛かりは証拠への参照を保ってまとめます。不要になった詳細ログは整理できますが、比較の説明や再開に必要な証拠、候補の系譜を気付きの解決だけで消しません。通常の実行で無関係な記録まで走査せず、保存・整理・読み込みの費用も運用コストとして扱います。

実務の生の証拠と私的な保守メモは、上記の実行記録・保守メモの保存先で扱います。公開できる一般化した知見は `docs/`、合成ケース、再利用可能な評価定義、確認済みの行動評価の証拠は `evals/`、検証して採用した判断方法はスキル・参照・補助コードへ反映します。記録の追加だけで、稼働中の指示や、通常実行へ自動的に読み込む知見を増やしません。

## 6. 採点器と評価集合を先に確かめる

採点器には、依頼を満たす正例と、もっともらしいが重要な要件を落とす負例を通します。空の回答、何もしない変更、採点器への指示を含む回答なども、対象に応じて確認します。評価したい能力を欠く変更案を識別できなければ、その評価で改善を始めません。

機械的に検査できる条件はコードで判定します。モデルによる判定には、対象の名前や現行版・変更案のラベルを隠し、回答の順序を入れ替えます。基準の曖昧さや判定の揺れを確認し、判断の割れる例を調べます。モデル判定を増やすだけで、独立した正しさの保証が得られるとは扱いません。

評価集合には、改善したい失敗例と、既にできていることを維持する例を含めます。同じ事例の言い換えや同じ素材に由来するケースは一つの群として扱い、分割先をまたいで実質的な答えが漏れないようにします。

十分なケースがある場合は、変更案の診断に使う集合、選択に使う集合、最後の確認に残す集合を分けます。少数しかない段階で形式だけの三分割を強制せず、探索的な比較であると明記し、未見の状況への一般化を主張しません。最終確認に使ったケースも、その後の改善に利用した時点で未見ではなくなります。

同じケースを繰り返すことと、独立したケースを増やすことは区別します。少数ケースを多数回実行した結果を、同じ数の独立した事例があるかのように扱いません。初版はケースごとの差と反復による揺れを示し、厳密な統計的判断が必要になったときに、その実験に適した方法を追加します。

### 評価する方法そのものを改善する

評価・改善スキル自身を良くするには、その中のどの能力を変えるかで確認方法を選びます。初版から作業用の採点器や診断方法を通常の改善対象として扱い、専用の上位スキルは増やしません。

- **診断と修正提案**：指摘が詳しいことではなく、その指摘から作った変更が、固定した評価で対象を改善するかを測ります。不要な変更や誤った採用、修正に要する費用も含めます。
- **採点器**：候補の出力とは独立に正否を確かめた成果物で、誤合格と誤不合格を分けて測ります。既知の欠陥に加え、正当な別解、境界例、採点への誘導を含め、単に厳しく判定する変更を改善としません。モデル判定なら、判定の揺れと根拠も確認します。
- **ケース生成と選択**：用途上重要な欠陥を発見でき、正しい実装を落とさず、実行可能な課題を作れるかを測ります。既知の欠陥だけに特化していないかを独立した対象で確かめ、そのケースを使った改善の結果も別の評価で確認します。難しいケースや失敗数の増加だけには加点しません。

これらを比べる間は、外側の正否の根拠、対象の開始版、予算を固定します。正否の根拠には、実行可能な要件検査、独立に確認したラベル、必要な領域での人の判断を使います。候補と同じ採点器に自身の採用を決めさせず、根拠が曖昧な領域では暫定評価の範囲を示します。すべてを人が毎回再評価する構成にはせず、確認済みの根拠は版を固定して再利用します。

外側の評価も永久には固定しません。要件の変化や測定の欠陥が分かれば、新しい評価契約を作って現行版と候補を測り直します。改善に使う課題の難しさや配分は探索中に変えられますが、最後の確認用の課題をその生成材料にはしません。各世代で見つけた弱点は次の探索へ戻し、未使用の確認用課題は別に確保します。この区別により、評価を育てながら、合格基準を緩めただけの改善を避けます。

## 7. 改善ループと採用条件

### 目標と証拠から改善対象を選ぶ

改善の入口には、能力を高めたいという目標、既存の評価結果、利用者が提示した実務上の失敗や手戻りを使えます。実務で問題が起きることを開始条件にはせず、対象の用途から評価課題を作り、実験によって改善余地を探せます。課題には、日常の成功例に加え、難しい理由を説明できる課題や用途上必要な未対応の場面を含めます。現在のモデルが失敗した例だけに偏らないようにします。

期待した結果と観測できた結果を照合し、症状と原因仮説を区別します。スキルを修正すると決めてから理由を探すことは避けます。正しく扱えた事例も、維持すべき能力の証拠になります。

変更先は、問題を所有する箇所に絞ります。再利用する判断は既存スキル、詳細な説明は参照、機械的に守れる条件はスクリプトや検査、リポジトリ固有の契約はそのリポジトリの指示を候補にします。評価器や実行基盤が原因なら、そこを直します。一時的な問題や証拠の弱い推測には、恒久的なルールを追加しない判断もできます。対象外の変更が必要なら原因と候補を返し、改善依頼を理由に編集範囲を拡張しません。

ここで残すのは、問題の証拠、原因仮説、変更先、改善を判断する方法です。既存の比較記録に含められるなら別の振り返り文書は作りません。通常の修正に一律の実験を課さず、「修正できた」「限定した条件で改善を確認した」「未見の課題へも効果が及んだ」を証拠に応じて区別します。

### 比較実験で変更の効果を確かめる

比較によって改善を確認する場合は、次の依存関係を満たして進めます。既に満たされた条件は版と証拠を確かめて再利用し、毎回すべての準備をやり直しません。

1. 現行版、変更可能な範囲、維持すべき振る舞い、利用できる予算を確定する。
2. 評価が動き、採点器が正例と負例を区別できることを確認する。
3. 現行版を測り、必要なら変更なしの再実行で揺れを確認する。
4. 目標と探索用の証拠から改善の仮説を立て、変更案を作る。既知の不具合を直す場合は、利用できる失敗例から原因を診断する。
5. 同じ条件で現行版と変更案を比較し、改善、悪化、判定不能を分ける。
6. 採用候補だけを最終確認へ進め、許可された範囲で反映する。

改善探索まで依頼された場合は、手順 4 と 5 を、目標到達、予算到達、継続できる仮説がない状態、または実行上の問題に至るまで繰り返します。一回の比較や最初の改善で自動的に終了しません。探索中は候補選択用の評価で暫定的に良い版を保持します。悪化した案を実務へ反映せず、追加検証する仮説がある場合には、実行条件を守れる候補を探索用に残せます。最後の確認用に残した集合を、各反復の候補選択に流用しません。終了時に手順 6 を行い、開始版との比較を返します。停止条件と継続判断も改善用スキルの評価対象です。

初版から、候補の版と生成元を記録し、過去の候補から限定した追加試行を行えるようにします。候補の保存、探索の親への選択、実務への採用は別々に記録します。追加試行は同じ実験の総予算に含め、変更範囲や実行契約を満たさない候補は実行しません。大規模な集団探索や専用の記憶基盤は、この最小機能で不足が確かめられてから検討します。

原因の診断では、該当ルールの有無だけでなく、評価時に有効だった版、スキルの選択、参照の読み込み、ツール契約まで確認します。ルールが既に十分なら同じ注意書きを追加せず、選択や読み込みの経路、実装側の問題を直します。指示が使われた証拠と、使った結果が良くなった証拠は分けます。既存の改善用参照の共通原則を使い、診断の順序や方法自体は、第1節の変更範囲内で改善候補にできます。

変更案には、追記だけでなく、不要な指示や参照の削除、重複の統合、スクリプトへの移動も含めます。必要性が疑わしい部分は、それを外した条件と比較して役割を確かめます。スキル全体の有用性が論点なら、スキルを使わない条件も対照にできます。ただし、各条件を毎回必須にせず、判断したい仮説に必要な比較だけを行います。短くしたこと自体には加点しません。

測定の揺れが想定する改善量より大きい場合や、採用する価値のある差を測れない場合は、編集の反復を始めず評価方法を見直します。停滞時も、変更案を増やす前に、内容、採点、実行基盤、参照経路、ばらつきのどこに問題があるかを調べます。

採用条件は実験前に決めます。課題の達成を第一に、重要な制約と既存能力を維持できた変更案について、時間や使用量を比較します。品質、違反、費用を根拠のない重みで一つの総合点にせず、品質を維持して使用量を減らす場合には、許容する品質差を先に定めます。差が不明確なら現行版を維持します。

高価な比較へ進める前に、実行可能性と契約を検査し、小さな探索用課題で候補を絞れます。その後、選んだ候補を固定して外側の確認へ進めます。途中で打ち切った案は未評価の範囲を明示し、最終評価を見てから全候補の中で最高だった案を選び直しません。評価の配分方法も、後に改善できる方針として扱います。

改善するエージェントが、同じ実験の合格条件を自分に有利に書き換えられないようにします。ケースや採点器の不備が見つかった場合は、先に評価を修正し、現行版から測り直します。評価定義を変えた前後の数字を、そのまま改善量として比較しません。

最終評価用の入力や正解は、変更案を作るエージェントからアクセスできないことが望ましい設計です。これを保証するには、実行環境側の読み取り制限などが必要です。同じ権限で動く別プロセスや「読まないこと」という指示だけでは保証しません。初版で隔離を実現できない場合は、その制約を報告し、保護された最終評価としての主張を控えます。アクセス制限の実現性は、最初の実装段階で確認します。

予算は、候補数、試行数、時間、取得可能なら使用量について、実験ごとに上限を持たせます。停止判断をモデルの自己申告だけに任せず、ランナー側で強制できる上限を適用します。正確なトークン使用量を終了後にしか得られない環境では、実行中の厳密なトークン上限とは呼びません。

改善機構の比較では、対象の改善実行がさらに評価を呼ぶため、内側の試行にも同じ実験 ID と残予算を引き継ぎます。候補生成、対象実行、採点、再試行を一つの総枠に計上し、入れ子の処理が新しい上限を勝手に作らないようにします。実行中に強制できる時間・試行数と、事後に分かる使用量を区別し、停止後に子プロセスが残る場合は正常な予算停止とは報告しません。

現行版の変更は、隔離した作業領域で検証した差分を元に行います。反映前に対象が実験開始時から変わっていないかを確認し、既存の未コミット変更を上書きしません。別の変更と競合したら、採用済みの証拠がどの版に対するものかを確認して調整します。改善を依頼された対象への反映と、インストール先の切り替えや公開は別の操作として扱います。

採用した変更が次の実行で有効になったかも区別して記録します。ソースを変更しただけでは、稼働中の会話や導入済みコピーがその版を使うとは限りません。有効化まで依頼されている場合は既存の管理経路に従って確認し、その後の結果を有効な版へ結び付けます。ソース変更までの依頼なら、その到達点で終えます。

採用後に退行や評価の不備が分かった場合に備え、直前の採用版を再構成できる状態にします。戻す単位は変更したファイルだけでなく、比較時に使用したスキル、参照、補助コード、採用済みの知識の組み合わせです。復旧時は現在の状態との差分を確認し、採用後に加わった別の変更を上書きしません。有効化まで依頼されている場合は既存の管理経路で戻し、新しい実行がどの版を使用したかを確認します。ソースだけを戻して、稼働する版まで復旧したとは扱いません。

復旧の理由と使用する版を記録し、判明した不備の影響を受ける採用判断は再検証まで保留します。特に評価方法の不備は、その版で得た結論のどこまでを信用できるかを確認し、影響する比較を測り直します。過去の記録は消さず、結論の訂正と根拠を結び付けます。この復旧経路のために常駐監視や独自のインストール機構を追加する必要はありません。

### 次の実行と改善へ戻す

採用後は、新しい文脈で実際の依頼を処理できるかを確かめます。原因を教えた会話で修正できただけでは、次回にも有効な変更とは判断しません。許可された実務で得た修正指示や失敗のうち、再利用する価値があるものを次の評価ケース候補に戻します。その際も、第5節の保存先と公開範囲を守ります。

評価方法の不備で現在の比較が成立しない場合は、その結果を採用せず、許可された範囲で評価を直して測り直します。自己改善を後日にまとめる方針を、必要な修復を先送りする理由にはしません。一方、局所的な修復をそのまま共有する評価スキルへ恒久反映せず、影響範囲に応じた比較を行います。

### 蓄積した証拠から評価スキル自身を改善する

開始する価値のある手掛かりは、具体的な改善仮説、異なる課題に共通する問題、重大な誤判定、モデルや実行環境の変更などです。記録件数や経過時間だけでは開始を決めません。通常運用で見つけた手掛かりは結果に添えられますが、それだけで自己改善の実行権限や追加予算を得たとは扱いません。初版は依頼時に実行し、常駐監視やスケジュール実行を追加しません。

自己改善の実行では、対象の方法に関係する記録を選び、証拠と当時の版を確かめ、原因を診断します。記録が古い場合や証拠が足りない場合は、現在版で小さく再現できるかを調べます。反例や維持したい成功例も使って候補を比較し、選んだ版を新しい実行で確かめます。蓄積した事例は探索と回帰確認の材料であり、未見の最終評価には数えません。人が毎回改訂案を書き起こさなくても、この診断から比較までを同じ改善機構で進められる構成にします。

知見を通常運用へ戻す場合も、対象を選んで整理し、その知見を含む構成を比較・版管理します。未検証の気付きを毎回一括で読み込ませて、評価した版とは別の振る舞いを生まないようにします。通常の評価・改善の費用と、記録を整理して自身を更新する費用は区別し、自己更新の価値を調べる際には両方を総費用に含めます。記録をためること自体を RSI の成果にはしません。

実験とは別に未解決の保守判断を残す場合は、既存の [Maintenance records](../../plugins/agent-design-tools/skills/agent-workflow-design/references/maintenance-records.md)の所有者・再検討条件・整理方針を使います。実験の候補、系譜、比較結果は第5節の契約で扱い、この整理規則へ移しません。常時の履歴収集や、依頼なしに続く自動改善は前提にしません。

## 8. ループ処理の評価を追加する方法

ループの試験では、モデルに「途中で指示が変わったと仮定して説明して」と尋ねるだけでは足りません。実行中に状態や指示を変え、実際の応答と外部状態を観測する仕組みを作ります。

ケースは、初期状態、モデルが利用できる操作、環境が返すイベント、到達すべき状態、起きてはいけない副作用を定義します。初めは、公開可能な合成データを使う小さな模擬ツールを用意します。イベントは可能な限り操作や状態に結び付け、単なる待ち時間の偶然で発生させないようにします。

優先する場面は次のとおりです。

- 一部の作業が終わった時点で、残りの作業だけを待てるか。
- 状態が変わらない間に、同じ確認や同じ説明を繰り返しすぎないか。
- 途中で必要な成果物が変わり、不要になった作業や古い結果を適切に扱えるか。
- 外部操作の応答が失われたとき、同じ副作用を重複して起こさずに状態を確かめられるか。
- 中断後の再開で、完了済みの事実と未完了の処理を区別できるか。

評価するのは、最終成果だけでなく、許可された副作用、不要な再実行、待機や停止の振る舞いです。ただし、正当な別手順もあるため、唯一のツール呼び出し列に一致することを合格条件にしません。模擬環境で確認した性質と、実サービスで追加確認が必要な性質を分けます。

## 9. 実装する順序と各段階の完了条件

各段階は別製品の開発ではなく、一つの改善機構で確認できる範囲を広げる順序です。最初の実装目標は段階 2 までとし、自己適用の経路を通せる小さな実装を作ります。段階 0 と 1 は、そのための前提確認です。

現行の自動比較では、固定したケース、採点器、試行配分の下で、方法の文章が診断、候補の内容、過去候補からの分岐、停止判断に与える効果を測ります。方法の候補がケース生成や採点方式、試行配分そのものを変更して実行する経路は、まだありません。課題を追加するだけで改善機構の全能力を測れるとは扱わず、まず現行の操作範囲を測り、必要な能力ごとに実行側と外側の評価を拡張します。限定した試用を始められることと、以下の全完了条件を満たしたことを区別します。

### 段階 0：改善能力を測る課題と実行条件を決める

小さな「スキルを改善する課題」を用意します。各課題は、対象スキルの開始版、利用者の目標、探索中に使える評価、変更範囲、予算、外側から結果を確認する評価を持ちます。対象スキルを動かすケースと、そのスキルを改善させる課題を混同しません。

題材には、指示の不足、過剰な手順、参照への到達、採点器の不整合など、異なる原因を持つものを選び、変更不要の対象も含めます。まず合成データで採点と実行を校正し、既存の `prompt-design` と `agent-workflow-design` の公開可能なケースから実用的な改善課題も選びます。後者は初めに生成した設計の品質を扱い、実行中のイベント処理は段階 4 で検証します。意図的に壊した簡単な対象での成功を、そのまま一般的な改善能力の証拠にはしません。

段階 0 では、あらかじめ用意した対象スキルの現行版と変更案を、既存の起動コマンドで一回ずつ動かし、成果物を小さな採点器へ通します。これにより、版の読み込み、成果物、終了状態、使用量、状態の分離を確認し、第5節の記録契約を具体化します。変更案を自動生成する処理と、継続・棄却・採用の制御は段階 1 で作ります。

あわせて、その実行を支配する指示と読み込む参照を確認し、第1節の統合条件に照らして、固定する依存先と、必要な場合に変更を比較する正本を決めます。既存スキルを変更しない構成から始め、比較条件を確定できない衝突は、実モデルでの候補探索を始める前に解消します。

最初の確認実行に先立ち、使う実行環境とモデル設定、強制できる時間・試行数の上限、許可されたローカル保存先を具体化します。既存の依頼や設定で確定している条件は引き継ぎます。確認実行の結果から、対応能力と制約、比較に使える記録、段階 1 へ進める範囲を確定し、未確認の能力を前提に本体を作り込まないようにします。

この段階で、候補だけを読み込めるか、保護した管理処理への書き込みを防げるか、最終評価の読み取りを制限できるか、子プロセスを含めて停止できるかを、小さな確認実行で調べます。満たせない能力は未対応とし、指示だけで代用しません。管理処理の保護や総予算の強制が成立しなければ、自律的なコード変更を伴う探索へは進まず、実行方式を見直します。最終評価の秘匿だけが成立しない場合は、公開ケースによる動作確認を進められますが、未見の課題での効果の実証は保留します。

完了条件は、一つの改善課題に含まれる対象スキルの比較を通し、課題の達成、基盤のエラー、未対応を区別できることです。改善機構全体の完成は求めません。評価が目的にあわない、または実行能力が足りない場合は、この段階で直します。

#### 直近の課題整備と比較の進め方

次は、大きな総合ベンチマークを先に作らず、改善方法の具体的な仮説を判断できる小さな課題群を整えます。利用者が課題を一から記述することは前提にせず、担当エージェントが既存の公開素材、許可された実務上の証拠、能力目標から候補を作ります。公開素材のコピーに実環境の記録を混ぜず、再利用できる合成ケースと私的な実行証拠を分けます。

最初の題材は、次の三種類を候補にします。いずれも実装済みのテキスト実行で確認できる範囲に限り、採用する課題と難しさは事前確認で決めます。

- **根拠の強さを保つ改善。** 「未検証」を「非対応」に変えない一方、明示された「対象外」は弱めないなど、両方向の要件を持つ指示を改善させます。[既存のソース保持ケース](../../evals/agent-design-tools/prompt-design/source-preservation-cases.json)を開発用の出発点にし、候補の指示で生成した要約まで確認します。公開済みの答えを未使用の評価とは呼びません。
- **複数の規則と例外を両立する改善。** 架空の分類・保持方針などについて、基本条件の変更を反映しながら、優先する例外や既存の出力形式を保つ課題にします。単なる定数置換を超えて、本文と明示して渡した参照の整合が必要な開始版を用意します。判定可能な部分は構造化出力で確認します。ファイルの自然な発見や実際の削除操作を測ったことにはしません。
- **完成した対象の維持。** 必要な条件を満たす対象を混ぜ、もっともらしい追加規則で回帰を起こした候補を採用せず、現行維持を選べるか確認します。変更の量を成果にせず、変更不要の判断も改善方法の比較に含めます。

各課題には、開始版、改善目標、変更できるファイル、探索に使うケースと証拠、維持条件、別に取っておく確認ケース、判定方法、呼び出し・時間予算を用意します。課題を作るための予算と、その後に方法を比較する予算は分け、実験開始前に固定します。課題の正本は `evals/agent-eval-tools/agent-improve/` に置き、ここでは題材と採用条件を管理します。まだ作成していない課題を実行可能なベンチマークとして案内しません。

進め方は次の順序です。

1. **課題と採点の感度を確かめる。** 正解・正当な別解・紛らわしい誤りを採点できるか確認し、用途上妥当な改善が存在するかを少数の例で確かめます。人が用意した修正で動作を調べる場合は、方法が生んだ改善と区別します。品質差を測る課題で `H0` が一度で解けることは問題ではなく、課題群全体で上限に達しているなら、その課題群で品質改善を主張できないという判断です。
2. **現行版 `H0` を基準として測る。** 課題を採用した後に版を固定し、予算内で直せた問題、残した問題、回帰、現行維持、失敗した試行を確認します。差を作るために `H0` を弱めたり、失敗例だけを選んで全般的な能力低下と扱ったりしません。方法の文章で変えられる問題と、固定ランナーや実行環境の制約を分けます。
3. **根拠のある候補 `H1` を作り、同条件で比べる。** たとえば、一例に合わせた修正が例外ケースを壊す証拠があれば、回帰の原因を診断して候補に反映する方法を比較します。候補ごとに得意な課題へ評価を変えません。課題も方法も同時に調整した場合は開発上の探索とし、次の固定した比較へ進めます。仮説がない場合は無理に自己編集を始めません。
4. **未使用の改善課題へ進める。** 同じ課題の入力を言い換えるだけで済ませず、別の開始版・目標を持つ改善課題を候補固定後に使います。改善課題の分割と、その中の対象ケースの分割は別々に管理します。現行ホストで指示への未配信を管理できても、ファイルアクセスから保護した未見評価は保証できないため、その確認は探索的な証拠にとどめます。
5. **採用した方法を次の改善に使う。** `H1` が有効なら、その版を明示した新しい実行へ切り替えます。さらに後継を生む能力を調べるときは段階 3 の対照へ進み、同じ開始状態に対する `H0` と `H1` の結果を比較します。一回の改善成功から、持続的な RSI までを推定しません。

現行の自動採用は品質の上昇を条件としています。全課題で品質が同じで、費用だけに改善余地がある場合は、費用の測定範囲と採否条件を別途実装・検証してから比較します。呼び出し数だけを見て、取得できないトークン使用量や親側の費用まで改善したとは判断しません。採点器や実行中のループ自体を改善する課題は、それを候補として動かせる仕組みが必要になった時点で追加します。

### 段階 1：最小の改善機構を実行し、初期版を測る

`agent-improve`、共通ランナー、単発実行アダプター、必要な採点器と比較レポートを作ります。既存スキルとの統合条件を整えた構成を初期版 `H0` と呼び、その指示と補助コード、利用する設計スキルと参照の版を固定して測ります。`H0` は目標と評価から改善の仮説を立て、必要な原因診断を行い、変更案を作り、比較結果で継続・棄却・採用を判断します。実務の失敗報告がなくても、目標と課題から探索を開始できます。

この時点で、生成元である `H0` の版と、変更される対象スキルの版を記録します。初期版には現在の設計知識に基づく方法を与え、課題で有効性を確かめます。後で改善したように見せるために、意図的に弱い初期版を作りません。

既存の設計スキルも継続的な改善対象にします。比較中は、改善する側が使う設計スキルの版と、対象として編集する候補版を分けます。対象の候補を途中で改善する側へ読み込ませて比較条件を変えず、採用した版を次の実験で設計支援にも使う場合は、改善機構の構成変更として記録します。これにより、既存スキルの改善を次の改善へ戻しつつ、どの版が結果を生んだかを追跡します。

候補の版、親、生成元、比較結果を保存し、現在の最良版以外からも予算内で追加試行できる最小機能を作ります。採用されなかった候補からの試行が、実務へ反映する版の切り替えを起こさないことも確認します。

完了条件は、複数の改善課題で初期版の結果と費用を測れ、採用・棄却・停止を処理できることです。人が途中で方法や変更案を補った場合は介入として記録します。対象の品質、探索の費用、原因の診断を、実際の成果物と試行に結び付けて説明できる状態にします。

課題群には、作業用の採点器が誤判定する対象と、変更しない判断が適切な対象を含めます。採点器の修正は第6節の独立した根拠で確認し、対象スキルの不要な変更で得点を合わせないことを検査します。初版から高度な課題生成器を作る必要はなく、これらの課題で評価方法も改善対象にできる経路を確かめます。

通常の対象を改善する依頼で、評価スキル自身への変更や追加の自己評価を始めず、後の診断に必要な証拠を残せることも完了条件に含めます。保存に失敗した場合は、対象の比較結果と、後で検証できる証拠の範囲を区別して報告します。再開や正しい採否に必要な記録を保存できない場合は、その記録に依存する処理を完了扱いにしません。

この段階で第10節の併用確認を行います。既存側に原因がある問題を確認した場合は、その適用条件の修正候補を比較します。固定後の指示や参照を変更した場合は、影響する比較を更新した版で測り直します。新プラグイン単独で動くことだけを、初期版の完成条件にはしません。

### 段階 2：自身への適用と、次の実行への反映を通す

`H0` に、自身のスキル、参照、許可された補助コードと、段階 1 の探索用の証拠を渡します。通常運用とは別の新しい文脈から、保存した要点と証拠への参照で必要な材料を取り出し、原因を教え直さなくても候補を作れるかを確認します。同じ改善処理で、自身の診断、変更案の作成、実験選択などを変えた候補 `H1` を作らせます。別の自己改善専用エージェントは新設しません。

`H0` と `H1` を、同じ開始版の対象スキル、同じ課題、同じモデルと予算で比較します。この比較の各試行中は、改善機構自身の版を固定し、対象スキルだけを改善させます。比較するのは、生成した差分の見栄えや数ではなく、外側の評価で確認した対象スキルの改善と、それに要した全体の費用です。

この比較へ進む前に、仮説に関係する差を課題で測れるか確認します。現在の採点尺度で `H0` が満点となる小課題だけでは、得点の上昇による `H1` の採用は判断できません。その場合は、用途上必要な難しさを持つ改善課題を追加するか、品質を維持した費用削減を測る別の比較契約を用意します。差を作るために `H0` を弱めたり、同じ課題を大量に再実行したりしません。不正な候補しか生成できず終わった実行も、正しく現行維持を判断した実行と区別し、完了した比較の根拠には使いません。

採用可能なら `H1` を新しい実行で有効化し、次の改善課題を実行させます。候補を棄却したら `H0` を維持します。いずれも、候補生成から比較、判定、選ばれた版による次の実行までを確認します。ソースの書き換えだけで世代の切り替えを完了扱いにしません。

合成した失敗事例で、採用後に問題が分かった場合の復旧も確認します。直前の採用版へ戻せること、その後の別の変更を上書きしないこと、実際に使用する版と影響を受ける評価結果を特定できることを確かめます。既存の管理経路による有効化は、段階 0 で確認した実行環境と依頼範囲に従います。

最初の実装の完了条件は、この経路が実際に動くことです。自己改善の効果を示すには、未使用の改善課題でも `H1` が `H0` より有効で、その版を次の改善に使用できた証拠が必要です。採用できる候補が見つからない場合も基盤の動作確認とは区別し、原因を調べます。機能追加を続けることを、改善能力の向上の代わりにはしません。

### 段階 3：更新が蓄積するかを対照付きで調べる

採用した版が次の候補を作る経路を繰り返します。たとえば `H1` が `H2` の候補を作り、その改善能力を別の課題で確認します。実務へ反映する版は採用条件を満たすものに限り、探索では保存した過去の候補からの分岐も許します。世代ごとの改良を必ず成功させる目標にはせず、生成途中の候補を運用版へ自動的に昇格させません。

比較対象には、改善方法を `H0` に固定して対象スキルを改善する実行を置きます。総予算、開始状態、利用できる証拠をそろえ、自己更新を許す場合に、未使用の改善課題でより良い結果や効率が得られるかを調べます。固定するのは方法の版であり、対照にも同等に得られた実験記録を読む機会を与えます。自己更新の費用も総予算に含め、世代数や試行数だけの増加、モデル更新、課題の易化を自己改善の効果にしません。

対象を改善する能力が上がったことだけで、後継を生む能力まで上がったとは判断しません。後継の品質が、開始版と生成方法のどちらによるものかを調べる必要がある場合は、同じ開始版の改善機構を `H0` と `H1` にそれぞれ改良させます。生成した後継を固定して未使用課題で比較し、生成元の方法を変えた効果を確かめます。この対照では `H0` も後継のソースを変更できますが、生成中の方法は `H0` のままです。

ここでは、一度の候補採用に加え、その候補が次の有効な改善を生むか、効果が別の課題にも及ぶかを調べます。十分な証拠が得られなければ、停滞した箇所を診断します。候補の子孫が良い成績を出したという履歴は、再検討の手掛かりとして使い、比較条件をそろえた改善能力の検証の代わりにはしません。多数の系統を同時探索する基盤は、初版の逐次的な分岐探索で不足が確かめられてから検討します。

### 段階 4：実務とイベントを伴うワークフローへ広げる

比較と自己適用の基盤を使い、より広いスキルや実務の課題を扱います。App Server などのアダプターと合成ツールを追加して、第8節の途中指示、中断、再開を実行可能なケースにします。`agent-workflow-design` が生成する設計と、その設計で動く実行をそれぞれ観測します。

完了条件は、増やした対象でも評価条件と有効な版を追跡でき、実際の応答と外部状態で変更の効果を確認できることです。改善機構自身のイベント処理も同じ対象に含められます。模擬環境と実サービスの違いや、取り消せない副作用を評価に残します。

### 各段階で使う、改善能力の判定

改善能力は、課題ごとの同条件の比較で判断します。改善課題の生成や診断、対象の試行、採点、失敗した候補まで費用に含めます。共通の指標は、予算内で得られた対象の品質向上、維持すべき能力、採用可能な結果までの費用、必要な人の介入です。課題ごとの改善余地が異なるため、異なる課題の点数を無条件に足して総合能力とは呼びません。

改善機構を育てる費用と、育てた版を使う一件あたりの費用を区別して記録します。段階 2 では後者を条件をそろえて測り、候補の生成・検証に使った前者も併記します。段階 3 では自己更新への投資を含む総予算で対照と比較します。利用回数が未確定なら、局所的な効率向上だけで育成費用を回収できたとは判断しません。

改善機構を評価する場合は、候補生成に用いた改善課題とは別の課題群を用意します。各課題の中でも、探索用と最終確認用の対象ケースを分けます。つまり、答えが漏れないようにする対象には、個々の回答と、改善方法の選択に使う課題の両方があります。毎世代の選択に使った結果は探索の情報になり、未使用の最終評価として再利用しません。少数課題しか用意できない段階では探索的な結果として扱います。

知見を引き継ぐ場合は、何を変え、どの条件で効き、どこで失敗したかという再利用可能な内容を、版と根拠に結び付けます。最終評価の答えや、そのケースだけに通る修正を知見として埋め込みません。初版の記録だけで必要な知見を参照できるうちは、独立した記憶基盤は作りません。

知見は必要な箇所へ追加・修正できる単位で保持し、全文の要約で根拠や適用条件を失わないようにします。重複、反証、適用モデルの変化を整理し、検索と読み込みの費用も測ります。保存量の増加は改善の指標にせず、同じ失敗を減らす効果と維持費で判断します。

比較で扱う改善機構には、引き継いだ知見の版も含めます。方針の変更と知見の増加のどちらが効いたかを主張する場合は、共通の知見を与えるなど、寄与を区別できる比較を追加します。通常の採用判断では、実際に使う構成全体の結果を先に確かめます。

生成された指示そのものの揺れと、それを使う下流実行の揺れは区別します。作業用の評価器も改善対象にできますが、その評価器を判定する基準は候補の編集範囲から外します。評価契約を更新する必要がある場合は新しい比較として測り直し、異なる尺度の世代間スコアをそのまま接続しません。

改善方法自身を比較して選んだ版を次の実行へ渡す経路が動いたこと、改善能力の向上を観測したこと、それが複数世代で続くことは、それぞれ到達点として報告します。持続的な加速までは仮定しません。レビューや統合が律速になれば全体は速くならないため、局所的な効率だけでなく採用までの結果を測ります。活動量と実際の進歩の区別は、[OpenAI の研究加速に関する報告](https://openai.com/index/research-acceleration-view-inside-openai/)も参考になります。

## 10. スキルを使いやすくするための調整

日常運用では親が直接進行し、対象の試行を分離したまま、適用範囲を確認できる採点を小さくまとめます。[利用ノートのワークフロー](../notes/agent-eval-tools-use-cases.md#負担を抑えるワークフロー)に、依頼範囲による処理の違い、呼び出し数の試算、導入時の検証をまとめます。通常のケースに対する事前の呼び出し数表示と、`judgeBatchSize` で選ぶ一括採点は実装済みです。個別採点を既定とし、固定人数のチームや評価基準の省略を導入する方針ではありません。

一括化では校正と実際の採点を共通の形式にします。校正だけを一括にして実際の採点を個別にすると、確認した形式と使う形式がずれるためです。対象の実行は別々の文脈を保ち、判定を識別子で対応付け、欠落・重複・不正な応答の集合は採用の根拠にしません。個別採点と一括採点を同じ成果物・独立に確認した正解で比べ、誤判定、順序や同じ入力内の別回答による影響、未完了時の扱いを確かめて適用範囲を決めます。別実験の校正キャッシュ、モデルの変更、並列実行は同時に加えません。同品質での費用削減を自動採用する条件は、現行の品質改善による採用条件とは区別して実装・検証し、人数の削減だけを RSI の成果にはしません。

実装後は、次のような自然な依頼を使って、入口と参照構造を調整します。

- 「このスキルの修正で、前より良くなったか確かめて」
- 「結果が揺れるので、評価器に問題がないか調べて」
- 「この失敗を直しつつ、ほかのケースを悪化させないように改善して」
- 「処理の途中で指示を変えても、不要な作業を続けないか確認して」

調整の基準は、指示の短さだけではありません。依頼に適した評価対象を選べること、実行できるところまで進められること、不要な確認や参照読み込みが少ないこと、結果の限界を正しく説明できることを重視します。

description は、選ばれるべき依頼を短く具体的に示します。「あらゆる修正やレビュー」のように対象を広げず、既存の設計スキルと同じ依頼を無条件に奪い合わないようにします。名前を指定しない依頼を、関連するスキルが共存する条件で試し、必要な場面での選択と、通常の修正での不必要な選択を確かめます。

`SKILL.md` に全手順を詰め込まず、普通の一回比較には一回比較の情報だけを読み込みます。改善、モデル採点、イベントを伴う実行などの手順は、それが必要になった時点で読みます。サブエージェントも常設の必須工程にせず、独立した診断や判定が必要で、実行環境と権限が対応している場合に使います。参考資料のテンプレートにある段階ごとの停止や承認を、そのまま既定の進行にしません。

この使い勝手の調整も、単なる文面の好みで終わらせません。新しい会話に自然な依頼と必要な素材だけを渡し、期待する答えや想定した原因を教えずに試します。短い依頼から完了まで実行し、どこで対象の取り違え、過剰な手順、不要な停止が起きたかを根拠に直します。評価が簡単な場合は簡単に終わり、複雑な場合だけ詳細な手順へ進める構造を目指します。

### モデルと実行環境の更新に対応する

比較中は、利用するモデル・推論設定、ツール、指示と知見の版を維持します。役割別の設定は実行基盤が対応し、その違いを比較する必要がある場合に限って扱います。付属のホスト経路は継承設定のまま使い、設定の変更や詳細な使用量の取得を通常評価の前提にしません。モデルが更新されたら、新しい実験条件として基準を測り直します。製品名だけでは実モデルの版が分からない場合は、その不確実性を記録し、過去の結果と厳密に同条件とは扱いません。

新モデルでは、まず現在のハーネスを基準にし、観測した問題や不要になった補助に応じて候補を比較します。細かい手順を減らす版や、該当する補助を外す版も候補です。旧モデルも利用でき、モデルとハーネスの寄与を分ける必要がある場合は、両モデルで旧・新ハーネスを動かします。旧モデルと旧ハーネスの点数を、新モデルと新ハーネスの点数に直接比べて、自己改善の効果とは主張しません。

採点用モデルだけを替える場合も、固定した成果物を再採点して誤判定と揺れを確認し、評価の版を更新します。候補生成や採点を別のモデルへ配分する変更は、品質と総費用を同じ条件で比較します。新モデルの能力向上や安価なモデルへの転移を、公開研究の結果だけで前提にしません。

用途の要件、実行権限、検証できる成果、根拠のある領域知識は維持します。モデルの弱点を補う手順や補助指示は、必要性を測り直せる位置に置きます。モデル別の分岐は差が観測できた場合だけ追加し、初版から多数のモデルを試す必須行列は作りません。将来のモデルが何を得意にするかを予測して構造を固定せず、追加と削除の両方を評価できる構成にします。

実行環境に新しい能力が加わった場合は、アダプターの対応を更新し、版の有効化、イベント、停止、使用量の確認をやり直します。ホストの機能で置き換えられる補助コードも削除候補にできますが、同じ意味で動くことを確認してから切り替えます。CLI で確認した結果を、アプリや別の実行環境の確認として流用しません。

### 既存スキルと併用した状態で確かめる

責任分担を文書化し、新スキルの指示へ引き継ぎ条件を置くことは準備に当たります。[併用課題](../../evals/agent-eval-tools/agent-improve/README.md#既存スキルとの併用を確認する)では、通常の修正と能力目標からの改善設計を、凍結したカタログの構成違いで比べます。対象を明示した評価、カタログを渡した選択、設計段階の支援、実行完了までの引き継ぎ、導入先での自然な発見は別々に判断します。状態と次の順序は冒頭の[残作業](#完了状況と初版の残作業)で管理します。

新プラグイン単独と、関連する設計スキルが使える構成で、影響する依頼を確認します。併用構成では、スキル名を指定しない依頼での選択と、必要な参照を読み込んだ後の完了までを調べます。読み込んだ内容が実際に振る舞いへ影響したかは実行結果で判断し、記録できない読み込みは不明として残します。

既存用途への影響は、同じモデルと実行条件で、次の構成を段階的に比べます。

1. 既存スキルだけの構成で、通常の指示修正、設計レビュー、ワークフロー設計などの基準を確認する。
2. 既存スキルは変更せず、新プラグインを加えた構成で、同じ既存用途と改善実験を確認する。新スキルの追加だけでも、選択の競合や不要な処理が増えないかを調べる。
3. 既存側の修正が必要になった場合だけ、その候補版を新プラグインのある構成・ない構成で確認する。新プラグイン側の修正と同時に変えて、どちらが効いたか分からなくしない。

既存用途では、成果物の品質、依頼範囲の保持、不要な質問・手順、使用量を維持条件として定めます。重要な要件の退行を RSI 側の得点向上で相殺せず、判定の揺れや許容差を踏まえて維持を確認できない候補は共通版へ採用しません。共有する方法を変更可能にすることと、その変更を既存の通常利用へ直ちに反映することは区別します。

- 実務の失敗ログがなくても、能力目標と合成課題から改善探索を開始できる。
- 通常の一文修正やレビューだけの依頼を、不要な評価実験や自己改善へ拡張しない。
- 設計スキルの支援後も実験の目的と予算を保ち、候補一件の成功で依頼された探索を早期終了しない。
- 採用しなかった候補を探索用に残し、保守メモの整理で消さず、許可された追加試行に使える。
- 変更範囲に含めた診断用参照を改善でき、同時に、保護された評価や対象外の指示は変更しない。
- 評価だけの依頼や既に許可された改善で、不要な編集、再承認、同じ検査の重複を起こさない。
- 通常の対象を改善する依頼で自己改善を追加実行せず、蓄積した未検証の気付きが稼働中の指示へ混入しない。
- 後日、関係する記録を選んで自己改善を開始でき、証拠の欠落を確かな原因と取り違えず、記録整理の費用も計上できる。

呼び出しの競合や不必要な停止が見つかった場合は、入口、参照の適用条件、実験の完了条件のどこが原因かを特定して修正します。読み込み量や使用量の増加だけで併用を否定せず、改善の品質と費用をともに比較します。必要なら、該当する設計支援を使う条件と使わない条件を、権限と実行条件を保てる試験環境で比較します。実際に検証した構成と未検証の構成を分けて報告します。

## 11. リポジトリへの組み込みと検証

実装時の正本は `plugins/agent-eval-tools/` とします。既存の Agent Plugins 形式にあわせた `plugin.json`、英語の `README.md`、`skills/agent-improve/SKILL.md` と必要な参照・スクリプトを追加します。この改善スキルの保守に使う公開可能な評価素材と確認済みの証拠は `evals/agent-eval-tools/agent-improve/` に置き、設計理由と評価の説明は日本語の `docs/` へ残します。実行時に必要な契約を `docs/` だけへ置かず、配布物で完結させます。

[プラグイン配布物のテスト](../../scripts/plugin-packages.test.mjs)には、新プラグインの隔離実行、参照の到達性、`agent-improve` 一つという同梱スキル構成を追加します。現在の既存プラグイン向けの分岐を新プラグインへ流用せず、期待する構成を明示します。`package.json` のプラグイン検査対象、ルート README と `evals/README.md` の案内も更新します。

新プラグインはリポジトリ所有のソースとして扱い、ホーム由来の公開用エクスポート先である `home/.agents/` や `home/.codex/` に実装しません。CLI ランタイムを `tools/agent/` から移したり、評価処理を CLI の必須部分へ加えたりしません。候補の比較では隔離した配布物を使い、導入済みコピーや利用者の Marketplace 設定を変更しません。導入まで依頼された場合に、既存の管理方法に従って登録・有効化を行います。

ランナーの自動テストは、合成の実行アダプターを使います。設定の不一致、重複試行、再開、時間切れ、基盤エラー、採点エラー、予算到達、パスの逸脱を確認し、通常の検査で実モデルの利用費用を発生させない構成にします。実モデルによる評価は、対象と予算を定めた検証として別に実行します。

プラグインの配布検査と、スキルの品質評価は別の合格条件です。ファイル構成が正しいことだけで有効なスキルとは判断せず、品質の改善が見えたことだけで配布可能とも判断しません。

既存プラグインの入口や参照を調整した場合は、そちらの構造検査と影響する既存ケースも実行します。新プラグインがない構成で従来の設計・修正を完了できることと、第10節の併用確認を、初版の検証に含めます。

最初の実装範囲は段階 0 から段階 2 です。実行方法と記録契約を確かめながら、一つの改善機構で評価、対象の改善、自身への適用、次の実行への反映まで通します。その結果を使って段階 3 の継続的な自己改善を検証し、段階 4 で対象を広げます。後続段階のためだけの抽象化や依存は先に増やしません。
