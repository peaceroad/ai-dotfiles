# 実行スクリプトの確認と Claude 側との機能差

`agent-improve` は、範囲を定めて実務の評価・改善を試用する段階です。[計画の完了条件](../plans/agent-eval-tools.md#完了状況と初版の残作業)をすべて満たした意味ではありません。本書は、実行スクリプトの正しさ、負担、使いやすさを確認した記録です。スクリプトの構成の正本は[プラグイン README](../../plugins/agent-eval-tools/README.md#package-structure)、コマンドと対応範囲の正本は[実行参照](../../plugins/agent-eval-tools/skills/agent-improve/references/runtime.md)に置きます。

リポジトリだけに置く課題準備スクリプトは、[検証用素材の案内](../../evals/agent-eval-tools/agent-improve/README.md)で説明します。このノートには判断理由と確認結果を残し、ファイル一覧やコマンド仕様を重複して管理しません。

## 確認して修正したこと

配布する六つの実行モジュール、二つの制御テスト、リポジトリの四つの課題準備スクリプトとそのテスト、配布検査を確認しました。課題準備スクリプトは検証用の入力を作るもので、通常利用の前提でも、モデルを起動する処理でもありません。

- **JSON の誤判定。** `json-equals` が、回答の配列に対する `length` や文字列に対する文字位置を、回答に含まれる値として読めました。オブジェクトのメンバーと配列の添字だけを辿るよう修正し、不正な `~` エスケープは設定時に拒否します。根の値、空のキー、エスケープ、欠損、無効な JSON、Unicode の文字数を合成例で検査します。参照の解釈は [JSON Pointer の定義](https://www.rfc-editor.org/rfc/rfc6901.html#section-4)に照らして確認しました。
- **同じ回答の再解析。** 複数の検査項目がある場合も、JSON の解析と Unicode コードポイント数の走査は、それぞれ必要になった最初の一回だけ行います。文字数のために文字ごとの配列を作る処理も外しました。検査結果は項目別に保持します。
- **再開時の不要な構築。** 予約済みの候補生成要求がある場合は、その要求を再利用し、結局使わない探索履歴や方法の表示用データを再構築しません。新規の要求に渡す情報と、予約済み要求の本文は変更していません。
- **CLI の壊れたイベント。** JSON として読めてもイベントではない値で受信処理が例外終了する問題を修正しました。応答の型の誤りを実行異常として扱い、失敗の終了イベントと成功の終了イベントが混在しても成功にしません。これは合成イベントによる検査であり、CLI の認証・起動・プロセス停止の実地確認ではありません。
- **リンク経由のコマンド起動。** スキルをソースへ直接リンクした場合、起動パスと実ファイルの文字列比較によって、ランナーが何も出力せず終了する問題を修正しました。実ファイルのパスを解決して起動を判定し、ソースとディレクトリリンクの両方からヘルプと実行能力の表示を検査します。モジュールとして読み込む場合はコマンドを実行しません。
- **検証入力の上書き。** 汎用の `prepare.mjs` も他の準備スクリプトと同じく、新しい出力先を要求します。再実行で人が調整した実験設定を上書きしないこと、新規の設定を作れることを検査します。
- **配布テストの空実行。** 子の Node テストが親の内部ワーカー環境を引き継ぎ、テストを走らせず終了しても、終了コードだけでは成功扱いになり得ました。子の実行環境からその内部変数を外し、テスト件数が正であることも確認します。過去の配布テストの終了コードを、そのまま全制御テストの実行証拠にはできません。

誤判定と不正イベントは、修正前の実装で再現を確認してから直しました。確認には `npm run check:eval-tools` と `npm run check:plugins` を使い、後者ではリポジトリから切り離したコピーでも制御テストを実行します。新しい依存関係やモデル試行は追加しません。

## 過去の評価への影響と再確認

JSON 参照の不具合について、保存された対象応答・校正用応答を、当時の条件のまま旧処理と修正後の処理で照合しました。記録済みの項目別の合否・得点とも一致し、この不具合による採否の訂正は必要ありませんでした。使われていた参照は、JSON 文書全体またはオブジェクト内の実際の項目を指しており、配列の `length` や文字列の文字位置を合格条件にしていませんでした。

[prompt-design の現行維持](../../evals/agent-eval-tools/agent-improve/evidence/prompt-design-retain.json)、[初回の自己適用](../../evals/agent-eval-tools/agent-improve/evidence/self-application-retain.json)、[自身の候補の比較](../../evals/agent-eval-tools/agent-improve/evidence/self-candidate-comparison.json)の各公開記録についても、記載された元記録のハッシュとの対応を確認しました。意味による採点は JSON の項目照合を使わないため、この不具合の対象外です。モデル応答の再生成や意味採点の再判定はしておらず、それらの妥当性全体を再認定する確認ではありません。元の応答、採否、版の記録は変更していません。

さらに実行モジュールを読み直し、深く入れ子になった JSON の比較が再帰上限に達する場合を、明示的な作業リストによる比較へ置き換えました。宣言した参照ファイル名が `__proto__` などの場合も版の固定から脱落しないよう、ファイル名の辞書を修正しました。深い構造の一致・不一致、オブジェクトのキー順序、配列との区別、特殊なファイル名の保持と変更検出を合成テストで確認します。この補強後も保存済みの決定的な採点結果との一致を確認しました。

上記の境界処理の補強では、通常の要求の本文、モデルの実行数、採否条件は変えていません。二重実行防止、共有予算、受領時の識別子、採用時のソース競合検査を保ったまま、入力の境界を補強しています。新たなスクリプトや操作手順を配布物へ増やす変更ではありません。

その後の [pstack との照合](measurement-review.md#pstack-との照合)では、対象への定型文から不要な実験の説明を除きました。課題とスキルの内容を保ち、比較の目的や採点情報を渡さないことを合成テストで確認します。この変更を含む実行部分は別の版となるため、過去の実モデル結果を現行版の結果へ読み替えません。

## 負担を増やさないために維持した構造

負担を抑える設計では、モデルの実行回数と読み込む文脈を重視します。決定的な検査にはモデル採点を足さず、品質差の比較や再採点は必要な場合だけ使います。候補生成へ渡す方法の参照は役割に応じて選べます。完了した試行は再開で再実行せず、受領と再開を一つのコマンドにまとめられます。通常の入口は `agent-eval.mjs` 一つで、利用側が六つのモジュールを使い分ける必要はありません。

比較のたびに現行版も実行する処理は、同じ条件で候補と比べるために必要です。最初の現行版の応答を常に流用する最適化は採りません。また、モデル実行を一律に並列化すると、予約、共有予算、応答の対応付け、候補間の依存を変更する必要があります。単に担当数を増やす変更は行いません。

履歴には、後から親候補を選び、診断できるように各候補の内容を保持します。候補数や対象が大きくなれば、これが文脈を占める点は残ります。現状は候補数の上限と役割別の参照選択で範囲を絞ります。差分や内容辞書への置換は、候補を正しく復元して使えるかの行動確認を伴う別の変更として検討します。採点情報や必要な履歴を黙って削り、軽くなっただけで改善扱いにはしません。

今回削った再解析・再構築はローカル処理です。モデルへ渡す情報を削減した変更ではなく、トークンや料金が下がったという実測結果もありません。厳密な金額上限、役割別モデル、effort の変更は通常利用の前提にしません。

## Claude 側との機能差

2026年10月5日に Anthropic の公開 `build-eval`、`eval-audit`、`eval-hillclimb` と[紹介記事](https://claude.dev/blog/automating-eval-design-and-hillclimbing/)を再確認しました。参照先は変更され得る `main` 上の文書です。以下は機能・指示範囲の照合であり、両実装を同じ課題と予算で動かした性能比較ではありません。Claude 側の付属スクリプトをこのリポジトリへ移植したり、その内部実装を監査したりしたものでもありません。

- **アプリとの接続と結果の表示。** Claude 側の [build-eval](https://github.com/anthropics/skills/blob/main/skills/claude-api/shared/evals/build-eval.md) は既存アプリの実行経路、非テキスト入力、実行記録、複数指標を扱う評価器を整え、軽量 HTML レポートを生成する手順を持ちます。大きなビューアーは、そのファイルが利用できる場合の機能です。こちらの付属ランナーはテキスト注入と JSON の記録・要約に絞り、画像、ツール、実際のアプリ状態は適した外部ハーネスで評価します。HTML ビューアーは付属しません。
- **費用・遅延・実行設定の探索。** Claude 側の [hillclimb](https://github.com/anthropics/skills/blob/main/skills/claude-api/shared/evals/eval-hillclimb.md) は品質だけでなく費用、遅延、モデルや実行設定も改善候補にする手順を持ちます。こちらの付属ランナーは役割間で同じ設定を使い、品質改善を採用条件にします。利用回数と時間を区切れますが、料金や品質同等での費用削減を自動判定する機能はありません。
- **測定の柔軟さ。** Claude 側の [eval-audit](https://github.com/anthropics/skills/blob/main/skills/claude-api/shared/evals/eval-audit.md) は、アプリに合う指標、実行経路、再試行、実際の使用量の監査を求めます。こちらには決定的な条件、意味による合否、両順序の比較、同一応答の再採点、関連グループ単位の限定した採用判定を実装しています。任意の連続指標や効果量の信頼区間を扱う汎用統計基盤ではありません。
- **改善方法自身を比較する経路。** こちらは、改善方法の候補を同じ下流の改善課題へ渡し、外側の共有予算で比べ、選んだ版を次の実行へ渡す契約を持ちます。確認した Claude 側の手順は、固定した評価に対するアプリ改善を中心にしています。この違いは、Claude 側で自己適用を構築できないという意味でも、こちらが RSI を実証したという意味でもありません。

対象分野の広さと、付属ランナーが直接実行できる範囲は別です。実務では必要な成果物と観測を先に決め、現在のランナーで測れれば使い、測れなければ既存ハーネスへ接続します。この分担を初期の運用方針とし、実務での適合性を確かめます。表示機能や役割別の実行設定は、具体的な利用上の必要が生じたときに検討します。外部ハーネスを選ぶ方針と、その接続の実装・検証が済んでいることも区別します。

入口の `SKILL.md` は増やしていません。実地で残る確認、自己改善の仮説、公開・導入の判断は、[公開前確認](prepublication-review.md#残る条件と次の進め方)と計画で引き続き管理します。
