# agent-eval-tools の公開前確認

本書は、対象を改善する経路、変更不要なら維持する判断、自身への適用、選んだ方法を次の実行へ渡す経路を確認した履歴です。初回の記録と、その後の[評価方法の見直し](measurement-review.md)を経た[自己候補の追加比較](#自身の候補を比較した追加確認)は、異なる版の実験として区別します。記録した条件を超えて結果を流用せず、[計画](../plans/agent-eval-tools.md)の段階 0〜2 全体や RSI の成立を完了扱いにはしません。

その後の[実行スクリプトの確認](implementation-review.md)では、採点と CLI イベント処理、準備入力の保護、配布テストの実行確認を修正しました。以下のモデル応答と版の記録は当時の証拠として保持し、修正後の実行部分を実モデルで検証した記録へ置き換えません。

## 初回に確認したこと

[自己適用の課題](../../evals/agent-eval-tools/agent-improve/prepare-self-application.mjs)では、現行の改善方法 H0 を固定し、保持方針の移行と、変更不要のスキルの維持を内側の改善課題にしました。いずれも架空のレコードを分類する課題で、実際の削除は行いません。

- **必要な対象変更。** 旧方針を満たす合成スキルに、新しい保持期間、保留条件、承認の版と有効期限を反映する候補を生成しました。新方針のケースを満たし、別ケースで検査した既存動作を保ち、境界条件の確認にも通ったため、実験内では候補を採用しました。正本への反映は行っていません。
- **不要な対象変更の回避。** 現行方針のまま使う別課題では、開始時点の対象が条件を満たしました。変更候補を作らず、現行版を維持しました。
- **改善方法自身の判断。** H0 は、内側の二課題が採点上の上限に達し、方法の変更を支持する欠陥も示されていないとして停止しました。H1 は生成されておらず、H0 と H1 の比較結果ではありません。
- **次の実行への引き継ぎ。** 選んだ H0 と同一の方法のハッシュを確認し、別の文脈で [prompt-design の後続課題](../../evals/agent-eval-tools/agent-improve/followup-source-preservation.json)を実行しました。意味による採点器が二つの正例と一つの誤例を区別した後、生成された指示を合格と判定し、対象の変更も不要と判断しました。

後続課題で確認したのは、架空の資料の計測範囲、未計測、対象外、未確定の予定を保つ指示文です。その指示文を使った下流の要約実行は含みません。

自己適用は12件、後続課題は6件のワーカー実行で完了しました。各試行を新しいサブエージェントへ一件ずつ渡し、別の進行役は追加していません。この18件は、今回の複数段階の確認に使った数であり、各ワーカー内部や親のモデル呼び出しをすべて数えたものではありません。通常の一回の評価で必要な人数や呼び出し数を意味しません。

なお、変更不要の内側課題に対する外側の得点は 0 です。これは「合格ケース数の増加がない」という意味で、保持に失敗した意味ではありません。得点だけでなく内側の判定と停止理由を併せて読む必要があります。

## 初回に残した証拠と検査

[公開用の証拠](../../evals/agent-eval-tools/agent-improve/evidence/self-application-retain.json)には、今回の二実験に含まれる全18件の最終応答、対象候補、判定、対象と方法のハッシュ、課題定義への参照を残しました。最終応答の文字列は変更していません。生の記録から項目を選び、ローカルのパス、ホストの実行識別子、時刻、環境設定などを除外した抜粋であり、完全な実行記録や単独で再現できるアーカイブではありません。

評価対象は未コミットの作業ツリーから固定した版です。ファイルと課題定義の SHA-256 を残し、公開抜粋の作成時に現行ファイルとの一致を確認しました。確定した公開コミットに対する評価とは扱いません。生の契約と応答の受領記録は、継続して参照できるリポジトリ外の保持先に残しています。

モデルを使わない検査では、`npm run check:eval-tools` の53テストと、`npm run check:plugins` の配布物検証・6テストが通りました。追加した課題の期待値は、独立した方針実装と照合し、正解の別表現、各項目だけを誤らせた回答、自己適用全体の呼び出し予算も確認しています。自動テストの成功は、実モデルの一般的な能力の証拠とは区別します。

## 自身の候補を比較した追加確認

初回の停止経路に加え、現行方法 H0 が自身の参照を変更する候補 H1 を作り、両方法で同じ対象を改善し、選ばれた方法を後続の改善へ渡す経路を実モデルで確認しました。[追加比較の証拠](../../evals/agent-eval-tools/agent-improve/evidence/self-candidate-comparison.json)に、課題、候補、応答、判定、版の対応を残しています。

候補生成では、親が「対象の入口と参照にまたがる要件を整合させる」という能力目標と変更範囲を指定し、H0 と `prompt-design` を明示した新しい担当へ渡しました。生成された H1 は、要件が交わる判断箇所と、維持すべき隣接動作との境界を改訂の単位にする、という一段落を `references/improvement.md` に追加したものです。実際の欠陥を診断した結果ではなく、事前の能力仮説です。親が目標と課題を選んだ介入を記録し、保守メモから課題を自律的に発見したとは扱いません。

下流比較には、公開済みのキャッシュ方針の移行課題を使いました。H0 と H1 に、同じ開始状態、要件、編集可能な二ファイル、試行上限を渡しています。両方法とも、期限切れの再利用条件を追加し、認可や強制更新などの既存条件を保つ候補を生成しました。生成した指示を別の新しい担当で実行し、いずれも25項目の機械的な検査を満たしました。外側では追加の改善差が得られず、H1 を採用せず H0 を維持しました。

選んだ H0 と後続実験の方法のハッシュが一致することを確認し、保持方針の移行という別課題を実行しました。生成した対象候補は、下流実行で20項目を満たし、実験内では採用されました。対象の文章がもっともらしいかだけでなく、その文章を使った分類結果まで確認しています。実験用の対象や方法を正本へ反映したり、導入済みの版を切り替えたりする操作は含みません。

上限として定めた候補作成1件、方法比較8件、後続実行4件の計13件で終了しました。担当は順に新しい文脈で実行し、審査員や常設の調整役は追加していません。採点は JSON の値の照合で行いました。これはワーカーの実行数であり、各担当と親の全モデル呼び出し、トークン、料金を測定した数ではありません。

今回は候補比較と引き継ぎの動作確認に絞り、各課題の既存バッチを一つの探索ケースへまとめています。項目ごとの退行は個別の検査で拒否しますが、25項目を独立した25試行とは数えません。元のバッチ名に `selection` や `confirmation` が含まれていても、この比較では未使用の確認集合ではありません。同点は統計的な同等性の証明でも、H1 が一般に不要だという証明でもありません。今回の H0 の結果は、この課題の採点上の上限に達しました。得点では捉えられない品質差を、同じ採点の反復だけで判断することはできません。

H1 の仮説のうち、参照の読み込み時点に関する効果はテキスト束の注入では測れません。明示した設計支援から候補、比較、採否への引き継ぎは通りましたが、自然なスキル選択や読み取りイベントを独立に確認した試験ではありません。生の実行記録はリポジトリ外へ保持し、公開用の抜粋では最終応答を変更せず、環境固有の識別子や時刻などを除外しました。

採用を支持する差がなかったため、本体の `SKILL.md` と参照は現行のままにしました。公開前の確認項目を通常利用の指示へ追加する必要もありません。

## notes の運用との兼ね合い

`agent-workflow-design` の[保守記録の参照](../../plugins/agent-design-tools/skills/agent-workflow-design/references/maintenance-records.md)は、再検討に必要な情報だけを残し、項目や履歴を一律に増やさない方針になっています。編集スキル側の、必要な観察・証拠の参照・再検討の条件を選んで残す運用とも整合します。この確認では、既存スキルの指示は変更していません。

`metadata`、`overall`、`findings`、`unresolved` は、構造化した応答を受け取るときには便利ですが、保守メモの必須項目にする必要はありません。何が改善の手掛かりになるか、どこで根拠を確認できるか、どの場面で読み直すかが分かれば十分です。判断理由、状態、候補、採用・棄却の経緯は、後で使うものだけ追加します。共通の保存・再読ルールは所有者の案内へ一度書き、各メモでは繰り返しません。

比較や再開に必要な実験記録と、次の改善を考えるための短いメモは役割が異なります。メモに全文を複製せず、必要な証拠へ参照を張ります。通常の対象評価で手掛かりを残しても、改善方法自身の更新を毎回始めることはありません。[保存先の考え方](../notes/agents-notes-local-convention.md)も維持します。

## 残る条件と次の進め方

同じ課題の反復は結果の揺れを調べる材料にはなりますが、採点尺度に含まれない品質差は測れません。次の自己改善は、具体的な失敗や能力目標から、方法の変更が結果を変え得る課題を選んで進めます。今回の現行維持を覆すために候補を強制したり、現行方法を弱めたりする必要はありません。

追加確認で、能力目標から候補を生成し、比較後に現行版を残して後続実行へ渡す経路を通しました。保存した観察から親が原因や方向を教え直さずに課題を選ぶこと、方法の差を測れる実務課題での有効性、採用した新しい方法による改善能力の向上は未確認です。経路の確認と、それらの成立を区別します。

導入後の確認では、既存の[併用課題](../../evals/agent-eval-tools/agent-improve/coexistence-cases.json)を使い、スキル名を指定しない通常修正と改善依頼を新しい会話で試します。実際に選ばれたスキル、読み取りを観測できる参照、完了した成果物を確認します。カタログを手渡したり入口を明示した試験で代用せず、導入前の配布検査とも分けます。

自然なスキルの発見、ツールや途中イベントを伴う実行、保護された未見評価、費用だけの改善の採用は、引き続き現在の確認範囲外です。同系統の既知の合成課題と一つの後続課題から、一般化、費用削減、世代をまたぐ改善能力の向上は結論できません。観測できないバックエンドの版と使用量も、推定値で埋めていません。

公開時はこれらの範囲を実験的機能として示し、実務で必要になった比較から利用を始める方針です。計画の完了条件は維持し、通常運用のたびに自己適用まで実行する手順は加えません。
