# 評価方法の見直しと、汎用性を保つ方針

## 結論

`agent-improve` は、扱う専門分野を問わず、エージェントスキルやエージェントプラグインを評価・改善するための共通の入口にします。文書編集、プログラミング、デザイン、物理・数学、工学、経済などは、改善対象が扱う内容の例です。対応分野を列挙して限定する設計にはしません。対象の目的、分野固有の要件、専門知識、検証方法を引き継いで、変更が役立つかを確かめます。

付属ランナーは、固定したテキストを渡して応答を比較する実験を担当します。実行テスト、画面、外部状態などが成否を決める課題では、適したハーネスを使います。複数スキルやツールが協調するプラグインでは、その連携も評価対象です。対象分野を限定しないことと、付属ランナーだけですべての正しさを検証できることは区別します。

この見直しで重視したのは、機能数や参考実装の模倣より、用途上の差を測れること、根拠の弱い変更を採用しないこと、判断に不要な呼び出しを増やさないことです。実行時の正本は、配布物に含めた [measurement.md](../../plugins/agent-eval-tools/skills/agent-improve/references/measurement.md) と [runtime.md](../../plugins/agent-eval-tools/skills/agent-improve/references/runtime.md) にあります。

## 前の判断で不足していた点

計画には、意味による採点、揺れ、保持条件、費用、自己適用を含めていました。しかし、実装では固定した条件の実行、記録、再開、予算と自己適用の経路が先行し、評価尺度の十分さを同じ強さで確認できていませんでした。合成応答による制御の検査と、少数の実モデル試行で経路が通ることを、用途上の評価能力の完成と混同しかけた点が問題です。

たとえば、二つの応答がどちらも必須条件を満たすとき、二値の合否だけでは質の差を測れません。また、複数の検査をまとめたケースが両版とも不合格なら、一つの既存条件が新たに壊れたことを見逃す実装でした。これらは、さらに実運用を待たなくても設計とコードから発見できる不足です。研究を追加で読むだけでは、要求と実装・試験の対応が抜ける問題は解消しません。

以後は「制御が正しい」「評価器が妥当」「対象が改善した」「改善方法が強くなった」を別々の主張として、実装と観測結果に対応付けます。計画の段階 0〜2 の完了条件は維持します。

## 今回実装したこと

- **保持条件を細かく検査する。** ケース全体が両版とも失敗していても、以前通った決定的な検査が新たに落ちたら採用を拒否します。
- **比較採点を任意で使う。** 必須条件を先に確認し、そのうえで品質の差が問題になる場合だけ比較します。版名を伏せ、同じ回答を両順序で採点し、同等、両方不適切、判断不能を区別します。順序で判定が変わったら未確定とします。
- **同一成果物への再採点を使える。** 対象を再生成せずに意味採点の不一致を調べられます。対象の揺れ、採点の揺れ、生成した指示の下流実行の揺れを区別します。
- **小標本から過大な結論を出さない。** 比較採点の自動採用を使う場合、反復をケース内、関連ケースをグループ内で集約します。観測された差とグループ単位の符号検定を採用条件にします。探索を伴う改善には未使用の確認群も必要です。これは効果量の信頼区間や、保護された未見評価の代用ではありません。
- **判断保留も使える。** 小さい探索にはレビュー用の比較を選べます。比較結果を保存しても自動採用せず、候補と根拠を別途検討できます。後から閾値を緩めて同じ記録を採用扱いにすることはしません。
- **実行数を先に見積もる。** 校正、対象、生成、比較の両順序、再採点を依頼数の計画へ含めます。トークンや金額の見積もりではありません。必須条件に失敗した候補への任意の比較採点は省きます。決定的な検査だけで答えが出る課題に、モデル採点を足しません。

合成テストは、判定の不一致、校正の誤り、途中の予算切れ、関連ケースの水増し、細目の退行、ホスト経由の中断・再開、確認群で支持されない候補の不採用を検査します。実モデルの採点精度や他方式との性能差を証明する試験とは区別します。以前の[公開前確認](prepublication-review.md)の実モデル結果は、そこで記録した版に対する履歴として残します。

## 領域を狭めず、実行を増やしすぎない

コードの正しさを調べるなら、既存のテストや型検査、結果のファイルが主要な証拠です。ルール適用なら正解付きの境界条件、画面設計なら実際の画面や操作、設計判断なら要求と制約への適合を確認します。文章の好みを比べる手順を、これらすべてに適用しません。

共通化するのは、版、初期状態、課題、採否条件、費用、証拠の対応付けです。プロジェクトのハーネスが必要な観測をすでに行えるなら再利用し、付属ランナーの記録へ無理に変換しません。外部ハーネスの手順を用意したことと、そのハーネスで実行検証を済ませたことも区別します。

小さい予算で自動採用までの証拠が集まらない場合は、範囲を絞った比較や既存成果物の検査で終える判断ができます。採点者を常設で増やすこと、すべての課題を二重採点すること、評価するたびに評価スキル自身を改善することは既定にしません。評価器の現在の欠陥は修正しつつ、共有の改善方法を育てる実験は必要なときに別の予算で行います。

## 一次資料との照合と独立実装

Anthropic の[評価設計と hillclimbing の記事](https://claude.dev/blog/automating-eval-design-and-hillclimbing/)と公開スキルは、評価が改善を導くための参考資料です。今回の指示、比較処理、設定形式、テストはこのリポジトリの契約から作成し、公開スキルの文章、コード、テンプレートの移植や翻訳は行いません。

併せて、次の別系統の資料から設計を確認しました。

- **Inspect。** [採点器](https://inspect.aisi.org.uk/scorers.html)、[指標](https://inspect.aisi.org.uk/metrics.html)、[再採点の手順](https://inspect.aisi.org.uk/scoring-workflow.html)は、対象に合う判定法、関連する観測の扱い、生成済み応答を使った採点器の検討を確認する資料です。本実装に Inspect のコードや依存関係を追加する理由にはしません。
- **採点のバイアス研究。** [Judging the Judges, v9](https://arxiv.org/abs/2406.07791v9)は、順序の影響が採点モデルや課題によって異なることを報告しています。両順序の一致を確認する理由になりますが、一致した判定の正しさを保証する研究とは解釈しません。今回参照したのは公開要旨の結果と研究範囲です。
- **改善探索。** [GEPA, v2](https://arxiv.org/abs/2507.19457v2)の公開要旨は、実行からの言語的なフィードバックと候補の系譜を使う方向を確認する資料です。報告された性能や費用削減を、本プラグインに移し替えて主張しません。
- **RSI。** [STOP](https://arxiv.org/abs/2310.02304v3) と [Hyperagents](https://arxiv.org/abs/2603.19461v1) から得た、改善方法も対象にし、その効果を下流の改善課題で測る設計は維持します。読んだ範囲と解釈は[研究ノート](../notes/agent-rsi-research.md)で管理します。採点の補強だけを RSI の実証にはしません。

確認した `claude-api` スキルの [LICENSE.txt](https://raw.githubusercontent.com/anthropics/skills/main/skills/claude-api/LICENSE.txt) は Apache License 2.0 です。実際にその著作物を組み込んで配布する場合は、ライセンスの写し、変更表示、通知の保持など同ライセンスの条件を確認する必要があります。本件は参考文献としての参照にとどめる方針です。別の論文も読んだという事実が、取り込んだ表現やコードの義務を消すわけではありません。また、原資料を読んでいるため、未接触のクリーンルーム開発とは称しません。

### 資料の役割と、2026年10月5日時点の追加照合

Inspect と順序バイアス研究を選んだ理由は、実装で判明した測定上の不足に対応するためです。Inspect は[公式の引用情報では2024年5月公開](https://inspect.aisi.org.uk/)の評価基盤であり、今回は現行の公式文書を参照しました。Judging the Judges は2024年の初稿、参照した v9 は2025年11月の改訂です。いずれも、2026年10月の最新研究であることを採用理由にはしていません。STOP と Hyperagents が自己改善の構造を検討する資料であるのに対し、これらは評価の実装と信頼性を検討する資料です。

直近の動向について、次の一次資料も追加で確認しました。網羅的な最新レビューや、本プラグインの性能を実証する資料とは位置付けません。

- [Agent Evaluation Reliability, v1](https://arxiv.org/html/2610.00651v1)（2026年9月30日投稿）。測定対象の定義、分散の分解、反復で減らせる不確かさ、限界の説明を確認しました。モデル単体とモデル・ハーネスの組み合わせでは、評価結果から言えることが異なります。本計画では、どのプラグイン構成をどのモデル上で改善した結果なのかを明示する理由になります。同様の課題を増やすだけであらゆる不確かさが消えるとは扱いません。
- [Certified Selective Automation of LLM Agent Evaluation, v1](https://arxiv.org/html/2609.34320v1)（2026年9月28日投稿）。課題単位の相関を扱う校正手順と限界を確認しました。自動判定できる範囲と誤りを一緒に評価する方向ですが、提案手法は有限標本での一般保証ではなく、訓練の乱数による変動も別の問題です。現行の符号検定にこの論文の保証を適用したり、直ちに自動校正機能を追加したりはしません。
- [AgentJudgeBench, v1](https://arxiv.org/abs/2608.26623v1)（2026年8月27日投稿）。今回は要旨と研究範囲を確認しました。依存関係を持つツール実行の評価を扱い、文章の好みの比較とは異なる課題です。これを踏まえても、プラグイン全体の改善では連携や結果状態を観測し、テキスト採点だけで完了としない方針を保ちます。

既存の研究から使う設計原則、現在保守されている評価基盤の実装、最近投稿された手法の検証状況を分けて扱います。新しい論文を採用機能の一覧へ直結させず、対象の改善判断に必要な観測と費用に照らして選びます。

### OpenAI の実務資料との照合

2026年10月5日に、OpenAI の公式記事と Cookbook も確認しました。以前参照した2本に加え、次の資料を現行の設計と照合しています。Cookbook は方法の実装例、開発者ブログは運用指針、製品発表は実行基盤の動向として読み、RSI の実証論文とは区別します。本文の設計説明を確認したもので、サンプルを実行したり、そのコードを取り込んだりはしていません。

- [Build an Agent Improvement Loop with Traces, Evals, and Codex](https://developers.openai.com/cookbook/examples/agents_sdk/agent_improvement_loop)（5月12日）。実行記録、専門家やモデルのフィードバック、評価、改善案を接続する例です。ハーネスの対象には指示だけでなく、ツールや振り分け、出力の要件も含まれます。例の採点は保存済みの出力に対して行われ、変更後のエージェントを検証するには、その版を実行する接続先が必要だと説明されています。本設計でも、記録から評価課題を作ること、採点器を調べること、候補の改善を実証することを区別します。Promptfoo や HALO はこの例の構成要素であり、本プラグインの依存関係にはしません。
- [Build iterative repair loops with Codex](https://developers.openai.com/cookbook/examples/codex/build_iterative_repair_loops_with_codex)（5月11日）。修正後の実行結果と残る問題を次の入力に戻し、成功、予算、進展の停止などで終える構造を確認しました。扱う成果物や検証方法は分野で変わります。成果物を直すループを動かせることだけでは、改善方法自身が育ったことにはならないため、本計画の下流の改善課題による比較は維持します。
- [Testing Agent Skills Systematically with Evals](https://developers.openai.com/blog/eval-skills)（1月22日）。入口で選ばれるか、実際に何をしたか、何ができたかを観測し、小さな重要条件から評価する方法です。自然な発見と明示的な指示投入を区別する現行の契約に対応します。ただし、記事中のケース数やコマンド検査を普遍的な必須手順とはしません。過去の実行順序を正解に固定すると、同じ目的をより良く達成する候補を誤って退ける場合があります。
- [Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)（9月11日）と [Iterating Development Workflows with Codex](https://developers.openai.com/cookbook/examples/codex/iterating-development-workflows-with-codex)（8月3日）も再確認しました。参照の条件付け、知見の反映先、実務の証拠、モデル更新後の指示の削減は引き続き参考になります。長いファイル構成や全段階の確認を、このプラグインの標準手順へ移植する理由にはしません。

5月29日の [A shared playbook for trustworthy third party evaluations](https://openai.com/index/trustworthy-third-party-evaluations-foundations/) は、比較したい主張に合うハーネスを選び、条件と評価の妥当性を示す必要を説明しています。これは、本プラグインのテキスト比較から実際のツール連携まで検証済みと推定しない理由になります。9月10日の [Agents API の発表](https://openai.com/index/introducing-the-agents-api/)では、モデルとともに進化するハーネスと実行環境を提供する方向が示されています。そこから本設計では、モデル実行や文脈管理を抱え込まず、既存ホストや適したハーネスを使い、評価条件と証拠を管理する役割を保つと判断します。API への移行を必要条件にはしません。

この照合で実行時の指示に補ったのは、実務の記録から課題を作るときの事実と原因仮説の区別、正当な別手順を許すこと、保存済み出力の再採点と変更版の実行を混同しないことです。モデル更新時に不要な手順を削る候補、判断に必要な分だけ実行する予算、自己改善を下流の成果で測る契約はすでにあり、維持します。資料の追加を、新たな常設エージェントや毎回の自己改善工程の追加には結び付けません。

### Google と Anthropic の研究・実務資料との照合

同じく2026年10月5日に、Google Research、Google DeepMind、Anthropic の資料を追加確認しました。Inspect と採点バイアス研究は測定方法、STOP と Hyperagents は改善方法の自己適用、以下の資料は実行の配分、知見の再利用、モデル進化への対応を検討するために参照します。資料は、答えたい問いに応じて選んでいます。

- **複数エージェントの効果は、課題と連携方法に依存する。** Google Research の [Towards a science of scaling agent systems](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/)（1月28日）と[論文 v3](https://arxiv.org/html/2512.08296v3)（4月8日改訂）を確認しました。並行して分解できる課題と、逐次の依存が強い課題では連携の利得が異なり、連携自体にも費用がかかります。ブログと改訂論文では実験範囲が異なるため、数値を混ぜません。参照したのは要旨、実験設定、予算をそろえた比較と限界です。本設計では常設の役割を増やす根拠にせず、必要な構成を比較する理由にします。一つの課題を協力して解く研究なので、比較評価の独立試行を省く根拠にも、一律のエージェント数上限にもなりません。
- **成功と失敗から、次の仕事に使える知見を得る。** Google Research の [ReasoningBank](https://research.google/blog/reasoningbank-enabling-agents-to-learn-from-experience/)（4月21日）と[論文 v2](https://arxiv.org/html/2509.25140v2)（3月16日改訂）の方法、費用分析、限界を確認しました。実行をそのまま蓄積するだけでなく、成功・失敗から抽出した知見を後続の課題で利用します。一方、自己判定の誤りや記憶のノイズがあり、行動の手数が減っても、判定と知見抽出を含む総トークンは増える例が示されています。本設計の選択的な知見保存を検討する資料ですが、毎回の抽出が最適とも、知見の追加だけで改善方法自身が強くなるとも結論付けません。
- **対象分野の広さは、適切な検証手段と組み合わせる。** DeepMind の [AlphaEvolve の設計説明](https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/)（2025年5月14日）と[応用報告](https://deepmind.google/blog/alphaevolve-impact/)（2026年5月7日）を確認しました。プログラム候補、実行可能な評価、候補の保持と選択を組み合わせ、数学や科学、計算基盤などに適用する方向は、本プラグインを特定分野に限定しない考えと整合します。ただし、本プラグインが同じ成果を出せる証拠ではなく、個別の応用研究も再検証していません。アルゴリズムや AI 基盤の改良と、後継の改善方法を生む能力の向上も区別します。
- **モデルの進化に合わせて、不要になった仕組みを外す。** Anthropic の [Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)（3月24日）は、生成役と評価役の分離、評価の校正、モデル更新後に構成要素を一つずつ外して調べる方法を説明しています。役割を固定して増やす根拠ではありません。掲載例は作業範囲や費用がそろった比較ではないため、構成全体の一般的な優位性は推定しません。[Infrastructure noise](https://www.anthropic.com/engineering/infrastructure-noise)（2月5日）は、計算資源や制限の違いが結果を変えることを示します。対象・モデルだけでなく実行条件をそろえ、基盤の失敗を区別する現行の契約を支える資料です。

これらは既存の参考資料を置き換える順位表ではありません。改善方法の自己適用、評価の妥当性、記憶の有用性、協調の費用は別の問いです。それぞれに合う根拠を組み合わせます。

### 完了までの費用と effort の扱い

提示された [What a task costs on Opus 5.5](https://claude.dev/blog/what-a-task-costs-on-opus-5-5/) と [Spending your effort](https://claude.dev/blog/spending-your-effort/)（ともに2026年9月25日）は、今回の運用設計に直接役立ちます。前者は、会話の継続、キャッシュ、出力、再試行などを含めて仕事の費用を見る説明です。料金表と例示的な使用量による試算を含み、購読契約での実請求や、あらゆる仕事での実測値ではありません。後者は、effort が検証量だけでなく、判断の範囲や前提の補い方にも影響し得ることを、作業例と内部ベンチマークから示しています。個別の作業例、測定条件の異なる比較、モデルによる失敗分類を含むため、すべてのモデルで同じ設定が最適とは解釈しません。

この照合から、実行時の測定指針に次を補いました。

- **同じ完成条件で費用を比べる。** 品質、作業範囲、人が補う条件をそろえ、失敗した試行、再試行、検証、連携、知見の整理も該当する予算に含めます。呼び出し数や行動の手数の削減だけを費用削減とはしません。完了の質と費用を併記し、改善実験の費用と、その後に一仕事を行う費用を分けます。
- **計測していない費用を埋めない。** トークン、経過時間、人の作業、金額は同じ尺度ではありません。金額を見積もるなら、提供者の使用量区分と日付のある単価を使います。API の試算を購読料金や利用枠の消費と同一視しません。
- **実行の配分も比較できるようにする。** モデル、effort、役割分担、追加検証へ進む条件は、実行基盤が制御できる範囲で改善候補にできます。比較前に方針を固定し、完成条件を変えずに確かめます。記事中の「低い effort で作り、高い effort で検証する」という運用例や、特定モデルの推奨設定を、このスキルの常設手順にはしません。同じ effort 名でもモデル間で計算量が同じとは限りません。

配分を改善できることは、RSI に向けた改善方法の候補になります。その価値は、同じ予算で有効な改善をより多く生むか、品質を保って費用を減らすかという下流の比較で測ります。今回追加したのは測定指針と判断の根拠です。役割別のモデル設定や、自動の配分最適化を付属ランナーに実装したわけではありません。研究・記事の文章、コード、設定を取り込む方針も採りません。

### 制御・計測できない環境でも使える範囲

通常の品質評価に、推論レベルの変更、役割別モデル、詳細なトークンや料金の取得は必要ありません。取得できない情報を埋めるために、ログ収集や課金連携を追加する設計にもしていません。比較中は利用可能な設定を維持し、試行数と経過時間で作業を区切り、評価結果を比べます。「同じ予算」と記す場合も、そろえたのが試行数なのか、時間なのか、実測トークンなのかを明示し、同じ計算量や金額だったと読み替えません。

付属のホストアダプターは設定の継承だけを契約にしており、ホストのツール自体にモデルや effort の指定引数があっても、この経路では上書きしません。`maxCalls` が数えるのはワーカーへの依頼であり、その内部のモデル呼び出しや親の全作業ではありません。使用量が取得できない場合は、開始時に任意の `maxTokens` を設定せず、必須の回数・時間の設定を使います。すでに合意したトークン制限を途中で外す意味ではなく、厳密なトークン・金額の上限が必要なら、それを実現できる実行基盤が必要です。コマンドと停止条件の正本は [runtime.md](../../plugins/agent-eval-tools/skills/agent-improve/references/runtime.md) と [host-execution.md](../../plugins/agent-eval-tools/skills/agent-improve/references/host-execution.md) に置きます。

回数が減ったことは回数の削減として記録し、料金やトークンが減ったと推測して採用しません。費用削減そのものが目的なら、その指標を測れる範囲で判断します。測れない費用上の効果は未確認として残せるため、通常の品質改善まで止める必要はありません。この区別を入口の指示にも反映し、研究で扱う制御能力を、すべての実行環境への必須要件にしないようにしました。

今回補ったのは、[評価手順](https://github.com/cursor/plugins/blob/main/pstack/skills/poteto-mode/playbooks/eval.md)が具体化している、対象へ渡す文脈と評価用の情報の分離です。付属ランナーは採点基準や比較の識別情報を対象入力から分離していましたが、定型文に残っていた実験についての説明を除き、比較用参照にも通常利用に近い依頼を保つ指針を加えました。課題本文やスキル内の正当な評価用語は削りません。これは不要な手掛かりを減らす変更であり、応答品質への効果を測定した結果ではありません。転送に使うパスやホストの継承文脈まで隠せる保証、自然なスキル発見の実証も含みません。

文章、コード、テンプレートの移植は行わず、設計の参考として記録します。入口の `SKILL.md`、サブエージェント数、モデル設定の必須条件は増やしていません。
