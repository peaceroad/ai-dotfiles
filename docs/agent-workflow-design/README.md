## 採用した構成と判断

本文は「契約を定める」「制御の形を選ぶ」「意味のある状態変化を定める」「制御の担当を決める」「影響する動作を検証する」という設計上の判断を入口にした。順番どおりの儀式や二重の確認一覧にはしない。既存ランタイムを使い、モデルが判断する部分と、実装が強制する必要のある部分を分ける。

| 改訂した点 | 狙いと残した条件 |
| --- | --- |
| 既存の許可を引き継ぐ | 保存場所の新設や公開・更新という操作名だけで再確認を要求しない。依頼の範囲、有効な承認、実際のランタイム制約で判断する。追加承認が必要なら、許可済みの作業で具体的なレビュー対象を用意する。 |
| 進行・待機・終了を区別する | 結果が揃った仕事から進める。無変化の継続中を失敗や停滞とみなさず、ランタイムへ待機を委ねる。監視の目的が終わったら監視を終える。 |
| 途中指示と外部操作を別に扱う | 追加質問で元の目的を失わず、依頼変更時には古い結果の有効性を再判断する。指示の受信・適用・キャンセル成功を区別し、縮小後の依頼の完了と残存ジョブの状態を分ける。 |
| 結果不明からの復帰を契約で決める | 状態照合に加え、検証済みの同一IDによる再送保証を利用できる。別IDでの再実行、古い更新の遅着、補償操作の権限を区別する。 |
| 検証を変更に合わせる | 必須チェックを残し、関連する失敗・既存動作・新規入力を選ぶ。主観的な品質だからと一律に人の承認へ送らず、判断の質、影響、可逆性などで選ぶ。 |
| 改善対象を実行証拠から診断する | 既存規則があるだけで単発ミスと決めず、実効版・読込経路・適用条件を確認する。旧モデルのための補助手順は寄与を再検討する。評価器や承認条件を弱めて自己採点しない。 |
| 保守メモを専用参照へ分離する | 通常の設計時に候補・判断記録の細則を読む必要をなくす。保存の許可、担当者、重複統合、候補の整理、独立した監査保存は維持する。 |

3つの既存参照のファイル名は維持し、[maintenance-records.md](../../plugins/agent-design-tools/skills/agent-workflow-design/references/maintenance-records.md)を追加した。`agent-improvement-and-rsi.md`は通常のハーネス保守を主題にし、AI研究・モデル開発に関わる再帰的改善との区別だけを必要な位置に残した。別モデルの過去の分類を、Astraの能力や安全性の根拠にはしない。任意の保守メモ用テンプレートは内容を変更していない。

`SKILL.md`は11,440バイトから8,091バイトへ縮小した。これはファイルサイズの比較であり、トークン消費、実行速度、品質の改善率を測った値ではない。説明を削るだけでなく、実行時の判断に必要な区別を優先し、用途限定の細則を参照へ移した。

## 評価と採用の根拠

旧版と初回候補を別の固定ディレクトリへ保存し、同じ5件の依頼から設計を生成した。各版は3件と2件の2つの独立した実行文脈へ分けた。したがって、5件は5回の独立した反復測定ではない。設計担当には依頼文だけを渡し、判定条件、継続イベント、別試行の結果は読まないよう指定した。

| 依頼 | 旧版と初回候補で確認したこと |
| --- | --- |
| 許可済みの評価保存と社内登録 | 両方とも保存場所新設の再確認を要求せず、許可済み登録と社外公開の境界を維持した。 |
| 非同期の納品状況確認 | 両方とも先着結果を使い、無変化時に待機できる設計だった。依頼縮小と残存ジョブの区別には説明上の不足が残った。 |
| 結果不明のプレビュー更新 | 両方とも同一IDの保証を利用し、版変更・キャンセル不能・サンドボックス拒否を扱った。旧版の失敗とは言えない。 |
| 主観的な草稿改善と検証範囲 | 両方とも必須コマンドを保持し、毎段落の承認を要求せず、影響範囲に検証を絞った。 |
| 取得済み承認を再度求めたエージェントの保守 | 両方とも読み込まれた規則を診断対象とし、許可済みのローカル修正と運用反映のレビューを分けた。 |

次に、生成した設計だけを読む別の実行者へ、納品状況確認とプレビュー更新の各3局面を提示した。新旧それぞれ計6局面で、次の行動は依頼と提示された契約に合っていた。ただし、両方の実行者が、A社だけで完了する依頼変更の扱いを設計外の追加指示から補ったと明記した。候補側にも広すぎるキャンセルの表現があったため、最新の依頼範囲での完了と外部操作の寿命を区別する一般則を参照へ追記した。これを最終候補の`candidate-v2`とし、納品状況確認だけを改めて生成・継続確認する対象にした。

また、初回候補の固定後に用意した共有保守メモの新規依頼では、設計だけという範囲を守り、共通規則の担当者への集約、重複統合、現行規則への反映確認、候補整理と監査保存の分離を満たした。この試行が読んだ本文と保守メモ参照は最終候補と同一である。ただし、評価側が読み込み対象をこの2ファイルに限定しており、自律的な参照選択や読み込み量の適切さを測った試行ではない。

最終候補の限定再試行でも、先着結果の整理、無変化時の待機、A社分だけでの完了を判断できた。広すぎるキャンセルの表現は再生成された設計に現れなかったが、監視解除や遅着通知を抑止する具体的なAPIまでは提示されていない。生成設計は依頼縮小の局面を列挙しておらず、実行者は現在の目的を照合する規則と追加指示から判断している。この一般則を残し、特定の継続イベントを毎回列挙する手順は追加しない。1回の再試行による差を、改訂だけに帰属させない。

構造検証には`quick_validate.py`と`npm run check:plugins`を使用した。ローカル参照の存在、保存版のハッシュ、差分の空白エラーも確認した。実行記録は[評価ディレクトリ](../../evals/agent-design-tools/agent-workflow-design/)、判定は[results.json](../../evals/agent-design-tools/agent-workflow-design/results.json)、対象版・設定と証拠の対応は[manifest.json](../../evals/agent-design-tools/agent-workflow-design/manifest.json)を参照する。

## 限界と保守方針

これは現在のCodexセッションからAstraを継承した少数試行である。旧モデルとの比較、統計的な優越性、最適性は検証していない。設計生成と机上の継続確認は、実ランタイムでの待機・キャンセル・永続化・外部更新・権限強制の試験ではない。判定は主担当による定性的な確認であり、文脈分離も指示による運用で、アクセス制御による隔離ではない。

採用理由は、現在のモデルが使う際の責任分担と適用条件を整理し、選んだ依頼で良い動作を保ち、具体的に見つかった曖昧さを修正したことにある。旧版も多くの依頼を正しく扱っており、改訂による成功率の向上は主張しない。今後の実作業で、不要な確認、待機の誤判断、過剰な検証、再開時の重複などの具体的な証拠が得られたときに、担当する層を再検討する。継続監視や評価の定期実行は今回追加していない。

評価時点のソースと生成結果を保存し、後続編集のために既存manifestの対象ハッシュを書き換えない。ソースの変更はローカルのスキルリンクを通じて利用される。`prompt-design`と編集中のGemini参照は今回の変更対象に含めていない。
