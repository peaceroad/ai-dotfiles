# agent-workflow-design の再監査

この文書は9月6日の比較と採用判断を保存した記録です。その後の[Astra公式ブログとの照合と評価参照の補強](../prompt-design/astra-blog-review.md)は9月12日に行いました。下記の候補、サイズ、件数、判定を最新の指示の動作証拠へ置き換えていません。

2026年9月6日。初回改訂の採用版`candidate-v2`を基準に、使いやすさと冗長さを再確認した。対象は本文、4参照、UIメタデータ、任意の保守メモ用テンプレート。`prompt-design`と`skill-creator`との役割分担、設定を選ぶ裁量、実行時の状態と権限、記録の扱い、出力の詳しさ、評価の限界を確認した。

前回は長さを減らして主要な動作を比較したが、冗長さと適用条件を十分に整理し切れてはいなかった。再監査では次の変更を採用した。

| 確認した点 | 判断と変更 |
| --- | --- |
| 制御の担当表 | 「ツール選択」をツール定義・実装の側へ置いた分類は不正確だった。許可された範囲でのツール・引数の選択と意味の評価をモデルへ、引数の受入条件・許される効果・再送保証をツール契約と実装へ分けた。 |
| 本文と参照の重複 | 承認の基本、変更に応じた検証、評価者の独立性、評価結果の報告、別モデル事例の留保が繰り返されていた。主な説明場所を定め、他の箇所は具体的な適用条件か参照リンクにした。 |
| 設計の初期値 | 数値を「作らない」という表現には、利用者が初期値の設計を依頼した場合まで抑える読み方があった。依頼に設定選択が含まれる場合だけ、対象の設定値を理由付きの変更可能な提案として示す。通常の改善は既存設定か進展条件で止める。 |
| 任意テンプレート | `human-reviewed`は一律の人の確認と読める余地があった。記録の担当者が定めるレビューへ置き換えた。候補の整理と独立した監査資料の保存も明確に分けた。実際に採用済みの利用者側の規約は変更していない。 |

設定値の条件には途中の失敗がある。初回の短縮候補`candidate-v3`では「設計に新しい設定が必要なら提案する」と広く書いた。その試行では、タイムアウトと再試行数を求めた検索設計に追加の全呼び出し上限を設け、小さな議事録レビューにも「修正は1回まで」を提案した。後者は、有用な修正まで途中で止めるおそれがある。設定を選ぶ依頼と通常の改善を区別する条件へ絞り、`candidate-v4`で同じ2件を再確認する対象とした。

## 短縮と意味の保持

`SKILL.md`は前回版の8,091バイトから6,065バイトへ約25％、本文と4参照の合計は43,101バイトから36,334バイトへ約16％減った。これはUTF-8ファイルサイズの比較であり、実行時のトークンや速度、品質の改善率ではない。

短縮後も、次の判断が残ることを本文と参照で照合した。

- 既存の許可を引き継ぎ、追加の許可が必要な作業だけを止める。実際の拒否や承認境界は維持する。
- 部分結果から進行し、無変化時は待機する。途中の質問、依頼縮小、残存ジョブ、遅着結果を区別する。
- 結果不明の外部操作は状態照合か検証済みの再送保証で扱う。別IDでの重複や競合する更新を防ぐ責任を実装へ置く。
- 必須チェックと意味の評価を保ち、主観的な判断のすべてを人や別エージェントへ送らない。
- 改善では実効版・読込経路・原因を確認し、受け入れ条件、保護された証拠、権限を弱めて成功扱いしない。
- 記録の担当者、再読条件、重複統合、候補整理、監査保存、任意規約の採用範囲を保つ。

本文の短い原則と参照の具体条件には、意図して残した重なりもある。たとえば既存承認の引き継ぎと、未作成の保存先を作る際の適用条件は両方必要である。任意テンプレートは別の場所へ設置して単独で読まれるため、記録の規約を参照へのリンクだけにはしなかった。状態・証拠・復帰は一緒に判断する場面が多く、現時点では参照をさらに細分化する利点より、関連条件を一度に確認できる利点を優先した。

## 確認の範囲と限界

新たに2件の依頼を固定した。1件は、検索先を意味で選ぶエージェントについて、ツールとの担当分担と未設定のタイムアウト・再試行数を設計する依頼。もう1件は、3人の全員一致で止まる小さな整形処理を、400〜600字程度でレビューする依頼である。各候補を読む担当へは依頼文だけを渡し、判定条件、他の試行、主担当の結論を読まないよう指定した。

基準版は、どちらの依頼にも適切な担当分担と具体的な提案を返した。数値設定を禁止したため常に失敗する、という実証結果ではない。短縮候補の不要な回数制限は、追加試行で見つかった適用条件の問題として扱い、原文と採用しなかった版を保存した。

最終候補`candidate-v4`は、求められたタイムアウト・再試行数を理由付きの提案とし、20秒の目安と同時2呼び出しの実制約を区別した。小さなレビューでは、必要なチェックを残して全員一致を外し、根拠のない修正回数の上限を追加しなかった。両ケースとも、追加の評価役や保存先、実行したという虚偽の報告はなかった。限定した再確認の結果として採用し、単発の差を改訂だけによる効果とは断定しない。

この試行は主担当による定性的な判定であり、モデル採点の精度を校正した記録ではない。9月12日の補強では、モデルの点数で候補を採否する場合に、独立して確認した例や実際の成果と採点基準を照合する条件を加えた。小さな草稿修正のたびに人の承認を求める条件は追加していない。

スキルの構造検証、プラグイン検証、参照リンク、復元用ソースと現行版の照合も確認した。テンプレートと保守記録参照の変更は静的に確認したもので、今回の2件の生成試行がその運用まで試したわけではない。

これは別文脈での設計生成と主担当の定性的な判定である。各版の2件は同じコンテキストで扱っているため、小さな議事録レビューだけを単独で依頼したときの参照選択や読み込み量は評価していない。ツール選択・権限・待機・保存などを実環境で動かした試験ではなく、反復測定や独立した採点者による統計評価でもない。初回改訂の5件をすべて再実行したわけでもない。意味の保持の静的確認と、今回変えた条件に関わる追加試行を区別する。

評価入力、各版の復元情報、途中候補を含む応答原文、判定は[再監査manifest](../../evals/agent-design-tools/agent-workflow-design/second-review-manifest.json)にまとめる。前回のmanifestと対象ハッシュは変更しない。
