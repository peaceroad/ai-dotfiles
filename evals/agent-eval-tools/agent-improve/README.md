# agent-improve の検証用素材

ここには、`agent-improve` の保守に使う公開可能な評価入力、検証手順、確認済みの応答・判定の記録を置きます。生の実行記録から保守に必要な証拠を選び、個人情報、秘密情報、非公開の案件資料、実環境の情報を含めないことを確認します。保存対象と配置の基準は[評価記録の案内](../../README.md)に従います。

## 小さな比較から始める

[compare.json](compare.json) は、明確な編集依頼、対象が曖昧な依頼、レビューだけの依頼に対する次の行動を比較します。対象は評価基盤の確認用に作った短い指示であり、完成した実用スキルの改善能力を代表する課題ではありません。実際の編集や途中指示を処理する試験でもありません。

リポジトリルートから、保存先を指定してローカル用の入力を準備できます。

```text
node evals/agent-eval-tools/agent-improve/prepare.mjs /private/agent-eval-inputs
```

生成するのは、現行版と用意済み候補の比較、候補の自動生成を伴う改善、変更不要の対象、書式への過剰適合を含む採点器、改善方法への自己適用の5種類です。このコマンドは実モデルを呼び出しません。

生成した設定のモデル、予算、保存先を確認してから、プラグイン内のランナーで実行します。自己適用の設定には、先に行った開発用の試行から、関連する証拠の抜粋と参照を記入します。未編集の説明文を、実際に得られた証拠として使わないでください。

標準の設定は `runtime.adapter: "host"` です。ランナーが `needs-host-response` を返したら、親エージェントが[ホスト経由の手順](../../../plugins/agent-eval-tools/skills/agent-improve/references/host-execution.md)に従って、予約された一件を新しいサブエージェントに渡します。最終応答を受け取って同じ実験を再開すると、共通の採点処理が進みます。CLI へのログインは不要です。

候補を提案する担当には、`proposalMethodFiles` で選んだ入口・評価・改善の指示を渡します。実行管理の参照は親が読み、比較ではそれも含めた方法全体を固定します。応答の受領と次の試行への再開は、`run ... --response ...` でまとめて進められます。手順の読み込みと担当間の受け渡しも時間を使うため、校正だけでなく候補判断まで通せる予算を先に設定します。

手元のターミナルで直接モデルを起動する場合は、私的な設定コピーの `runtime` を、たとえば `{ "adapter": "codex-cli", "model": "<利用可能なモデル>" }` に変更します。この経路では、実行するターミナルの Codex CLI が認証済みである必要があります。入れ子の改善課題も同じ実行設定にそろえます。

```text
node plugins/agent-eval-tools/skills/agent-improve/scripts/agent-eval.mjs validate /private/agent-eval-inputs/compare.json
node plugins/agent-eval-tools/skills/agent-improve/scripts/agent-eval.mjs run /private/agent-eval-inputs/compare.json --out /private/agent-eval-runs/compare
```

これらは少数の公開ケースによる探索的な確認です。自己適用の設定も同系統の題材を使うため、未見の改善課題への転移を測るものではありません。改善方法自身の有効性を調べるには、異なる原因を持つ改善課題、既存スキルとの併用、候補を固定した後の新しい課題、次の世代の実行などの追加検証が必要です。

生成した自己適用の設定は、そのまま大量実行するための既定手順ではありません。現在の方法が小課題の採点上の上限に達しているなら、その尺度では得点の上昇による改善を判断できません。実行前に、証拠から立てた仮説と課題の感度を確認し、必要な改善課題を選びます。時間上限はホストでの入力受け渡しと待機も含み、自己適用では入れ子になった対象実行・候補生成・採点の全体が呼び出し上限を共有します。

## 改善と現行維持を確かめる

[improve-retention.json](improve-retention.json) は、架空の保持ポリシーが変わったときに、分類用のスキルを更新する課題です。候補は改善方法から生成させ、保持義務と承認条件を維持したまま、新しい日数条件を反映できるか比較します。実際の削除は行いません。意図的に古い対象を使う処理確認であり、改善方法を弱めた対照や、汎用的な改善能力のベンチマークではありません。

[preserve-prompt-design.json](preserve-prompt-design.json) は、既存の `prompt-design` と、[公開済みの回帰ケース](../../agent-design-tools/prompt-design/evaluation-cases.json)の R03・R09 を使います。要件を満たす場合に現行維持を選べるかを確認します。採点は意味に基づくため、モデル採点器を正例・別表現の正例・誤例で先に校正します。この設定が測るのは生成した指示の品質であり、その指示を使う下流実行やスキルの自然な発見は別途検証します。

どちらも設定と保存先を指定して同じランナーで実行できます。探索中に対象や方法の正本を変更せず、比較対象は記録したスナップショットとして扱います。予算は候補生成、対象の試行、採点を含み、ホストが報告しない使用量をゼロとは扱いません。

[prompt-design の現行維持の記録](evidence/prompt-design-retain.json)には、公開済みの二つの課題、実際の応答、判定、変更を提案せず終了した理由を抜粋しています。応答が要件を満たし、具体的な欠陥が示されなかったための `retain` です。候補を作って比較した末に現行版が勝ったという意味ではありません。不要な改稿を避けた判断と、今後の回帰確認の基準として残しています。

この抜粋は、公開可能性と保守上の用途を確認して選んだ一例です。元の生記録は非公開の保持先に残し、課題への応答は書き換えていません。ローカルのパス、実行識別子、時刻、運用診断などは含めず、抜粋した項目と省略した条件を記録内で示しています。対象ソースはコミットとハッシュで特定できますが、当時の改善方法とコントローラーは現行版と異なり、この公開抜粋だけでは実験全体を復元できません。二つの既知課題に対する成果物の確認であり、一般的な優位性、下流実行、費用改善、RSI の証拠にはしません。

`validate` は通常のケースについて、校正、現行版、候補比較、確認に必要なランナーの依頼数も見積もります。ホスト経由ではワーカーへの依頼数であり、内部のモデル呼び出し全体の数ではありません。意味に基づく採点は既定では個別です。一括採点を比較する場合は、私的な設定コピーで `judgeBatchSize` を明示します。校正と実際の採点には共通の形式を使い、対象の実行は別々の文脈を保ちます。同じ成果物を個別にも判定させ、既知の正解との一致、順序、別の回答からの誘導、部分的な応答を確認します。一括化の比較は、対象スキルの品質改善を測る実験とは区別します。生の実行記録はリポジトリ外へ保持し、公開用の証拠は上記の基準で選びます。

## 既存スキルとの併用を確認する

[coexistence-cases.json](coexistence-cases.json) は、通常の指示文の修正と、能力目標から始める改善の設計を扱います。[prepare-coexistence.mjs](prepare-coexistence.mjs) は、既存の設計スキルだけの構成と `agent-improve` を加えた構成について、同じ依頼、固定したスキルと参照、内容のハッシュ、担当へ渡す入力を私的な保存先へ用意します。

```text
node evals/agent-eval-tools/agent-improve/prepare-coexistence.mjs /private/agent-eval-catalog
```

これはランナーのテキスト束比較とは別の、カタログを明示した選択試験です。四つの入力を、それぞれ新しい文脈の担当へ一度ずつ渡し、適用するスキルと必須参照の読み込みを許します。判定基準は入力から分離し、親が成果物と実際に観測できた操作から確認します。応答、担当の実行 ID、渡した入力のハッシュ、読み込みを確認できる範囲を私的な記録へ残し、凍結コピーが変わっていないことも確認します。必要な責務を分けるためだけに、別の進行役や採点担当を追加しません。

見るのは、通常の修正を重い評価へ広げないこと、改善の依頼では設計支援を使いながら比較の責任を保つこと、失敗ログや自己改善を必須にしないことです。読み込んだファイルの自己申告は、読み取りイベントを独立に確認した証拠とは扱いません。カタログの提示による選択を、インストールしたクライアントでの自然な発見と取り違えず、後者は別に検証します。

## 複数条件を保った変更を確かめる

[prepare-cache-policy.mjs](prepare-cache-policy.mjs) は、架空のキャッシュ分類スキルへ「期限切れでも、明示的に許可されたオフライン利用では猶予内だけ再利用する」という要件を追加する改善課題を用意します。対象の旧版は旧要件を満たす合成素材です。改善方法の現行版を弱めたり、実用スキルの欠陥を作ったりする課題ではありません。

```text
node evals/agent-eval-tools/agent-improve/prepare-cache-policy.mjs /private/agent-eval-cache
node plugins/agent-eval-tools/skills/agent-improve/scripts/agent-eval.mjs validate /private/agent-eval-cache/experiment.json
node plugins/agent-eval-tools/skills/agent-improve/scripts/agent-eval.mjs run /private/agent-eval-cache/experiment.json --out /private/agent-eval-cache/run
```

候補は入口とポリシー参照の両方を整合させ、認可、テナント、破損、強制更新、未知の値、通常の再利用を保つ必要があります。新しい能力と既存動作の保持は別ケースで採点し、一方の得点増で他方の退行を隠さないようにします。選択には別の境界条件、最終確認には既存の優先関係を組み合わせたケースを使います。最終確認は保持の検査であり、新能力の一般化を独立に証明するものではありません。

各依頼は複数レコードを含みますが、一つの応答を一試行として数えます。レコード数を独立した試行数や改善課題数と数えません。JSON の各値を決定的に判定し、正例、順序や書式の異なる正例、誤例、空回答で校正します。現行版の三試行、候補生成一回、両版の比較六試行、確認二試行で最大十二回です。これはこの課題の上限であり、通常の評価に必要な担当数ではありません。

この課題で成功した場合に確認できるのは、固定した版の方法が、この合成方針の移行を扱えたことです。改善方法自身がよくなった証拠にはなりません。自己適用へ進むときは、ここで得た失敗や負担が方法の変更で改善し得るかを診断し、現行版が採点上の上限に達している課題だけで自身の品質向上を主張しないようにします。

## 公開前の自己適用確認

[prepare-self-application.mjs](prepare-self-application.mjs) は、保持条件の移行と、変更不要の対象の維持を内側の改善課題にした自己適用を準備します。前者は旧方針を満たす合成スキルへ、保持期間の分類、処理を保留する条件、承認の版と有効期限を追加する課題です。新能力と既存動作の保持を別ケースにし、境界条件を確認用に残します。後者は現行方針のまま使う別課題で、不要な変更を避けられるか確認します。

```text
node evals/agent-eval-tools/agent-improve/prepare-self-application.mjs /private/agent-eval-self
node plugins/agent-eval-tools/skills/agent-improve/scripts/agent-eval.mjs validate /private/agent-eval-self/self.json
node plugins/agent-eval-tools/skills/agent-improve/scripts/agent-eval.mjs run /private/agent-eval-self/self.json --out /private/agent-eval-self/run
```

現在の方法を固定して内側の課題を実行し、その証拠から自身の候補または停止を判断します。候補は一版、共有予算は最大40回です。内側の最大経路が合計13回で、最初の測定13回、自身の候補生成1回、両版の比較26回を含みます。正常な現行維持では早く終了します。方法の品質差を測れないほど課題が解けている場合は、それを理由に停止でき、候補の生成・採用は必須ではありません。

この課題群は同系統の合成方針による探索です。改善課題を作った後に方法や採点を調整した場合は、新しい契約で比較します。現行版を弱めたり、運用時間の交絡を方法の欠陥と扱ったりして差を作りません。候補がなければ、候補比較の動作を実モデルで確認できたとは報告しません。候補を採用・棄却した場合も、選んだ版による後続の改善実行と、未知の課題での改善能力の実証は区別します。

[課題の検査](prepare-self-application.test.mjs)では、手で定めた期待値を独立した方針実装と照合し、別表現の正解と各項目の誤りを実際の採点器が区別できること、入れ子の最大呼び出し数を予算で賄えることを確かめます。

[followup-source-preservation.json](followup-source-preservation.json) は、選んだ方法を次の改善実行へ渡すための別課題です。既存の `prompt-design` に、架空の資料の計測範囲・未計測・対象外・未確定の予定を保つ指示の修正を依頼します。方法の指定は、自己適用で選んだ束とハッシュが一致することを確認してから実行します。意味による採点の校正と候補比較を含む上限は10回です。生成された指示の確認であり、その指示による下流の要約実行や、未見課題への改善能力の転移を実証するものではありません。

[実モデルでの確認記録](evidence/self-application-retain.json)では、内側の対象変更を採用し、変更不要の対象と改善方法自身は現行維持としました。選んだ方法のハッシュを照合した後続課題も完了しています。自身の候補は生成されなかったため、方法の新旧比較を終えたとは扱いません。[公開前確認の説明](../../../docs/agent-eval-tools/prepublication-review.md)に、判断、残した証拠、未確認の条件、保守メモとの関係をまとめています。

### 自身の候補を比較し、選んだ版を使う

[自己候補の比較記録](evidence/self-candidate-comparison.json)では、能力目標から H0 が自身の参照への追加候補 H1 を作りました。両方法へ同じキャッシュ方針の移行を依頼し、各方法が生成した対象候補を下流で実行しています。どちらも要求を満たし、追加の効果が示されなかったため H0 を維持しました。同じ H0 を別の保持方針の改善へ渡し、候補生成から下流の分類結果まで確認しています。

候補設計1件、比較8件、後続4件の計13件を逐次実行し、採点用のモデルは使っていません。親が能力目標、変更範囲、課題を指定した介入を含みます。この経路確認では、既存バッチを一つの探索ケースへまとめ、各項目を個別に照合しました。元のバッチ名は未見の分割を意味せず、項目数は独立試行数ではありません。課題の変換、使った版、生成物、全12件のランナー応答、判定、観測の限界を記録内に示しています。

候補を不採用にする経路の証拠であり、方法の一般的な同等性、品質向上、自然な発見、継続的な RSI の証拠ではありません。候補設計から比較への設計支援の引き継ぎは明示的に行い、支援スキルの自然な選択や読み取りイベントの独立監査は含みません。詳しい判断は[公開前確認](../../../docs/agent-eval-tools/prepublication-review.md#自身の候補を比較した追加確認)にまとめています。

## モデルを使わない自動テスト

プラグイン内の `agent-eval.test.mjs` は、合成応答を使い、実験契約の固定、校正、試行の重複防止、予算、候補の採否、元ファイルの保持、反映と復旧、入れ子の予算共有を確認します。成功しても、実モデルの接続や指示の有効性を確認したことにはなりません。

[移行課題の自動テスト](prepare-cache-policy.test.mjs)は、公開した課題の正解ラベルと校正例を、架空の方針をコードで表した参照判定と照合します。各回答の一項目だけを誤らせた場合の検出、既存動作と最終確認での退行による採用拒否も確認します。参照判定による合成応答なので、実モデルが方針を理解した証拠とは区別します。

リポジトリのルートから `npm run check:eval-tools` でこれらを実行できます。記録の自動テストには、保持したコピーの再読、契約の不一致、保存前後の失敗と重複実行の防止も含みます。配布物単独の検査はプラグイン内のテストで完結し、このリポジトリの評価素材を実行時依存にしません。

各経路の実行条件、現在対応している評価の種類、出力の扱いは[実行契約](../../../plugins/agent-eval-tools/skills/agent-improve/references/runtime.md)を参照してください。設計上の目標と段階ごとの完了条件は[計画](../../../docs/plans/agent-eval-tools.md)、利用像は[利用場面のノート](../../../docs/notes/agent-eval-tools-use-cases.md)にあります。
