# グローバルAGENTS.mdの評価セット

`home/.codex/AGENTS.md`の旧版と現行版を比較する、小さな開発用ケース集です。13ケースを定義しています。行動評価はまだ実行していません。設計の意図、採用判断、限界は[評価方針](../../docs/notes/codex-agents-md-evaluation.md)を参照してください。

| ファイル | 用途 |
| --- | --- |
| [cases.json](cases.json) | 入力、環境条件、継続イベント |
| [criteria.json](criteria.json) | 実行者に見せない判定条件と必要な証拠 |
| [manifest.json](manifest.json) | 比較するコミット、指示ファイルのハッシュ、比較条件 |
| [suite.mjs](suite.mjs) | 定義の検査と試行用フォルダーの生成。モデルは起動しない |

## 定義を検査する

リポジトリルートで実行します。Node.jsの標準モジュールと、manifestに記録したコミットを含むGit履歴が必要です。

```powershell
node evals/codex-agents/suite.mjs check
```

ケースIDと判定条件の対応、比較対象のサイズ・SHA-256、生成する短文・長文参照とCRLF入力の性質を検査します。成功しても、モデルが指示に従えることを確認したわけではありません。将来AGENTS.mdを変更しても、過去のmanifestを最新ファイルに合わせて書き換えず、次の比較用manifestとして保存します。

## 試行を準備する

出力先は、存在する親フォルダーの下にある未作成のディレクトリを指定します。次の例では一時領域に作ります。既存ディレクトリは上書きしません。

```powershell
node evals/codex-agents/suite.mjs prepare load-inner-limit current "$env:TEMP/agents-eval-current-01"
node evals/codex-agents/suite.mjs prepare load-inner-limit baseline "$env:TEMP/agents-eval-baseline-01"
```

`global-instructions.txt`、`input.json`、該当ケースの`fixtures/`、未実行の`run-record.json`が生成されます。継続イベントがあるケースには、運用者用の`events.json`も生成します。長い参照は約32KBで、先頭付近・中央・末尾にメモの条件を置いています。CRLFは生成入力だけに使用し、リポジトリのテキストはLFで保存します。

準備コマンドは、実際の`~/.codex/AGENTS.md`、設定、インストール済みスキルを変更しません。`global-instructions.txt`は単なるスナップショットであり、置いただけではグローバル指示として読み込まれません。

## 試行と証拠の取得

各ケース・各版を独立した新規セッションで実行します。同じ会話の途中で指示を差し替えたり、現行指示を継承したサブエージェントを旧版条件として使ったりしません。モデルは`gpt-6-astra`とし、実効推論設定、上位指示、ツール、権限、入力、予算をそろえて記録します。APIで指示文を渡す試行は、Codexによるグローバルファイルの発見・読み込み試験とは区別します。

`simulation`は判断の机上試行です。比較対象の指示文を適用した実行者に、`input.json`のpromptとsetupを渡します。待機ケースでは次に選ぶ行動と理由を回答させ、応答品質のケースではpromptへの通常の回答を得ます。完了していないイベントの結果を先に与えません。`wait-monitor`では、最初の応答の後に`events.json`のイベントを1件ずつ渡します。他の待機ケースでは、開始時点の判断までを採点します。実際の待機ツール、通知、監視停止の成功は証明しません。

`codex-live`は実際のCodex環境で行います。運用者がsetupを満たす環境と選択対象スキルを用意し、実行者にはprompt、対象スキルの位置、作業に必要なファイルだけを渡します。評価基準、他ケース、run-recordは実行者の作業領域から分離します。環境に適した方法で比較対象をグローバル指示として読み込ませ、実効指示の確認記録を残します。この設定を隔離できない場合は、グローバル指示の比較として採点しません。

内側・外側の読取上限は運用者が設定し、その値を記録します。上限を再現できない、切詰めを観測できない、必要なブラウザーが利用できない場合は、その観点を`not_observed`にします。仮想のツール結果を渡して代用した場合は、modeを`simulation`として記録します。

スキル読取では、呼出し順序とモデルに返った内容を保存します。内側ツールが全文を出しても、外側で切り詰められた内容は取得済みと数えません。必要条件が出力に反映されたことだけでは、途中の全範囲を読んだ証拠になりません。LFでは出力のバイト列と変更対象外ファイルの開始前後のハッシュを確認します。

## 判定と記録

試行後にcriteriaと証拠を照合し、run-recordの各条件について`pass`、`partial`、`fail`、`not_observed`を記録します。証拠ファイルへの参照と理由も残します。未実行のstatusは`not_run`のままにし、実行した場合は`completed`または`incomplete`に変更します。設定が不明なまま結果を比較しません。run-recordには評価定義と準備スクリプトのハッシュも記録するため、対応するGitコミットかソースのコピーを保存し、後からその版を復元できるようにします。

旧版のLFスクリプト実行は、旧版が要求した正しい動作として扱います。現行版も、必要性があれば検査スクリプトを使えます。スクリプトを使ったこと自体を失敗にせず、成果物の正しさと追加呼出し・待ち時間などのコストを分けて記録します。両環境には同じ版のLF検査スクリプトを用意し、欠落による失敗を指示文の効果と混同しません。

保存する場合は、公開可能な入力・応答・ツール記録とrun-recordを`evals/codex-agents/runs/<run-id>/`にまとめ、評価の説明を`docs/`に置きます。個人パスや認証情報は除去し、加工した範囲を明記します。記録ファイルの参照はリポジトリルートからの相対パスとします。単一試行の合計点だけで優劣を断定せず、重要な失敗と未観測項目を個別に確認します。
