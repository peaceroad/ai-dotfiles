# dot-toolkitの受け入れ確認

このページはdot-toolkitの開発・検証担当者向けです。プラグインを使い始めたい場合は、[インストールと初期設定](../../docs/dot-toolkit/setup.md)へ進んでください。

この評価セットは、0.2.0のプラグイン内の共通指示、条件付き参照、読み取り専用の補助コードを対象にします。ソース・配置の検査と、実際のメインdotが通常の依頼で指示を使う動作を分けて確認します。ここに置くのは公開用の合成入力と判定条件で、利用中の環境の記録は含めません。

- [ローカルで実行する検査](#ローカルで実行する検査)：配布ファイル、検査器、合成ケースの回帰確認
- [実環境での確認を始める前に](#実環境での確認を始める前に)：導入済みリソースの取得・実行と観測条件
- [実際のメインdotで確かめる](#実際のメインdotで確かめる)：読み込み・暗黙の選択・継続性の観測
- [証拠と記録](#証拠と記録)：判定の根拠と観測記録の形式

## ファイル

- [cases.json](cases.json)：通常依頼4件と、条件付き参照・選択・保全・移行などの模擬入力37件
- [criteria.json](criteria.json)：実行者に渡さない合格・失敗条件、必要な観測、合成の参照素材
- [manifest.json](manifest.json)：対象とする公開パッケージ11ファイルのパス・バイト数・SHA-256と未実施範囲。実導入版を示すものではない
- [suite.mjs](suite.mjs)：定義・対象ソースとの内容一致・観測記録の形式検査と、通常依頼文の抽出
- [suite.test.mjs](suite.test.mjs)：合成記録による判定条件と対象ファイル集合の回帰検査
- [scripts.test.mjs](scripts.test.mjs)：使い捨ての合成ルートを使う補助スクリプトの検査
- [plugin-packages.test.mjs](../../scripts/plugin-packages.test.mjs)：公開ファイルの厳密な許可リスト、隔離した配布物のリンクと補助コードの実行確認

既存の[agent-improveの評価原則](../../plugins/agent-eval-tools/skills/agent-improve/references/experiments.md)に合わせ、成果物と観測可能な操作を判定します。同スキルの[ランナー](../../plugins/agent-eval-tools/skills/agent-improve/references/runtime.md)は明示的なテキスト束の比較用です。自然な発見、メインdotの読み込み、継続性を測れないため、ここではモデル実行アダプターを追加しません。

## ローカルで実行する検査

リポジトリルートで実行します。必要なのはNode.js 24以上の標準モジュールと対象ファイルです。外部依存を追加インストールしません。Git実行ファイルや履歴は不要で、squash後のチェックアウト、shallow clone、ソースアーカイブでも同じ内容照合を行えます。

```text
node evals/dot-toolkit/suite.mjs check
node --test evals/dot-toolkit/suite.test.mjs evals/dot-toolkit/scripts.test.mjs
node --test scripts/plugin-packages.test.mjs
```

### 配布ファイルと定義の照合

ケースと判定条件の対応、入力への読み込みヒントの混入、段階定義のモード・条件名・重複、対象ソースのバイト数・SHA-256、観測記録の形式と合否の前提を検査します。manifestの形式2は、対象をパス・バイト数・SHA-256で特定し、旧形式のsourceCommitは受け付けません。プラグイン版0.2.0と、次の配布集合を過不足・重複なく要求します。

- `plugins/dot-toolkit/README.md`、`plugin.json`
- `skills/dot-guidelines/SKILL.md`
- 同スキルの`reference/setup.md`、`computer-checks.md`、`skills-maintenance.md`、`migrations/0.1-to-0.2.md`
- 同スキルの`scripts/inspect-computer.mjs`、`check-skill-index.mjs`、`verify-skill-files.mjs`、`lib.mjs`

上記のスキル以下のパスはすべて`plugins/dot-toolkit/`内です。対象をmanifestから削って検査を省けないよう、必要な全パスを検査器とテストにも独立して保持します。旧`dot/AGENTS.md`と`dot/dot-setup.md`は0.2.0の対象に含めません。移行時の比較が必要なら、確認できた採用版のGit履歴を別に使います。現行ソース照合自体はGitを必要としません。

各対象の欠落、同サイズの改変、不正な形式や内容に一致しないハッシュ・サイズを拒否することを検査します。Gitのない使い捨てのソース一式からも検査コマンドを実行します。隔離パッケージでは余分なファイル・空ディレクトリ、ファイル位置にあるディレクトリ、配布外への相対リンクを拒否し、三つの補助コマンドの`--help`を外部コマンドや追加依存なしで実行します。これはソースをコピーした配布物の試験であり、インストール済みプラグインの資源アクセス試験ではありません。

リポジトリの`.gitattributes`は、Gitがテキストと判定したファイルをLFでチェックアウトする方針です。検査器は改行を正規化せず、読み取ったバイトをそのまま照合します。新しいチェックアウトにはこの指定が適用されます。既存のチェックアウトにCRLFが残る場合は、未コミットの編集を退避して該当ファイルを再チェックアウトしてください。

### 判定処理の回帰確認

段階ごとのモード・前提・確認条件はテスト側にも独立した受け入れ条件として保持し、合格用の合成記録をcriteriaから自動生成しません。条件を一つずつ削った定義が独立した回帰検査で失敗することと、各必須条件を欠落・fail・自己申告へ変えた記録が合格の根拠にならないことを確認します。これは判定文全体を固定するものではありません。意図した契約変更では、criteriaと独立した受け入れ条件の両方をレビューします。旧入口との不一致、未実施、既読会話、子タスク、未観測の再起動も合成記録で区別します。互換性のため四つの段階と既存の必須条件名は保持します。`targetLoaderMatches`は0.2.0では実際に導入され読めたプラグイン所有の入口の一致を指し、旧常設ファイルへ転送する構成を要求しません。条件の意味はcriteriaの`conditionMeanings`にも記載します。

### 検査結果が示す範囲

このコマンドは実モデルもCodexタスクも起動せず、設定・導入済みプラグイン・個別ファイルを変更しません。成功が示すのは、現在の対象ソースが信頼したmanifestの内容識別と一致することと、検査器の動作です。ハッシュは公開者の真正性や安全性を保証せず、失われたソースを復元する材料でもありません。ソースとmanifestを同時に変更すれば一致し得るため、この検査は変更の妥当性や承認を判定しません。

実際のインストール済み資源の読込み・実行、普通の依頼からの自動選択は未実施のままです。`behavioralRuns`と`liveChecks`の`installedEntry`、`installedReferences`、`installedScriptsRetrieved`、`installedScriptsExecuted`、`ordinaryMainDotContext`はすべて`not_run`を保持します。定義検査はこれらを合格へ書き換えません。

対象ソースが変われば照合は失敗し、検査時に期待値を書き換えることはありません。意図した変更を評価する際は、過去の試行を支えるmanifestと対応する証拠を保持したうえで、新しい対象の記録を明示的に作り、変更内容と期待値を一緒にレビューします。古い対象の検査結果を、新しい候補の検査済み証拠にはしません。

## 実環境での確認を始める前に

実装後の実利用確認は、次を別々に記録します。公開manifestの`not_run`は、この定義と合成試験が実利用を実施していないことを表します。後に行う実際の試行の観測記録とは混ぜません。

1. 実際の導入済み入口を全文取得し、対象版・内容を確認する
2. 条件に応じた四つの参照文書を実際の導入済み資源から全文取得する
3. 三つの補助スクリプトと`lib.mjs`の完全なコードと由来を確認する。テキストでしか取得できない場合は完全性と同一版を確かめた実行用コピーを使い、省略コードを補完しない
4. Node.js 24以上で、取得した同一版の補助コードを、承認された読取り範囲で実行する。コードを読めたことだけでは実行確認にしない
5. 実際のメインdotの普通の依頼で、共通指示、必要な個別指示、INDEXから選んだスキルと必須参照、初期設定が不要な通常利用を観測する。旧指示が既読の会話の成功だけでは新しい文脈の確認にならない

参照資源や補助コードを確認できなければ、それに依存する移行の切替と旧ファイル廃止を止めます。同じ操作中の手順・コードの版を混ぜません。固定リポジトリsnapshotを代替に使う場合も、インストール済み資源と同一であるとは別途確認なしに言いません。普通の未誘導メインdotの文脈や必要な境界を用意できない項目は未実施、試行しても識別や証拠が足りない場合は観測不能とします。

## 実際のメインdotで確かめる

観測する担当は、始める前に対象の実導入版、共通指示、採用スキル、会話の既読状態、利用できる記録を確認します。ソースを読んだだけで導入済みとせず、実際に読めたプラグイン入口の内容と照合します。利用可能な実行設定や識別情報が非公開なら不明のまま残します。記録のためだけに新しい保存領域や常駐処理を作る必要はありません。

### 判定を四つに分ける

1. 配置・整合：採用ソースとの内容一致、必要な参照、INDEX・manifestの整合を調べる。ファイル検査の成功から自動読み込みを推論しない。
2. 現在の会話での読み込み：実際のメインdotで、プラグイン所有の共通指示、存在する個別指示・INDEX、選んだスキルと条件に該当する必須参照が、依存作業より前に完全に提供されたことと、成果物を確認する。既読の会話もこの範囲で使える。
3. 通常依頼からの暗黙選択：指示文や期待結果を先に読んでいない本物のメインdotへ、スキル名・パス・読み込み指示を含まない依頼だけを渡す。利用可能なカタログ、実際の読み取り、適切な選択、成果物を確認する。
4. 継続性：実際に観測した再開・再起動などの境界前後で、対象版とファイルの同一性、必要な指示の利用、選択と成果物を確認する。結果はその境界に限定する。アプリの閉開をクラウド再起動や新規環境とみなさない。

配置の`indexManifestAgree`では、`.agents/skills-state/INDEX.md`に意図して選ばれた項目と、`.agents/skills-state/manifests/<name>.json`、`.agents/skills/<name>/SKILL.md`の対応を確認します。INDEXからのリンクは`../skills/<name>/SKILL.md`です。全manifestを通常利用へ選ぶ必要はなく、選択集合を自動で増やして整合と呼びません。正常な空のINDEX、初回の未作成、既知の一覧の消失、破損、読取不能を区別します。任意の`.codex/AGENTS-private.md`も、不在だけで拒否・不要・読取成功と判断しません。

管理対象も保持すべき記録もない構成では、その事実と任意ファイルを作成する必要がないことを観測で確かめます。ファイル不在だけで自動的に合格にはしません。状態を確かめられなければ観測不能とします。構造検査では説明の各行の`> `接頭辞と空行の`>`を扱い、説明内の見出しや水平線を項目境界にしません。ただしdescriptionの全文・意味・改行がfrontmatterと合うかはdotが確認します。スクリプトの成功を汎用YAMLの解析や厳密な意味的一致の証拠にはしません。

通常依頼は、たとえば次のコマンドで一件だけ抽出できます。

```text
node evals/dot-toolkit/suite.mjs input rewrite-instruction
```

対象に渡すのは出力された依頼文だけです。試験名、判定条件、期待スキル、他の試行結果は渡しません。観測する担当も同じメインdotで、すでに評価セットを読んでいるなら、結果は現在の会話での確認に限ります。語句を少し変えただけでは未誘導になりません。保護された未見ケースや統計的な発見率を、この小さな公開セットで主張しません。

採用されていないスキルを期待するケースは、そのまま実施せず、対象に合うケースを選びます。短い算術の負例は不要なタスクスキルを選ばないかを見るもので、共通指示や、存在する個別指示の読み込みまで不要にするものではありません。任意ファイルがないことだけで失敗にはしません。クラウドのINDEXがなくても、クライアントから利用できるスキルは選択できます。必要な技能が別の適切な経路から提供される場合も、支配的な指示に照らして判定し、特定の読み取りコマンドだけを正解にしません。

criteriaの`skills`は代表的な選択先です。別の適切なスキルが同じ要件を満たす場合、選択そのものを失敗にしません。ただし、特定の採用スキルが自動選択された証拠が欲しい場合は、別経路の成功で確認済みとせず、その対象の選択は未確認と記録します。

条件付きの個別参照は、実際に適用可能な既存条件を、非機密な成果物で確認できる場合だけ実動作を観測します。合成の個別指示を本番へ書き込んだり、実際の私的ファイルを公開用素材に置き換えたりしません。該当条件がなければ未実施、見分ける証拠が得られなければ観測不能とし、模擬ケースの成功で補いません。

現在のツールやクライアントで、本物の未誘導main dotや必要な再開境界を用意できるか先に確認します。子タスク、別プロセス、指示本文を渡したモデルは代用になりません。操作が未対応ならその項目は未実施です。試験のためのリセット、再導入、個別指示の変更、環境再生成、定期試験を暗黙に承認された操作と扱いません。

## 合成ケースで維持する判断境界

既存の任意指示、保留入力、アクセス拒否、既知の消失、必須参照、個別入力状態のケースは残します。追加の模擬ケースは次を扱います。

- プラグイン所有の共通指示と、セットアップ・点検・保守・移行の条件付き参照。通常依頼では保守文書や全manifestを常時読まない
- 現在の文脈で確認済みの指示と導入状態の再利用、変更時の再確認、初回でも個別指示だけを保存する依頼、取得元を必要としない一覧からの除外
- 意図した選択集合、明示的な空のINDEX、破損と未作成の違い、複数行description、曖昧なfrontmatterを推測で書き戻さないこと
- 説明できない追加・削除・変更の保全、検査を通すための再ハッシュ禁止、同じ操作の解決済みcommitへの固定、中断と同時編集への対応
- 読取成功と書込み権限の違い、部分変更、失われたローカル内容とハッシュの限界、リンクや非対応ファイルを無視しないこと
- 旧AGENTS.mdが採用元と一致する、異なる、採用元が不明、保存先が存在する各分岐。必要な旧全文は`.codex/AGENTS-migrate-0.1.md`へ上書きせず保存し、保存を通常読込みや個別指示への自動採用にしない
- 移行前の選択・採用版・ローカル変更・未決入力の保持。部分移行を準備完了とせず、新構成と必要な保全を確認するまで旧構成を廃止しない
- インストール済み参照・コードが読めない場合、コードの省略や依存の不足、途中の版変更。同一版の完全な資源取得と実行を別に確認する
- 合成テスト・構造検査・明示実行を、普通の依頼からの選択や実際の境界を越えた継続性へ昇格させないこと

これらは公開用の合成入力と判断条件であり、実動作の試験結果ではありません。回帰検査はケースが定義に残り、模擬入力と通常入力が分離され、正負の条件があることを確認します。文面の意味やモデルが正しい判断を選ぶことは機械判定しません。補助コードのファイル・構造検査は`scripts.test.mjs`の隔離した合成試験で扱います。モデルによる判断の観測や移行操作の成功は別途必要です。全分岐、すべてのスキル、すべてのクライアントや保存境界を網羅しません。

## 証拠と記録

各条件を`pass`、`fail`、`not_run`、`unobservable`で記録します。意味はcriteriaにあります。失敗や未観測を削除して、成功するまで同じ試行を繰り返しません。修正後の再試験は対象版と条件を分けて残します。

完全読み込みの証拠には、モデルへ実際に返ったツール結果または検証可能な実行時提供を使います。切り詰めがある場合は不足範囲を最後まで確認し、依存作業との順序も調べます。読み取りの自己申告や、末尾の条件が回答に現れたことだけでは全文を読んだ証拠になりません。一方、有効な既読指示の再読み取りがないことだけで失敗とはしません。

既存の観測記録をJSONで整理する場合は、`stage`、`mode`、`execution`、`verdict`、空でない`reason`を記載します。`execution`は`completed`または`not_run`、`mode`は`file-inspection`、`main-dot`、`simulation`、`delegated`、`codex`から選びます。合否を主張するmodeは該当段階の定義と一致する必要があります。

`preconditions`と`checks`を付ける場合はオブジェクトにし、キーをcriteriaの該当段階・区分から選びます。未知のキーや誤記は、判定が`unobservable`や`not_run`でも拒否します。各項目の`result`は`pass`、`fail`、`not_run`、`unobservable`、`basis`は実際の観測なら`observed`、自己申告なら`self-report`です。

- `observed`の`pass`・`fail`には、空でない参照文字列を一つ以上含む`evidenceRefs`配列が必要です。記録全体が観測不能でも、この要件は変わりません。
- `not_run`・`unobservable`の項目と、`self-report`の項目では、`evidenceRefs`を省略または空配列にできます。付ける場合は空でない参照文字列の配列にします。
- `pass`には全前提と全確認条件の観測による合格が必要です。`fail`には全前提の観測による合格と、一つ以上の確認条件の観測による違反が必要です。失敗を直接確認した時点で残りの確認条件を省略した記録は受け付けます。
- `unobservable`・`not_run`では前提や確認条件を一部だけ記録するか、省略できます。自己申告も説明用に残せますが、合否に必要な観測の代わりにはなりません。どの判定でも、記載した全項目の型・値・参照形式を検査してから合否の前提を調べます。

実施した記録には、観測不能でも、証拠を確認した担当の空でない`review.reviewer`、一つ以上の参照を持つ`review.evidenceRefs`、`review.referencesInspected: true`を付けます。未実施の記録ではreviewを省略できますが、付ける場合は担当・参照と真偽値の`referencesInspected`が必要です。行動試験の合否には実際の依頼への`taskReference`、継続性の合否には`boundaryDescription`も必要です。これらを付ける場合は空でない文字列にします。検査器は参照を取得せず、その真正性や内容を確かめません。観測する担当が根拠を開いて判定してから、必要な場合だけ次の形式検査を使います。

```text
node evals/dot-toolkit/suite.mjs validate-record /private/dot-check.json
```

返り値の`recordStructure: valid`は、記録が必要な項目を備えるという意味です。`reportedVerdict`は担当が記載した判定であり、プログラムが実動作を合格認定した結果ではありません。`behavioralVerification`は常に`not_performed_by_checker`です。テスト内の合成記録は、この区別を検査するための架空データです。

公開する場合は合成入力と公開可能なケース別証拠だけを選びます。実際の個別指示の内容・ファイル名、実環境の在庫・構成・時刻・測定値、全トレースをリポジトリへ入れません。匿名化しただけの実環境情報も保存対象にはしません。記録先の規約と[セットアップの受け入れ確認](../../docs/dot-toolkit/setup.md)に従います。
