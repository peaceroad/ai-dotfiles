# dot-toolkitの受け入れ確認

ローダー、共通指示、構築手順を一緒に確認する小さな評価セットです。配置の検査と、メインのdotが通常依頼から指示を読む実動作を分けます。ここには公開用の合成入力と判定条件だけを置き、利用中の環境の記録は含めません。

## ファイル

- [cases.json](cases.json)：通常依頼4件と、条件付き参照・適用範囲の模擬入力3件
- [criteria.json](criteria.json)：実行者に渡さない合格・失敗条件、必要な観測、合成の参照素材
- [manifest.json](manifest.json)：公開ソースの固定コミットとファイルのハッシュ。導入済みローダーの版を示すものではない
- [suite.mjs](suite.mjs)：定義・固定ソース・観測記録の形式検査と、通常依頼文の抽出
- [suite.test.mjs](suite.test.mjs)：合成記録による判定条件の回帰検査

既存の[agent-improveの評価原則](../../plugins/agent-eval-tools/skills/agent-improve/references/experiments.md)に合わせ、成果物と観測可能な操作を判定します。同スキルの[ランナー](../../plugins/agent-eval-tools/skills/agent-improve/references/runtime.md)は明示的なテキスト束の比較用です。自然な発見、メインdotの読み込み、継続性を測れないため、ここではモデル実行アダプターを追加しません。

## ローカルで実行する検査

リポジトリルートで実行します。Node.jsの標準モジュールと、manifestの固定コミットを含むGit履歴が必要です。

```text
node evals/dot-toolkit/suite.mjs check
node --test evals/dot-toolkit/suite.test.mjs
```

ケースと判定条件の対応、入力への読み込みヒントの混入、固定した公開ソースのバイト数・SHA-256、記録の誤った合格判定を検査します。固定コミットの検査とは別に、作業ツリーの対象4ファイルがその版と一致するか確認し、変更・欠落を見逃さないことを使い捨てのコピーで試します。旧ローダー、未実施、自己申告だけ、既読会話、子タスク、未観測の再起動などを合成記録で区別します。

このコマンドは実モデルもCodexタスクも起動せず、設定・導入済みプラグイン・個別ファイルを変更しません。成功が示すのは検査対象のソース同一性と検査器の動作です。実際の読み込みや自動選択は未実施のままです。対象ソースが変われば現在版との照合は失敗します。意図した変更を評価する際は、過去のmanifestと対応する証拠を保持したうえで、新しい版の対象記録を明示的に作ります。古い固定コミットの検査だけを、新しい候補の検査済み証拠にはしません。

## 実際のメインdotで確かめる

観測する担当は、始める前に対象の実導入版、共通指示、採用スキル、会話の既読状態、利用できる記録を確認します。ソースを読んだだけで導入済みとせず、実際に読めたローダーの内容と照合します。利用可能な実行設定や識別情報が非公開なら不明のまま残します。記録のためだけに新しい保存領域や常駐処理を作る必要はありません。

### 判定を四つに分ける

1. 配置・整合：採用ソースとの内容一致、必要な参照、INDEX・manifestの整合を調べる。ファイル検査の成功から自動読み込みを推論しない。
2. 現在の会話での読み込み：実際のメインdotで、対象ローダー、共通・個別指示、INDEX、選んだスキルと条件に該当する必須参照が、依存作業より前に完全に提供されたことと、成果物を確認する。既読の会話もこの範囲で使える。
3. 通常依頼からの暗黙選択：指示文や期待結果を先に読んでいない本物のメインdotへ、スキル名・パス・読み込み指示を含まない依頼だけを渡す。利用可能なカタログ、実際の読み取り、適切な選択、成果物を確認する。
4. 継続性：実際に観測した再開・再起動などの境界前後で、対象版とファイルの同一性、必要な指示の利用、選択と成果物を確認する。結果はその境界に限定する。アプリの閉開をクラウド再起動や新規環境とみなさない。

通常依頼は、たとえば次のコマンドで一件だけ抽出できます。

```text
node evals/dot-toolkit/suite.mjs input rewrite-instruction
```

対象に渡すのは出力された依頼文だけです。試験名、判定条件、期待スキル、他の試行結果は渡しません。観測する担当も同じメインdotで、すでに評価セットを読んでいるなら、結果は現在の会話での確認に限ります。語句を少し変えただけでは未誘導になりません。保護された未見ケースや統計的な発見率を、この小さな公開セットで主張しません。

採用されていないスキルを期待するケースは、そのまま実施せず、対象に合うケースを選びます。短い算術の負例は不要なタスクスキルを選ばないかを見るもので、共通・個別指示まで不要にするものではありません。必要な技能が別の適切な経路から提供される場合も、支配的な指示に照らして判定し、特定の読み取りコマンドだけを正解にしません。

criteriaの`skills`は代表的な選択先です。別の適切なスキルが同じ要件を満たす場合、選択そのものを失敗にしません。ただし、特定の採用スキルが自動選択された証拠が欲しい場合は、別経路の成功で確認済みとせず、その対象の選択は未確認と記録します。

条件付きの個別参照は、実際に適用可能な既存条件を、非機密な成果物で確認できる場合だけ実動作を観測します。合成の個別指示を本番へ書き込んだり、実際の私的ファイルを公開用素材に置き換えたりしません。該当条件がなければ未実施、見分ける証拠が得られなければ観測不能とし、模擬ケースの成功で補いません。

現在のツールやクライアントで、本物の未誘導main dotや必要な再開境界を用意できるか先に確認します。子タスク、別プロセス、指示本文を渡したモデルは代用になりません。操作が未対応ならその項目は未実施です。試験のためのリセット、再導入、個別指示の変更、環境再生成、定期試験を暗黙に承認された操作と扱いません。

このセットは代表ケースによる確認であり、初期設定の全分岐、欠落・読取拒否からの対応、すべてのスキルや保存境界を網羅しません。追加が必要なら、確かめたい動作と実行権限を絞って別のケースにします。

## 証拠と記録

各条件を`pass`、`fail`、`not_run`、`unobservable`で記録します。意味はcriteriaにあります。失敗や未観測を削除して、成功するまで同じ試行を繰り返しません。修正後の再試験は対象版と条件を分けて残します。

完全読み込みの証拠には、モデルへ実際に返ったツール結果または検証可能な実行時提供を使います。切り詰めがある場合は不足範囲を最後まで確認し、依存作業との順序も調べます。読み取りの自己申告や、末尾の条件が回答に現れたことだけでは全文を読んだ証拠になりません。一方、有効な既読指示の再読み取りがないことだけで失敗とはしません。

既存の観測記録をJSONで整理する場合は、`stage`、`mode`、`execution`、`verdict`、`reason`を記載します。`preconditions`と`checks`のキーはcriteriaの該当段階から選び、各項目へ`result`、`basis`、`evidenceRefs`を付けます。実際の観測のbasisは`observed`、自己申告は`self-report`として区別します。

実施した記録には、証拠を確認した担当の`review.reviewer`、確認対象の`review.evidenceRefs`、`review.referencesInspected: true`を付けます。行動試験の合否には実際の依頼への`taskReference`、継続性には`boundaryDescription`も必要です。検査器は参照を取得せず、その真正性や内容を確かめません。観測する担当が根拠を開いて判定してから、必要な場合だけ次の形式検査を使います。

```text
node evals/dot-toolkit/suite.mjs validate-record /private/dot-check.json
```

返り値の`recordStructure: valid`は、記録が必要な項目を備えるという意味です。`reportedVerdict`は担当が記載した判定であり、プログラムが実動作を合格認定した結果ではありません。`behavioralVerification`は常に`not_performed_by_checker`です。テスト内の合成記録は、この区別を検査するための架空データです。

公開する場合は合成入力と公開可能なケース別証拠だけを選びます。実際の個別指示の内容・ファイル名、実環境の在庫・構成・時刻・測定値、全トレースをリポジトリへ入れません。匿名化しただけの実環境情報も保存対象にはしません。記録先の規約と[セットアップの受け入れ確認](../../docs/dot-toolkit/setup.md)に従います。
