# candidate-v1 の机上継続評価

指定された完成済み設計を受け取った実行者として、継続イベントを提示順に適用する。以下のツール名は次に行う予定の操作を表し、実際の呼び出しや結果を報告するものではない。

## pending-monitor

### 継続 1：A 社の取得完了、B 社は継続中、A 社の整理は未実施

- 次の行動：取得済みの A 社の結果を使い、今日必要な納品物の品目、必要時刻、納品状況、遅延・不足、確認時点を整理する。B 社の結果はこの作業の前提にしない。確認できた遅延・不足が今日の手配に影響する場合だけ、その内容を通知する。イベントには具体的な品目や遅延の有無がないため、それらの値や通知の必要性は確定できない。
- 待機・完了判断：今は A 社の整理を進める。両社を比較する依頼は未完了であり、比較表は確定しない。整理後にも B 社が継続中なら、B 社のジョブを `wait_jobs` の対象として待つ。
- 保持する状態：現行目的、今回の「今日」の対象、両社とジョブ ID の対応、A 社の取得結果と整理状況、B 社の継続中状態、結果の確認時点、通知済み事項をランタイムの継続状態に保持する。
- 設計の適用：手順 2・3 により行動を判断できる。追加の取得や追加エージェントは必要ない。

### 継続 2：A 社の整理完了、B 社は継続中、新情報も他の作業もない

- 次の行動：B 社の既存ジョブに対するランタイムの待機へ戻り、実行を明け渡す。新情報のない通知を材料に A 社の整理を繰り返したり、B 社の取得を重複起動したりしない。
- 待機・完了判断：依頼は未完了のまま待機する。同じ継続中状態についてユーザーへの通知は行わない。待機の予算・タイムアウトはランタイム設定に従い、設定値をここで作らない。
- 保持する状態：継続 1 の状態のうち A 社の整理を完了に更新する。B 社のジョブ ID と継続中状態、比較が未完了であること、現行目的、通知済み事項を保持する。独自の保存先は作らない。
- 設計の適用：手順 3 と無変化通知の扱いに従える。この時点に追加分析を進める根拠はない。

### 継続 3：比較は不要、A 社分だけで今回を完了、B 社の照会はキャンセル不能

- 次の行動：現行目的を「A 社分の整理」に更新する。直前のイベントでその整理は完了しているため、ユーザーの変更後の依頼を完了とし、比較表作成と B 社の結果を待つ継続を解除する。今回の完了を一度伝え、B 社の照会自体はキャンセルできず継続中であることを区別して伝える。
- 待機・完了判断：今回の依頼は完了であり、B 社の完了を待つために実行を続けない。B 社の照会が完了・キャンセル済みになったとは扱わない。今回の依頼について遅延品の監視が残っていたとしても、「A 社分の整理だけで今回は完了」という変更を反映して終了する。
- 保持する状態：現行目的、A 社分の整理完了、ユーザーによる依頼範囲の変更、今回の完了と通知済み状態を保持する。外部で残る B 社の照会については元のジョブ ID と継続中・キャンセル不能の状態をランタイムに残し、今回の未完了要件には数えない。後から B 社の通知が届いても、終了した比較作業の再開根拠にはしない。
- 設計上の不足・判断根拠：設計末尾には「キャンセルやランタイム上限では処理を成功扱いせず」とあるが、依頼範囲の変更と不要になった個別ジョブを明確には区別していない。今回はユーザーが A 社分だけでの完了を明示しているため、その指示に従って依頼を完了とし、未停止の B 社ジョブは別状態として保持する。継続解除後の B 社ジョブや遅着通知をランタイムがどう回収するか、具体的な解除操作は設計と提示された API から確定できないため、存在しない操作を補わずランタイムの規定に委ねる。

## uncertain-release

### 継続 1：v7 のビルド・契約テスト成功、release の応答喪失、status は一時利用不能

- 次の行動：現行対象がまだ v7 であり、有効設定が許可済みの社内プレビューを指すことを確認したうえで、既存の組 `release(v7, op-7)` を再送する。`status` が使えない状態で行える、設計手順 3 と提示された API 契約に基づく次の操作である。別の ID は発行しない。
- 待機・完了判断：現時点の更新結果は不明であり、失敗にも成功にも確定しない。再送で元の処理の状態が分かればその状態に従い、実行中ならジョブ継続で待つ。再送も結果不明なら、ランタイムの予算・タイムアウト内で同じ組の照合・再送または `status` の回復待ちへ移る。応答喪失のたびに別処理を起動しない。表示版と画面の確認も済んでいないため、依頼は未完了である。
- 保持する状態：現行対象 v7、有効設定、成功した v7 のビルド成果物と契約テスト根拠、`v7` と `op-7` の対応、応答喪失による結果不明、`status` の一時利用不能、未実施の表示確認を保持する。
- 設計の適用：同一の版と ID に限る重複抑止保証により判断できる。実際の再送結果はこのイベントでは与えられていないので仮定しない。

### 継続 2：op-7 は実行中、対象を v8 に変更、op-7 はキャンセル不能

- 次の行動：現行対象を v8 に更新し、v8 のビルドと契約テストを進める。同時に保持済みの op-7 の状態を実行中・キャンセル不能に更新し、旧処理の終了をランタイムのジョブ継続と利用可能な照合手段で待つ。直前のイベントで利用不能だった `status` が回復したとは仮定しない。v7 の `release` は再送しない。
- 待機・完了判断：v8 のビルドとテストは独立して進められるため、それが終わるまでは作業を進める。共有プレビューへの v8 の更新は、op-7 の終了と実際のプレビュー状態を照合できるまで待機する。キャンセル不能を停止成功とはみなさず、v8 のテストが成功しても旧処理の状態が未確定なら投入しない。依頼は未完了である。
- 保持する状態：現行対象 v8 と変更指示、v8 の成果物・テスト進捗、旧版 v7 と op-7 の対応、op-7 の実行中・キャンセル不能、旧処理終了と外部状態の照合待ち、共有環境への更新待ち、最新の有効設定を保持する。v7 のテスト結果を v8 の合格根拠として使わない。
- 設計の適用：対象版変更とキャンセル不能の段落に従える。旧処理があとから反映される可能性が残るため、v8 の投入まで完了した扱いにはできない。

### 継続 3：v7 の更新完了、v8 のビルド・契約テスト成功、v8 の release はサンドボックス拒否

- 次の行動：op-7 を終了済み、v8 のビルドと契約テストを成功済み、v8 の更新工程をサンドボックス拒否による未完了として記録する。実際のプレビュー状態の照合記録がなければ、許可された読み取り手段の範囲で確認する。v7 の更新完了という通知だけから、現在表示中の版まで確定しない。拒否された v8 の更新、判明している理由、残る更新・表示確認工程をユーザーへ報告する。
- 待機・完了判断：v8 をプレビューに出す依頼は未完了である。引数変更、別の ID、別経路や権限による拒否回避の再試行をしない。v8 のビルド・テストを理由なくやり直すこともしない。必要な状態照合と報告が済んだ後に他の作業がなければ、拒否で更新が止まっている状態を保持して実行を止める。イベントには障害を解消する変更がないため、自動再試行を予定しない。
- 保持する状態：現行対象 v8、有効設定、v8 の同一成果物とテスト成功根拠、送信前に保持した v8 の `operation_id`、拒否された操作と実際に得られた拒否情報、更新未確認・表示確認未完了を保持する。v8 の ID の具体値は入力にないため補わない。op-7 の完了は旧版の記録だけを更新し、全体完了に反映しない。実際の表示版は観測した値を、観測できなければ未確認として残す。
- 設計上の不足・判断限界：入力には拒否理由の詳細と解除方法がなく、設計にもこの拒否を解消する具体的な操作はない。したがって、ユーザーに特定の設定変更を要求したり、実行可能な復旧操作があると断定したりできない。また、v8 の呼び出し前に旧処理終了とプレビュー状態を照合したかはイベントに明記されていないため、済んだことにはしない。拒否への対応と未完了判断自体は、設計のサンドボックス拒否に関する段落で判断できる。

## 実際に読んだ入力と試行範囲

- `evals/agent-design-tools/agent-workflow-design/evidence/candidate-v1-a.md` から `pending-monitor` と `uncertain-release` の設計を抽出して読んだ。末尾ケースの抽出結果には、その後の入力出典を述べるフッターも含まれた。そこに列挙されたスキル・参照ファイルの本文は開いておらず、評価根拠には用いていない。
- `evals/agent-design-tools/agent-workflow-design/cases.json` を JSON として解析し、同じ 2 ID の `request` とトップレベル `continuations` 内の同じ 2 ID のイベントだけを抽出して読んだ。格納位置の確認時に、当該ケースとトップレベルのキー名も確認した。
- 委任メッセージ、および会話内で渡された適用指示を読んだ。他ケースの内容、`criteria.json`、スキル本文、他の試行結果、docs は読んでいない。

この試行はシミュレーションによる机上継続評価であり、実ランタイム試験ではない。実サービスの操作、上記 API の実呼び出し、設計の書き直しは行っていない。
