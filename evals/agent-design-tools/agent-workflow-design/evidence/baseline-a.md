# authorized-records

毎週の起動からレビューキューへの登録確認までを自動化する。収集と文章上の判断はモデル、起動・権限・保存・ジョブ照合・再試行制御はランタイムが担当する。社内キューへの登録と `evals/report-agent/` の作成・保存は許可済みとして設計し、追加承認を挟まない。社外公開は人が担当する。

処理は `起動 → 収集 → 草稿 → 出典確認 → 評価記録の保存 → レビューキュー登録 → 登録確認 → 完了` とする。出典確認で修正可能な問題が見つかった場合だけ、問題箇所と根拠を草稿工程へ戻す。確認は実際の完成稿に対して、主要な事実の出典対応、引用の整合、情報の対象時点、依頼された調査範囲の充足を検査する。裏づけが取れない主張を残して完成扱いにせず、除去・限定できなければ未解決事項として担当者へ渡す。同じ問題が新しい根拠なしに残る場合や設定された実行上限に達した場合は修正を打ち切る。

保存と復旧の契約は次のとおり。

| 対象 | 正本・保持内容 | 利用と終了条件 |
| --- | --- | --- |
| 実行状況 | ランタイムが週次実行ID、工程、対象稿の版、未解決事項、登録ジョブIDを保持する | 中断時は保存済み工程と外部ジョブを照合し、次の未完了工程から再開する |
| 評価入力と結果 | プロジェクト所有の `evals/report-agent/<実行ID>/` に、対象稿の版と参照、出典参照、評価基準の版、レビュー結果を保存する | 次週の評価時に前週の結果を読み、同じ基準で指摘の継続・解消・新規発生を比較する |
| 完成稿と登録結果 | 完成稿は既存の成果物管理先、登録結果は既存のレビューキューを正本とする | 評価記録には参照と登録結果だけを結びつけ、本文や外部状態の重複コピーを増やさない |

`evals/report-agent/` が未作成なら初回保存時に作成する。プロジェクトのワークフロー担当を保存先の管理者とし、実行IDごとに書き込みを直列化して不完全な記録を確定扱いにしない。生の会話ログや秘密情報は保存せず、翌週の比較に必要なレビュー結果と参照を残す。保持期間はプロジェクトの保持方針を設定値として受け取り、少なくとも次週の比較が済むまでは保持する。削除はその方針に従い、未設定の段階では自動削除しない。

同一週の多重起動はランタイムで同じ実行に集約する。週の区切り、タイムゾーン、遅延起動の扱い、再試行上限はスケジューラー設定を使い、未設定なら実装時の必須設定とする。登録前に完成稿の版、送信先、評価記録の保存成功を確認する。登録後はジョブIDを保存して再取得し、同じ完成稿がキューに登録されたことを確認して完了する。応答喪失時は既知のジョブIDで照合し、結果不明のまま登録を再送しない。ジョブIDを受け取る前の応答喪失については、提示された機能だけでは重複防止を保証できない。実装側で登録要求の安定した識別子による照合か冪等登録を用意できなければ、その場合だけ照合待ちとして担当者へ渡す。

取得資料は内容判断の材料として扱い、記載された指示から権限や送信先を変更しない。設定済み権限に加え、保存パスと社内キューの宛先をランタイムで検査する。実装時には、通常登録、修正後の再確認、保存失敗、登録応答の喪失、途中再開、次週の参照比較を検証する。本設計では実行検証はしていない。

# pending-monitor

一つのワークフローから A 社と B 社の取得を同時に開始し、結果が届いた社から納品物整理を進める。追加エージェントは使わない。両社の結果を待つ必要があるのは、全体の比較表を確定する段階だけとする。

1. 起動時に「今日」の基準日と、必要な納品物の範囲を現在の目的に固定する。`run_lookup(A)` と `run_lookup(B)` を並行して呼び出し、返されたジョブIDをランタイムが保持する。
2. 未完了ジョブを対象に `wait_jobs` を呼ぶ。A 社の結果だけが得られたら、その結果で A 社の納品物、入荷済み、未入荷、確認事項を整理する。B 社の取得完了はこの作業の開始条件にしない。B 社が先に届いた場合も同様にする。
3. 片方の整理中に届いた他方の結果を取り込み、各社の整理が完了したら比較表を作る。片方が失敗・未取得なら、その社を未確認として扱い、両社確認済みの確定表とは表示しない。
4. 今日必要な品目に遅延分が残る場合は、入荷イベントで再開する継続機構へ引き継ぎ、現在のターンを終える。ユーザーは待機と続行を許可済みなので、追加の許可は求めない。再開時はイベントの到着だけを完了根拠とせず、保持されたジョブと現在の納品状況を照合し、変化した社・品目の整理と比較表を更新する。

各社の状態は `取得中 / 整理可能 / 整理済み / 入荷待ち / 失敗` とし、比較表の状態は別に `暫定 / 両社確認済み / 必要品目の整理完了` を持つ。必要な継続情報は、既存のランタイムが保持するジョブIDと現在の目的に紐づける。整理済みの成果物参照と反映済み結果の識別情報も復旧に使えるようにする必要があるため、実装ではランタイムが再取得可能な情報と成果物管理の契約を確認する。会話全文や独立した監視ログ保存先は作らない。

`wait_jobs` が継続中または前回と同じ通知を返した場合は、成果物更新、再分析、追加問い合わせを行わず、対応する待機機構へ戻る。単なる継続中を失敗や停滞と判定しない。以降の進行が入荷イベントだけに依存するときは継続機構を登録してターンを終え、短い間隔の手動ポーリングで待ち続けない。イベントの重複・順序違いは最新状態との照合で処理し、同じ結果を二重に反映しない。

予算・タイムアウトと一時障害の再試行はランタイム設定に従う。片社の失敗中も他社の整理は進め、復旧可能な失敗だけを再試行する。再試行の上限、取得不能、必要な判断の欠落は、整理済み結果と未確認部分を添えて通知する。通常の継続中や変化のない状態は通知しない。入荷によって今日の対応が変わる、必要品目の整理が完了する、取得が失敗する、ユーザー判断が必要になる場合に限って知らせる。

今日必要な品目の入荷確認と整理が終わったら、この目的の継続登録を終了する。日付をまたいだ場合は保持された目的を照合し、遅延していた品目を自動的に対象外へ落としたり、新しい日の全調査を無断で追加したりしない。実装検証では、片方だけ早く完了する場合、同じ継続中通知、片社の失敗、遅延品のイベント到着、重複イベント、再開時にすでに両社が完了している場合を確認する。本設計では実行検証はしていない。

# uncertain-release

プレビュー環境を対象に、`ビルド → 契約テスト → 更新 → 表示確認` を実行する。プレビュー更新は許可済みなので追加承認を挟まない。本番環境への操作はランタイムの宛先・権限で拒否し、サンドボックスの拒否を別の経路や再試行で回避しない。

ランタイムは、ユーザーが希望する最新の `desired_version` と、外部へ送信した `active_operation = { version, operation_id, state }` を別々に保持する。ビルド成果物と契約テスト結果は対象版に結びつける。更新要求の送信前に operation_id を確定して保持し、一度送信した組の version や operation_id は書き換えない。ユーザーによる対象変更と更新開始の状態遷移はランタイムで直列化し、外部への送信直前にも有効な対象版を確認する。

| 状況 | 次の処理 |
| --- | --- |
| ビルドと契約テストが対象版で成功 | 有効な対象版と一致することを確認して `release(version, operation_id)` を呼ぶ |
| 更新開始または実行中を確認 | 同じ operation_id の状態を追跡する。表示確認や完了報告へ先に進まない |
| 応答を失い、開始失敗・実行中・完了を区別できない | `結果不明` として保持し、まず `status(operation_id)` で照合する。失敗扱いにして新しい operation_id を発行しない |
| status が一時的に利用不能で、対象版は現在も有効 | API 契約による冪等性を使い、保持している同じ version と operation_id で `release` を再送して照合できる。新しい更新を重複して起こさない契約に依存するため、組の同一性をランタイムで検査する |
| 更新が完了 | プレビュー上の版と表示を確認する。現在の希望版と一致し、契約テストと表示確認が成功したときだけ完了する |
| サンドボックスが拒否 | 拒否された操作を停止し、対象版・拒否内容・未完了工程を返す。経路変更や反復実行は行わない |

対象版が途中で変更された場合は、旧版の作業段階で分岐する。

- 更新要求をまだ送信していなければ、旧版の更新を取りやめ、新版のビルドと契約テストから進める。旧版のテスト成功を新版へ流用しない。
- 旧版が実行中または結果不明なら、まず旧操作を照合し、必要に応じて cancel を呼ぶ。cancel 成功はキャンセルされた状態として扱う。キャンセル不能は完了の可能性が残るため、旧操作が終端状態になるまで追跡する。新版のビルドとテストは進められるが、同じプレビューへの新版の更新は旧操作の終了後に直列化する。
- 旧版の結果が不明で status も使えない場合は、旧版の `release` 再送で新たに旧版を開始する可能性を避け、状態照合とキャンセルに限定して待つ。対象変更後の同一キー再送は、重複しないという理由だけでは許可しない。旧操作を終端まで照合できなければ、新版の更新は未実施として引き継ぐ。
- キャンセル不能だった旧版が完了しても、最新の希望版の完了とは扱わない。旧版の完了を記録してから、その時点の最新版を再確認し、新版の更新へ進む。希望版が再度変わっていれば中間版の更新を省く。

中断からの再開では、ランタイムが保持した active_operation と有効な設定を先に読み、外部状態を照合してから次の副作用を判断する。復旧のために新しい operation_id で最初から実行し直さない。再試行・待機の上限はランタイム設定を使い、状態不明のまま上限に達したら「失敗」や「完了」と断定せず、対象版、操作ID、既知の証拠、必要な照合を返す。

実装時には、応答喪失後に status で完了を確認する場合、status 不通時の同一組再送、更新中の対象版変更、キャンセル不能後の旧版完了、結果不明の旧版が残る間の新版送信抑止、表示確認時点での再変更、サンドボックス拒否を検証する。API の冪等性とキャンセル結果は依頼で提示された契約を前提とし、本設計では実サービスに対する検証はしていない。
