# subjective-repair

編集者のフィードバックを受けた草稿を更新し、その変更が影響する草稿と出典だけを検証する形に改訂します。編集・保存は承認済みとして進め、毎段落の承認は追加しません。公開処理は設けません。

1. **入力と影響範囲を確定する。** 対象草稿の版、フィードバック、想定読者、草稿が参照する出典、直前の検証結果を既存の保存先から取得します。変更する記述から、対応する出典URL・見出し・本文中の参照箇所をたどり、今回の検証対象を作ります。出典が変わる場合は、その出典を使う草稿も対象に含めます。変更のない別文書は、内容と依存先、検証ルールが以前の検証時と一致している限り再検証しません。対応関係が不明な部分は、まず対象草稿内で依存先を調べ、根拠のある範囲まで広げます。
2. **編集判断をして保存する。** モデルがフィードバックを三つの基準に対応づけて改訂します。「要点」は、忙しい読者が冒頭から何が起きたか・自分にどう関係するかを読み取れるかで判断します。「出典の主張」は、事実、条件、確度、適用範囲を原文と照合し、推測や可能性を断定に変えていないかを確認します。「具体例」は、想定読者の仕事や知識で理解でき、説明対象と対応しているかで判断します。修正案が複数あっても、この基準で選べるものは編集者への質問なしに進めます。
3. **保存した版を検証する。** 改訂した草稿は全体を読み戻し、段落の局所修正が冒頭、見出し、結論と食い違っていないかを確認します。主張の照合は変更記述と関連する出典を対象にします。加えて、既存の出典URL検証コマンドと見出し検証コマンドを、影響する草稿・出典の一覧を渡して必ず実行します。両方の成功結果を、検証した草稿・出典の版に対応づけます。
4. **残った問題だけを修復する。** 失敗した基準、該当箇所、根拠を次の修正入力にします。修正後は、その修正で無効になった検証だけを実行し直します。同じ問題が残る場合は根拠や編集方針を見直し、新しい情報を得られない反復を続けません。出典の取得不能やフィードバック同士の矛盾が残る場合は、独立して進められる編集を終えたうえで、未解決箇所と必要な情報をまとめて返します。必須検証が未完了なら、完成扱いにはしません。

実行の骨格は次のとおりです。`URL_CHECK` と `HEADING_CHECK` は既存コマンドを表す記号で、コマンド名や対応オプションはこの依頼では未提示です。

```text
対象 = 変更草稿と、変更した出典に依存する草稿・出典
編集して保存する
保存版について三つの編集基準を確認する
URL_CHECK(対象) を実行し、成功と対象の版を記録する
HEADING_CHECK(対象) を実行し、成功と対象の版を記録する
問題が残る場合だけ修正し、無効になった確認へ戻る
保存版と検証版が一致し、三基準と必須コマンドを満たしたら終了する
```

影響範囲の計算、対象引数の受け渡し、コマンドの終了状態と版の照合は既存の実行制御側が担当し、文章の意味や読者への適合はモデルが判断します。コマンドが対象指定を受け付けない場合は、対象指定を追加するか、対象の依存関係を保持した一時入力で同じ検査を実行できるようにします。全件実行の出力だけを後から絞っても速度改善にはならず、検査を省略して成功扱いにしてもいけません。外部出典はURLが同じでも本文が変わり得るため、今回使う出典の内容や更新情報を確認し、古い取得結果を無条件には再利用しません。

改訂後の確認には、一つの段落だけを直すケース、共有出典の変更で別の草稿にも影響するケース、URLまたは見出し検証が失敗するケースを使います。対象草稿で必須検証が動くこと、影響する共有参照を漏らさないこと、無関係な文書の検証が呼ばれないことを確認します。既存の全件検証で指摘される関連問題を拾えるかも、限定した比較用入力で照合します。所要時間や検証対象数は速度改善の証拠として記録しますが、編集品質や必須検証の代わりにはしません。

これは改訂設計です。実際の草稿、出典、既存コマンドがないため、編集や検証の成功を報告するものではありません。

# harness-maintenance

まず疑う層は、現在読み込まれているスキルの承認規則です。提示された失敗では承認が取得済みであり、ツールも承認IDを受け取れる一方、スキル本文が毎回の再確認を要求しています。この一件でも規則の矛盾を局所修正する根拠になります。他の二件が正常であることは保存すべき挙動の証拠ですが、この修正の効果を証明するものではありません。

1. **三件の記録から比較の基準を固定する。** 保存済み実行記録を読み、依頼内容、実際の結果、読み込まれたスキルの版、ツール定義、承認取得と再質問の順序を確認します。失敗ケースでは、取得済み承認が同じ対象・配送先変更内容を許可していたかを照合します。有効期限や撤回などの既存ポリシーがある場合は、それも確認します。承認IDをツールが受け取れるという事実だけでは、ツールが承認の妥当性を検証しているかまでは確定しないため、実際の契約を確認します。
2. **再現に必要な小さなケースを保存する。** 既存の `evals/support-agent/` 配下に、三件の再現入力と元記録の参照ID、ベースラインのスキル版、必要な設定を保存します。個人情報を含む生の会話は元システムに残し、ケースには挙動の再現に必要な情報だけを持たせます。配送先や承認IDを置換する場合は、対象・承認・ツール引数の対応関係を維持します。生成結果はスキルのディレクトリに入れず、同じ評価領域の結果保存先に置きます。
3. **承認規則だけを局所修正する。** ベースラインを復元できる形で保存してから、「取得済み承認の範囲が今回の変更と一致し、既存ポリシー上有効なら、同じ承認IDを使って処理を続ける。承認がない、失効している、対象や変更内容が範囲外なら、必要な承認を取得する」という分岐へ改訂します。ユーザーからローカル修正・評価の許可は出ているため、この作業のために再承認を求めません。その他の業務要件、ツールの承認検査、運用反映のレビュー条件は維持します。
4. **同じ条件でベースラインと候補を実行する。** 使用モデル、実効設定、ツール、権限、入力、予算などをそろえ、既存の評価手順で三件を比較します。ツール実行は評価用の代替実装や隔離環境を使い、実際の配送先は変更しません。候補版が失敗ケースで再質問せず、取得済み承認IDを渡して依頼を完了するか、正常だった二件を引き続き完了するかを確認します。保存済み結果と今回の再実行は区別し、条件がそろわない差は記録します。
5. **承認境界を新しいケースで確認する。** 承認がまだない場合、別の注文・配送先に対する承認しかない場合、承認後に変更内容が変わった場合を追加します。既存ポリシーに失効・撤回がある場合はそのケースも加えます。再確認の削減によって必要な承認まで省かれていないかを調べます。新規ケースは既存の受け入れ基準に従う診断・回帰入力とし、評価器や合格条件を修正して候補を通すことはしません。
6. **結果に基づいて終えるか修正する。** 失敗が残れば、承認情報の受け渡し、規則の適用、ツール引数のどこで失敗したかを結果から調べます。新しい根拠がある箇所を直して関連評価を実行し、同じ試行を理由なく繰り返しません。三件と追加した関連ケースが必要な評価を満たせば、ローカル改善をレビュー可能な状態として終了します。評価器が利用できない、承認の対応関係が不明などの場合は、その未検証事項を明示します。

担当者には、元記録への参照、スキルの差分、比較した版と設定、ベースラインと候補の結果、残る不確実性、戻し方をまとめて渡します。結果は試行ごとに区別し、以前の出力や評価記録を書き換えません。別チームが管理する評価器・受け入れ基準と保護された評価材料は、改善作業から変更できない状態を保ちます。運用中エージェントへの反映は担当者のレビュー完了後に、既存の反映権限・手順で行います。

この手順で確認できるのは、指定した条件下での承認再利用と正常挙動の維持です。三件と追加ケースの結果だけで、問い合わせ対応全般の改善率や本番での信頼性までは主張しません。ここでは保存済み記録そのものの調査、スキル修正、評価実行、運用反映は行っていません。
