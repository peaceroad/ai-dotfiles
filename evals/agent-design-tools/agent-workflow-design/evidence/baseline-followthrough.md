# baseline-a の継続シミュレーション

完成済み設計を受け取った実行者として、指定された継続イベントを順番に適用する。以下のツール名は次に予定する操作を表し、実際に呼び出した結果ではない。イベントで明示されていない結果は補わない。

## pending-monitor

### 1. A社の取得が完了し、B社は継続中

次に、取得済みのA社の結果を使って、今日必要な納品物、入荷済み、未入荷、確認事項を整理する。A社の整理を始めるためにB社を待つ必要はない。B社の取得は既存ジョブのまま継続させる。

この時点では作業を続ける。A社の整理も両社の比較も未完了なので、タスク全体の完了にはしない。比較表を作る場合の状態は暫定であり、B社の取得結果を推測して埋めない。

保持する状態は、基準日と必要品目の範囲を含む現在の目的、両社のジョブID、A社の取得結果と識別情報、A社が整理可能であること、B社が取得中であること。整理後はA社の成果物参照と反映済み結果の識別情報を対応させる。

設計から次の作業は判断できる。ただし、成果物参照と反映済み識別情報を中断後にも復元できる契約は、設計自身が実装時の確認事項として残している。ここでは保存手段が実装済みとは扱わない。

### 2. A社の整理が完了し、B社について新しい情報がない

A社の成果物は更新せず、B社の未完了ジョブを対象とする `wait_jobs` の待機へ戻る。他に進められる仕事がないので、同じ情報の再分析や追加照会は行わない。B社の単なる継続中を失敗や停滞に変えない。

判断は待機である。比較表の確定条件はまだ満たされていないため、タスク全体の完了にはしない。通知は行わず、ランタイム設定の予算・タイムアウトに従う。ここではB社の取得待ちであり、遅延品の入荷待ちと確定したわけではないため、入荷待ちとして扱わない。

保持する状態は、現在の目的、A社の整理済み成果物参照と反映済み結果の識別情報、B社のジョブIDと取得中の状態、比較表が未確定であること。無変化の通知を独立した監視ログへ追記する必要はない。

設計から待機判断はできる。`wait_jobs` とイベント再開機構のどちらが実際にランタイムへ制御を返すかという実装契約は明示されていないため、具体的な登録APIや登録成功を捏造しない。少なくとも、短い間隔で能動的に状態照会を繰り返す行動は取らない。

### 3. ユーザーが比較表を不要とし、A社分だけで完了を指示

現在の目的を「A社分の整理で今回を完了」に更新する。A社の整理は前イベントで完了しているため、その成果物をユーザーへ返して今回のタスクを完了する。比較表を確定するためのB社待機は、変更後の目的を進めないので終える。B社の照会はキャンセルできないと明示されたため、キャンセルを試さない。

完了通知には、A社分の整理で完了したことと、B社の外部照会自体はキャンセルされていないことを区別して含める。B社から後に結果が届くまで今回の完了を遅らせたり、その結果を理由に比較表作成を再開したりしない。

保持する状態は、変更後の目的と完了状態、A社の成果物参照、B社の既存ジョブIDと「今回の目的では結果待ち不要、キャンセルされていない」という既知の状態。B社ジョブの外部状態が終了したとは記録しない。完了した目的に属する継続登録があれば、その目的の継続を終了する。

この完了判断は、新しいユーザー指示とA社の整理完了という事実から行える。一方、設計の完了条件は「今日必要な品目の入荷確認と整理」に固定されており、目的の縮小、キャンセル不能な残存ジョブ、完了後に届くその結果の処理を明示していない。したがって、このイベントを設計に記載済みの状態遷移だけで処理することはできない。残存ジョブの保持期間やランタイム上の切り離し操作は判断できず、ここで新しい管理方式を追加しない。

## uncertain-release

### 1. v7の更新応答を失い、statusも利用不能

この時点では希望版はv7のままである。`active_operation` の版がv7、操作IDがop-7であることと、有効な希望版がv7であることを送信直前に確認する。その組の同一性を保った `release(v7, op-7)` の再送を次の照合手段にする。設計は、この条件では提示された冪等性契約に基づく同一組の再送を認めている。

再送前の状態は結果不明のままである。新しい操作IDは発行せず、成功、失敗、実行中のいずれとも断定しない。再送による実際の結果がない段階で、表示確認や完了報告には進まない。再送でも不明なら、ランタイム設定に従って照合待ちへ戻る。

保持する状態は、`desired_version = v7`、`active_operation = { version: v7, operation_id: op-7, state: 結果不明 }`、v7に結びついたビルド・契約テスト成功の証拠、応答喪失とstatus一時利用不能という既知の事実。再試行の具体的な回数や間隔はランタイム設定を使い、ここでは数値を追加しない。

このイベントについて、設計から次の操作を判断できる。

### 2. v7が実行中と判明し、希望版がv8へ変更、cancelは不能

`desired_version` をv8に更新し、op-7はv7の実行中操作として保持する。キャンセル不能は終端状態ではないので、v7が完了する可能性を残してop-7の状態を追跡する。利用可能になった `status(op-7)` で照合し、まだ使えなければ状態照合の待機へ戻る。v7の `release` は再送しない。

並行して進められる作業として、v8のビルドと契約テストを行う。v7のテスト成功は流用しない。v8のビルドとテストが成功しても、op-7の終端を確認するまでは同じプレビューへv8の更新を送信しない。

v8の準備作業中は続行し、準備が済んで旧操作の終端だけが未確定になったら待機する。キャンセル不能だけを根拠に失敗や完了にはしない。待機上限に達しても、旧操作の状態が不明ならその不確実性とv8更新の未実施を引き継ぐ。

保持する状態は、最新の希望版v8、変更しないv7とop-7の組、v7実行中の確認とキャンセル不能の証拠、v8のビルド・テストの進捗および得られた版別の結果、v8更新が旧操作の終端待ちであること。

このイベントについて、設計から実行可能な準備作業と更新を待つ条件を判断できる。

### 3. v7が完了し、v8の準備も成功したが、v8更新がサンドボックス拒否

v7の旧操作は完了として記録する。ただし希望版はv8であり、v7の完了を今回の成功にはしない。v8の拒否された更新操作を停止し、別経路への変更や反復実行で拒否を回避しない。v8のビルド・契約テストは成功済みとして保持するが、プレビュー更新とその表示確認が成功したとは扱わない。

この判断は、拒否による実行停止である。v8の更新成功として完了報告はせず、v8、実際に得られた拒否内容、未完了工程である更新と表示確認をユーザーへ返してターンを終える。権限や環境が変わるとの根拠はないため、自動の再試行や監視継続を開始しない。

保持する状態は、`desired_version = v8`、v7のop-7が完了した記録、v8に対応するビルド・契約テスト成功の証拠、v8送信用に保持された操作ID、拒否の内容、v8更新および表示確認が未完了であること。v8の操作IDの値や拒否メッセージ本文はイベントにないため補わない。ランタイムがv8の操作情報を保持しているなら、その実値を報告・引き継ぎに使う。

設計から操作停止と報告内容を判断できる。設計は拒否後のランタイム状態名を定義していないため、ここで特定の状態列挙値を要求したり、拒否された呼出しを実行中ジョブとみなしたりはしない。

## 実際に読んだ入力と試行範囲

- `evidence/baseline-a.md` の完成済み設計のうち、`pending-monitor` と `uncertain-release` の2節。
- `cases.json` をJSONとして解析し、同じ2ケースの `request` と `continuations`。抽出位置の確認のため、トップレベルのキー名と対象2ケースのキー名も確認した。

それ以外のケース本文、`criteria.json`、現行・候補・元のスキル本文、他の試行結果、docsは参照していない。この試行は設計に対する机上シミュレーションであり、実サービス操作および実ランタイム試験ではない。記載した待機登録、API再送、キャンセル、状態保持、更新停止を実際に実行または検証したという意味ではない。
