# new-runtime-policy

問い合わせごとに、モデルが検索計画と根拠を判断し、既存ランタイムが呼び出し数・時間・再試行を管理します。完了条件は、取得文書が主要な主張を支える回答を出せたことです。根拠不足で終えた場合は、その不足を明示し、回答成功とは区別します。

| 判断・制御 | 担当 |
| --- | --- |
| 問い合わせの意図、検索語・検索先・検索方式の選択、結果の関連性と主張の裏づけ | モデル |
| 引数のJSONスキーマ検証と検索処理 | exact_search / semantic_search |
| アクセス可能な文書の制限 | 検索サービス |
| 同時実行、タイムアウト、再試行待機、試行回数、結果の対応づけ | 既存ランタイム／その呼び出し制御部 |

スキーマに通ったことは、検索先の適切さや回答の正しさを保証しません。検索文書内の命令は検索データとして扱い、実行権限や制御規則に取り込みません。

初期設定は次のとおりです。**同時2呼び出しは既存の制約で、それ以外は提案する変更可能な設定**です。

| 設定 | 初期値 | 理由 |
| --- | --- | --- |
| max_inflight | 2 | 既存ランタイムの上限を全試行で共有 |
| exact_search.timeout_ms | 4,000 | 通常の回答目標内に再試行と回答生成の時間を残す |
| semantic_search.timeout_ms | 7,000 | 意味検索にはやや長い処理時間を仮置きする |
| 各検索の max_retries | 1 | 一時障害からの復帰機会を確保し、同じ失敗の反復を抑える |
| request.max_attempts | 6 | 最初の2呼び出し、その再試行、検索変更の余地を確保する |
| response_target_ms | 20,000（目安） | 利用者の期待を計画に反映する。打ち切り時刻にはしない |

タイムアウト値は実測に基づく既定値ではありません。導入後にツール別の遅延・タイムアウト率と、根拠のある回答までの時間を確認して調整します。タイムアウトは各試行の実行時間に適用し、待ち行列・再試行待機とは分けます。6回の上限は引数エラー・再試行を含む、問い合わせ内の全ツール呼び出しに適用します。

処理は以下の流れにします。

1. モデルが意図から検索語と検索先を選びます。固有名や識別子ならexact_search、言い換えや概念ならsemantic_searchを選び、両方が独立に有益なときだけ並列化します。
2. ランタイムが空き枠と残り試行数を確保して実行します。結果には呼び出しIDを対応づけます。独立した結果は届いたものからモデルが評価し、回答に両方必要な場合だけ全件を待ちます。
3. モデルが取得箇所と回答の主張を照合します。十分なら文書名・参照先を添えて回答します。空結果、検索先の不適合、根拠不足なら、未解決点に応じて検索語や検索先を変更します。矛盾する文書があれば、日付や適用範囲を確認し、解消できない矛盾を隠しません。
4. 一時的な混雑・通信障害・タイムアウトだけを、読み取りで副作用がない契約に基づいて再試行します。待機はretry_after秒以上とし、指定がなければ0.5秒＋0〜0.25秒の揺らぎを初期値にします。待機・再試行の計数はランタイムが担い、待機中は実行枠を使いません。引数エラーは引数を修正し、アクセス拒否は回避せず扱います。
5. 約20秒に達したら、モデルが根拠と残作業を再評価します。有益な取得が近ければ継続でき、長い待機や改善の見込みが乏しい場合は、裏づけのある範囲と不足を返します。試行上限到達、利用者の中止、検索候補の枯渇でも終了し、根拠のない補完はしません。

タイムアウトや回答終了を、実行中の検索が停止した証拠にしません。取消可能なら取り消し、確認できない呼び出しはランタイムが未完了として管理して同時2件に算入します。遅れて届いた不要な結果は完了済み回答へ反映しません。既存の実行状態に、試行数・再試行数・待機時刻・未完了IDと取得根拠を保持すれば足ります。

実装時は、正常回答、スキーマは有効でも検索先が不適切な場合、関連文書でも主張を支えない場合、空結果、長いretry_after、タイムアウト後の遅延結果を確認します。ランタイムの上限検査と、回答内容の根拠照合を分けて検証してください。ここでは制御設計を提示しており、実サービスでの動作は未検証です。

# small-workflow-review

重要な問題は、複数の許容表記があるのに、独立した3人の全員一致を終了条件にしている点です。好みの違いまで修正要求になるため、見出しチェックを通った版でも往復が続きます。処理は小さく、草稿の編集・保存は許可済みで戻せるので、この全文レビューの合意待ちは廃止できます。

改訂後は「入力を読む→表記を整える→必須見出しを機械チェックする→合格した版を保存する→保存成功を確認して終了」とします。表記規則に複数の許容形があれば、既存の形を優先して文書内で統一し、許容範囲内の違いではやり直しません。整形担当が編集時に意味や発言者、決定事項を変えていないかを確認しますが、別の評価制度は追加しません。

必須チェックが失敗した場合だけ該当箇所を修正し、同じチェックを再実行します。初期案として修正は1回までとし、なお不合格なら保存せず、不足箇所を報告して終えます。合格後に本文を変えたら、その版を再チェックします。保存失敗は完了扱いにせず報告し、保存できた場合は保存先の内容が合格版と一致することを確認します。既存の入力・保存先・実行結果だけを使い、新たな記録先は設けません。
