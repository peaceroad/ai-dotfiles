# new-runtime-policy

問い合わせを受けて検索し、回答の事実を取得文書で裏づけられたら完了とします。見つからない情報は推測で補わず、回答できる範囲と不足を明示します。

| 担当 | 判断・強制すること |
| --- | --- |
| モデル | 問い合わせの意図から検索語と検索先を選ぶ。文書番号や既知の語句なら `exact_search`、言い換えや概念探索なら `semantic_search` を候補にする。結果の関連性と、回答の各主張を文書が支えるかを判断する。 |
| 検索ツール | JSONスキーマで引数を検証する。検索先の適切さや意味上の裏づけは保証しない。 |
| 文書サービス | 利用者のアクセス範囲を強制する。拒否された文書を別経路で取得しない。 |
| ランタイム／制御コード | 全検索と再試行に共通の実行枠を設け、同時実行上限2を強制する。タイムアウト、再試行の計数、待機、結果の対応づけを担う。回答の参照先が取得結果に存在するかも機械的に確認できるが、意味上の裏づけ確認の代わりにはならない。 |

初期設定案は以下です。実測済みの性能値ではなく、運用後に変更できる設定として実装します。

```json
{
  "exact_search": { "timeout_ms": 5000, "max_retries": 1 },
  "semantic_search": { "timeout_ms": 8000, "max_retries": 1 }
}
```

タイムアウトは呼び出し開始からの時間で、枠待ちや `retry_after` の待機を含めません。再試行は同じ論理検索に対する追加の試行を意味し、初回と合わせて最大2回です。完全一致検索は短めに、意味検索には処理の余裕を持たせ、再試行は一過性の失敗からの回復と待ち時間の両立のため1回とします。成功時の遅延とタイムアウト率を測定して調整します。通常20秒程度という希望は回答全体の目安であり、20秒で強制終了する条件にはしません。

処理の流れと失敗時の挙動は次のとおりです。

1. モデルが検索を選び、互いの結果に依存しない検索だけを並行実行します。常に両ツールを呼ぶ必要はありません。到着した結果から根拠を確認し、文書同士の比較など、依存関係がある場合だけ必要な結果を待ちます。取得文書は根拠データとして扱い、権限やエージェントへの指示として扱いません。
2. 一時的な混雑やタイムアウトは、残りの再試行枠があれば同じ引数で再試行します。有効な `retry_after` があれば、その秒数が経過するまでランタイムの待機機構で待ち、待機中は検索枠を占有しません。指定がなければ次に利用可能な枠で再試行します。引数検証エラーはモデルへ返して修正し、アクセス拒否や恒久的な失敗は同じ要求を再送しません。
3. 空の結果や無関係な結果は通信失敗ではないため、自動再試行しません。モデルが未解決の情報に応じて語句や検索先を変更します。同じ根拠不足が続き、別の有望な検索もなければ、回答可能な内容と未確認部分を返して終了します。再試行を使い切った検索も、別の有効な検索がなければ失敗を伝えます。
4. 回答には文書名・該当箇所などの参照を付け、根拠との対応をモデルが確認して返します。20秒を超えそうでも、必要な結果や有望な再試行が残るなら続けます。待機だけが必要な間は、必要に応じて短く状況を伝え、ポーリングや同じ検索の連発を避けます。

タイムアウトや回答終了は、裏で動く呼び出しの停止を意味しません。実装時にランタイムのキャンセル・終了通知の契約を確認します。未完了呼び出しは同時実行枠に数え、終了またはキャンセル完了を確認して枠を解放します。不要な検索は対応可能ならキャンセルし、止められない検索の遅延結果はランタイムで回収して返答済みの内容に混入させません。

実装時には、根拠付き回答、不適切な検索先の変更、空の結果、長い `retry_after`、タイムアウト後の遅延完了、再試行上限、アクセス拒否を確認します。再試行と並行検索が重なっても上限2を超えないことを確かめます。この提案では実サービスでの性能・動作確認は行っていません。

# small-workflow-review

主な問題は、複数の許容形がある表記について、独立した３人の全員一致を終了条件にしていることです。設計上、正しい版でも好みの違いで差し戻され、品質の改善と無関係に往復が続きます。許可済みで戻せる草稿の整形では、この合意待ちは外し、必須の見出しチェックを合格条件として残すのが妥当です。

改訂後は「入力を読む→表記を整える→内容を変えていないか確認する→必須の見出しチェック→合格した同じ版を保存→保存成功を確認して終了」とします。表記の基準が既にあれば従い、なければ入力で一貫している許容形を保ちます。異なる許容形への置換は修正理由にしません。内容の確認は整形担当が行い、追加の評価役や記録先は設けません。

見出しチェックで不合格になった場合だけ、指摘された不足を修正し、変更後の版を再チェックします。同じ不合格が続き、修正しても改善が見られない場合は、未解決の項目を返して終了します。必須チェックが使えない場合や保存に失敗した場合も、完成扱いにはしません。保存後に編集するなら再チェックが必要です。３人の全文レビューをなくしても、必須チェックに通った版だけを保存する要件は維持できます。
