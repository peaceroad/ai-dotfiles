# 二つの編集スキルが共有する保守メモの運用設計

`docs/editorial-maintenance/candidates.md` を、共通規則の既存の保守担当が管理する共有候補一覧とする。両スキルから同じ一覧を参照し、共通規則に関する候補を各スキルで別々に管理しない。保存場所と記録保存は許可済みなので、設計上、フォルダー作成の再承認は不要。今回は設計だけを行い、候補一覧の作成・整理やスキルの変更は実施しない。

一覧の目的は、次の保守で判断に必要な未解決候補と根拠を取り出せること。候補数やメモの存在を、規則の追加・強化の根拠にしない。実際の振る舞いを定める正本は現行スキル内の共通規則であり、候補メモにはその効力を持たせない。

## 保存する内容と管理主体

候補一覧の冒頭に、以下の参照・追記・整理ルールを一度だけ置く。共通規則の保守担当が、重複の統合、反映確認、候補の除去を管理する。二つの編集スキルは観察と根拠を提供し、共通規則の変更判断は既存の保守手順で行う。

各候補には、判断に必要な次の内容だけを残す。

- 対象の共通規則と、改善したい具体的な症状。
- 元の観察を確かめられる実行記録・箇所への参照。異なる実行の観察は区別する。
- 未解決の論点と、次に確認すること。必要な場合は再検討の条件。
- 既知の別名。重複候補を検索・統合するために必要な範囲に限る。

新しい管理番号体系、発生回数の手入力、候補別ファイル、大きな状態管理表は設けない。特定の判断を後から説明する必要が生じた場合だけ、候補一覧とは別に短い判断記録を残す。その場合も、採用・棄却の理由や再検討条件など、将来必要な情報に限定する。

## 参照・追記・次回保守

1. **参照する時点を限定する。** 共通規則を保守するとき、記録済みの再検討条件が満たされたとき、ユーザーが候補を指定したときに、関連候補を読む。通常の編集作業で全メモを毎回走査しない。
2. **追記前に関連候補を確認する。** 共通規則の同じ保守担当が扱う候補のうち、対象と症状が近いものを確認する。名称だけで一致判定せず、同じ問題と判断できる候補は一つに統合する。別名と根拠への参照をまとめ、同じ実行記録を重複して観察回数に数えない。改善案が似ていても問題や成立条件が違う候補は分ける。
3. **「解決済み」は反映確認から始める。** 次回保守では、解決したと書かれた候補を、現行スキルの該当箇所と照合する。確認できるまでは「反映未確認」として残す。現行規則で問題が解消されていれば一覧から除去し、反映されていない場合や根拠が不足する場合は、未解決の論点と次の確認事項を明らかにする。
4. **現在の根拠で採否を決める。** 未解決候補について、元の観察を確認し、現行の規則で既に対応できるか、実際に変更が必要かを判断する。件数が多くても、それだけでは規則を増やさない。必要な変更は既存の保守担当が通常の変更・確認手順へ渡す。
5. **判断を終えた候補を整理する。** 反映済み、既存規則で対応済み、棄却、根拠喪失、現在の対象外になった候補は、共有一覧から除去する。除去前に、残すべき監査資料と将来必要な判断理由を確認する。追加の観察を待つ候補は、再検討条件を記して残し、次の保守まで待つ。

## 監査記録との境界

元の実行記録に課された独立した監査保存要件は、そのまま維持する。候補一覧はその代替保存先にしない。重複候補の統合や一覧からの除去に伴って、監査対象の実行記録を削除・書き換えたり、保存期間を短くしたりしない。

監査記録の保管場所と保存条件は提示されていないため、この設計では既存の監査契約に従うものとし、新たな場所や期間を決めない。候補一覧には判断に必要な参照を残し、全文を複製しない。元記録を確認できなければ、解決済みと断定せず、確認不足を未解決事項として残す。

## 次回整理時の完了確認

別名だった同一候補を一つにまとめても根拠にたどれること、反映未確認の候補を誤って解決扱いしていないこと、一覧から除去した候補に対応する監査記録が保たれていることを確認する。残った各候補から、対象の共通規則、未解決の論点、次の確認事項が読み取れれば整理完了とする。全候補の解決や新しい規則の追加は完了条件にしない。

これは運用設計であり、実際の重複関係、現行スキルへの反映状況、監査保存の実施状況は検証していない。
