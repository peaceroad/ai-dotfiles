# candidate-v2-monitor の机上継続評価

完成済み設計を受け取った実行者として、`pending-monitor` の継続イベントを提示順に適用した。以下の行動はシミュレーションであり、ツール呼び出しや実サービスの結果を記録したものではない。実際のジョブ ID、納品物の明細、入荷状況は入力にないため、値を作らない。

初期目的は、依頼時点の「今日」に必要な A 社・B 社の納品物を整理し、両社の比較表を確定すること。未入荷分は入荷を待ち、必要な変化だけを通知する。A 社と B 社の取得ジョブは独立して開始済みで、ジョブ ID と現在の目的は既存ランタイムが保持しているものとして継続する。

## イベント 1：A 社の取得完了、B 社は継続中、A 社の整理は未着手

**次の行動：** 受け取った A 社の結果について、会社・ジョブ・対象日が今回の取得に対応することを照合し、A 社の必要納品物一覧を作成する。明細の情報だけに基づいて入荷済み・未入荷・未確認を整理する。B 社の終了はこの作業の前提にしない。A 社の整理後、他に進められる作業がなければ、既存の B 社ジョブを指定して `wait_jobs` へ進む。A 社や B 社の取得を新規に起動し直さない。

**待機／完了判断：** A 社の整理という実行可能な作業があるため、直ちに待機へ移らない。両社比較に必要な B 社の結果がないため、比較表も依頼全体も未完了。取得完了という事実だけではユーザーへの通知は行わない。A 社の結果に今日の対応を変える情報がある場合は設計の通知条件を適用するが、その有無はこのイベントだけでは判断できない。

**保持状態：** 現在の目的と対象日、ランタイムが保持する既存ジョブ ID と状態、整理済み A 社一覧、その取得時点・処理済み結果の識別、判明した未入荷・未確認項目を保持する。比較表は B 社待ちの未完了として扱う。保持先は既存機構を使い、新しい台帳を作らない。

**判断の限界：** A 社の取得結果の具体的な内容は提示されていないため、一覧の中身や通知の必要性までは確定できない。設計に従う処理順は判断できる。

## イベント 2：A 社の整理完了、B 社は継続中、待機結果に新情報なし

**次の行動：** 整理済み A 社一覧を保持し、未完了の B 社ジョブ ID と現在の目的を既存イベント継続機構へ引き継いで、この実行を終了する。`wait_jobs` を即時に再呼び出さず、変化のない状態を再分析しない。イベントで再開したときに目的と既存状態を照合する。

**待機／完了判断：** 他に進められる仕事がなく、新情報もないため、イベント待機に戻る。依頼全体は未完了のまま。定例報告や「まだ待っています」という通知はせず、待機継続の再承認も求めない。独自のポーリング間隔・回数・タイムアウトを追加しない。

**保持状態：** 現在の目的と対象日、継続中の B 社ジョブ ID、処理済み A 社結果と整理済み一覧、未完了の比較表、既に判明している未入荷・未確認項目、通知の重複を防ぐ既存継続状態を維持する。

**判断の限界：** 継続機構への具体的な引き継ぎ API は提示されていない。操作名は確定できないが、既存機構に制御を返して今回の実行を終えるという判断は設計に明記されている。

## イベント 3：ユーザーが比較表を取り下げ、A 社分だけで完了を指示、B 社照会はキャンセル不能

**次の行動：** 再開時に、ユーザーの新しい指示を現在の目的へ反映する。今回の完了条件を A 社分の整理完了へ変更し、比較表の作成、B 社分の整理、今回の依頼としての入荷待ちを終了対象とする。前のイベントで A 社の整理は完了しているため、その成果物を最終成果として扱う。追加取得、B 社への停止要求、B 社終了までの `wait_jobs` は行わない。

既存継続機構で今回の監視を解除し、依頼完了を一度通知する。通知内容は、例えば「A 社分の整理をもって今回の依頼を完了しました。比較表の作成と監視を終了します。B 社への照会自体はキャンセルできないため継続します」となる。これは送信文案であり、実際の送信記録ではない。

**待機／完了判断：** 依頼は完了。B 社ジョブの実行継続は、改定後の目的の未達を意味しない。A 社に未入荷項目が残っていたとしても、「A 社分の整理だけで今回は完了」という最新の指示によって、今回の入荷待ちは完了条件から外れる。B 社の終了や追加のユーザー承認を待たない。

**保持状態：** A 社の整理済み成果物、改定後の目的、ユーザー指示による完了・監視終了という状態、完了通知済みの状態を既存機構に残す。B 社ジョブは、キャンセル済み・成功・失敗のいずれにも書き換えず、実行状態をランタイムの管理下に置く。今回の完了目的と未完了の B 社ジョブを混同せず、B 社の遅延結果を理由に今回の整理・比較・通知を再開しない。独自の孤立ジョブ台帳や新しい監視は作らない。

**設計から判断できる範囲と不足：** 設計の「イベントで再開」時に現在の目的を照合する規則と、キャンセル時に監視を解除し、ジョブ停止可否をツール契約に従わせる規則を、最新の明示指示に適用すれば上記の完了判断はできる。ただし、目的の縮小後にキャンセル不能ジョブだけが残る場合の継続状態の更新手順、ジョブと完了済み依頼との関連を解除する方法、監視解除後にも届く結果の抑止・破棄方法は具体化されていない。実装に使う API や、監視解除によって以後の起動を完全に止められるかは、この設計と入力だけでは確定できない。遅延イベントが届いた場合は、まず完了済みの現在の目的を照合し、不要になった B 社処理を再開しないという判断までを示す。
