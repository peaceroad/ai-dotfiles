以下は、2026年11月15日時点の固定資料に基づく再設計案です。**classic Gem は自動変換後の欠落を補う移行、Opal は処理の再設計が必要**です。元の指示本文や Opal の各ステップは未提示なので、現時点では構成と必要成果物を定めます。実アカウントの確認、保存、インポート、実行は行っておらず、移行済みとは扱いません。

1. **まず、失われる前に元の状態を保存する**

   個人の18歳以上アカウントでは、固定資料上、classic Gem は2026年11月17日に読み取り専用となって利用できなくなり、12月17日にアクセスが削除される予定です。指示本文、資料一式、各資料の用途、利用ツール、代表的な入力と期待する出力を保存対象にします。自動変換が案内されていても、内容や機能の完全な維持は保証されません。[Gems から Skills への移行案内](https://support.google.com/gemini/answer/18560919?hl=en)

   Opal は11月17日に終了し、自動移行はありません。ワークフローファイルは Drive の Opal フォルダに残るとされていますが、対話的なワークフローは動作しなくなります。ファイルの残存と、実行可能なアプリの存続を区別し、入力項目、各ステップの指示、接続関係、参照資料、出力形式を読み取れる形で保存します。[Opal FAQ](https://developers.google.com/opal/faq)

   これらの日付は準備の判断材料です。生成する Skill の恒久的な指示には埋め込まず、実際に移行するときにアカウント別の案内を再確認します。

2. **Gem の資料と機能を、移せる形に組み替える**

   - **120 MB の資料：** Apps Skills のアップロード合計上限は100 MBです。classic Gem の自動変換では、合計が100 MBを超えると大きいファイルから制限内になるまで削除されるため、重要な資料が欠ける可能性があります。容量順の削除に任せず、必須の根拠、用語・判断基準、例、保管用の原本を区分します。重複除去や適切な圧縮を行い、必要な箇所を根拠と対応付けた参照ファイルにします。原本は別に保持し、要約で失われる細部が必要な仕事では、対象箇所を依頼ごとに供給する運用を決めます。
   - **音声：** 自動転送されず、Apps Skills の音声・動画添付も非対応です。原音を保存し、文字起こしを作成して参照資料にします。発言時刻や原音との対応を残し、聞き取り不明箇所を明示します。声の調子など、文字起こしだけでは保持できない情報が仕事に必要なら、その分析工程は別途残します。
   - **GitHub ファイル：** 自動転送されません。必要な内容を対応する形式の参照資料として用意し、リポジトリ、ファイルパス、コミットなどの版情報を記録します。静的なコピーを置いた場合は更新手順も必要です。元ファイルへのリンクを書くだけでは、内容の取得や同期を保証できません。
   - **Deep Research：** 固定資料では Skills で未対応です。既存の調査結果と出典を保存し、今後は調査を利用可能な別の実行手段で行って、その成果物を Skill に渡す構成にします。指示に「Deep Research を実行」と書いても機能は追加されません。

   容量・転送対象・ツールの扱いは固定資料に基づく制約です。音声の文字起こしや GitHub の版付きコピーは、その制約に対応する設計案です。[移行時の欠落に関する案内](https://support.google.com/gemini/answer/18560919?hl=en)、[Skills の作成・管理](https://support.google.com/gemini/answer/17094296?hl=en)

3. **移行先の指示を、用途と実行能力に合わせて再構成する**

   classic Gem 側は、元の反復的な仕事を一つのまとまりとして Skill 化します。名前・説明には利用場面を、本文には目的、必須条件、出力要件、資料の選択条件を置きます。長い基準や実例は参照ファイルへ分け、本文から「どの依頼で何を読むか」を指定します。元の指示の必須条件と変更可能な好みを区別し、通常の依頼内容や毎回変わる資料はタスク入力へ移します。[効果的な Skills の作成](https://support.google.com/gemini/answer/17102773?hl=en)

   Opal 側は、まず次のような処理図と入出力の契約に分解します。

   `依頼・資料 → 調査 → 出典付き調査メモ → 書類の下書き → 根拠・形式の確認 → 最終書類`

   この処理図は仮案です。実物のステップを確認して、分岐や中間成果物、書類の形式を補います。「調査メモから書類を作る」部分は Skill の手順にまとめられます。調査メモには、依頼、判明した事項、出典、未確認点、書類へ反映する条件を含めます。Skill は根拠が不足した箇所を明示し、未実施の調査を完了扱いにしない設計にします。

   一方、外部情報の取得、実ファイルの作成・保存などは、実行先に必要な機能があるかを確認して割り当てます。複数ステップを文章化しただけでは、Opal の自動実行、接続、画面や出力機能は再現できません。手動で調査結果を渡す運用でよければ Skill と引き渡し手順を用意し、元と同じ自動実行が必要なら別途、実行可能なワークフローと必要な連携を構築します。Skills 内のスクリプトは外部サイトへの要求やインターネット接続に依存できないため、その手段で調査を復元する案にはしません。[Skills の機能制限](https://support.google.com/gemini/answer/17094296?hl=en)

   二つの Skill に分けるかは、旧製品の数ではなく仕事の違いで判断します。Gem と Opal の目的が重なるなら統合も可能ですが、選択条件や成果物が異なる場合は分けます。

4. **移行に必要な成果物を揃える**

   - **移行元の保存一式と対応表：** 元の指示、資料、Opal ワークフロー、代表的な入出力と、それぞれの移行先・代替手段・未対応事項を記録します。欠落を意図したものと、未解決のものに分けて追跡できる状態にします。
   - **Apps Skills 用の完成原稿またはパッケージ：** エディタへ入力する名前・説明・指示本文と添付対応表、またはルートに `SKILL.md` を置いたフォルダ／ZIPを用意します。依存する参照を同梱し、対応形式とアップロード総容量を確認します。
   - **再構成した参照資料：** 資料の用途と参照条件を示す索引、必要な本文、音声の文字起こし、GitHub の版付きコピー、既存調査の出典付きメモを用意します。これらは原本への対応を維持します。
   - **Opal の代替設計と引き渡し手順：** 各工程の入力、処理、出力、実行担当または実行先、必要機能を定義します。自動化まで求める場合は、設計書に加えて実行可能な成果物が必要です。
   - **移行確認用のケースと結果記録：** 通常の依頼、資料不足、資料間の矛盾、Skill の対象外の依頼、許容する好みの変更を用意します。Deep Research が必要なケースでは、調査未実施を明示して正しく引き渡せることも確認します。

   名前・説明や参照条件は実際の元指示を読んで確定します。この案だけから、元の業務ルールを保持した完成版 `SKILL.md` ができたとは判断しません。

5. **「移行完了」を段階ごとに確認する**

   原稿の作成、パッケージのインポート、保存、有効化、依頼に応じた自動選択、必要資料の利用、代表的な仕事の完了を分けて記録します。明示的に Skill を指定した成功だけでは、自動選択の確認にはなりません。資料の存在だけでなく、元の重要な指示と根拠が実際の出力へ反映されるかも比較します。

   元の資料や機能との対応表に未解決項目が残る間は、全面移行済みとはしません。特に Deep Research と Opal の実行機能については、代替工程が動作したか、手動運用でよいかを確定させます。Drive 等の選択方法や更新動作には固定資料内でも不明確さがあるため、ライブ連携を前提にせず、実際の対象アカウントの画面で確認する項目として残します。
